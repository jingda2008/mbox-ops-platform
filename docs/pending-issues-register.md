### MBOX-PENDING-005：手机浏览器库存扫码无法调用摄像头

- 状态：`待验收（本地修复）`
- 类型：`功能缺陷`、`测试覆盖缺口`
- 优先级：高
- 发现日期：2026-08-22
- 环境：生产环境；苹果、安卓和华为手机浏览器现场反馈；代码与响应头检查
- 影响岗位：调酒师、副店长、店长及库存收货人员

事实：

- 线上使用 HTTPS，响应头已允许同源摄像头 `camera=(self)`，服务器权限策略不是主要原因。
- 当前 `InventoryBarcodeScanner` 在申请摄像头权限前，先同时检查 `window.BarcodeDetector` 和 `navigator.mediaDevices.getUserMedia`。
- 只要浏览器没有原生 `BarcodeDetector`，代码就直接进入“当前浏览器无法调用摄像头”，不会触发摄像头授权弹窗。
- Safari/WebKit、部分安卓 WebView、微信内置浏览器和部分华为浏览器对 `BarcodeDetector` 的支持不完整或不稳定。
- 当前异常处理把权限拒绝、无摄像头、摄像头被占用、识别器不支持等错误统一显示为“浏览器无法调用摄像头”，无法指导员工恢复。
- 现有自动化测试只检查源码中是否出现后置摄像头、条码格式、关闭轨道和手工兜底等字符串，没有在真实手机浏览器中验证摄像头授权与识别。
- 项目已有 `jsqr` 依赖但未接入该扫码组件；它只能补充二维码，不能独立覆盖 EAN-13、EAN-8、UPC、Code128 等酒瓶常见一维条码。

风险：

- 手机扫码入库在主流现场设备上不可用，员工只能手工输入，容易产生输错条码、包装数量和商品匹配错误。
- 仅在支持原生 `BarcodeDetector` 的浏览器上修补，仍会造成不同手机和浏览器体验分裂。

后续开发边界：

- 摄像头申请必须只依赖安全上下文和 `getUserMedia`，不能把原生 `BarcodeDetector` 作为打开摄像头的前置条件。
- 原生识别器可作为快速路径；不支持时必须使用可审计的浏览器端解码后备，覆盖二维码与常见一维商品条码。
- 保留手工输入，并对“用户拒绝权限”“系统未授权浏览器”“没有摄像头”“摄像头被占用”“浏览器解码不支持”分别给出恢复说明。
- 不允许上传连续摄像头画面到服务端；只提交员工确认后的条码文本和既有收货事实。

验收标准：

- iPhone Safari、安卓 Chrome、华为浏览器以及实际使用的微信内置浏览器分别完成真机摄像头授权测试。
- 每个平台至少验证 EAN-13、Code128 和二维码各 1 个真实样本。
- 拒绝权限、永久拒绝、切到后台、关闭弹窗、重复打开和摄像头被占用均能恢复或给出明确说明。
- 扫码只建立待收货单，仍需第二次确认实物后才增加库存。
- 自动化门禁包含能力降级测试，不能再用源码字符串断言代替真机验收。

本地开发状态（2026-08-22）：

- 摄像头权限申请已移到识别器能力判断之前：不支持原生 `BarcodeDetector` 的浏览器仍会先申请后置摄像头权限。
- 新增完全本地运行的一维码/二维码识别后备，覆盖 EAN-13、EAN-8、UPC-A、UPC-E、Code128 与二维码；不会上传连续画面。
- 权限拒绝、无设备、设备占用与本地解码不可用会给出不同恢复说明；关闭或识别成功仍会停止摄像头轨道。
- 此项只完成本地开发与构建验证，尚未在 iPhone、安卓、华为及微信内置浏览器完成实机验收，不能提前标记为已关闭。

### MBOX-PENDING-006：库存扫码入口的视觉层级与选择反馈不清晰

- 状态：`待验收（本地修复）`
- 类型：`体验问题`、`可操作性缺口`
- 优先级：中
- 发现日期：2026-08-22
- 环境：员工端调酒师登录后的库存管理页面
- 影响岗位：调酒师，以及具备库存权限的店长、副店长、库存管理人员

事实：

- “手机扫码入库”使用实心深绿按钮；同级的“首次绑定条码”“单项盘点”“登记损耗”使用白底描边按钮。它们都是同一组库存动作，但没有说明颜色差异代表默认动作、当前选择还是风险等级。
- 页面内部虽保存当前操作模式，但按钮本身没有选中样式、`aria-pressed` 状态、图标变化或“当前正在进行”的文字提示。
- 再次点击同一按钮会收起当前表单；切换按钮会清除通用提示，员工不会得到明确的“已切换到哪一项操作”或“已收起”反馈。
- 扫码成功后才会显示“条码已识别，请核对后继续”；在选择入库、绑定、盘点或损耗操作的阶段，没有同等明确的反馈。

影响与边界：

- 这不是库存数据越权或直接误记账问题：各业务动作仍需后续填写、核对和提交。
- 但调酒师在手机上难以判断当前选择的流程，容易反复点击、误切换或错过“首次绑定条码”这一前置动作；视觉层级也与已确定的品牌绿交互语言不一致。

后续统一修复要求：

- 将四项入口设计为语义一致、可识别的操作组：选中项必须持续可见，并通过颜色、边框、图标和简短状态文案共同表达，而不是只依赖表单是否出现在下方。
- 明确颜色语义：入库可作为正向主动作；盘点、绑定为中性操作；损耗应保留审慎提示，但不能误导为不可用。
- 为收起、切换和扫码识别分别提供清楚且不打断操作的反馈；切换前后不得误提交、误清除已确认的库存事实。
- 在 320px、390px 及常见移动浏览器上验证：按钮不溢出，选中状态可辨，表单焦点和后续步骤可见。

验收标准：

- 使用调酒师实际权限分别选择四项操作，录屏或真机截图能清楚辨别当前模式。
- 选择、切换、收起、扫码识别及最终提交各有对应的界面反馈；未确认前不产生库存写入。
- 补齐针对选中状态、移动窄屏布局和无障碍状态的界面契约测试。

本地开发状态（2026-08-22）：

- 入口现采用统一操作组；已选项持续显示品牌绿底色、边框和“当前”标记，并写入 `aria-pressed`。
- 选择、切换和收起均给出即时文字反馈；“新建酒水物料”纳入同一操作组。
- 已通过组件契约与构建验证；仍需由调酒师在真实手机窄屏上完成验收。

- 从提交到结果提示，页面员工身份与服务端审计主体保持一致；任何会话切换均要求显式确认。
- 没有价格配置权限时，系统必须在写入前阻止完整上架流程，或创建可追溯、明确标记且不影响目录的草稿；不得留下未说明的半成品商品。
- 用店长、系统管理员和无价格权限员工分别验证：商品资料、价格、成本的授权边界与结果提示一致，审计记录可追溯。

本地开发状态（2026-08-22）：

- 商品新增或编辑与标准售价现由同一服务端命令、同一数据库事务完成；定价权限在商品写入前核验，价格失败会整体回滚，不再先生成未定价商品再补写价格。
- 员工切换后会强制重建当前模块，避免上一个会话遗留的商品页面状态继续显示。
- 尚未复现生产页面从“李艳”跳到“乌鸦”的现象，不能据此断言该身份显示问题已经根治；上线前仍需用服务端会话、命令审计和页面切换录屏复测。

### MBOX-PENDING-008：空库存门店无法从员工端建立首个酒水物料

- 状态：`待验收（本地修复）`
- 类型：`业务流程阻断`、`库存主数据缺口`
- 优先级：高
- 发现日期：2026-08-22
- 环境：生产员工端模拟演练；清理测试业务数据后，库存物料为 0 项
- 影响岗位：老板、店长、副店长、调酒师、库存收货人员

事实与复现证据：

- 老板和调酒师的“库存与存酒”页面都显示 `0 项物料`。
- “首次绑定条码”要求先从“酒水原料或瓶装酒”的下拉框选择已有物料；空库时该下拉框没有任何可选项。
- “手机扫码入库”要求输入已绑定的条码以建立待收货单；它不提供创建物料、名称、规格、库存单位或初始成本的入口。
- 商品编辑页的“库存扣减配方”显示“当前还没有库存物料。请先在‘库存与瓶存’中扫码或手工建立物料”，但库存页实际只有扫码收货和绑定已有物料，未提供手工建立物料表单。
- 新建测试商品不会自动生成库存物料；库存页仍为 0 项物料。

风险：

- 新店、测试环境或清库后的恢复场景无法由员工按正常业务流程录入第一批酒水、成本和库存，也就无法配置配方扣减。
- 任何为绕过该问题直接写数据库的做法都会绕过收货、成本、审计和岗位权限链，不能作为现场操作方案。

验收标准：

- 有权限员工可从空库存状态通过明确的“新建酒水物料”流程录入名称、规格/单位、初始数量、单位成本、供应商及可选条码，并生成审计事实。
- 条码绑定、待收货、实物确认和配方配置均可在新物料创建后按原有两步控制继续执行；未确认收货前不得改变可用库存。
- 用空库门店完成“新建物料 → 绑定条码 → 待收货 → 实物确认 → 配方 → 下单扣减”的端到端员工演练。

本地开发状态（2026-08-22）：

- 库存页新增仅限库存管理权限的“新建酒水物料”：录入编号、名称、库存单位和安全库存后，自动进入条码绑定步骤。
- 物料主数据建立不直接增加库存；供应商、实际数量和货款总额仍由“待收货单 → 实物确认”两步写入，避免把未经核对的初始数或成本直接计入库存。
- 已通过组件契约与构建验证；仍需按完整空库路径进行真实员工端演练。

### MBOX-PENDING-009：退款后仍待制作的出品异常未从收银页形成直达闭环

- 状态：`待验收（本地修复）`
- 类型：`可操作性缺口`
- 优先级：高
- 发现日期：2026-08-22
- 环境：当前代码与生产遗留数据只读检查
- 影响岗位：收银员、店长、副店长、调酒师、后厨

事实：

- 系统已有受权限、理由、审计和异常证据约束的 KDS 经理终止命令；它不会伪造库存或财务结果。
- 收银工作台已能显示退款和跨日支付，但没有投影关联 KDS 任务，也没有把“已退款且仍待制作”的任务带入同一异常处理链。
- 因此收银员核实退款后，仍需自行到出品工作台查找并处理任务；对于跨日遗留数据，这一步容易漏掉，造成调酒师或后厨继续制作。

处理边界：

- 不能以退款申请、退款处理中或支付未知为由自动取消 KDS；只有退款渠道已明确终态、且具备 `kds.exception.manage` 权限的员工填写现场原因后，才允许终止未制作任务。
- 已开始制作、已完成或已送达的任务必须转入受控异常与库存、财务复核，不能在收银页静默取消。

验收标准：

- 收银异常页能明确标识关联出品任务及其当前状态，并引导授权人员处理。
- 终止操作保留原订单、支付、退款、KDS 状态链和原营业日，不自动改写库存或退款事实。
- 退款未知、制作中、已送达及无权限员工均有明确的拒绝或升级提示。

本地开发状态（2026-08-22）：

- 收银工作台现投影订单关联的吧台、后厨任务；套餐组件任务也会按其可退款的父订单明细归集，不会因组件行而遗漏。
- 仅当退款分配已由渠道确认成功、且出品仍为“待接单”或“已接单未制作”时，具备 `kds.exception.manage` 权限的员工才会看到“核对退款后处理出品”。操作要求现场说明和二次确认，仍调用原有受审计的经理终止命令。
- 退款处理中、未退款、制作中、制作完成或无权限时不提供终止按钮；页面明确给出升级复核提示。
- 已通过收银投影、界面边界、KDS 经理终止既有权限契约和双端构建验证；仍需用真实岗位完成一次“退款成功 → 未制作任务终止 → 库存/财务复核”的现场验收。

### MBOX-PENDING-010：已送达的测试订单取消未付款应收后仍无法关台，缺少受控测试清理路径

- 状态：`本地修复完成，待部署后复核`
- 类型：`测试数据清理阻断`、`结果提示不一致`
- 优先级：高
- 发现日期：2026-08-22
- 环境：生产运营后台；陈方宇账号
- 影响岗位：老板、店长、收银员、服务员

事实与复现证据：

- S1 存在一笔 ¥226 的已送达、无支付记录订单；按用户确认的“测试订单清理”理由执行“取消未付款订单”后，系统返回成功并说明历史履约和库存事实保留。
- 随后关台仍被拒绝，明确提示“本桌仍有1笔未结订单（待收¥226.00）”。
- 这证明该命令只取消未履约部分，不能将已送达应收直接核销；其账实保护方向正确，但成功提示未说明桌台仍会被阻断，也没有面向测试环境的受控清理命令。

处理边界：

- 不得虚构现金、POS 或线上支付来关台，也不得删除已送达、库存消耗和原营业日事实。
- 正式营业订单应先补权威收款凭证，或由授权人员走独立的坏账／免单／争议核销流程；“测试清理”不能复用正式收银通道。

本地修复（2026-08-22，未部署）：

- 普通“取消未付款订单”现在明确说明：已送达金额不会被取消，仍需异常结清后才能关台。
- 新增独立的“异常结清已送达金额”命令，只接受已取消、未付款、且所有订单行均已送达或取消的订单；它不创建现金、POS 或线上付款，也不删除履约、库存或原营业日事实。
- 异常结清只授予老板、运营负责人、店长和副店长；测试清理在该范围内再限制为老板角色。每次均要求至少四字现场说明、二次确认、幂等键和不可修改事件。
- 关台与跨日关台校验都会识别该独立结清事件；若还有出品、支付、退款或服务任务，仍继续拒绝关台。

剩余治理边界：

- 当前门店没有独立的“测试门店／测试模式”强配置，所以“测试清理”只能以老板角色和不可变审计作最小控制，不能自动判断一笔生产数据是否真的属于测试。正式上线前应决定：保留该老板专用入口，或在门店配置中再增加显式测试模式开关；不能把它下放给收银员或服务员。

部署后验收标准：

- 若取消不会使已送达订单可关台，界面必须在提交前和结果中明确说明仍需的结算或核销步骤。
- 老板对 S1 的测试订单执行“取消未付款订单 → 异常结清已送达金额 → 关台”后，原订单、已送达记录、库存和原营业日仍可查，且不生成虚假付款；其他岗位与无权限员工不能执行异常结清。
