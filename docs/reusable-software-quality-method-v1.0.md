# 可复用软件功能、性能与发布质量方法 V1.0

## 1. 目的

这套方法适用于 Web、App、小程序、后台管理、交易系统和现场运营系统。目标不是“跑了多少测试”，而是对每个版本回答五个问题：

1. 做的是哪一条需求，边界和风险是什么。
2. 哪些功能、角色、异常和状态迁移已经验证。
3. 在什么负载、设备、网络和数据规模下达到什么性能。
4. 发现的问题是否复现、修复并完成回归。
5. 当前代码、CI、部署物和现场运行版本是否是同一个不可变版本。

## 2. 先检查问题定义

每项需求先分为事实、推测和偏好。缺少下面任一项时，不能直接把需求写成“已完成”：

- 使用角色和权限边界。
- 前置状态、触发动作、成功结果和失败结果。
- 数据事实来源及最终写入位置。
- 重复点击、并发执行、断网、超时和第三方失败时的行为。
- 是否涉及付款、退款、库存、隐私、审计或不可逆操作。
- 验收设备、浏览器、网络、峰值人数和数据规模。

## 3. 风险分级

| 等级 | 定义 | 最低测试要求 |
|---|---|---|
| P0 | 资金、权限、数据丢失、营业中断、安全事故 | 单元、集成、端到端、并发、故障注入、回滚和人工现场验收 |
| P1 | 核心流程不可用、错单、漏单、重复执行、严重性能下降 | 单元、集成、端到端、边界、幂等、性能和角色交叉验证 |
| P2 | 次要流程错误或明显体验问题 | 功能、移动端、异常反馈和回归测试 |
| P3 | 文案、视觉或低风险配置 | 目标页面检查、截图对比和基础回归 |

测试范围按风险增加，不能因修改文件少就降低资金、权限和数据风险的门禁。

## 4. 从需求到证据

使用同一条可追溯链：

```text
需求ID -> 风险 -> TC -> 自动/人工测试 -> 原始证据 -> 缺陷ID -> 修复提交 -> 回归结果 -> 发布版本
```

TC至少包括：正常流程、边界值、无效输入、权限拒绝、重复点击、并发冲突、状态迁移、第三方失败、恢复/回滚、移动端与弱网。使用`docs/templates/software-tc-register-template.csv`登记，不允许只写“已测”。

## 5. 功能测试层次

1. **静态门禁**：格式、类型、依赖漏洞、密钥扫描、迁移连续性。
2. **单元测试**：纯规则、价格、权限、时间、状态机和幂等键。
3. **集成测试**：API、数据库、缓存、消息、文件、第三方模拟器。
4. **端到端测试**：按真实角色从入口执行到最终状态，并反查数据库和接收端。
5. **交叉验证**：发起人、处理人、管理人看到的状态必须一致。
6. **现场验收**：真实设备、真实网络、真实外设和真实第三方通道。

模拟支付、模拟推送和模拟打印只能证明内部协议处理，不能替代真实通道验收。

## 6. 性能测试方法

先建立真实工作负载模型，再测数字。至少分开测：

- 整机/App或浏览器进程冷启动、新浏览器上下文首开、已有会话页面启动和页面内切换。
- 客户读取、员工读取和写操作。
- 单请求延迟与完整端到端延迟。
- 常态负载、峰值突发、极限压力和长时间稳定性。
- 单实例、双实例、数据库连接池和队列等待。

每个关键指标必须记录环境、样本量、到达率、并发上限、实际吞吐、调度延迟、成功数、错误率、P50、P95、P99和最大值。少量样本不能证明长尾：关键接口P95至少300个成功样本；正式P99容量结论通常至少1000个成功样本并重复3轮，或给出统计置信依据。300个样本中的P99只有约3个尾部观察值，只能作为PR回归信号，不能单独证明生产容量。性能结论必须同时检查：

- 客户端感知时间。
- 服务端路由时间。
- 数据库连接获取和查询时间。
- 事件循环、CPU、内存、重启和队列高水位。
- 数据是否正确、是否重复写入、状态是否回退。

乐观更新只能改善感受，不能掩盖服务端失败；失败时必须恢复权威状态并明确提示。

### 6.1 先把经营规模换成请求模型

“300位客人”不是“300个请求同时发生”。必须先记录营业时长、到客分布、在线设备数、轮询间隔、每位客人的动作次数、员工人数和岗位并发，再计算到达速率：

```text
平均到客率 = 到客人数 / 营业秒数
员工心跳率 = 在线员工数 / 心跳间隔秒数
接口到达率 = 在线设备数 / 轮询间隔秒数 + 业务动作率
```

性能测试至少保留四种互不替代的模型：

1. **常态到达率**：按时间逐步发起请求，验证正常P95/P99。
2. **峰值突发**：短时间提高到达率，验证队列、长尾和自动恢复。
3. **极限压力**：逐级增加负载，找出拐点；只用于容量规划，不冒充正常SLO。
4. **持续稳定性**：运行数小时，检查内存、连接、句柄、重启和延迟漂移。

闭环并发会在一个请求完成后立刻补发下一个请求，容易制造不符合现场节奏的持续饱和；开放式到达率更适合经营系统SLO。两者都要测，但报告必须分开，不能用压力拐点放宽正常门禁，也不能用低到达率证明极限容量。

同一个脚本不得同时冒充三种结论。建议固定拆为：

1. **代表性经营窗口**：角色、动作比例、数据规模和到达节奏接近真实峰值，判断现场SLO、错误率和资源余量。
2. **单路由性能回归**：隔离某条关键路由，取得足够样本，判断本次提交是否比基线退化；不直接声称整店容量。
3. **热点容量与拐点**：逐级提高写入或并发，记录开始排队、长尾突增、拒绝和恢复的位置；允许超过正常SLO，但不允许错单、丢单或状态回退。

报告必须给每轮写明`conclusionLevel`，至少区分`regression`、`representative_peak`和`capacity`。三者的阈值、样本和发布作用分别配置，不能在结果文件中临时自定义。

当完整营业时段过长，可按固定比例压缩时间，但必须保留各角色动作比例并让它们同时发生。例如5.5小时压缩到300秒时，时间压缩倍数为66；报告必须同时写真实平均到达率、压缩到达率和压缩倍数。测试程序必须记录目标RPS、实际RPS和调度延迟；压测机无法按时发出请求时，本轮无效，不能把较低实际负载当成通过。

### 6.2 固定环境与共享CI分工

- 共享CI用于发现代码回归、错误、竞争、泄漏和证据不一致；其CPU会波动，不单独决定生产容量。
- 固定规格候选环境用于执行绝对P95/P99、CPU、内存和数据库容量门禁。
- 正式环境只做可控的小流量、只读或隔离数据验证，不直接用生产资金和订单做破坏性压力测试。
- 报告必须写明CPU、内存、操作系统、运行时、数据库版本、实例数、构建模式、数据量、预热量、到达率和最大并发。

如果本地通过而CI失败，不能简单重跑或放宽指标。应先比较相同提交、相同数据、相同负载模型，再判断是代码回归、测试模型错误、资源饱和还是共享运行器噪声。

### 6.3 性能执行顺序

```text
环境校准 -> 准备接近生产规模的数据 -> 预热 -> 常态SLO
-> 峰值突发 -> 极限拐点 -> 稳定性 -> 恢复验证 -> 数据一致性复核
```

每轮前后都记录资源基线。性能失败时同时保留客户端报告、服务端路由分位数、事件循环、连接池、慢查询、队列、日志和最终数据库状态，否则无法区分“接口慢”和“测试机忙”。

单路由回归必须隔离数据基线。若多个写路由按固定顺序复用同一数据库，后执行路由面对更大的订单、事件或聚合状态，测试结果会混入数据增长影响，不能用于路由间比较。正确做法是每个阶段从同一快照恢复，分别启动应用、测量、封存日志和指标，再由合并器核对阶段完整性。

阶段合并不能只信任客户端延迟JSON。每个阶段必须同时满足：客户端请求与最终不变量、服务端路由日志、运行指标/资源门禁、环境指纹。环境指纹至少包含提交SHA、脏工作区标识、构建输入指纹、构建产物摘要、依赖锁、迁移集、种子数据、运行时、实例数和连接池参数。提交SHA可在运行时注入，不能单独证明运行目录来自当前源码；复用构建前和测量结束后都必须核对包含未提交源码的构建输入指纹。测试运行中源码、依赖锁、构建参数或测试脚本变化时，本轮判无效，不得把前半段旧构建和后半段新验证器拼成证据。合并器要核对四类证据的阶段名、完整性、一致性、通过状态和摘要；缺任一类即`DENY`。

准备数据和正式测量尽量使用不同窗口。无法重置指标时，报告必须明确“包含准备流量”，不能把准备动作和目标动作混为同一路由结论。多实例共享同一权威状态时，状态增长斜率的分母使用集群总写入数，不能用单实例样本数把同一份全局增长重复计算。

“重置指标”不是只清一个客户端数组。一个可归因的测量窗口至少需要同步重置路由直方图、事件循环分布、连接池获取分布、应用写队列等待/服务时间及错误计数，并从数据库当前权威状态重新建立数据体积基线。多实例必须逐实例完成重置并验证成功；任何实例重置失败、重置时仍有在途请求或生产环境允许重置，均应阻断测试。

聚合状态增长至少用三道门槛共同判断：绝对字节上限、每个成功业务写的字节增长斜率、接近真实营业量的数据包络。初始状态很小时，单纯使用“增长倍数”会制造假阳性；倍数可以预警，但不应脱离绝对体量和业务事件数单独阻断。还必须执行连续多个业务周期的稳定性测试，确认归档、切日或保留策略能让活跃状态保持有界。

## 7. 如何系统发现问题

### 7.1 用状态不一致找问题

同一业务动作同时检查页面、API响应、数据库、接收岗位和审计记录。任何两处不一致都建立缺陷，不以“页面显示成功”作为完成证据。

最终状态断言必须理解时间。测试持续时间跨过提醒、升级、超时、自动关闭或营业日切换时，预期应由状态机和权威时钟推导，而不是固定写死测试开始时的状态。允许合法演进时仍需检查对应事件、时间戳、操作者、责任人和副作用，防止用宽泛状态集合掩盖错误。

### 7.2 用异常矩阵找问题

对每个核心动作依次注入：重复提交、慢响应、超时、断网、重连、并发操作、权限变化、库存不足、第三方拒绝、回调重复、服务重启和数据库连接耗尽。

### 7.3 用运行指标找问题

同时观察错误率、P95/P99、连接池等待、队列深度、事件循环、内存、容器重启和外部依赖耗时。平均值正常但长尾异常，仍然是现场问题。

### 7.4 用真实角色找问题

客户、执行员工、替补、主管、财务和管理员分别只使用自己的权限完成任务。检查入口是否过多、提示是否可执行、是否需要反复翻找和是否必须一直盯着手机。

### 7.5 用历史日志找问题

先将动态 ID 归一为路由或事件类型，再统计错误信号、状态码、分位数和重复操作。日志中的一次异常必须关联版本、时间、角色、请求 ID 和处理结果，禁止记录令牌、PIN或完整个人信息。

### 7.6 用模型和不变量找问题

为订单、支付、库存、预约、任务等核心状态机写不可违反的不变量，例如：

- 同一幂等键不能产生两个订单。
- 退款累计额不能超过实付额。
- 制作完成不能把已送达状态退回制作中。
- 同一座位同一时段只能有一个有效锁定。
- 权限拒绝不能留下半写入数据。

使用属性测试、随机操作序列、状态机遍历和差分检查，比只写若干固定案例更容易发现遗漏组合。

### 7.7 用可观测性缺口找问题

无法回答以下问题本身就是缺陷：哪一版本、哪一请求、哪一角色、在哪一状态失败；是否重试；最终是否成功；是否产生重复副作用。核心动作必须有请求ID、业务ID、幂等键、状态迁移、耗时和审计结果，但敏感值只能保存脱敏摘要。

### 7.8 先验证测试工具本身

测试脚本不是事实来源，必须先通过自己的单元和故障测试：

- 固定输入能产生固定请求数量、角色和租户范围；随机场景必须保存种子。
- 开放到达脚本记录目标RPS、实际发起RPS、漏发数、调度P95/P99和最大并发；压测机跟不上时本轮判无效。
- 模拟身份必须与业务权限匹配；预期的403/409应放在权限或冲突TC中，不能混入成功性能样本。
- 模拟器应能主动返回超时、重复回调、乱序、部分成功和格式错误，验证系统不是只适配“永远成功”的假外部服务。
- 证据生成器必须用反例测试证明无法用零样本、未来时间、脏提交、伪造引用、降低阈值或删除门禁获得通过。
- 统计程序必须用已知分布校验P50/P95/P99，并拒绝`P50 > P95`、成功数大于样本数等不可能结果。
- 修改一项构建输入后尝试复用旧产物，测试启动器必须在服务启动前拒绝；只核对接口返回的提交SHA不够。

测试失败时先按四类归因并保留证据：产品缺陷、测试脚本缺陷、环境/资源问题、需求或阈值定义错误。修复测试脚本后必须重跑，不得直接删除失败样本。

### 7.9 建立独立测试预言

每个关键结果至少由一个独立于被测页面的事实源判断：数据库约束、只读查询、审计事件、接收端状态或第三方查询接口。测试代码不能只复述被测接口返回的`success`。资金、库存和权限场景至少使用两种独立事实源交叉验证。

### 7.10 从指标分解定位性能问题

端到端慢时按同一个请求ID拆成：压测机排队、网络、鉴权、连接池获取、数据库行锁/事务锁等待、状态读取与克隆、业务计算、序列化、权威写入、投影/消息、事务提交、响应传输和前端渲染。只看到总耗时不能直接归因于服务器配置；连接池等待接近零但事件循环和写队列上升时，应优先检查同步CPU、过大对象、锁竞争和串行写路径。

### 7.11 验证多实例后台调度

定时提醒、清理、对账、补偿和SLA升级在单实例正确，不等于多实例正确。必须同时验证：同一租约窗口只有一个实例执行；租约持有者退出后其他实例能接管；后台动作不会重复产生副作用；后台任务与前台写入共享锁或队列时优先寻找短暂空闲窗口；避让达到最大期限后仍会执行并告警，不能为了前台延迟让关键调度永久饥饿。报告分别记录前台P95/P99、后台最大延后、重复执行数和漏执行数。

### 7.12 测量后台任务的空转成本

后台任务没有到期工作时也可能拖慢系统，例如周期性复制大对象、全表扫描、序列化、日志刷新或GC。必须把“无工作空转”和“工作到期”分成两个场景：前者记录每个周期的CPU、事件循环P95/P99、扫描行数、复制字节和写入次数，后者记录实际执行延迟、前台P95/P99变化、重复/漏执行和恢复。平均值正常但P99按固定周期出现尖峰时，应优先对齐定时器周期和GC/序列化时间，不能先扩大连接池或提高阈值。

### 7.13 失败本身也必须形成证据

测试失败时仍要保存原始报告、样本量、分位数、错误样本和环境身份。`fail`、`blocked`、`not_run`和`artifact_missing`必须分开表达；没有制品不能解释成失败，也不能把失败解释成没有执行。PR和主分支都要上传可校验的失败制品，才能复现和归因。

制品上传本身也是门禁。报告已生成但对象存储额度耗尽、权限拒绝或网络中断时，测试结果仍按原始执行状态记录，同时证据链单独标记`artifact_missing`并阻断发布。不得因为CI日志里能看到部分数字就宣称可追溯性完成；清理历史制品属于账号级破坏性操作，应经授权并保留清理清单，正式系统应准备第二不可变存储或明确保留策略。

## 8. 缺陷闭环

```text
稳定复现 -> 写最小失败TC -> 定位根因 -> 修复根因
-> 运行最小回归 -> 运行同风险域回归 -> 运行发布门禁
-> 绑定提交和证据 -> 候选部署 -> 现场复验
```

不得只增加重试或隐藏报错；需要判断是前端反馈、接口幂等、状态机、数据库竞争、资源容量还是外部依赖问题。

## 9. 发布门禁

发布证据至少包含：完整40位提交 SHA、CI run id、测试报告、性能原始数据、迁移清单、镜像摘要、部署环境、备份、健康检查和回滚验证。代码通过但现场依赖未验收时，结论必须是`DENY`或“仅验证环境”。

使用V2格式的`docs/templates/software-quality-evidence.template.json`建立证据总账。门禁集合、最低样本和性能阈值必须来自独立、版本化的质量政策JSON，结果文件不得自行删减门禁或放宽阈值。V2同时强制声明性能环境和工作负载，防止“性能作业显示成功但没有路由明细”等空证据放行。执行：

```bash
node scripts/verify-quality-evidence.mjs --input evidence.json
node scripts/verify-quality-evidence.mjs --input evidence.json --policy quality-policy.json --require-release-pass
node scripts/verify-quality-evidence.mjs --input evidence.json --policy quality-policy.json --require-release-pass --require-deployment
node scripts/verify-tc-register.mjs --input tc-register.csv
node scripts/verify-tc-register.mjs --input tc-register.csv --required-baseline required-tc.txt --expected-commit "$GIT_SHA" --max-evidence-age-days 7 --require-release-pass
node scripts/verify-quality-model.mjs --state-machine state-machine.json --invariants invariants.csv --require-release-pass
```

第三条只适用于已经完成不可变部署和回滚验证的版本。

质量政策文件必须由独立代码所有者审查并受主分支保护，否则开发者可在同一PR中修改政策来降低门禁。离线验证器只能核验账本结构、计数、阈值、提交和已提供的摘要；GitHub、对象存储、应用商店或部署平台上的证据是否真实存在，必须由CI使用平台身份生成、下载复核并封存，不能只相信一段引用字符串。

开发CI和商业发布门禁必须分开：开发CI可保留`not_run/blocked`以继续迭代，但标签、镜像切流和商业发布必须调用`--require-release-pass`，所有P0/P1 TC、不变量、真实第三方验收和回滚证据未通过时稳定拒绝。发布流程不能只等待“某个CI成功”。

TC登记必须有独立的必需ID基线或需求基线摘要。验证器不仅检查剩余行是否合法，还要检查是否有人删除了必需P0/P1用例。政策、必需TC基线、状态机、不变量和验证器应由`CODEOWNERS`及主分支保护共同约束；只有仓库内文件而没有平台保护，仍不构成独立信任根。

## 10. 团队执行节奏

- 每项需求进入开发前：补齐需求ID、风险和验收条件。
- 每次提交：运行静态、单元和相关风险域测试。
- 每个PR：按变更范围自动选择门禁，P0/P1和未知改动强制全量。
- 每个候选版本：完整端到端、数据库、性能、漏洞、不可变镜像和回滚测试。
- 正式上线后：观察实际指标和现场反馈，新增问题写回TC，形成永久回归项。

这套方法的核心约束是：没有原始证据不算测试，没有对应提交不算版本证据，没有真实外部验收不算商业可用。

## 11. 可复制到其他软件的最小落地包

新项目复制下面十二项即可开始，不依赖M-BOX业务代码：

1. `docs/templates/software-tc-register-template.csv`：需求、TC、缺陷和证据登记。
2. `docs/templates/software-quality-evidence.template.json`：一次候选版本的质量总账。
3. `scripts/verify-quality-evidence.mjs`：按独立质量政策阻止删减门禁、样本不足、失败项未关闭、脏工作区或非完整SHA冒充发布通过。
4. `scripts/verify-tc-register.mjs`：阻止重复TC、伪造通过、缺少证据和过期提交。
5. `docs/templates/software-required-tc-baseline-template.txt`：独立保存不能从执行清单删除的TC ID。
6. `scripts/load-workload-model.mjs`：按到达率而不是凭感觉建立负载，并记录压测机调度偏差。
7. CI中的“分类、功能、浏览器、数据库、性能、证据、发布物”独立作业。
8. `docs/templates/software-state-machine-template.json`：登记合法/非法迁移、角色、守卫、副作用和补偿。
9. `docs/templates/software-invariant-register-template.csv`：登记守恒、唯一、单调、权限和最终一致性约束。
10. 独立版本化的`quality-policy.json`：固定必需门禁、最低样本、性能模型和证据时效；项目PR不能自行降低。
11. 构建输入指纹与产物摘要工具：阻止旧构建目录、错误镜像或运行时注入的伪版本声明进入测试证据。
12. `docs/templates/software-test-round-template.md`：逐轮记录问题定义、测试预言、性能窗口、五线证据、缺陷闭环和发布判定。

公共核心保留证据格式、状态一致性、样本校验、提交绑定和发布门禁；项目适配层只替换角色、状态机、不变量、风险阈值、真实负载和现场设备。不要把M-BOX的桌台、KDS或营业日规则硬编码进公共验证器。

### 11.1 新软件第一次接入的执行顺序

1. 建立角色、资产、外部依赖和不可逆动作清单。
2. 为核心对象画状态机并定义不变量。
3. 将需求拆为可执行TC，标记风险、自动化级别和测试预言。
4. 建立最小真实数据集、生产规模数据集和可复现故障数据集。
5. 先跑单元与集成，再跑角色端到端和异常矩阵。
6. 校准压测机，分别执行代表性窗口、单路由回归和容量拐点。
7. 用日志、指标、数据库和接收端交叉定位，不以页面提示代替事实。
8. 把每个缺陷转成永久回归TC。
9. 生成提交级证据账本，验证代码、镜像、迁移和部署版本一致。
10. 真实设备、网络和第三方通道验收后才允许商业发布。

第一次接入完成后，用至少三个故意失败的样例反测门禁：删除一个P0用例、伪造一个通过证据、让压测机漏发请求。三种情况都必须稳定得到`DENY`，否则测试系统本身尚未合格。

完整执行步骤、缺陷归因和交付清单见[通用软件测试执行手册](reusable-software-test-execution-runbook-v1.0.md)。

## 12. 禁止的测试结论

- “页面能点”不等于业务完成。
- “HTTP 200”不等于数据库、接收岗位和审计一致。
- “平均很快”不等于P95/P99达标。
- “本地通过”不等于固定候选环境或生产容量通过。
- “新浏览器上下文首开通过”不等于真实设备完整冷启动通过。
- “模拟支付通过”不等于真实支付、退款和对账通过。
- “重跑后绿了”不等于偶发失败已修复。
- “有AI监督”不等于有独立证据；监督者也必须引用原始结果并允许判定失败。
