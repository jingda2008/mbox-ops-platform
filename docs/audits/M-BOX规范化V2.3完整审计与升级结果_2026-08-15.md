## 一、结论

原问题清单整体有经营合理性，但不能得出“全部问题都应塞进一次规范化改造、一次性上线”的结论。清单混合了四类不同工作：

1. 规范化前后真实功能回退，需要本轮修复；
2. 原能力已有但默认入口、权限或失败恢复不足，需要回归和补齐；
3. 支付、打印、POS、微信等外部联调，代码不能替代真实渠道和设备验收；
4. 菜单发布、库存、会员、经营分析、SOP、AI/语音等完整产品域，应独立版本开发。

本轮保留原 88 项，并补录此前矩阵没有单列的 4 项：`CFG-02 线上支付经营开关`、`UX-04 多终端响应式`、`AUD-01 规范化前后完整差异审计`、`CRM-01 客户通知同意强类型事实`。92 项当前分类如下：

| 结论 | 数量 | 含义 |
|---|---:|---|
| 已完成（本地候选） | 19 | 本地代码和自动测试完成，但尚未提交、部署或现场验收 |
| 已通过本地回归 | 13 | 基线能力保留，自动回归通过 |
| 部分完成 | 34 | 有局部能力，跨域状态、权限、配置或失败恢复仍缺 |
| 未实现（后续版本） | 19 | 需求合理，但应进入独立版本 |
| 外部条件阻塞 | 7 | 需要真实账号、渠道、硬件、网络或门店现场 |

因此，回答“都是合理的吗”：没有发现应直接删除的经营目标，但有两类表述必须收紧。第一，经营配置不能等于所有登录员工都能修改，必须由岗位权限、数据范围、版本、原因和审计控制；第二，AI/语音可以提醒、分析和生成候选，不能自主分配人员、修改业务状态、执行支付退款或扩大权限。

## 二、本轮实际升级范围

### 1. 李艳等员工责任分配

- 授权管理人员可选择员工、当次岗位、主服务员/候补/临时责任、开始与结束时间、原因、区域或多张桌台。
- 区域或多桌批量发布使用同一数据库事务；任一桌失败整批回滚。
- 发布后从服务端读回当前生效责任；结束责任要求二次确认。
- 默认权限只授予有 `table.assignment.manage` 的岗位，不向所有员工开放。
- 浏览器专项已验证“李艳作为店长负责一张桌台，再安全结束责任”。

### 2. 线上支付经营开关

- 最高管理/获授权管理岗位可关闭或开放门店线上支付。
- 每次调整必须填写原因，生成策略版本、审计和 Outbox 记录。
- 顾客点单和员工协助点单均由服务端强制执行开关，前端不能绕过。
- 经营策略开关与渠道当前可用性分开显示；渠道故障时仍允许有权限人员关闭原本开放的策略，避免渠道恢复后未经复核自动重新开放。
- 本地候选只验证支付保护逻辑，没有在本轮操作或复测远端渠道。

2026-08-15 已对远端做脱敏只读复核：`pay.shmbox.com` 的 DNS/TLS、反向代理和应用健康正常，空载伪造回调返回 `401 PROVIDER_SIGNATURE_INVALID`；但活动运行时仍是 `validation`，`MBOX_PAYMENT_MODE=disabled`，星驿机构号、商户号、公钥和回调字段均未在应用运行配置中启用。因此当前事实是“支付入口已接通、真实支付渠道仍关闭”，不能表述为已完成真实收款。候选不会写入、显示或覆盖渠道密钥；没有门店经营策略记录时即使未来渠道配置完成也默认关闭新的线上支付，必须由有 `payment.policy.manage` 的最高管理/门店管理岗位填写原因后显式开放。在途回调、查单、退款和对账不因关闭新支付而中断。

付款前库存/KDS 隔离已在本地候选重构：即时支付订单创建后保持 `awaiting_payment`，只形成有有效期的库存预占，不扣减账面库存、不创建库存消耗流水，也不进入 KDS。只有可信人工入账、渠道回调或主动查单确认成功时，才在同一数据库事务内消耗预占、更新付款与履约状态并创建 KDS；明确失败或关闭会释放预占。超时但渠道结果未知时不自动释放，保留预占并进入查单/人工复核，避免“顾客已付款、系统却把库存卖给别人”。预占时长可由获授权管理人员按门店配置为 2–30 分钟并保留策略版本。上述结论已由数据库并发测试和浏览器跨岗位流程证明，但尚未用远端真实资金、乱序回调和门店硬件验收，因此仍不能直接批准生产开放。

### 3. 演出、演员和歌单

- 演员资料和演出场次可由有权限员工登录后维护。
- 歌手原 JSON 数组已规范化为歌曲、歌曲别名和导入批次。
- 支持歌单搜索、文本批量导入、单曲修改/停用和点歌/演唱次数统计。
- 顾客点单页显示当日演出，预约页显示所选日期演出；演出读取失败不阻断点单或预约。
- 尚未完成顾客新点单页的歌单搜索/点歌提交，也未完成 XLSX/CSV 文件预览、错误行导出和歌单版本回滚。

### 4. 商品、推荐和门店主数据

- 商品页面支持新增、编辑、销售状态、顾客可见、搜索文本、推荐开关、人数范围、优先级、成本、标准售价、文案、图片和组合组件。
- 可见状态、搜索文本、人数范围、推荐优先级与标签、备选商品、菜单排序、供应时段、允许渠道、单笔上限、KDS 优先级、出品时限和成本金额均改为强类型运行字段；图片、文案等灵活展示字段保留 JSONB。
- 为 `rc.87` 应用回退保留了一次发布窗口的兼容副本和写入适配器；当前候选的资格、筛选、排序、金额、履约与推荐决定只读强类型字段，兼容 JSON 不再是运行权威。
- 商品编辑与调价分权；若商品保存成功而调价失败，页面明确显示部分成功，不伪装成整体成功。
- 区域和桌台支持新增、编辑、停用、排序、容量和最低消费；班次、工作站和统一版本回滚仍属后续版本。

### 5. 预约运行参数

- 预约申请保留时间、确认后到店宽限时间等关键参数改为强类型策略字段。
- 预约释放 worker 不再从 `reservation_snapshot` 解析关键运行参数。
- 顾客预约拆为“时间人数 → 位置联系 → 确认提交”三步；首步显示所选日期演出，第二步再填写偏好与联系信息，避免手机单页过长。

### 6. 客户通知同意

- 微信和短信通知同意改为追加式强类型事实，记录渠道、用途、状态、策略版本、生效/撤销时间、来源、操作者和证据。
- 根据经营审查意见，会员页不展示“消息授权”、微信通知或短信通知开关；会员页只保留权益、预约和必要身份信息。
- 授权或撤回应来自微信原生授权、短信退订或其他明确的受控业务触点；后台能力不接受调用方伪造客户 ID、用途或策略版本来扩大权限。
- 通知发送资格只读取当前强类型同意记录，不再从 `consent_snapshot` 的自由键决定是否外发。
- 员工客户资料接口明确拒绝写入 `consentSnapshot`，避免旧调用重新制造自由 JSON 授权事实。
- 历史迁移只把明确为 `true` 的旧同意回填为“旧版导入”事实；缺失或 `false` 不推导授权。生产前仍需法务确认通知文案、策略版本，以及微信/短信渠道退订同步。

### 7. 顾客、员工和跨端布局

- 顾客点单页分离当前购物车与历史订单，情绪输入降为可选，推荐默认三款比较。
- 员工首页按岗位和使用频率分层，高频入口不超过主要操作面，并保留“全部工作入口”；李艳的管理路径为“全部 → 现场 → 人员与责任桌”，不重复占用首页。
- 李艳责任桌分配由一次展开 61 张桌改为“区域折叠 + 桌号/区域搜索 + 已选摘要 + 整区选择”，避免长页和误选；批量事务与权限规则不变。
- 商品编辑只默认展示名称、状态、价格、成本、搜索和推荐等高频字段；供应、标签、渠道、KDS 等低频字段按需展开。系统配置中的角色范围和支付说明也改为按需查看，但支付当前状态和开关始终可见。
- 预约页拆成三步，并把生日、庆祝和备注等低频信息收进第二步的可展开区；会员页只保留权益、预约和身份信息，不展示通知技术开关。
- 关键页面按电脑、平板、手机调整密度、排列和触控尺寸；主要可见操作目标统一到至少 44px，并覆盖清晰状态反馈、弱网/断网恢复和视觉键盘遮挡代理检查。
- 已生成 22 张真实浏览器页面预览，覆盖 1440、1024、844 横屏、390 和 320px；另生成 2 张 iOS 模拟器安全会话主界面截图。浏览器专项覆盖 320/360/390/430px、大字体、深色偏好、弱网和横竖屏，均无页面级横向溢出。
- iOS 模拟器必须通过临时本地 HTTPS 才能验证 `__Host-` 安全会话；测试后临时证书、代理、数据库和端口均已清理，工程和构建产物恢复默认验证地址。Android 真机、iPhone 真机、厂商权限、发热、相机和真实通知仍未验收。
