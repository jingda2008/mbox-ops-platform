# M-BOX 性能测试分层模型 V1.0

## 1. 结论边界

M-BOX使用三套互不替代的性能模型。PR回归通过不等于经营峰值通过，经营峰值通过也不等于已经找到系统容量上限。

| 模型 | 目的 | 执行位置 | 发布作用 |
|---|---|---|---|
| 提交级单路由回归 | 发现代码导致的接口退化 | 每个P0/P1 PR的隔离PostgreSQL环境 | 源码合并门禁 |
| 代表性经营峰值 | 验证300人营业夜高峰的真实动作组合 | 固定规格候选环境 | 候选切流门禁 |
| 热点容量与恢复 | 找到1/2/4/6/8次业务写每秒的拐点 | 隔离容量环境 | 扩容和架构决策，不单独放行发布 |

## 2. 提交级单路由回归

- 两个API实例、PostgreSQL 16、12个真实岗位身份。
- 员工启动使用12个真实岗位，每个岗位至少10轮，测量“登录成功至首屏Bootstrap返回”的完整API旅程，共至少120个样本；不能把单独一次Bootstrap请求称为客户端启动。
- 读取类使用开放到达率，并记录目标RPS、实际发起RPS、漏发和调度延迟。
- 其他关键路由每条至少300个成功样本；写入类也使用固定开放到达率，不允许用“上一个请求完成才发下一个”的闭环单工作者隐藏排队。
- 每条写路由都从全新数据库基线开始，避免先执行的任务、订单或KDS状态持续膨胀，使后执行路由天然更慢。
- 权限身份和桌台来自权威Bootstrap目录；不存在或无权桌台不进入成功性能样本。
- 数据未变化的Bootstrap必须100%返回304；完整读取必须返回200，两者分别计时。
- 300个不同匿名客户首次扫码后，再跨两个实例重复同一批身份；返回的`tableSessionId`必须一致，不能只检查HTTP 200。
- 每个写阶段结束后必须反查两实例：返回ID唯一、实体数量正确、幂等重放不新增、最终状态正确，订单品项与KDS/库存关联完整。
- 每个阶段必须同时通过客户端、服务端日志、运行指标和环境指纹四类门禁；合并报告保存四类SHA256，环境必须同提交、同依赖锁、同迁移集、同种子数据且工作区干净，不得由客户端报告单独声明`evidenceEligible`。
- 状态增长使用绝对上限、集群总写入数对应的每次写入斜率和300人数据包络；小初始状态下的倍数只作预警。

这套模型只给`regression`结论。共享CI资源波动时，先比较提交、数据、脚本和调度证据，不允许靠重跑挑选最好结果。

## 3. 代表性经营峰值

开业前暂用以下假设，开业后三个高峰营业日必须用真实日志重新校准：

- 营业5.5小时、300位客人、12名员工。
- 每位客人约0.5张订单、0.5个服务需求、1.5个KDS品项。
- 十倍平均到客突发约0.15位客人/秒。
- 峰值暂定：客户会话0.15/s、订单0.075/s、任务创建0.075/s、任务完成0.075/s、KDS工作流0.225/s、员工心跳0.27/s、预约0.2/s、工作台读取0.6至2.4/s。
- 固定规格候选环境持续30分钟，保留前后资源基线和最终数据对账。

判定要求：实际到达率不低于目标98%、漏发0、意外4xx/5xx为0、丢单/重复/错状态为0、连接池与写队列无超时、事件循环P99不超过100ms。每条低频路由样本不足300时，只能用于混合经营正确性和资源判断，其路由P95仍引用单路由回归或更长固定环境测试。

## 4. 热点容量与恢复

- 真实读取负载保持不变，业务写按1、2、4、6、8次/秒逐级增加。
- 80%请求集中同一热点桌，20%分散到其他营业桌。
- 每级预热60秒、测量300秒、恢复观察120秒；正式容量结论每级重复3次。
- 记录队列等待、单次写服务时间、整店状态字节数、事件循环、CPU、内存、连接池、投影和状态一致性。
- 最高连续3次通过的档位才是安全容量；任何错单、丢单、状态回退、意外错误、漏发、队列拒绝或恢复超时均判失败。

6次业务写/秒可以作为容量阶梯，但不能称为300人正常经营峰值。当前架构仍有整店聚合串行写路径，测试应暴露其拐点，而不是放宽正常SLO。

## 5. 证据要求

每份报告必须绑定：完整提交SHA、脚本SHA、工作负载版本、环境ID、数据集摘要、随机种子、目标与实际到达率、原始响应、服务端日志、运行指标、最终数据库不变量检查和SHA256清单。

失败报告与成功报告同等保存。测试脚本错误、环境错误和产品错误分别记录，修复脚本后重跑但不得删除原失败事实。
