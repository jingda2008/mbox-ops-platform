# 软件功能与性能质量方法 V1.0

## 1. 适用范围

本方法适用于交易、经营、员工协作和客户应用。它用于回答四个不同问题，不能互相替代：

1. 功能是否正确。
2. 本次修改是否产生性能退化。
3. 固定资源下可以承受多少真实混合业务。
4. 某个不可变版本是否具备发布、切流和回滚条件。

## 2. 结论分层

每轮报告必须分开写：

- **事实**：请求数、成功数、P50/P95/P99、资源指标、业务对象数量和证据摘要。
- **推断**：瓶颈可能位于客户端、事件循环、应用队列、连接池、SQL锁或外部依赖。
- **决定**：继续观察、修复、扩容、拒绝发布或允许进入下一环境。

一次本地通过不能覆盖不可变CI失败；一次共享CI失败也不能直接证明生产服务器容量不足。

## 3. 五类测试必须分开

| 类型 | 目的 | 环境 | 最低要求 |
|---|---|---|---|
| 功能与不变量 | 证明状态、权限、资金、库存和审计正确 | 隔离数据库 | 正常、拒绝、重试、并发和回滚 |
| 提交级回归 | 发现本次代码是否明显变慢 | 标准CI | 每条核心路径独立基线，固定样本和阈值 |
| 候选容量 | 找出吞吐、安全余量和排队拐点 | 固定规格候选环境 | 1/2/4/5 RPS阶梯，每档至少3轮 |
| 稳定与故障 | 验证长时间、依赖异常和实例切换 | 候选环境 | 混合流量、断网、进程退出、数据库故障和恢复 |
| 真机体验 | 验证人实际感受到的速度 | 正式设备与网络 | 冷启动、已登录恢复、微信WebView、弱网和前端反馈 |

## 4. 每轮标准流程

1. 冻结提交SHA、依赖锁、迁移集、数据种子、机器规格和业务负载。
2. 建立全新数据库，不复用上一轮状态。
3. 将造数阶段与测量阶段分开；造数失败仍记录，但不得污染动作延迟。
4. 测量客户端、服务端、事件循环、队列、连接池、数据库和业务副作用。
5. 用请求ID或幂等键核对发起、响应、数据库修订、事件、审计和库存数量守恒。
6. 对失败做归因，不先改阈值、不先扩容，也不只重跑挑最好结果。
7. 任何优化都做同机、同数据、同负载的旧版/候选成对实验。
8. 固定候选环境连续3轮均通过后，才形成容量结论。
9. 真机和外部支付、打印、消息依赖必须单独验收。
10. 封存原始报告、日志、指标、环境清单、SHA256和最终判定。

## 5. 必测指标

- 客户端：动作反馈、首个可操作时间、P50/P95/P99、错误恢复。
- API：状态码、路由P95/P99、响应体积、重复请求和幂等结果。
- Node运行时：事件循环P95/P99、进程重启和内存趋势。
- 应用队列：总等待及按业务来源的P95/P99、拒绝、超时和高水位。
- 数据库：连接获取P95/P99、等待者、失败、SQL执行和锁等待。
- 业务守恒：订单、明细、KDS、任务、库存、支付和审计数量。
- 数据增长：活跃状态大小、每次写入净增、历史归档和查询退化。

阈值是产品质量策略，不是测试脚本的便捷参数。修改阈值、样本、RPS或路径集合必须单独评审，并记录旧值、新值、原因、有效期和回退条件。

## 6. 证据与结果分离

每轮必须同时记录三个状态：

- `test_result`：业务与性能门禁通过或失败。
- `evidence_integrity`：摘要、SHA、运行ID和提交是否一致。
- `evidence_transport`：附件上传、下载和长期存档是否可用。

附件额度不足不能把业务通过改写成性能失败，也不能把真实性能失败改成通过。PR可用日志和校验摘要作为短期诊断；正式标签发布必须取得完整原始证据，否则拒绝发布。

## 7. 发布判定

只有以下条件同时满足才允许发布：

- 所有P0和要求发布通过的P1功能/不变量TC通过。
- 提交级回归通过，且没有放宽质量策略或缩小负载。
- 候选环境容量、稳定和故障测试达到本次发布要求。
- 真机、支付、打印或消息等实际依赖按范围完成验收。
- 测试提交、镜像摘要、数据库迁移、发布证据和回滚对象完全一致。
