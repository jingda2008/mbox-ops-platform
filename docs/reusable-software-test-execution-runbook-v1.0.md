# 通用软件功能与性能测试执行手册 V1.0

## 1. 适用范围

适用于Web、App、小程序、后台、交易、运营和物联网系统。目标是让另一个项目在不复制业务代码的前提下，复用同一套发现问题、修复问题和证明版本可发布的方法。

## 2. 每轮测试输入

开始前必须固定：

- 候选提交SHA、依赖锁文件和构建方式。
- 需求ID、风险等级、角色、权限和验收条件。
- 状态机、不变量和权威数据源。
- 环境规格、数据集摘要、第三方模拟/真实通道边界。
- 工作负载模型、目标RPS、并发、样本量和SLO。
- 当前已知缺陷、历史失败和未执行P0/P1。

缺任一项时，先记录为测试前提缺口，不能自行假设后宣称通过。

每轮可直接复制`docs/templates/software-test-round-template.md`。它不是总结文档，而是执行记录：测试开始前填写版本、风险和预言，执行中追加原始证据，结束时只依据证据给出发布判定。

## 3. 一次标准执行

### A. 需求与风险审计

1. 找出前提跳跃、互相冲突和不可验证的描述。
2. 将事实、推测和体验偏好分开。
3. 标出资金、权限、库存、隐私、不可逆写入和外部依赖。
4. 为P0/P1建立正常、拒绝、重复、并发、超时、恢复和回滚TC。

### B. 建立测试预言

每个核心动作至少指定一个独立事实源：数据库约束、只读查询、审计事件、接收端状态或第三方查单。禁止只读取被测接口自己的`success`字段。

示例：

```text
点击下单
-> 前端即时反馈
-> API返回orderId
-> 数据库只有一个订单
-> 幂等重放仍返回同一orderId
-> 库存/KDS只产生一次副作用
-> 第二实例读取结果一致
```

### C. 分层执行

1. 静态：格式、类型、依赖、安全、迁移、密钥。
2. 单元：规则、状态机、金额、时间、权限、幂等。
3. 集成：API、数据库、缓存、消息、第三方模拟器。
4. 端到端：真实角色从入口到最终状态。
5. 异常矩阵：重复、并发、断网、超时、乱序、重启、部分成功。
6. 性能：单路由回归、代表性峰值、容量拐点、持续稳定性。
7. 现场：真实设备、网络、外设和真实第三方小额流程。

### D. 性能执行

1. 先分开三种测试：提交级单路由回归、经营代表性峰值、容量阶梯；三者不能互相替代。
2. 每个到达率必须写出来源、假设和倍率。没有真实数据时允许使用显式估算，但必须标为估算，并在取得线上数据后校准。
3. 校准压测机，确认它能达到目标到达率。
4. 每个写路由使用独立数据库基线。
5. 准备流量和测量流量分窗，并让日志和指标保留阶段标识；不能分窗时明确披露且不得给动作级服务端SLO结论。
6. 同时采集客户端、服务端、数据库、事件循环、队列、CPU和内存。
7. 测量后执行数量、唯一、幂等、状态、关联和跨实例一致性检查。
8. 客户端启动单独测量“导航开始到可操作界面”，不能用API耗时代替JS下载、解析、渲染和交互就绪。
9. 失败与成功原始报告都封存并计算SHA256。
10. 隔离测试服务使用动态端口；就绪检查必须同时验证新进程仍存活、候选提交SHA和环境身份，防止误连旧进程产生假通过。
11. 提交SHA只是版本声明，不能证明运行目录确由当前源码构建。复用构建产物前必须比较包含未提交改动的构建输入指纹；不一致时拒绝测试并重新构建。
12. 明确区分整机/浏览器进程冷启动、新浏览器上下文首开、已有会话页面启动和页面内切换。四类数字不能互相替代，也不能把“新上下文首开”写成“App冷启动”。
13. 准备阶段结束后，性能窗口必须同时清零事件循环分布、路由计数、连接池获取、应用队列和服务时间，并用当前权威数据重新建立体积基线。只清客户端计时或日志标签仍会把造数压力混入服务端结论。
14. 指标重置入口必须受监控凭证保护，仅允许测试或候选环境使用，生产环境稳定拒绝；重置时存在其他在途请求或业务写入则本轮无效。
15. 正式测量后执行样本守恒：实际发起数、成功响应、服务端路由数、写服务样本、数据库增量、审计和副作用数量逐项核对；监控读数必须绕过健康缓存并标注采集时间。
16. 多实例后台调度必须在前台负载同时存在时测试数据库租约、单实例执行、前台队列等待、最大避让期限、租约释放和故障接管；只在空闲环境验证定时任务会漏掉真实竞争。
17. 后台任务必须分开测“无工作空转”和“工作到期”两种成本。无工作时不得周期性复制、序列化或全表扫描大对象；工作到期时必须验证不漏执行、延迟上限、前台请求影响和失败恢复。平均事件循环正常但P99周期性尖峰，通常正是空转定时器、GC或同步序列化信号。
18. 故意制造一次失败和一次取消，确认质量总账分别记录`fail`和`blocked`；跳过项记录`not_run`，失败原始制品仍可下载和校验。
19. 故意模拟制品额度耗尽、上传403或对象存储不可用；执行结果不得被改写，质量总账另记`artifact_missing`并拒绝发布。
20. 对关键写路由采集连接获取、行锁/事务锁、状态读取与克隆、领域逻辑、序列化、权威写入、投影和提交耗时；只有分段证据指向连接获取或数据库写入时才调整连接池或资源规格。
21. 测量结束前重新计算源码、依赖锁、构建参数和测试工具指纹；与启动时不同则保留诊断原始数据，但整轮标记`invalid/source_drift`并拒绝发布。
22. 多实例系统判断“前台空闲”必须使用数据库时间戳、分布式租约或等价共享事实；只看单进程队列会把另一实例的活跃写入误判为空闲。必须同时验证正常空闲、持续高峰、最大避让、强制执行和实例故障五种情况。
23. 分布式租约不能只测“正常释放”。测试必须先证明第二实例在租约存活时不执行，再用数据库管理连接终止租约持有后端或杀死持有进程，验证旧实例失败、连接不回池、新实例在时限内接管。业务任务还需另行验证认领、外部副作用、完成回写三个断点，不丢失且不重复。
24. 必需TC基线不能只保存编号。至少锁定原始优先级，正式发布基线还应保存需求、风险、角色、前置、步骤和预期结果的定义SHA256；修改定义必须走独立评审，禁止通过把P0/P1降成P2/P3或改写预期结果绕过发布门禁。
25. 执行状态统一为`pass/fail/blocked/not_run`，有效性统一为`valid/invalid`，证据状态统一为`available/missing/unverified/not_applicable`。源码漂移、观测不守恒和窗口污染必须标记`invalid`并记录原因；`artifact_missing`只能作为“执行结果已形成但证据状态为missing”的问题分类，不能写进执行状态字段，也不能把真实失败改写成未执行。
26. 时间敏感测试必须分别固定“业务参考时间”和“实际执行时间”。前者生成营业日、班次和账期，后者生成活跃会话、令牌、租约和超时起点；二者业务日不一致时测试启动即失败。浏览器目标控件缺失时先抓取可见业务状态，若页面处于冻结、过期、未开通或待交接等合法保护态，应标记`fixture_state_mismatch`并修正前置数据，不能误报为页面性能超时。
27. 优化响应时间前先列出同步关键路径和异步旁路。鉴权、权限、会话、价格、库存、资金受理、状态迁移、幂等占位和命令持久接收必须同步确认；外部支付退款的最终结果可保持`PENDING`等待权威确认。分析埋点、非关键遥测和可选通知可异步，但必须具备幂等、背压、失败监控、退出排空和必要的重试/死信。
28. 性能修复执行成对实验：原条件稳定复现，按客户端/服务端/数据库/资源分段定位，一次只改变一个主要机制，从同一数据快照按同一负载重跑，并同时比较分位数、错误率、资源指标和业务不变量。
29. 本地脏工作区只形成诊断证据。修复必须提交后由不可变CI验证；绝对容量和P95/P99门禁在固定规格候选环境至少重复3轮并报告轮间方差和最差轮。共享运行器波动不得成为放宽阈值的依据。

负载判定示例：若提交回归使用2次写入/秒，而容量探针使用5次/秒，报告必须同时保留两项。2次/秒通过只证明该回归档位；5次/秒失败仍是容量缺陷，不能通过删除测试、降低样本或把它改称“不真实”来消除。

### E. 缺陷归因

| 分类 | 判断信号 | 处理 |
|---|---|---|
| 产品缺陷 | 请求按模型发出，但状态、权限、数据或SLO错误 | 写最小失败TC，修复业务根因 |
| 测试脚本缺陷 | 身份不具权限、断言与状态机不符、统计错误 | 修脚本并保留原失败，再完整重跑 |
| 测试基础设施问题 | 压测机漏发、采集器失效、误连旧进程或测试网络异常 | 判本轮无效，修复测试设施后按原条件重跑 |
| 测试数据状态错误 | 目标控件缺失且页面明确进入过期、冻结、未开通、待交接等合法保护态 | 保留页面/API证据，标记`fixture_state_mismatch`，修正时间与前置状态后原样重跑；不得关闭产品保护 |
| 可观测性问题 | 客户端成功数与路由、写队列、数据库或审计样本无法守恒 | 标记`invalid_observability`，先用单次和固定批次校准采集链，再按原负载重跑 |
| 被测环境容量问题 | 应用/数据库CPU饱和、连接耗尽、磁盘或内存不足 | 保留为容量失败；只有证明环境不属于目标规格时才另行校准 |
| 外部依赖故障 | 真实DNS、支付、消息或供应商不可用 | 验证超时、降级、查单、补偿、告警和恢复追平；不能直接删除样本 |
| 产品韧性缺陷 | 外部故障导致卡死、重复副作用、数据丢失或无法恢复 | 写故障注入与恢复TC并修复产品根因 |
| 需求/阈值错误 | 规则互相矛盾或阈值没有业务依据 | 回到需求评审，不靠放宽测试解决 |

归因必须用分层指标证明。例如HTTP P95很高，但连接池获取P95接近零、业务写服务时间稳定而串行队列等待持续增长，应判为应用写模型或队列瓶颈，不应盲目扩容数据库连接池。

长时间流程还要先核对时间语义。若任务在测试期间依法从`pending`进入`escalated`，把最终状态固定断言为`pending`属于测试脚本缺陷；正确断言应是“仍处于允许的开放状态，且升级级别、升级事件、责任人和审计一致”。反过来，不能因为允许状态演进而接受已完成、取消、归档或无事件的异常状态。

### F. 修复验证

```text
原失败可稳定复现
-> 最小修复
-> 原TC转绿
-> 同风险域回归
-> 全量门禁
-> 不可变提交CI
-> 候选环境复验
```

任何重试、过滤失败样本、隐藏错误信息或提高阈值，都必须有独立依据，否则视为规避缺陷。

## 4. 两类门禁

**开发门禁**用于合并代码：静态、单元、相关E2E、数据库、性能回归和证据结构必须通过；允许明确记录现场`not_run/blocked`。

**商业发布门禁**用于标签、镜像和切流：所有P0/P1 TC与不变量通过，真实第三方和现场验收完成，迁移、备份、回滚和镜像证据绑定同一提交。任一未完成即`DENY`。

## 5. 测试系统自测

每次引入门禁至少执行以下破坏性样例：

1. 删除一个必需P0 TC，必须拒绝。
2. 伪造不存在的证据引用，平台核验必须拒绝。
3. 将一个P0不变量改成`not_run`，发布门禁必须拒绝。
4. 让压测机漏发或达不到98%目标RPS，性能结论必须无效。
5. 让日志包含损坏行、5xx、连接池超时或投影回退，日志门禁必须拒绝。
6. 让接口返回2xx但不写数据库，最终不变量必须拒绝。
7. 混入另一个提交、依赖锁、迁移集或种子数据，阶段合并必须拒绝。
8. 将员工浏览器报告冒充客户报告，或把准备流量日志混入测量窗口，必须拒绝。
9. 修改源码但复用旧构建目录，构建输入指纹门禁必须在启动被测服务前拒绝。
10. 先用高到达率造数、再用低到达率测量同一服务时，若未重置服务端指标，门禁必须拒绝动作级性能结论。
11. 让测试对象在执行期间越过合法SLA时间点，断言必须识别合法状态演进，同时拒绝缺少状态事件或非法终态。
12. 让后台调度处于“没有到期工作”状态并持续采样；若仍出现全量复制、写入、扫描或周期性事件循环尖峰，性能门禁必须拒绝。
13. 在压测进行中修改一处源码或测试脚本；结束前指纹复核必须把本轮判为无效。
14. 测试本身通过但制品上传失败；执行状态必须保持`pass`，证据状态必须为`missing`并阻断发布。
15. 强制终止分布式租约持有连接；第二实例必须在规定时限内接管，失去连接的实例不得报告成功，也不得将锁状态不明的连接放回连接池。
16. 把一个必需P0改为P2并跳过，或只修改其预期结果；独立基线必须拒绝优先级降级和定义漂移。
17. 让测试本身失败且制品上传同时失败；总账必须同时保留`fail`执行结果和`missing`证据状态，不能折叠成`not_run`。

通用TC发布校验示例：

```bash
node scripts/verify-tc-register.mjs \
  --input tc-register.csv \
  --required-baseline required-tc.txt \
  --expected-commit "$GIT_SHA" \
  --max-evidence-age-days 7 \
  --require-release-pass
```

必需基线格式为`TC_ID|ORIGINAL_PRIORITY|DEFINITION_SHA256`。开发阶段可兼容弱格式，但弱格式无法防止优先级和测试定义被同一改动静默降级；商业发布必须使用完整格式，并把基线交给独立代码所有者保护。

## 6. 最小交付物

- 需求与风险清单。
- TC登记及必需TC基线。
- 状态机和不变量登记。
- 环境与数据集清单。
- 原始功能、浏览器、数据库和性能报告。
- 缺陷清单及修复提交。
- 质量总账、SHA256和发布判定。
- 候选部署、健康、回滚和现场验收证据。

每份证据还必须记录执行身份、完整命令与参数、工具版本、开始/结束时间、原始日志位置、产物签名或摘要、保留期限和访问审计。SHA256只能证明内容未变化，不能单独证明由可信执行者在可信环境生成。

## 7. 发布结论模板

```text
候选提交：<40位SHA>
测试环境：<不可变环境ID>
功能：通过/失败/未执行，原始证据：<引用+摘要>
性能：回归/峰值/容量，模型和样本：<说明>
不变量：通过/失败/未执行
P0/P1未完成：<数量与ID>
第三方与现场：通过/阻塞/未执行
结论：ALLOW / DENY / 仅验证环境
未证明边界：<明确列出>
```

没有原始证据不算测试，没有候选提交绑定不算版本证据，没有真实外部验收不算商业可用。

## 8. 通用自动门禁

仓库提供了不依赖 M-BOX 业务模型的执行器。模板带有`template: true`保护，必须先复制、替换产品名和所有命令，并删除该标记；未适配模板会立即拒绝执行：

```bash
cp docs/templates/software-quality-plan.template.json docs/quality/my-product-quality-plan.json
# 修改产品名、profiles和每个gate的真实命令，并删除template字段
node scripts/run-software-quality-plan.mjs \
  --plan docs/quality/my-product-quality-plan.json \
  --profile release \
  --output artifacts/quality/quality-plan-report.json
```

迁移到其他软件时，复制执行器、测试和计划模板即可。每个命令使用参数数组，执行器不通过 shell 拼接命令；必选门禁失败、超时或命令不存在时均拒绝通过，并保留退出码、耗时和输出尾部。报告同时记录 Git 提交和工作区是否干净，脏工作区报告只能用于诊断，不能作为不可变发布证据。

M-BOX已适配的示例位于`docs/quality/mbox-software-quality-plan-v1.json`，`pull_request`档执行静态、质量模型、单元、集成、安全和浏览器流程；`release`档另加隔离性能套件和商业P0/P1门禁。

## 9. 如何系统地发现问题

不要从“页面能不能点”开始，而要从业务损失倒推：资金错账、重复出品、库存漂移、权限越界、服务漏单、客户等待和高峰不可用。每个风险依次建立：

```text
风险 -> 状态机 -> 不变量 -> 独立事实源 -> 正常/拒绝/重复/并发/恢复TC -> 性能阈值
```

执行时同时观察五条线：用户端反馈、API结果、数据库最终事实、接收岗位状态、日志与资源指标。若五者不一致，即使界面提示“成功”也算缺陷。

定位性能问题时按层拆分，禁止只看一个总耗时：

- 浏览器：导航、资源下载、JS解析、渲染、可操作时间、页面错误。
- 服务端：路由处理、事件循环、队列等待、外部调用。
- 数据库：连接池等待、SQL耗时、锁、扫描行数、连接数。
- 聚合或事务写入：连接获取、revision/行锁、状态读取与克隆、领域逻辑、序列化、权威写入、投影/索引更新和事务提交分别计时；总耗时异常时不得直接归因给数据库或服务器规格。
- 压测器：实际到达率、并发、漏发、错误和本机资源。
- 业务结果：数量、唯一性、幂等、副作用和跨实例一致性。

后台任务与前台请求共用权威写模型时，还要分别记录本实例队列和全实例共享活动信号。单实例显示空闲而数据库行锁等待升高，通常表示其他实例正在写入；此时应修复调度隔离、共享空闲判定或写模型，而不是增加连接池掩盖竞争。

修复后必须先用原失败条件复现转绿，再跑相邻风险域和全量门禁。只降低并发、扩大阈值或加入重试，不算修复。

异步优化还要单独执行四类故障：旁路写入失败、重复调度、队列饱和和进程退出。主业务结果必须保持正确，重复副作用为零，在途任务能够排空或可靠转移，失败必须可查询和告警。任何“前端已完成但服务端没有权威落地”的情况都按产品缺陷处理。

## 10. 浏览器响应时间怎么测

用户感受到的是页面内部从导航开始到关键内容完成绘制的时间，不是测试工具下一次轮询到元素的时间。自动化应在页面最早阶段注入观察器，并记录：

1. 导航开始。
2. 必需API成功返回。
3. 关键内容进入DOM。
4. 关键内容连续两帧绘制完成。
5. 首个关键按钮可执行。
6. 绘制完成后保留短暂诊断观察窗，捕获懒加载资源、页面异常和紧随首屏发起的API失败；观察窗不计入用户可见绘制耗时。

Playwright、Selenium等工具在进程外轮询元素产生的额外等待只能作为测试框架诊断值，不能冒充用户可见延迟。报告必须同时保留页面内时钟、API时钟、DOM时钟和测试工具观察值；若差异显著，先检查测量方法，再判断应用性能。

## 11. 数据增长和稳定性怎么测

正常订单、任务、审计和库存流水会增加数据，不能把“比空库增长很多倍”直接判成泄漏。通用门禁应同时使用：

- 绝对上限：活跃数据或单个聚合对象不得超过容量预算。
- 单次业务写入斜率：净增长字节除以集群成功写入数，超过阈值且已经达到显著体量才阻断。
- 多业务周期趋势：连续3至7个代表性业务日后，活跃状态应因归档、分区或保留策略保持有界。
- 查询退化：不同数据规模下重复执行相同路由，确认P95/P99、扫描行数和锁等待没有非预期恶化。

增长倍率只做趋势预警。若绝对体量或单次写入斜率异常，即使接口仍快也要阻断；若当前快但多周期持续无界增长，则登记为结构性容量缺陷，不能用扩容掩盖。

## 12. 迁移到其他软件的执行清单

1. 识别资金、安全、权限、关键业务结果和用户体验五类损失。
2. 为每类损失建立状态机、不变量和独立事实源。
3. 编写正常、拒绝、重复、并发、故障、恢复和跨周期TC，并固定P0/P1基线。
4. 准备确定性种子、环境指纹、构建输入指纹和可重复负载模型。
5. 先跑单路由基准，再跑混合峰值、容量阶梯和稳定性；每阶段恢复同一数据基线。
6. 用页面、API、数据库、接收方、审计、日志和资源指标交叉验证结果。
7. 故意破坏幂等、权限、证据、数据写入和负载发起率，证明测试系统本身能拒绝假通过。
8. 修复后复跑原失败条件、相邻风险域、全量回归和发布门禁。
9. 把报告绑定到提交、构建摘要、环境和数据集；脏工作区结果只作诊断。
10. 生产发布前补真实设备、网络、第三方、备份恢复和人工岗位验收，任何P0/P1未完成均保持`DENY`。

## 13. 真实设备矩阵

每个项目按支持范围登记，不允许只写“手机已测”：

| 维度 | 至少覆盖 |
|---|---|
| 系统与容器 | 主流与最低支持OS、浏览器、WebView、App/小程序容器 |
| 生命周期 | 安装、首次启动、升级、后台恢复、强杀重启、降级或拒绝降级 |
| 视口与输入 | 最小/最大屏幕、横竖屏、字号放大、触控面积、键盘遮挡、无障碍 |
| 网络与资源 | 弱网、切网、断网、低电量、低存储、系统时间偏差 |
| 外设 | 打印、扫码、摄像头、NFC、推送、耳机；含断电、缺纸和权限拒绝 |

## 14. 外部依赖矩阵

对每个支付、消息、地图、模型或硬件服务记录：生产/沙箱差异、API版本、密钥与权限、限额限流、超时、重复/乱序回调、签名与防重放、主动查单、对账、补偿、人工接管、停机恢复后的数据追平。真实验收证据要包含依赖名称、交易或动作类型、脱敏业务ID、样本量、金额范围、供应商流水和明确预期。

数据库迁移不能只在空库和超级用户下测试。至少保留“上一正式版本快照 -> 当前迁移”的非超级表所有者用例，并覆盖强制RLS、已有历史数据、新旧应用并存、候选写入后回滚旧应用、失败回滚和约束/触发器恢复。历史正文已不可恢复时必须使用明确的`unknown-legacy`，不得凭摘要猜测算法、来源或业务含义。

## 15. 发布后控制

商业发布计划必须写明灰度比例、观察时长、业务与技术基线、自动停止/回滚阈值、负责人、最大恢复时间、发布后数据核对、迁移核对和第三方对账。P0不得豁免；P1风险接受必须有批准人、有效期、补偿措施和复验期限。

## 16. 追溯与统计

建立双向链路：`需求/风险 -> TC -> 自动化/人工执行 -> 原始证据 -> 缺陷 -> 修复提交 -> 发布物`，并反查每次代码、配置、模型或基础设施变更影响哪些需求和TC。商业发布的必需TC基线必须同时锁定ID、原始优先级、测试定义摘要和自动化等级，禁止把自动门禁静默改成人工结果。性能协议另行固定开放/闭环模型、预热、持续时间、轮次、方差、缓存状态、数据倾斜、热点对象、GC/JIT、地域网络、扩缩容和恢复时间；单路由隔离基线用于定位，真实混合峰值必须保留共享资源争用，两者不得互换。
