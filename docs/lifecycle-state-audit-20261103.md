## 已复现的问题与业务边界

| 编号 | 触发条件 | 已验证结果 | 修复 |
|---|---|---|---|
| RELEASE-LIFECYCLE-20261103-01 | 已暂停/退役区域或桌台，应用新的门店配置版本 | 原 SQL 无条件把区域设为 active、桌台设为 available；4 种状态回归在基线上失败 | 冲突更新保留既有状态；新建资源仍采用数据库默认状态 |

门店配置模型没有区域、桌台、角色和权限定义的状态字段，因此上述恢复不是操作者明确提交的配置变化。修复没有阻止配置中明确的名称、容量等字段更新，也没有改变角色权限默认配置与运行时管理权记录的协调规则。需要重新启用时应走明确的管理操作；不会通过升级版本隐式启用。

目录配置则明确包含 `enabled`/`soldOut`：不能把所有状态更新一律视为缺陷。本轮未改变该业务语义，未增加迁移或修改发布配置文件。

## 回归方法和证据

新增 `server/normalized/provision-lifecycle.integration.test.ts`，使用一次性本地 PostgreSQL 数据库、随机租户/门店和合成账号。初始化通过真实 `provisionNormalizedRelease`，权限检查使用真实受限 LOGIN、RLS 事务和真实权限仓储。没有调用生产环境。

6 个场景分别检查区域 paused/retired、桌台 paused/retired、角色 inactive、权限定义 inactive：

- 先证明原始权限可用，再停用，并证明角色/权限定义停用后确实拒绝访问。
- 应用新版本，原状态必须保留，撤销的权限必须仍被拒绝。
- 同时添加新区域、桌台、角色、自定义权限，验证默认初始化仍生效；显式门店名称变更仍生效。
- 对员工及员工角色做全行快照，验证未重写；同时监测口令、订单、桌次、桌码表未新增（本测试这些表为空，不把空表比较说成真实营业数据验收）。
- 同版本、同来源提交并发重试仍保留状态和保护表。

## 继续检查的可比路径

| 路径 | 本轮检查结果与限制 |
|---|---|
| 相同版本门店/目录回执 | 内容哈希冲突拒绝，已有回执只追加来源，不重新覆盖配置；既有集成回归一并运行 |
| 账号/PIN/员工角色/门店口令 | 已有账号插入冲突后保留，存在口令历史时不重建；既有 same/new-version 保留回归一并运行 |
| 角色权限、范围、审批、导航默认值 | 核对 `role_access_configuration_authorities`：运行时接管的项跳过默认值覆盖；本轮修复独立的角色/定义状态 |
| 目录启停与售罄 | 新版本来自显式配置字段，相同版本回执不回写；不擅自改变发布新目录的语义 |
| 桌码生成 | 已有有效桌码需明确轮换，退役桌台被排除；不自动换现场码 |
| 原生桌台配置回执 | `nativeGuardedExecutor` 在认领/读回执前检查当前权限；首次执行另查配置版本及营业中桌次，不把历史操作重新执行 |
| 预订创建/入座 | 请求和回执路径有当前权限检查；已有原键撤权和桌台范围回归，纳入全数据库测试 |
| 会员配置 API | 路由执行前检查当前对应权限；本轮为静态检查，未据此声称所有并发撤权交错已经穷举 |
| 旧运行态初始化 | `provision-runtime.ts` 使用插入冲突保留并拒绝覆盖已有运行态，不构成同样的强制恢复状态路径 |

这是有边界的跨路径审计，不是所有功能、所有并发交错或现场真实营业的无缺陷证明。部分拆并桌规则 RULE-AUDIT-20261102-02 仍待业务明确，本轮不改。
