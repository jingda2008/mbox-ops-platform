# M-BOX 员工后台与未来 App：界面、术语和操作流程梳理

日期：2026-09-20。范围：全部员工后台，未来供店内员工使用、管理者兼用。

后续实际操作审计已完成，见 [员工操作缺陷与证据](staff-operator-audit-20260920.md)。其中的资金、存酒及记录提交缺陷应先于界面改版处理；下文静态证据范围保留。

## 1. 结论与证据边界

建议把现有后台重组为“按岗位进入、围绕业务对象连续办理、按状态给出下一步”的员工工作台。现在最值得改的，不只是措辞，还包括导航层级、长页面的功能混放、重复摘要，以及异常状态的表达。

不建议以“做成 App”为理由先全面重写。当前已有按权限显示、桌台直接收款、扫码入库、盘点批量审核、部分信息折叠和操作恢复能力，应保留并统一。App 包装本身不能解决流程绕路，且会增加设备、版本、登录恢复、扫码和打印适配成本。

本次结论分为三种：

- **代码已核实**：从远端 main 拉取并建立独立只读审阅基线，SHA `887461043e521463f73b9bd17efa381e4eeea6ad`，package 版本 `1.0.0-rc.214`。员工模块定义共有 **20 个入口，其中 8 个会员相关入口**。这不是每位员工实际看到的菜单数，实际显示仍由权限及门店配置决定。
- **设计判断**：下面的导航、文案和交互调整是依据代码结构提出的方案，尚未经过门店对照实验；不能据此声称已提高某个百分比的效率。
- **待现场验证**：未登录生产后台逐页操作，未测量当前任务耗时、误操作率、各岗位真实高频顺序，也未核验本次基线是否已经部署。真实岗位权限、手机体验、付款及打印结果不能由源码代替。

辅助扫描覆盖 `src/normalized-ui` 的 88 个员工相关 TS/TSX 文件，排除测试、顾客、会员门户、预约顾客端及小程序预览。抽取 7,265 条中文文本候选，其中关键词匹配 95 条；**候选数不是已确认问题数**，包含程序提示、动态片段和开发校验文本。完整索引保存于 `/Users/jingda/mbox/outputs/staff-ux-audit-20260920/source-copy-index.json`。服务端动态文案和实际门店配置仍需后续运行验收。

## 2. 已确认的主要问题

| 编号 | 已核实的现状 | 对使用的影响：设计判断 | 建议 |
|---|---|---|---|
| UX-01 | 设置页含“规范化数据库”“版本校验、幂等键”；演出页解释避免“整块 JSON 覆盖” [E01] | 员工需要理解系统实现，才能判断自己该做什么 | 从业务页面移除开发解释；保留必要的操作影响及管理员诊断入口 |
| UX-02 | 20 个模块定义中，会员被拆为待办、异常、等级、草稿、审批、发布、查询及其他配置 [E02] | 导航围绕系统模块与权限拆分，用户需记住同一事情分布在哪里 | 会员做一个业务入口；查询、办理、规则分层；审批仍严格分权 |
| UX-03 | 手机底部直接取 `entries.slice(0, 4)` 再加“全部” [E03] | 前四项受排序与权限影响，不一定是当前岗位的高频操作 | 明确岗位导航模板，稳定顺序；不因待办数量改变标签位置 |
| UX-04 | 工作台有 bootstrap 数据时始终渲染“连接正常”，同时可展示刷新失败 [E04] | 旧数据可能与正常连接标识并存，影响员工判断 | 分别显示正常、更新延迟、离线及最后成功更新时间；不能只根据曾经读到数据判断在线 |
| UX-05 | 工作台有高频入口、营业状态摘要、下一步待办；后两者均可由同一领域摘要生成 [E04] | 重复的信息占用首屏，但仍需点进模块找具体对象 | 首页只保留常用动作和具体待办；摘要作为筛选或管理者概览 |
| UX-06 | 桌台弹层并列收款、观察、推荐、点单、赠送、转桌、拆并桌、锁购物车、结台、翻台等操作，按权限显示 [E05] | 高频服务动作和低频管理动作争抢注意力 | 保留当前状态最重要动作，其余进入“更多”；收款继续保留桌卡快捷入口 |
| UX-07 | 库存页同时挂接收货发布指引、存酒、盘点审核、物料维护、入库、损耗及商品配置 [E06] | 日常库管、商品维护和顾客存酒混在同一工作空间 | 库存分收货/盘点/损耗；商品配方单独工作区；存酒从会员及桌台办理入口进入同一详情 |
| UX-08 | “其他会员经营配置”连续挂接存酒、群发、弹窗、专属卡、营销、规则、兑换及账户恢复等组件 [E07] | 页面内容随权限膨胀，岗位切换与功能定位困难 | 按会员办理、活动营销、规则设置分组，按需加载 |
| UX-09 | 会员配置用 `Object.entries` 递归生成字段；存在“倍率分子/分母”“商品 ID”“需要桌台会话”等字段 [E08] | 存储结构被当成操作表单；仅翻译字段名不够 | 按业务句式重做表单、单位换算和选择器，并增加真实案例预览 |
| UX-10 | 收银界面存在“权威事实”“日结阻断事实”“受控重收”等表达 [E09] | 异常发生时，还需解释系统语言 | 显示具体对象、影响、当前状态、处理人和下一步；技术信息折叠 |
| UX-11 | 会员兑换等页面有直接展示 `fulfillmentKind`、控制状态代码的分支 [E10] | 可能出现内部英文值或无法理解的状态 | 所有前台枚举统一映射；未知值显示“状态待确认”并保留原值供诊断 |
| UX-12 | 已有两类以上存酒入口；会员待办同时出现在服务任务及专门会员页 [E07/E11] | 多入口有便利性，但可能产生重复认知、重复提醒 | 保留场景快捷入口，共用唯一详情与任务标识；聚合待办按对象去重 |

这不是“所有系统词都应该删除”。“待付款、款项确认中、退款处理中、库存不足、需要他人审核、已保存未生效、利润暂估”等是操作判断依据，必须保留并讲清楚。

## 3. 信息展示：每一层回答不同问题

| 层级 | 回答的问题 | 默认展示 | 展开后展示 |
|---|---|---|---|
| 列表/桌卡 | 哪一件需要我处理？ | 桌号或单号、业务名称、金额或数量、明确状态、必要等待时间、主动作 | 不堆内部编号、版本、长解释 |
| 业务详情 | 怎么办，做完会怎样？ | 本次对象、待办原因、当前结果、下一步、影响金额/数量、必要确认 | 相关订单、经办员工、时间、备注、凭证 |
| 处理记录 | 之前发生了什么？ | 按时间排列的申请、审批、收款、退款、出品及交接记录 | 历史版本和更正记录 |
| 管理配置 | 哪条规则决定这个结果？ | 业务规则、适用对象、生效时间、修改前后、审批要求 | 成本影响、预算、容量、变更历史 |
| 故障诊断 | 技术人员怎样定位？ | 经授权打开的诊断编号、刷新时间、错误码 | 关联请求、外部流水、内部标识；敏感信息仍受权限限制 |

具体原则：

1. **标题用业务名，按钮用动词和对象。** “出品履约”改为“制作与送达”；“生成服务端影响预览”改为“查看修改影响”；成功反馈写“已提交退款申请”，不能统称“操作成功”。
2. **解释出现在需要判断的地方。** 例如“原款未确认，再次收款可能多收”放在再次收款前；不要整页常驻开发原理或历史修复说明。
3. **页面至少区分加载、无记录、无权限、失败、显示旧数据。** 不把读取失败表现为“没有待办”，不把缺成本显示为 0。
4. **保留诊断能力。** 技术细节从首屏移到详情，不删除日志、审计、业务凭证或必要的业务编号。
5. **筛选、滚动和输入连续。** 返回列表保持原筛选与位置；切桌、切员工后不能沿用上一人的敏感数据；自动刷新不覆盖正在填写的内容。
6. **低频功能仍可发现。** 进入“更多”的内容须有业务名称、分组和搜索别名；不能把复杂度简单扔进一个无序长列表。

这符合渐进披露的基本做法：先提供完成主要任务所需的内容，把低频与高级选项放在下一层。参考 [NN/g：Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)。隐藏信息的前提是不会改变用户的业务判断。

## 4. 建议的导航与岗位首页

电脑和平板可采用“列表 + 同屏详情”，保留搜索、键盘操作及必要的批量处理。手机使用“列表 → 详情 → 单一步骤”，适配底部操作区与系统返回，不将宽表格整体缩成小字。

电脑的一级入口建议收敛为：**工作台、现场、收银、商品库存、会员活动、经营管理、设置**。二级入口保持可搜索，旧地址保留跳转能力。

| 岗位工作模式 | 首页核心内容 | 手机建议固定入口（全部仍按权限过滤） | 常用内容 |
|---|---|---|---|
| 服务员 | 我负责的桌台、待服务、待送达 | 工作台 / 桌台 / 待办 / 会员 / 我的 | 开台、加单、送达、会员核销、存取酒 |
| 吧台/后厨 | 本工位待制作、制作中、待取走 | 工作台 / 制作 / 待取 / 记录 / 我的 | 开始制作、分批完成、缺料处理 |
| 收银 | 待收款、款项确认中、退款待办、交班 | 工作台 / 收银 / 订单 / 待办 / 我的 | 收款、团购核销、退款、补打、交班 |
| 库管 | 待收货、盘点、库存提醒 | 工作台 / 库存 / 收货 / 盘点 / 我的 | 扫码收货、实盘、损耗、条码维护 |
| 店长 | 需要决策的异常、审批、现场概况 | 工作台 / 现场 / 审批 / 经营 / 我的 | 责任桌安排、异常处理、审核、经营查看 |
| 老板/财务 | 经营趋势、资金、成本缺口 | 工作台 / 经营 / 审批 / 订单 / 我的 | 经营分析、费用工资、资金核对 |

以上是待实操验证的导航模板，不等于新增权限。兼任人员可选择已授权的工作模式；模式变化只调整入口和信息密度，服务端继续验证每一次操作权限。没有会员权限的服务员模板可退化为四项或配置另一常用业务，不能展示越权入口。

“我的”放个人身份、当前门店/班次、工作模式、全部功能、帮助、设备状态及退出；拥有管理权限的人能从这里进入设置。扫码是具体页面的动作，例如“扫会员码”“扫码收货”，不以不明用途的扫描按钮代替导航。

任务聚合不是一张混合长表：按“我现在能处理 / 等待他人 / 已完成”分区，再按岗位、责任范围、紧迫程度、等待时间排序。待办带桌号、业务名、负责人及深链接；同一对象出现多个入口时去重，审批人与业务办理人的权限继续独立。

## 6. 跨模块高频流程怎样收短

### 桌台服务与结账

目标路径：桌台列表 → 本桌详情 → 当前动作 → 就地显示结果。桌号、当前桌次、订单、会员关联由系统带入，避免重新搜索；返回仍停留原桌台位置。

- 空桌：主动作“开台”；填写人数等必要信息。
- 已开桌：按岗位优先显示“加单”“收款”或“查看待送商品”；“推荐、转桌、拆并桌、锁购物车”进入明确的更多分组。
- 待收款：首屏给应收、已收、待收，以及未确认款项；默认保留当前全桌合付能力，部分付款再展开。
- 顾客离店：独立表达“释放桌台”和“财务已结清”；有后续财务事项时明确交接给谁。不能用“已结束”同时代表两件事。
- 退款后继续收款及原支付未知时再次收款，沿用现有授权和业务规则；界面提示未确认原款及潜在多收，不擅自改成全局禁收。

### 制作、传菜与售后

制作卡首层仅显示桌号、商品、份数、必要备注、等待时间及下一动作。制作人员操作“开始制作 / 完成所选份数”，传菜人员操作“取走 / 已送达”。已完成记录保留在“记录”，不要把所有历史卡持续堆在当前队列。

商品处理从原商品进入，选择“停止制作、重新制作、补送原商品、换商品”等业务意图，再显示相应字段；退款是否需要、退多少、材料怎么处理由已有业务规则确定并明确预览。不要让员工先选择内部案件类型，也不能把“重做”当作无成本补送。

### 收款、退款、团购与交班

收银首页按照“待收款、待审核退款、退款处理中、待交班事项”分区，订单详情共用。不能用同一个“待处理”隐藏不同权限和处理时机。

退款详情顺序：原订单/商品 → 本次原因和金额 → 预计退回方式 → 当前审批人/处理结果。获批后显示“待退款”或“退款处理中”，到账后才显示“已退款”。

团购核销：选择/识别平台 → 扫码或输入 → 展示券名、可用数量、有效期及适用信息 → 明确确认核销 → 显示平台确认结果。查询券信息不能顺便消耗券；四平台代码存在不代表已完成真实平台验收 [E17]。

交班：列出未完成事项、金额、对象和接手岗位；逐项直达原业务，处理后回到交班清单。**交班（员工交接）与日结（营业日关闭）是两件事，必须分别呈现，不能因同一入口而合并状态。** 日结显示所属营业日、实际营业时间和未完成事项，跨午夜不自动归为新营业日。通过页面入口重组减少跳转，不减少财务复核。

### 库存、商品与存酒

- 常规收货：扫已绑定条码 → 输入本次包装数及必要成本信息 → 核对换算数量 → 确认入库。新物料建档、条码绑定只在首次需要时出现。
- 新酒上架：建档/选物料 → 销售规格与配方 → 售价及可售检查 → 预览并发布。保留已存在的入库和发布联动，清晰显示“已入库、未上架”等组合结果；不同权限的人可接续办理。
- 盘点：按区域/物料连续录入实盘 → 提交 → 他人复核；库存发生变化时退回重盘，不能靠隐藏警告或批量通过缩短步骤 [E12]。
- 存酒：查会员/扫码 → 选存酒 → 展示酒名、剩余量、位置、照片 → 原有验证码核验 → 确认实际取走。再存/归档在取走结果后衔接；已授权存酒详情保留业务所需完整手机号，不泛化到无关列表 [E11]。

### 会员规则、活动与内容发布

规则编辑使用“每消费 [金额] 元，获得 [积分] 积分”，并显示示例消费结果；金额统一用元展示，内部仍转换为分。倍数、精度、取整方式保留真实语义，不能在改文案时变更算法。

同一规则详情呈现“草稿 → 待审核 → 已审核待发布 → 已生效”。各角色只看到自己可执行的动作；审批查看变更对照、影响人数、预计积分/成本、库存缺口和有效时间。导航可以合并，权限和独立复核不能合并 [E08]。

活动办理聚焦名单、付款、签到、交付；活动策划和规则编辑另页。顾客内容按“草稿、待发布、已发布、已撤下”管理，提供顾客视角预览。群发必须保留受众、渠道、时间、预算/配额及最终确认，不能自动把保存草稿变成发送。

## 7. 关键状态表达规范

| 业务事实 | 列表文案 | 主动作或下一步 | 不能简化成 |
|---|---|---|---|
| 请求已提交，付款结果未知 | 款项确认中 | 查看付款进度；按现有权限可选择再次收款并提示原款风险 | 已收款 / 支付失败 |
| 现金经员工确认实收并登记成功 | 现金已登记 | 查看凭证 | 仅点击按钮就显示已入账 |
| 退款申请已提交，未审批 | 待审核退款 | 审核人处理；申请人查看进度 | 退款成功 |
| 已批准但渠道尚未确认退款 | 退款处理中/待执行退款，按实际状态 | 查看进度或有权人员继续执行 | 已退款 |
| 员工确认制作完成，尚未送达 | 待取/待送达，按实际状态 | 取走 / 确认送达 | 已完成订单 |
| 翻台已释放但仍有未结款项 | 桌台已释放 · 账单待处理 | 财务接续处理 | 全部结清 |
| 实物已收，商品未发布 | 已入库 · 未上架 | 有权人员完成上架 | 顾客已可购买 |
| 盘点提交后库存发生变化 | 库存已变动，需重新盘点 | 退回重盘 | 可直接通过 |
| 规则保存成功但未发布 | 草稿已保存，尚未生效 | 查看影响/提交审核 | 配置成功且已生效 |
| 券已核销但实物尚未交付 | 已核销 · 待领取/制作 | 交付流程 | 已交付 |
| 打印结果未知 | 尚未确认出纸 | 检查打印机及原任务 | 打印失败后直接生成新票 |
| 数据读取失败但有旧数据 | 更新延迟 · 上次更新于… | 重试；执行前重新校验状态 | 连接正常 / 没有待办 |
| 缺少采购成本 | 利润暂估 · 缺少成本 | 补齐成本资料 | 利润已完整核对或成本为零 |

错误提示采用“发生什么 + 当前结果是否确定 + 能做什么”。例如：“退款申请是否提交成功尚未确认，请先查看处理进度。”技术错误码放到可复制的诊断详情；服务端错误消息也应进入统一的业务错误映射，不能只清理静态页面文字。

## 8. App 适配与技术边界

当前仓库存在 Capacitor/iOS 配置及 Android 验证构建脚本。`capacitor.config.ts` 默认仍指向验证域名，且使用远程页面、调试日志；这只证明有验证基础，不能据此声称已有可发布的正式 App [E18]。

建议实施顺序：

1. **共用业务展示规则**：先统一业务状态、文案、单位、金额、错误提示和能力判断。前端的显示状态由真实业务状态映射，不修改数据库状态机来适应界面。
2. **统一业务详情与岗位导航**：桌台、订单、会员、商品、待办各有一个可直达的详情。保留旧路径兼容，所有入口带上对象上下文；服务端仍验证权限与最新状态。
3. **移动工作流程**：短步骤、单手可达按钮、系统返回、键盘不遮挡、相机扫码、扫码枪与手输备选。仅对复杂输入使用完整页面，避免连续叠加多个弹层。
4. **设备验证后选择 App 实现**：先验证扫码、推送、切后台恢复、共享设备换人、打印与网络恢复。若现有 Web/Capacitor 满足高频任务，可继续复用；若硬件与后台任务要求超出能力，再确定哪些部分需要原生实现。现阶段直接承诺全面原生重写没有依据。

移动端建议采用约 44–48 CSS px 的主要点击区域、可随系统放大的文字、清晰的文字状态和图标，品牌绿 `#315d46` 用于主要动作与选中态。不能只靠红绿区分业务结果。44–48 是本项目的操作设计建议；WCAG 2.2 AA 的目标尺寸最低要求是 24×24 CSS px，且存在间距等例外，两者不要混淆。参考 [W3C 目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。原生端按对应平台单位和规范单独验证。

弱网与离线必须按业务区分：可以查看带时间标识的缓存、保留经过设计的输入草稿；不能离线宣称收款、退款、出品扣料或盘点已成功。应用回到前台先核对旧请求结果，不能为恢复显示自动创建一笔新交易。当前源码主动移除旧 Service Worker，故“已有可靠离线模式”也不能成立 [E18]。

推送只通知与当前人员相关且可行动的事项，按对象去重；通知点击直达原业务，重新核验身份和权限。锁屏消息避免暴露完整手机号、会员信息、工资或财务详情。通知能力、背景恢复及打印均需真机验证。

## 10. 如何证明操作真的更简单

先在现有版本建立同岗位、同任务、同设备和相近网络条件下的基线，再比较候选界面。低点击数只是一项指标，不能奖励跳过核对、审批或实物交接的设计。

建议首轮验收任务集：

| 岗位 | 必须覆盖的任务 |
|---|---|
| 服务/接待 | 开台、加单、会员核销、送达、预约到店、转桌、顾客离店但仍有账务事项 |
| 出品 | 普通制作、分批完成、缺料、重做、取送交接、查询本人记录 |
| 收银 | 全桌合付、部分收款、现金、原款确认中再次收款、退款申请/审核/执行、团购核销、补打、交班 |
| 库管 | 已绑定/未绑定条码收货、包装与毫升换算、盘点提交、本人不可自审、库存变化后重盘、损耗 |
| 会员/营销 | 查会员、权益领取、无法交付、规则草稿/审批/发布、活动签到、内容预览发布、群发最终确认 |
| 店长/老板 | 责任桌安排、异常决策、经营暂估、费用工资、权限变更、打印故障处理 |

建议的首轮门槛（设计目标，尚未测得）：

- 从本岗位首页到主要任务入口通常不超过 2 次导航；不计填写内容、真实扫码及必要业务确认。
- 同一桌、单、会员不重复手工输入已经确定的身份信息；允许在需要重新核验身份时要求扫码或验证码。
- 验收场景中不出现“未收款显示已收”“退款申请显示已退”“读取失败显示无待办”“草稿显示已生效”等错误。
- 主要任务需在窄屏、系统大字、键盘弹出、弱网、恢复网络及切换员工后完成；资金、库存、积分、通知和打印不因重复提交而重复执行。
- 实操计时报告中分别列中位耗时、较慢任务、错误与求助次数；样本小时报告原始结果，不宣称统计显著。是否降低 20% 等目标应在取得真实基线后确定。
- 审批、自审限制、成本权限、联系人可见性、历史营业日及原打印凭证的检查独立列示。

## 11. 需要提前考虑的成本与偏差

1. **老板界面不代表员工界面。** 管理员看到的功能最多，不能据此认定所有员工都看到同样的长页面；应按真实岗位各走一遍。
2. **前端简化不自动降低服务端复杂度。** 统一待办需要处理不同来源、负责人、状态和去重；共用详情需要处理深链接、并发与旧状态，不能只换菜单文字。
3. **共享设备与个人手机不同。** 需确定收银机、吧台屏、员工私人手机的登录与换人方式，避免个人数据残留；具体设备名单待现场盘点。
4. **低光、噪声、湿手和忙时注意力。** 少依赖颜色、长文字和纯声音提示；触控、键盘、扫码枪均要可用。
5. **学习成本。** 新旧词建立搜索别名和短期引导，保留原链接；不要一次把所有岗位入口重新排序却没有对照表。
6. **App 独有成本。** 安装分发、签名、升级兼容、权限授权、推送、崩溃诊断与设备支持，均需要长期维护；当前无法仅凭代码给出可信工期或总价。
7. **适度保留专业业务词。** 盘点、核销、对账、营业日等已有行业语义，可以使用简短解释；把所有词换成口语可能反而损失准确性。
