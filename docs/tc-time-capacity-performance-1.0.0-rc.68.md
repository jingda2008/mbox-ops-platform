## 扩容门槛

最新不可变CI `31342339033`中代码质量、数据库、员工浏览器和业务功能请求通过，但客户浏览器P95、心跳P95、KDS写服务、队列长尾、事件循环和制品上传仍失败。同一旧提交在本地复测明显更快，说明共享运行器不适合作为绝对容量依据，但不改变CI回归失败。连接池获取持续远低于50ms，因此当前没有“增加数据库连接数即可解决”的证据。只有在同一不可变镜像部署后，阿里云峰值连续15分钟出现以下任一情况，才批准运行期扩容：

- ECS CPU持续超过70%，事件循环P95超过75ms或P99超过100ms；P95超过50ms先告警并分析阻塞来源。
- 可用内存低于20%，发生OOM或容器重启。
- 数据库连接获取P95超过50ms、等待队列持续大于0，或连接使用率超过70%。
- 核心读取P95超过500ms、核心写入P95超过800ms，且错误率超过1%。
- 部署双容器并存时资源不足，影响现网请求。

扩容不能替代慢SQL、过大bootstrap、同步分析写入、连接池往返或聚合JSON写入修复。

部署容量与营业容量必须分开判断：`CAP-006`已证明双容器部署有资源压力，即使日常请求尚未证明需要扩容，也应采用单候选容器、远程镜像分层缓存或临时升配完成部署。若当前ECS低于2核4GB，验证环境不应继续降低；商业上线建议4核8GB作为蓝绿切流和300人峰值的起始容量，最终仍以`CAP-005`线上15分钟窗口决定。
