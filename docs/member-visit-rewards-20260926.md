## 用户确认与实现映射

| 确认要求 | 实现 |
|---|---|
| 无需消费，签到即可 | 仅员工确认的会员到店签到计次，每营业日一次，沿用早上6点换日；不依赖报名或订单 |
| 次数可配置 | 1–365次，默认3；启用后冻结，保留历史。新规则从启用时开始，不补计之前的签到 |
| 商品可配置 | 绑定已审核、发布的免费商品券活动，沿用商品池、每轮份数、目标人群、可用时间、数量及成本预算。组合甜点的每人限一套规则不兼容循环奖励，不能绑定 |
| 每累计3次可再领一次 | 每完整一轮建立一条申请，3、6、9次分别对应一轮；余数继续累计 |
| 发放前管理审批 | 达标时只保存申请和来源签到，不生成可被后台自动执行的发券任务 |
| 每日批量/单独 | 按达标营业日筛选、分页读取；提交明确选中的1–50条ID，单条和批量共用审批边界 |
| 发放结果可核对 | 审批、发券回执、预算和审计同事务；任何一条失败整批回滚，全部仍待审批。列表区分待审批、已发券、已驳回、原签到撤回作废；已发券显示券状态和已核销份数 |

## 员工与管理操作

1. 员工在任务页扫码会员，选择“仅到店签到”，看到每轮次数、距下一轮次数、待审批与已发轮数。选择具体活动仍走原报名/付款/活动签到。
2. 会员管理 → 会员经营配置中心 → 入卡礼与定向发券：先建立并审核发布免费商品券活动，配置商品、有效期及预算。读取活动后，在“累计签到奖励”绑定活动并设置签到次数。
3. 管理人员读取待审批奖励，可按达标营业日筛选。查看会员号、每轮签到日期、赠品和份数，填写原因，单独批准或选择最多50条批量批准。
4. 审批成功后权益进入原会员券包，领取实物仍走现有免费商品券核销链，不直接生成营业收入或扣库存，也不代表消息通知已送达。

## 一致性与权限

- 查询：`loyalty.configuration.view`。配置/停用：`loyalty.policy.publish`（老板）。审批/驳回：`loyalty.configuration.approve`（运营负责人）。店长继续按原权限起草赠品活动，原活动独立审核、发布仍保留；不得要求同一员工兼有三个岗位权限。原员工到店签到权限保持，取餐角色不增加权限。
- API严格字段校验；服务器确定操作者和营业日；命令幂等并在回放前/事务内重新检查权限；禁止前端传入客户/员工身份替代真实身份。
- 规则与赠品版本冻结；同活动编号不能通过重建规则重置次数，停用后仍保留。活动到期/停发、成本未知、预算不足或资格变化均不能绕过发放检查。待审批必须在赠券活动仍有效时处理。
- 合并身份共享客户锁并按营业日去重；已发/已驳回轮次的原日期永久消耗，撤回后当天重签也不会再次领奖。合并前生成的重复待审批在发放前再次校验，冲突必须由管理核对并驳回。
- 未审批的签到撤回：原申请作废，其他有效日期重新累计。已发券的签到撤回：保留已发权益，在管理列表标记异常；不自动作废已核销或订单占用中的券，不伪造退货/库存冲回。管理人员需核对该例外，原日期不再计次。
- 驳回是该轮终态，填写原因，不自动反复申请；后续新签到继续累计。停用规则阻止新申请和待审批发放，已发券仍按原条件使用。
- 数据库强制门店RLS、同域外键、来源记录不可改写、规则仅可停用、审批仅可由待审批进入终态，已发状态必须对应本轮真实发券回执。
