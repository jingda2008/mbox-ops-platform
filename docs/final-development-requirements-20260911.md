## 3. 站在使用者和经营者角度的统一规则

### 3.1 高频操作和低频核对

员工首页只突出当班需要做的动作：收未收款、制作、配送、处理真实投诉/退款。旧支付未知、打印历史和渠道核对进入相应详情/财务/设备页；它们有追溯入口，但不长期夺取首页注意力。顾客当前桌号、订单和需要支付的金额最清晰，不能让内部异常名词占菜单首屏。

默认路径目标（拟定验收指标）：从对应岗位首页到收款/制作/送达主动作至多一次页面进入；付款方式直接可选，无旧支付释放步骤；岗位历史一次切换即可查看。风险操作保留必要确认，但不重复要求确认已具备的授权。不用逐帧操作次数承诺替代财务核验。

### 3.2 将四类状态分开

| 状态维度 | 回答的问题 | 不允许的替代判断 |
|---|---|---|
| 账单收款状态 | 还应收多少、是否结清、多收多少 | 不能只凭某笔pending判账单未结 |
| 单次支付状态 | 这一次渠道动作有没有确认到账 | 不决定员工是否可对真实待收款再次操作 |
| 商品履约状态 | 未做、制作中、待送达、已送达或取消 | 退款/关桌不能伪造制作送达 |
| 财务核对状态 | 谁核对、最后证据、下一步和是否关闭 | 退出营业待办不等于终态确认或删除历史 |

收款资格取权威剩余应收与原权限，取消且无需收费的订单不是可收款对象；这一业务边界仍保留。退款后是否需要再次收款由原有明确重收授权/业务依据判断，不能只看“收款减退款”就重新催款。金额展示必须复用同一权威读模型，禁止各页面自己拼公式。

| 指标 | 用途与口径 |
|---|---|
| 本营业日收款 / 退款 / 净收 | 取真实资金流水归属营业日；净收=确认收款−确认退款。未知、模拟/零元赠送不冒充真实收入；取消订单晚到款仍保留资金事实 |
| 销售额、优惠、赠送 | 按原订单与成交快照的既有经营口径展示，独立于资金到账；赠送可有商品参考价值但不是收款 |
| 待收 | 当前确实应收且授权可处理的余额；退款和旧未知不能自动生成欠款 |
| 多收 | 已确认资金超出权威应收的部分，显示退款待办；不扩增销售额抵消 |
| 历史订单汇总 | 按订单原营业日/桌次，不能混同今日到账流水；跨日到账须能关联原订单 |

财务日报头部明确“资金按入账营业日、销售按订单营业日”，提供两种对应汇总，避免跨夜/晚到款使员工误以为账不平。先复用现有统计，字段语义不一致时修合同并给差异依据，不造第三套计算。

### 3.3 必须让经营者知道的取舍

- 允许显式新尝试与旧未知并行，**无法承诺渠道层绝不多次到账**；必须保证每笔实际款都记录、多收可发现/退款、收入和履约不重复。这是按用户要求允许再次收款后的客观取舍，须用并发与晚到测试控制，不回加“先释放”的门槛。
- 一次扫新桌只调整本人当前桌位；如果还有旧桌待送达订单，应告知其原归属及需要现场协调，不能静默把别人的整桌账、制作任务和库存一起迁走。
- 付款自动票提升核对便利，也会增加纸量；按实际付款事件去重，一笔付款一份，补打明确标记。不同站点需要不同制作票，不能强求全店任何订单只出一张混站票。
- 月度批量排班节省录入，但改已预约场次有经营影响；复用改期影响与通知，不因一次编辑而删除既有预约事实。

### 7.2 操作性、布局和性能验收目标

以下为本次拟定验收目标，不是已测性能，不将正常网络或渠道到账时长做无依据保证。

- 常用按钮手机有效点击区至少44×44 CSS像素；320/375/390/430宽和桌面1024/1440宽检查，无页面级横向溢出，表格宽内容转卡片/折叠。200%字体缩放、长品名、大金额和空列表均可读、可操作。
- 点击后200毫秒内提供本地当前项反馈；服务端成功后1秒内更新当前已确认项，后续全量刷新不得回退。正常在线环境关联视图目标3秒内收敛；离线显示最后更新时间与实际连接状态，不伪称实时。
- 性能先用代表性菜单、历史量和预计高峰并发建立基线；分别记录点单/提交/库存事务/异步打印任务耗时和P50/P95。容量数字由实际门店峰值确定，未测前不写“支持多少人”或承诺后端统一响应秒数。
- 搜索输入不失焦，手机键盘不盖结果/确认按钮；抽屉/弹层有合理焦点顺序，操作状态不只靠颜色。超时原请求核对和新动作语义清楚，其他任务仍可处理。
- 现场用真实授权员工完成任务，记录路径、误触、是否需要旁人解释。遇到需要猜状态或反复跳页才能确认本次收款/送达的情况，列为未通过；不以管理员可做替代岗位可用。

### 7.3 发布完成的独立证据

按模块分别记录：需求确认、代码实现、定向测试、并发/权限测试、合并、后端部署、原生小程序上传/选版/正式发布、终端升级、实机及岗位验收。某项不涉及某端时写“不适用及依据”，不能直接全勾。

本轮仅完成需求分析和代码比对。主线代码、运行服务、上传包、用户正在使用的包和Windows桥各有独立版本；发布前重新核实，不能把这份文档的SHA当未来发布证明。支付整改尤其不能只删除一条拦截条件即上线。

## 8. 排期、依赖与商业成本

按以下三批交付，每批可回读验收。P0是营业/账务安全或关键路径；P1是当班效率；P2是低频配置和呈现完善。模块表标示该模块主要新增工作的优先级；已有能力的P0保护由DEV-13统一作为相关交付的发布门槛，不能因归入P1模块被降级。原子项优先级仍可追溯，不把所有P2强行提前。各批涉及的并发、权限和发布门槛同步执行。

| 批次 | 交付范围 | 先决依赖 | 交付价值及成本 |
|---|---|---|---|
| 第一批：营业可连续 | DEV-01/02，DEV-03换桌核心，DEV-06已有售后验证，DEV-13；相关高风险提示、扫码/赠送/送达确认/打印未知防重既有能力回归及必要补缺 | 统一应收/营业状态与原因合同；并发测试数据；换桌身份/目标规则 | 先减少收款受阻、桌号错误和历史假待办。主要成本是资金竞态/权限回归及真实岗位验证；不得省成只改按钮 |
| 第二批：当班操作和票据 | DEV-04合付、DEV-05岗位历史/金额/站点、DEV-07成本链、DEV-08后台预览、DEV-09移动问题、DEV-10打印；DEV-12对应P1提示 | 第一批金额合同；合付分摊；历史价格快照；Windows终端可验证环境 | 减少一单一结、重复跳转、上架求助和错误纸票。成本涉及前后端、小程序及两台实体打印联合验收 |
| 第三批：配置效率与剩余提示 | DEV-11月度排班、菜单细节真机验收、DEV-12剩余P2及历史例外复核 | 发布/改期事实复用；具体设备投诉复现；跨岗位回归 | 降低月度录入及解释成本。不得延期真实欠款、权限或已知高风险问题来换界面美化 |

同一共享组件/接口只由一个模块主责实现，其他模块调用并补自己的验收。建议负责人按模块拆为服务端、员工网页、原生小程序、打印终端与门店验收角色；具体人名和天数须在团队资源、机型/终端配合及实际峰值核实后填写，当前不编造。

经营效果用上线前后同营业时段的基线比较：一次正常收款用时、历史未知造成的阻断次数、每单误出/重出票数、查制作送达历史的操作数、套餐上架被迫跨人求助次数。记录样本量和业务量变化；不能将客流变化或渠道恢复全部归功于界面改版。
