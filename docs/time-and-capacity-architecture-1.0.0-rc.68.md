# M-BOX 时间与容量架构 1.0.0-rc.68

## 结论

阿里云部署在中国大陆不等于所有进程天然使用同一时间，也不需要购买或调用第三方“北京时间API”。系统采用操作系统NTP、数据库权威时钟、UTC绝对时间、IANA门店时区和服务端营业日计算。

当前本地候选性能硬门禁通过，但阿里云实时资源指标仍未取得，因此没有证据支持“必须立即扩容”或“确定无需扩容”。日常营业容量和双容器部署容量必须分开判断。

## 时间模型

1. ECS使用阿里云默认NTP或chrony保持系统时钟同步；容器允许使用UTC。
2. PostgreSQL时间字段使用`timestamptz`保存绝对时间，业务日期使用独立`date`字段。
3. 门店配置使用IANA时区`Asia/Shanghai`，不从服务器所在地、浏览器时区或固定`+08:00`推断。
4. M-BOX营业日以门店本地时间06:00切换，00:00至05:59仍属于上一营业日。
5. 开台、支付、退款、任务、SLA、库存和审计时间由服务端生成；客户端只负责显示和单调计时反馈。
6. 浏览器根据服务端时间计算偏移，员工修改手机时间不能改变资金、库存或营业日事实。
7. 应用与数据库时钟偏差超过5秒时，就绪探针失败并禁止切流。
8. 自动切日具备幂等和停机补切能力；历史记录不因新营业日而改写。

第三方时间API会引入网络依赖、限流和新的单点故障，不能替代NTP。只有跨组织可信时间戳、电子签名或监管存证场景才需要另行引入可信时间戳服务。

## 当前验证

- PostgreSQL分别以`UTC`和`Asia/Shanghai`会话时区运行同一矩阵，绝对时间与06:00营业日结果一致。
- 23个数据库迁移、85张强制RLS表、跨实例员工租约和61桌规范化经营投影通过验证。
- 2个API实例、60读取并发、12名员工冷启动和10个初始化写并发共2712次测量，业务失败与5xx均为0。
- 一个实例事件循环P95为50.266ms，比50ms理想目标高0.266ms；P95 75ms和P99 100ms硬门禁均通过。
- 20并发聚合写极限观察中快速下单P95为1587ms，说明聚合写路径仍是后续横向扩展风险。

## 扩容判定

不依据“感觉卡”直接购买服务器。不可变候选部署后，在阿里云连续15分钟出现以下任一情况才批准运行期扩容：

- CPU持续超过70%。
- 可用内存低于20%、发生OOM或容器重启。
- 事件循环P95超过75ms或P99超过100ms；P95超过50ms先告警并定位阻塞来源。
- 数据库连接使用率超过70%、等待持续大于0或获取P95超过50ms。
- 核心读取P95超过500ms、核心写入P95超过800ms且错误率超过1%。

验证环境若低于2核4GB不应继续降低。商业上线建议4核8GB作为300人峰值和蓝绿切流的起始容量，但最终购买决定仍以阿里云实时指标为准。历史`rc.67`双容器部署出现约6分钟资源饱和，因此在资源证据补齐前，应优先使用远程镜像分层缓存、只构建一次和候选容器顺序验证；扩容不能替代慢SQL、过大响应或整店聚合写拆分。

## 发布边界

本文件只证明代码与隔离环境的时间、数据库和容量模型。阿里云NTP、CPU、内存、磁盘、连接、OOM、重启、真实支付、打印、弱网及连续三个营业晚班仍需按TC取得线上证据。
