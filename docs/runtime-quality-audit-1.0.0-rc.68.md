# M-BOX rc.68 历史日志与运行质量审计

审计日期：2026-08-09

## 结论

历史日志证实“页面感觉慢”不是单纯主观感受。`rc.64`在员工启动、心跳、任务和KDS动作上均存在秒级长尾，并出现数据库连接池超时；`rc.67`错误信号下降，但关键路由仍超过候选SLO，任务与KDS还缺足够线上样本。因此`rc.68`必须重新采样，不能沿用旧版本的压力测试结论。

## 根因判断

以下为代码与日志交叉验证后的工程判断：

1. 员工心跳曾读写约7MB整店聚合状态，连接池和变更队列在高峰互相放大。
2. 受保护接口鉴权会读取并克隆整店状态，心跳和启动轮询重复支付相同成本。
3. 工作区投影循环中反复创建`Intl.DateTimeFormat`，单次投影产生明显CPU阻塞。
4. 客户会话轮询虽有数据库幂等，但每次仍建立事务并尝试写事件。
5. 任务和KDS仍是聚合写路径；`rc.65`已增加串行队列和revision缓存，但缺少`rc.67`线上样本验证实际改善幅度。

## rc.68整改与验证点

- 心跳迁移到独立员工租约表，鉴权与续租合并为一次轻量事务，正常心跳不得改写整店revision。
- 中国时间格式化器复用；本地2500次调用从旧线上同类路径约1036ms降至约7ms。此数字只证明CPU热点被消除，不代表完整接口延迟。
- 客户会话到访事件在进程内合并，并继续由数据库幂等约束兜底。
- 预约接口去除重复聚合读取，员工首屏延后非关键心跳。
- 增加规范化路由直方图、事件循环延迟、连接池、变更队列和投影就绪指标。

## 未关闭风险

- 任务/KDS聚合写路径必须在候选镜像上重新压测。
- 单实例进程内缓存只能减少重复工作，不能代替数据库幂等或跨实例一致性。
- 阿里云当前资源较小，真实300人高峰仍需观察CPU、内存、连接池和事件循环，而不仅是HTTP成功率。
- 真实支付、打印机、微信容器、门店弱网和连续3个营业晚班不在日志模拟范围内。

## rc.68当前候选复测状态

PR #62首次提交级性能运行`31306680108`未通过：员工/客户读取、任务、点单与KDS均存在超限，事件循环P95约165.0/158.7ms。

第二次不可变提交级运行`31316732711`把问题进一步拆清：员工API启动旅程120/120成功、P95 101.6ms，但浏览器页面内双帧P95 701.4ms，主要时间落在API就绪357.5ms至工作区就绪665.7ms之间，证实工作区懒加载资源瀑布；一个实例的登录聚合写队列等待P95 133.97ms，超过100ms门槛。KDS开始在持续5次/秒下P95 3469.7ms，两个实例写队列等待P95约2599.7/2601.4ms，而连接池获取P95只有约0.32/0.31ms，说明当前瓶颈是整店聚合JSON串行改写，不是数据库连接池。下一阶段因固定PostgreSQL端口冲突未启动，属于测试基础设施缺陷；因此该运行整体失败，且商业发布结论不变。

同一阶段的后续脏工作区本地诊断曾在5次/秒下得到KDS开始P95 96.5ms、300/300成功，但最大并发仅1，而上述不可变CI最大并发达到17。两组证据不是同一提交、同一构建和同一运行环境，不能相互覆盖；它们共同说明结果对构建身份和写入服务时间高度敏感。CAP-018继续以不可变CI失败为准，必须由启用完整构建来源证明的新提交CI重新裁决。

随后审计发现旧负载脚本把多条写路由按固定顺序放在同一个持续增长的数据集上，并使用闭环单工作者；这会混入状态体积增长并隐藏固定到达率下的排队。当前工作区已经改为七个独立阶段，每阶段使用全新PostgreSQL数据库和两个新API进程，写路由采用开放到达率，`all`模式被标记为无发布证据资格。

早期脏工作区的隔离诊断曾得到员工浏览器P95 398.7ms和客户P95 377.1ms，但不可变CI没有复现员工结果，因此不能再把该本地数字当作候选结论。代码已经在应用入口预取员工工作区，重复增加预加载不能解释或修复CI长尾；必须继续拆分API、资源下载、解析和渲染，并增加弱网与低端移动设备档位。

修正动态端口并把源码、构建环境、构建产物和来源工具摘要全部绑定后，最新本地诊断重新构建了当前源码：员工API旅程120/120成功，P95 97.1ms；员工新浏览器上下文页面内部双帧绘制30/30成功，P95 391.1ms。相同样本从Playwright外部导航到可见工作区的观测P95为1096ms，说明391.1ms只能表示页面内部就绪，不能替代完整设备启动指标。客户首次会话API的前一轮诊断为300/300成功、P95 24.8ms；客户新上下文首屏双帧绘制30/30成功、P95 373.9ms。读取阶段1812次测量无失败，Bootstrap 200/304 P95分别为30.9/15.6ms。员工复测两个实例连接池获取P95约0.04ms，写队列等待P95最高51.1ms。以上仍是绑定当前脏工作区构建来源的诊断证据，尚未替代不可变CI；浏览器进程启动、网络条件、员工登录准备和真实设备均未纳入完整冷启动验收。

最新脏工作区KDS诊断使用双实例、独立PostgreSQL和300个样本：在2次/秒下300/300成功，P95 200.7ms、P99 210.7ms；连接池获取P95约0.07ms、写队列等待P95约0.03ms，业务不变量与跨实例检查均通过。该结果只证明提交回归档位；5次/秒容量失败仍保留，且脏工作区结果不能将对应TC改为正式通过。

本地点单不变量阶段300/300通过，P95 114.9ms、P99 120.5ms；订单、审计、库存销售流水、打印任务、KDS关联和幂等重放均验证为一次。修正门禁后重新执行KDS完成阶段：准备300单、准备300次制作，再测量300次完成，P95 153.7ms、P99 169.6ms；完成审计、配送任务、跨实例状态、5xx、连接池和投影均通过。种子最初没有商品库存，曾造成“库存扣减0/300”的真实测试失败；补充确定性入库基线后转绿，证明测试必须核对业务前置条件，不能只看接口成功。

KDS阶段的聚合状态由约80KB增长到约3.29MB，倍率约41倍，但约916次集群业务写入的净增长约3.5KB/写，低于5KB门槛且未超过10MB绝对上限。旧门禁单凭倍率阻断属于低基数误判，已改为倍率预警、绝对上限和显著体量下每写斜率联合阻断。该结果仍暴露结构风险：`runtime_states.state`仍是兼容性权威写模型，规范化表主要承担投影和读取；连续3个营业日的有界增长、归档和查询退化尚未验证。

提交级单路由回归默认KDS写入2次/秒。该值建立在“300位客人、每人估算3个出品、每个出品4次状态流转、营业5.5小时”的显式估算上，约为估算夜间均值0.182次/秒的11倍；它不是实测经营事实。5次/秒约为27.5倍，保留为容量探针且当前失败。后续应由真实订单与KDS事件校准模型，不能用2次/秒通过覆盖5次/秒容量缺陷。

任务写入、容量阶梯、三轮重复、多营业日稳定性、完整App冷启动、全部阶段合并、全量CI、固定候选环境和阿里云资源门禁仍待执行。完成前`rc.68`性能与商业发布结论继续为`DENY`。历史20并发聚合写冲击和`rc.67`双容器部署约6分钟资源饱和仍保留为扩展风险，不能据局部本地结果宣布无需扩容。
