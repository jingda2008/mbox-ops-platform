# v9七项补充规则与实现（2026-09-16）

用户明确：报表范围可选；优惠互斥；支付诉求指IP风控；再存不强制关联原单。组合赠送、状态流转和归档采用本次建议的简单方案，均以后台配置办理；没有启用真实活动或调整生产配置。

| 项目 | 本次规则 | 实现边界 |
|---|---|---|
| 报表 | 可选存酒、消费、全部，会员/品类/日期过滤并导出 | 存酒为选填的登记价值；消费为订单应付金额，二者分别汇总，均不是实收收入。同一消费订单只计一次。品类筛选消费订单时统计符合条件的整笔订单金额，不冒称品类销售额。消费范围须有全店订单查询权限，导出另需存酒导出权限。 |
| 券＋甜点 | 一个已审核活动发一张商品券/低价券，加一份甜点权益；同会员同活动只发一套 | 同事务两份权益一起成功或回滚；前后批次不能重复领。发放预算包含券商品最高成本和甜点成本。甜点在券包按现有赠品核销流程领实物；发权益不等于已出品或已取。后台勾选已发数量、甜点核销、剩余名额、承诺成本。 |
| 专属价 | 多卡取最低有效价格，标准价更低时用标准价；优惠不叠加 | 菜单、购物车、下单读取有效卡资格；选择其他授权优惠时整单从标准价重新算，原专属价不参与二次优惠。用券不保证比持卡价更低，页面先显示用券后金额，用户可取消用券。订单保存成交快照，后续掉卡或改价不改历史成交。 |
| IP风控 | 使用可信代理链识别的真实客户端IP，保留渠道拒绝分类 | 增强IPv4/IPv6格式校验，不能把服务器IP冒充客户IP；明确IP异常才归类IP风控，“异地交易”单独不足以证明IP原因。现有记录包含脱敏网络前缀、渠道错误代码。用户无法提供故障订单/时间，历史失败原因未确认，不能宣布已修复。 |
| 状态流转 | 保留在存→验证码核验→确认取走→再存/完结；配置部分取存、再存开关 | 不增加通用工作流编辑器；验证码与数量检查始终生效。关闭再存只禁止新的再存操作，不抹去既有存酒或已取记录。 |
| 不强制关联原单 | 员工可选沿用原单或新建再存单，默认允许选择新单 | 新单重新计算存期并独立编号；后台保存取酒来源，锁定本次取走数量，不重复增加数量。强制关联开关保留可配置。新单金额不机械复制整笔旧单价值，避免金额重复统计。 |
| 归档 | 默认自动归档，也可改为员工手动归档 | 仅在剩余数量为零、所有取走批次均已处理后归档；有酒或待处理取酒时拒绝。历史事件保留，不自动删除、不直接重开已归档旧单；再次寄存建新单。 |

需注意：模板消息、群发配额和平台风控由真实账号及渠道能力约束，本地开关不能解除平台风控。没有实际发消息、推送、部署、小程序上传或门店实物操作。历史支付事故继续开放，待出现可追踪样本后核对。

仍保留前轮差异：存酒编号默认添加防重流水尾段，与原文三段格式不同；双字母号段从AA开始及其他默认值见逐条审计。这些没有被本次七项补充自动确认。

## 存酒补充需求（用户后续明确提出）

取酒验证码渠道已由用户确认：**继续使用微信服务号验证码**。手机号用于联系与核对，不改成短信验证码。

| 项目 | 本地实现 | 验收边界 |
|---|---|---|
| 剩余比例 | 单位为瓶时选择整瓶、1/2、2/5、1/5、3/5、4/5、1/4、3/4、1/10，亦可手填其他数量；服务端精确核对比例与数量 | 再存不能超过本次取出数量；部分再存仍需启用现有“允许部分取酒和再存”配置 |
| 拍照与水印 | 新存、原单再存及新单再存均必须提交一张照片；页面只提供摄像头入口，拍完/关相机/收起表单/离开页面即释放相机；服务器转成JPEG并加北京时间、会员号、数量水印 | 水印证明服务器收存时间，不证明无法伪造的物理拍摄时间；模拟相机通过不等于真机验收 |
| 必留手机号 | 自动读取有效会员登记手机号并保存加密快照；没有登记则必须补填有效联系号码；界面仅显示掩码，照片需员工存酒权限读取 | 补填号码不冒充已经验证的会员手机号，不自动写回会员注册信息；有多条有效号码时先核对会员资料 |
| 取酒验证码 | 保留服务号发码→验证→确认实物取走；错误次数、过期、重复消费及并发防重继续生效 | 真实服务号账号、模板、绑定身份、平台发送和客户收码仍需现场验证，未真实发码 |
