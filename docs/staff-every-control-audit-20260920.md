# 员工后台逐控件、功能闭环与文案审计

审计时间：2026-09-20。基线为刚合并的 `5c4bde7de5ed154ab3dd9227a64751dcc65293eb`。审计对象为店内员工使用、管理者兼用的后台，不包含顾客小程序全部页面。

**当前不能判定“每项功能全部闭环”。本轮归并17项待处理问题：2项P1、13项P2、2项P3。** 最优先的是库存损耗重复扣减和超限损耗无法继续办理。此前CI通过与这次发现新问题并不矛盾：既有用例没有覆盖这些操作序列。

本轮只新增审计工具、清单和证据，没有修改业务实现，没有提交、合并、部署、上传小程序，也没有真实收退款、发送微信通知、改生产库存或员工权限。以下均是基线代码与本地隔离数据库证据，不是生产事故归因。

## 调整界面与展示逻辑

一线人员先看到“现在要处理什么、在哪桌、下一步是什么”。开台、加单、收款、出品、送达、存取酒围绕同一笔桌次或记录展开。管理者兼岗时可切换工作入口，但权限继续由真实授权决定。表单只显示完成当前任务所需项目，价格、规则、模板和系统接入放在明确的管理入口。

每次操作都应有连续状态：待填写→核对提交内容→处理中→已保存/已提交平台/结果待核对→下一步。读取失败不覆盖已保存结果；网络未知不让员工重新建一笔。审批后、发布后、到达生效时间后分别表达，不能用一个“成功”概括。关键结果要显示记录、时间、操作人及必要业务编号。

文案示例：“服务端试算”改“计算优惠结果”；“产能发布后成为运行事实”改“产能规则经审批和发布后生效”；“金额快照”改“本次打印时的金额”。但“应发/实发”“异常结清不是收款”“平台受理不等于送达”“看到的事实与个人判断”必须保留业务区别。AppID、模板ID和密钥属于管理员接入参数，可以分区，不应改成无法配置的模糊文字。

修复顺序：先处理库存两项P1，再修入口衔接、类型/乱序/反馈与权限依赖，之后统一文案、金额输入、步骤和窄屏。每条修复必须关联SYS编号，先保留失败证据，修后重复原操作并核对业务记录；不能仅做字符串替换或静态断言。原生App还需独立验收回到前台、弱网恢复、摄像头权限、推送、键盘/安全区、设备切换及门店真实使用。
