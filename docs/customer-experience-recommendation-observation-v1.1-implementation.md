## 1. 不可变业务决定

1. 现场点单必须先建立有效桌台会话；没有桌码时，点单页只显示明确的扫码入口和说明，不显示菜单、购物车、服务呼叫或支付动作。会员PRD中“未扫码可浏览菜单”的建议已被用户后续决定覆盖。
2. 付款前升级只发生在未付款购物车确认环节。不得恢复付款后返现、已付款单杯抵扣、口头补差或模拟支付成功。
3. 超嗨长期占用一个底部入口，定位为活动发布与参与中心，不是把报名表直接铺满的长列表。
4. “我的”必须展示本人真实可用权益、已获赠内容、活动报名和待付款状态；营销内容卡不得冒充已经到账的权益。
5. 推荐系统只读商品、库存、产能、演出和客户授权证据；AI不能直接修改价格、库存、菜单、退款、赠送或客户权益。
6. 商品观察默认归属桌台或商品。只有明确、重复且可追溯的客户级证据，才允许进入个人偏好候选池。
7. 经营、资金、权限、可见范围、资格、时限和排序条件使用强类型字段或有版本的策略；图片、长文案和展示编排可以保留在受约束 JSONB。
8. 顾客端不提供语音入口；员工观察的主动授权、最长20秒、无原录音留存转写是可选辅助，文字始终可用。
9. 会员首页不堆短信/微信等通用授权开关；通知只在积分或预约等具体上下文请求一次性平台授权。

## 2. 小程序信息架构

### 2.1 五个底部入口

| 入口 | 未扫码状态 | 已扫码且桌次有效 | 首屏优先信息 |
|---|---|---|---|
| 首页 | 预约、近期演出、超嗨活动、会员权益摘要 | 桌号、人数、当前/下一场演出、责任服务、进行中任务、桌账摘要 | 只放下一步动作和异常，不铺后台说明 |
| 预约 | 可用 | 可用 | 分步完成时间人数、位置联系、确认提交 |
| 点单 | 显示“扫码点单”门禁 | 推荐、菜单、购物车、付款前升级、支付 | 桌号、当前演出、推荐和菜单 |
| 超嗨 | 可用 | 可用 | 活动列表，点入详情后报名/支付 |
| 我的 | 登录后可用 | 登录后可用 | 可用权益、获赠内容、活动报名、积分 |

### 2.2 首页状态

首页不得用大段品牌文案替代经营信息。按照当前客户所处阶段切换内容：

```text
未到店
→ 最近可预约日期 / 最近演出 / 下一场超嗨活动 / 可用权益摘要

已扫码未开台
→ 桌码已识别 / 等待门迎开台 / 联系门迎

已开台
→ 桌号与人数 / 当前及下一场演出 / 责任服务员 / 进行中服务 / 桌账摘要

存在异常
→ 待付款、服务超时、活动名额将释放、经理正在处理等单一高优先级提示
```

低频隐私、规则解释和内部状态不占首屏；通过详情、折叠说明或底部链接进入。

### 2.3 扫码点单

点单主流程：

```text
进入点单 Tab
→ 检查是否已有有效桌台会话
→ 无会话：显示扫码主按钮
→ 微信扫码或小程序码 scene 进入
→ 服务端验证签名、门店、桌号、有效期和设备绑定
→ 校验桌台是否已开台
→ 建立客户—桌次参与关系
→ 返回桌号、人数、当前演出和菜单版本
→ 推荐 / 浏览菜单 / 加入购物车
→ 付款前升级
→ 服务端创建权威订单和支付意图
```

本期明确不另设“到店前浏览菜单”；首页、预约、超嗨和“我的”仍可在未扫码时使用。过期桌码、换桌和已闭桌必须失败关闭并提示重新扫码。

## 3. 点单、推荐与付款前升级

### 3.1 推荐的硬筛选

生成推荐前，服务端必须同时确认：

- 商品、价格版本和套餐组成已发布且当前可售。
- 套餐人数覆盖当前桌次人数。
- 客户明确排斥、过敏或不能饮用的内容已排除。
- 原料库存和增量组件库存充足。
- 吧台、冷厨和服务产能允许在承诺时间内完成。
- 当前时段和演出阶段适用。
- 商品没有处于临时隐藏、售罄、出品异常或高延迟状态。

评分可以参考场景、人数、酒水偏好、历史接受度、演出阶段、库存稳定、出品稳定、合理利润和价格风险。利润不得覆盖明确禁忌，也不得隐藏合理的低价选择。

### 3.2 三档展示

每次最多展示三个主方案：

1. 轻松开始：满足基本需要，不得故意设计成明显不足。
2. 今晚推荐：体验、价格和履约稳定性最平衡，视觉上为主推荐。
3. 完整体验：明确说明增加的酒水、餐食、互动或服务。

每档显示名称、总价、核心内容、适用人数、推荐理由和当前可售状态。不得只显示“猜你喜欢”或“AI推荐”。

### 3.3 推荐证据闭环

`recommendation_sessions`保存当时的顾客、桌次、人数、场景、演出、菜单版本和排序快照；`recommendation_behavior_events`以追加式事件记录`generated`、`exposed/viewed`、`selected`、`ignored/rejected`、`staff_modified`、`ordered`、`paid`和`refunded`。事件类型进入数据结构不等于生产者已经完成，必须逐项核对真实写入点和强类型关联。

当前本地候选已接通以下证据：

- 生成方案时记录`generated`；推荐卡实际加载后记录`exposed`。
- 客户加入推荐商品时记录`selected`；点击紧凑的“不合适”操作记录`rejected`，成功后移除对应推荐卡。
- 结账请求可选携带服务端生成的推荐公开ID和所选商品ID，该二元组进入`commerce.order.submit`幂等指纹。
- 同一订单事务验证推荐会话/方案属于当前顾客、桌次和营业日，并验证方案商品真实存在于最终顶层、数量大于零、订单与品项均为`submitted`的订单行；失败时订单、库存暂留和推荐事件整体回滚，成功时才写`ordered`并绑定强类型`order_id`和`order_item_id`。
- 客户先选择推荐、后接受付款前升级时，小程序不再携带原推荐归因：原`selected`意向保留，被套餐替换的来源商品不虚写`ordered`，升级转换由独立报价证据负责。
- 订单在权威支付成功事务内达到全额已付后写一次`paid`；权威退款成功且`refund_items`确实给推荐订单行分摊了大于零金额时，按每笔退款写`refunded`。
- 顾客明确选择“不喜欢”或“过敏/不能饮用”时建立本人强类型商品限制；普通“这次不需要”只影响当前会话。本人可查看、撤回，推荐按规范客户身份族硬排除。
- 排序已接库存、强类型产能、可售时段、商品演出阶段资格和可靠的当前演出阶段；受阶段限制的商品在没有可靠阶段时不参与推荐。
- 偏好事实支持本人声明、明确客户级观察、相反证据、衰减、最新修订、撤回和重算；桌台级观察不会自动进入个人偏好。
- 体验计划只在有效桌账订单或权威付款成功后激活；失败/unknown不生成节点，全额退款取消尚未执行节点。
- 管理端已有推荐漏斗、实付/退款、商品销量/退款/冻结成本/贡献、观察质量和带样本量/相反证据的周度建议。

本地候选已经形成从硬筛选、证据、展示、选择/拒绝/明确移除、员工受权调整、订单、权威支付/退款、体验计划到管理分析的强类型主链，并提供同桌后续加单与跨日同品复购的非因果投影。真实资金和营业样本仍未验收，投影也不得解释为推荐因果，因此只能称本地代码闭环，不能称线上经营效果闭环。分析端必须分别使用`ordered`、`paid`和`refunded`，不得互相推断。

聚焦PostgreSQL用例已验证有效归因、跨桌/缺失商品零写入、支付失败或unknown零写入、重复回调/查单幂等、非推荐商品退款零写入、推荐商品部分/全额/多次退款、跨单/跨店拒绝、升级组合不虚写和同桌并发隔离。当前工作树已继续演进到迁移096；最终全量数字和候选SHA见本文末尾“证据状态”，不得继续引用早期迁移的陈旧数字判断当前候选。

#### 3.3.1 `paid/refunded`强类型归因（本地候选已实现）

迁移059和权威支付/退款事务按以下边界实现：

1. `recommendation_behavior_events`增加强类型`payment_id`、`refund_id`、`order_item_id`、`attributed_amount_minor`和`attributed_currency`；复合外键同时约束`tenant_id/store_id/order_id`、支付所属订单、退款所属支付、订单行所属订单及退款分摊的精确订单行，不靠JSON或商品名关联。
2. 事件约束要求：`ordered`必须有`order_id/order_item_id`；`paid`必须有`order_id/order_item_id/payment_id`、正金额和币种且不得有`refund_id`；`refunded`必须再有`refund_id`，并精确命中`refund_items`分摊；非资金事件不得携带上述资金字段。事件类型由数据库受限枚举/检查约束，订单、订单行、支付、退款、金额和币种全部来自规范化强类型事实。`evidence_snapshot`只保留非权威展示来源标签，任何生产者不得从JSON推断资金事实。
3. 增加部分唯一幂等约束：`ordered`和`paid`都按推荐会话、方案和订单唯一，`refunded`按推荐会话、方案和退款唯一。重复回调、查单重放、拆分支付和退款执行重试只能返回既有事件，不能累计虚假转化次数；同一订单有多笔支付时不能生成多次`paid`。
4. `paid`只由权威支付成功事务产生：从既有`ordered`事件反查同一订单和推荐商品的有效订单行，并在订单权威结算状态达到`paid`后写入一次；`payment_id`引用使订单首次达到全额已付状态的触发支付。单笔支付成功但订单仍为`partially_paid`时不能写`paid`，客户端提交、页面返回或`selected/ordered`也不能产生`paid`。
5. `refunded`只由权威退款成功事务产生：必须联结`refund_items`，且推荐商品对应订单行的实际退款分摊金额大于零。退款只命中同单其他商品时不写推荐退款；部分退款和多次退款按不同`refund_id`追加，分析端再聚合，不覆盖`paid`。
6. 付款前升级组合继续沿用不可伪写边界：来源推荐只有`selected`而无`ordered`时，不得从套餐支付或退款反推来源推荐的`paid/refunded`。只有最终仍存在有效`ordered`归因的推荐商品才进入资金事件。
7. 该事件只能在服务端权威资金事务中写入；自动化已覆盖重复支付回调、支付失败/unknown、同单多商品、仅退款非推荐商品、推荐商品部分/全额/多次退款、结果重放和跨店/跨单伪造。仍需补真实商户资金、四方对账、退款失败后的真实渠道恢复和不可变提交证据，不能由模拟Provider替代。

### 3.4 付款前升级

当前本地候选已经实现原子主链：服务端在同一数据库事务中锁定报价和规则，重新校验当前价格、毛利、桌次/人数/时段、商品状态、套餐结构、BOM、配方、库存与强类型产能窗口，完成购物车服务端替换、权威订单、库存/产能暂留和报价转换；事务提交后才调用支付，受信支付结果前不生成KDS。可信支付成功激活产能，明确失败或超时释放暂留，KDS完成/取消/失败释放已激活产能。

迁移089进一步补齐不可变规则版本、起草—独立审批—第三人发布、从历史版本复制回滚草稿、吧台/厨房/收银多时间窗产能政策、顾客浏览/拒绝/接受/成交事件和员工经营汇总；员工端已有规则与产能配置入口。`checkout_upgrade`仍由迁移和管理API强制保持`disabled`，因为正式菜单/BOM/成本、真实高峰产能、岗位分离、真实资金和营业晚班尚未验收。小程序prepare仅对身份或桌次错误失败关闭，其他准备失败会保留原购物车继续结账并提示降级。

升级触发顺序：

```text
购物车确认
→ 读取已启用且已审批的升级规则版本
→ 匹配一项明确来源商品和一个目标套餐
→ 服务端重新计算标准价、成本、人数、库存、产能和有效期
→ 展示“保持原选择 / 升级”
→ 接受后用目标套餐替换购物车中的指定来源行
→ 同一事务创建订单、价格快照、库存暂留和升级核销
→ 事务提交后发起支付
```

必须满足：

- 功能总开关、规则状态和正式菜单未就绪时返回无升级，不返回测试报价。
- 规则保存为不可变草稿，由第二人审批、第三人发布；回滚通过复制历史版本为新草稿完成，不改写历史。
- 同一报价只对应一个购物车指纹、桌次、客户、规则版本和有效期。
- 接受升级、订单创建、库存暂留和报价转换必须原子提交；任一步失败全部回滚。
- 支付调用在数据库事务外执行，支付成功只认验签回调或服务端查单。
- 付款前库存/KDS隔离：支付待定时不得进入制作；支付失败或超时释放暂留；支付成功只释放一次到KDS。
- 重复点击、双设备并发和网络重试复用同一幂等结果，不重复订单、扣库存或派发KDS。

## 4. 超嗨活动中心

### 4.1 活动列表

列表卡只显示有助于决定是否点入的信息：封面、类型、标题、日期、简短摘要、价格起点、剩余名额、会员限定标识和“查看详情”。退款全文、报名人数选择和安全长文不在列表展开。

### 4.2 活动详情

详情页包含：

- 封面或图集、完整介绍和活动日程。
- 开始/结束时间、集合地点、主办人和联系方式边界。
- 包含内容、可获得积分、活动权益或赠品。
- 适合人群、年龄/装备/健康要求和安全说明。
- 费用、计价方式、订金/全额预付、剩余名额和付款时限。
- 取消和退款规则，以及规则版本/快照生效说明。
- 底部固定报名、候补、待付款或已报名动作。

图片、图集、长文和内容块可以保存在受约束 JSONB；费用、容量、可见范围、报名资格、付款方式、时限和状态必须强类型化或引用已发布策略版本。

### 4.3 报名与支付

当前本地候选已实现收费活动主链，但默认关闭：报名记录、名额暂留与`activity_registration`权威支付对象在同一事务创建；详情页和“我的”均可读取付款状态、发起首次渠道动作或执行查单。渠道结果为`unknown`后只能查单，不能再次创建支付动作。渠道回调复用既有权威支付处理；到期任务仅在尚未创建渠道动作或权威明确失败时释放名额，`unknown`或金额不符会延长保留并写审计/Outbox。活动支付必须同时通过门店线上支付、本地Provider配置和`community.activity.payment`三道门禁，迁移054默认将功能开关设为`disabled`。门禁不可用时，`deposit_optional`只允许`none`，`deposit_required`和`full_required`失败关闭。

```text
活动详情
→ 选择同行人数
→ 服务端复核可见资格和剩余容量
→ 确认费用、预付金额、安全要求和退款快照
→ 免费/无需预付：直接确认
→ 必须预付：暂留名额并创建权威支付订单
→ 微信/星驿支付
→ 验签回调或服务端查单确认
→ 报名确认并展示凭证
```

满员进入候补且不收预付款；迁移088只在取消、未到或退款成功等明确释放名额后，按候补顺序并发幂等递补。收费候补在递补前不预扣款；若收费门禁关闭则保守延期并审计，不能偷偷改为免费确认。金额不足、部分退款、重复回调或渠道结果未知时进入人工复核，不自动确认也不擅自释放。已付款活动报名禁止顾客直接取消，只能由店长以`refund.request`发起，再由另一名收银通过`refund.approve`和`refund.execute`复核执行，不为活动另开无审批退款入口。

公开活动不得因为点击报名而强制成为会员；会员或分群活动按已发布可见规则校验。

### 4.4 活动后台

独立活动运营工作台可配置封面、详情、类型、时间、地点、人数、计价、费用、预付方式、付款时限、权益、可见范围、参与要求、安全说明和退款规则，并集中展示报名/候补名单、签到、未到、取消、付款和退款状态。创建者保存草稿，另一名具有`community.activity.publish`权限的人员复核后发布；发布后客户承诺不可静默修改。旧的第二套活动表单退出默认界面，新建/编辑禁止未批准的`black`客群，历史记录只读兼容。旧`points_reward`固定为0且不展示、不发分；活动促销积分必须使用独立版本化规则。收费活动仍须同时满足门店线上支付、本地Provider和活动支付功能三门禁，当前默认`disabled`。

## 5. 我的、权益和赠送可见性

“我的”按以下顺序展示：

1. 会员身份、等级和积分摘要。
2. 可用权益：名称、来源、数量、有效期、使用条件和当前状态。
3. 已获赠内容：员工赠送商品、活动赠品、服务补偿和已到账权益。
4. 我的活动：待付款、已报名、候补、已取消和退款中。
5. 积分明细和本人可修改的到店偏好。

真实权益复用现有`benefits`、`benefit_reservations`和核销链路。`member_content_cards`只用于活动、文章或促销内容，不能作为到账证明。员工赠送商品在桌账订单中明确标记“门店赠送/服务补偿”和数量；若同时形成长期权益，必须通过正式权益发放记录展示。

会员页不放短信/微信通知开关等非必要功能。通知同意由具体业务场景按渠道、目的和策略版本记录，不占用会员首页主要版面。

## 6. 商品观察与偏好证据

### 6.1 员工十秒入口

每个已开台桌位固定提供“记录桌台情况”。首屏只含：文字输入、可选员工语音转写、自动关联的桌号和订单摘要、“只记录/需要马上处理”、提交按钮；确认页可反选商品候选、纠正表达分类/事件类型/程度，提交后可查看本桌最近5条并追加修订。目标是在约10秒内完成常见文字记录。

文字录入为必备能力。员工观察页已有受控语音转写：员工主动点击后才申请麦克风，单次最长20秒，转写完成或失败后不保存原始录音；适配器关闭、设备不支持或转写失败时文字录入不受影响，也不得伪造转写成功。该入口仅属于员工观察页，顾客小程序没有且不得新增顾客语音能力。供应商、隐私、准确率和iOS/Android微信真机权限仍待外部验收。

### 6.2 解析与确认

```text
员工原始文字或语音
→ 绑定营业日、桌次、记录人、当前演出和真实订单
→ 只从该桌真实订单、商品别名和已发布目录中生成候选
→ 拆分客观事实、客户原话、员工判断、系统推断
→ 给出候选商品、事件类型、程度、原因和置信度
→ 员工确认或修正
→ 保存原始内容、结构化版本和修订历史
→ 可选生成现场服务任务
```

低置信度保留“不确定”，商品不在该桌订单中不得自动匹配。原始内容不可被结构化结果覆盖；每次修订保存旧值、新值、修改人、时间和原因。

### 6.3 数据对象

建议最少包含：

- `observation_records`：桌次、订单、记录人、原始文本/录音引用、处理选择和提交状态。
- `observation_candidates`：候选商品、匹配依据和置信度。
- `observation_events`：事件类型、表达类别、作用范围、程度、原因、来源和是否需处理。
- `observation_revisions`：追加式修订历史。
- `preference_evidence`：明确客户级证据、有效期、相反证据和是否允许推荐使用。
- `customer_preference_summaries`：从证据聚合的偏好、置信度、证据数和最近证据时间；可重算，不覆盖原始证据。
- `product_experience_weekly`：按商品、套餐、场景、演出和人数聚合的可重算分析结果。

观察默认`scope=table`或`scope=product`。客户级证据必须同时满足明确客户身份、明确表达或本人行为、证据来源可追溯；不得把整桌剩余复制给所有客户。

### 6.4 即时处理与长期分析

- “只记录”仅进入商品和菜单分析。
- “需要马上处理”只在员工确认观察的同一事务内创建一项最小摘要服务任务，并继续使用现有接单、前往、到桌、完成和升级状态机；解析、取消或修订草稿不得提前派单。
- 换酒、退款、赠送、升级和权益变更只能生成申请，由有权限人员审批执行；AI和普通服务人员不得直接落地资金或权益变化。

### 6.5 管理分析

后台已提供三个独立视图：

- 推荐分析：曝光、选择、成交、实付、客单、毛利、退款、投诉和复购。
- 商品体验：销量、剩余、评价、退换、出品延迟、场景差异和菜单建议。
- 数据质量：无法匹配率、人工修正率、员工记录倾向、样本分布和缺失关联。

当前周度建议显示样本量、支持/相反证据、置信度和数据时间窗；经营页按商品、员工、桌号、人数、场景和演出阶段筛选，并只从权威订单/退款/冻结成本和已确认观察计算。它只生成建议，菜单和价格变更进入现有草稿、审批和发布流程；真实营业样本、性能和岗位解释一致性仍待验收。

## 8. 微信身份、会员、积分与授权实现边界

### 8.1 身份、桌码与发布

- 本地候选使用`wx.login`一次性code、官方换码、加密微信身份和短期会话，不信任客户端自报OpenID或会员ID。
- 官方小程序码只从`launchOptions.query.scene`读取并严格解码；scene与query冲突、未知键、畸形值、跨店和失效桌次失败关闭。
- 正式候选构建与商业就绪检查已纳入AppID、合法域名、隐私主体、模板审核、官方桌码、开发者工具/真机和上传/审核/发布回执。缺任一外部证据时`DENY`，但不伪造服务已上线。
- 本期点单先扫码；会员PRD中“未扫码可浏览菜单”的建议由用户后续决定覆盖。拒绝入会或授权不影响扫码后的基础点单。

### 8.2 入会条款与会员找回

- 新入会先进入独立完整条款页，按当前已发布版本在同一事务保存接受事实；条款缺失时只阻断新入会，不阻断点单和旧会员找回。
- 点单页邀请为非阻断、可配置冷却和幂等重试；“我的”保留主动加入入口。页面不自动取得手机号、头像、昵称或通知权限。
- 微信手机号只在顾客主动找回时使用。0/1/多候选、掩码、规范客户身份族、员工候选核验、异人复核、驳回、幂等和来源保留已本地实现；正式微信手机号接口与真实岗位仍待外部验收。
- 条款和找回的员工管理API已存在；完整图形化条款管理页不是本轮已完成能力，不得仅凭表/API宣称授权人员自助闭环。

### 8.3 双账户、等级、权益与兑换

- 可用积分与成长值分账；订单冻结基础规则和等级倍率，只有权威付款成功才发放，失败/unknown不发。退款逐笔按强类型订单、支付、退款和原award冲回，不能从JSON推断。
- 漏积分由店长申请、异人审批。执行前重新锁订单、权威支付、会员、原策略、资格、倍率和当前award；自动恢复先完成则合法转`not_required`，补发后历史及后续退款都按总award冲回。
- 规则采用起草、审批、发布三人分离并允许未来排期，当前版本不会被未来版本提前退役。黑卡未批准，本期只有普通、银卡、金卡。
- 等级周期、升级/保级/降级、自动权益、积分批次/FIFO/到期、兑换库存/限额/KDS、失败/超时按原批次恢复均已本地实现。
- 新积分发放、积分兑换、微信通知有三项独立紧急暂停；暂停不阻断付款、订单、KDS和退款，暂停期权威付款进入待补算并在恢复后幂等处理。
- 积分不抵现金、不提现、不转账；同一商品不做积分加现金。比例、等级门槛、成本预算和试点天数均为待经营试算的可配置参数，不是已批准事实。

### 8.4 通知与顾客界面覆盖

- “我的”不放短信/微信通用授权面板。积分到账、退款冲回、即将到期和预约演出变更只在具体场景请求一次微信授权，并强绑定本人、通知类型、用途、上下文、模板、策略版本和可用次数。
- 顾客拒绝授权后仍通过页面查看订单、积分、预约和活动；旧通用同意不能跨场景放行。
- 短信营销、通用活动推广开关和顾客语音不在当前默认开放范围。员工观察语音是独立的受控辅助，不能推导顾客授权。

### 8.5 促销积分

旧活动`points_reward`已固定为0，不展示也不发放。迁移091已实现独立的活动促销积分规则，包括活动范围、付款/签到/完成触发、门店预算、个人上限、叠加组、有效期和退款冲回，并采用起草、审批、发布三人分离；积分暂停时保留强类型待处理事实，恢复后幂等发放，退款冲回不受正向发放暂停阻断。该能力仍默认不开启，须财务预算和权益成本签字、14天影子核算、真实退款/并发预算压力及三名真实岗位演练。

## 9. 失败恢复和安全边界

- 网络重试使用同一幂等身份；客户端不得根据超时推断失败或成功。
- 支付结果未知时查单并保留名额/库存的有限时租，不生成KDS。
- 活动支付、订单支付和退款均以渠道回调或服务端查单为权威。
- 推荐或观察解析失败时保留原始输入，允许人工继续，不阻断基本点单和服务。
- 图片和确需长期留存的大文件放受控对象存储，数据库只保存引用和摘要；当前员工观察语音只用于即时转写且不保存原始录音。不得保存支付密钥或原始敏感回执。
- 所有功能使用门店级开关：`disabled`、`shadow`、`pilot`、`enabled`；资金功能不得仅凭页面开关绕过渠道配置和权限。
