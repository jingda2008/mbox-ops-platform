## 交叉验证方法

1. 从 HTTP 入口追踪服务、公共错误包装、幂等执行器及数据库授权，和既有审计索引交叉比对，排除仅凭局部文件差异产生的误报。
2. 本机临时 PostgreSQL 数据库、受限 LOGIN 与 RLS 执行真实服务。锁住真实回执行，以 `pg_blocking_pids` 确认请求等待，再撤权或缩小可见范围、释放锁；核对状态码、字段及业务/审计/出站/回执快照；恢复授权后原键仍能正常恢复。
3. 控制应用时间跨过偏好有效期，对比原键恢复和新键过期请求。
4. 状态序列：声明→撤回→恢复旧声明，撤回→新增声明→恢复旧撤回；与当前 GET 投影及不可重复业务事实对照。
5. 同键改参数、换身份，以及结构化冲突/处理中/回执不可用与真正内部故障的 HTTP 分类对照。
6. 相邻预约、联系治理、偏好、通知和取餐的既有数据库回归；完整检查及准确提交 CI 另行留证。

- 活动制作、异常和顾客活动退款虽局部没有错误映射，实际经过公共 commerce/customer-experience 包装，已经分类幂等错误；不重复修复。

- SOP 服务对象存在，但未找到生产 HTTP 或调用者直接执行其 trigger；后台 worker 是另一条链路。不能把内部未接入模式当作已暴露生产漏洞，也不能据此断言 SOP 全部安全。
- 本轮没有穷尽权限最终查询之后、网络返回之前的全部并发交错。历史回执物理清理、身份合并、跨设备、旧客户端、外部渠道、实际权益/资金/打印/硬件仍需独立验证。
- 新测试的守恒快照涵盖预约、桌台预约锁、偏好声明/撤回、审计、出站与幂等记录；不包含授权配置、顾客测试夹具及可重算偏好派生表。原生创建合法历史回执提升允许既有 updated_at 更新，其余字段严格一致；拒绝操作仍比较完整快照。
