# 多人操作、拆桌原绑定与退款后再消费审计

日期：2026-11-15。范围：本地前后端模拟及隔离 PostgreSQL；暂不部署。

## 本轮修复

员工渠道优惠面板原来没有单独刷新绑定记录的入口，另一位员工拆桌、用券或退款后，页面可能继续显示旧记录。新增“刷新本桌绑定记录”：

- 仅查询当前桌绑定、已占用优惠和客组上限；不重新领券、不提交核销。
- 保留待核对请求的原编号与本地恢复日志；刷新不能代替“恢复原操作”。
- 连续点击只发一次读取；换桌后旧响应不覆盖新桌。
- 刷新时清除旧选择、预览和金额；失败或返回不完整时提示重新核对，不继续展示旧金额。

服务员操作：多人协作或拆桌后，在当前桌点“刷新本桌绑定记录”，核对来源、券和客组上限。有待恢复请求时，回原桌次核对原回执；不能把原请求修改成新桌重发。目标桌明确确认同一张券时复用原绑定，不增加次数。

## 新增场景与结果

| 场景 | 验证结果 |
|---|---|
| 待恢复请求期间连续刷新 | 单次 GET，原日志不变，不新发券或核销 |
| 原桌响应迟到、页面已切至拆桌目标 | 不覆盖目标桌数据、不显示旧桌错误 |
| 刷新返回缺少绑定数组 | 清除旧额度并提示异常，保留恢复记录 |
| 两名员工误用同一请求编号 | 一个成功、一个冲突；后者不能读取前者回执 |
| 拆桌后核对原请求及目标桌同券 | 原员工恢复原回执；另一员工明确确认目标桌后复用同一绑定；总共一张券、一次绑定 |
| 部分退款及全额退款后再消费 | 原报价失效，退款不恢复已使用优惠额度，两桌仍共用原绑定和客组上限 |
| 拆桌两边同时使用有效报价 | 仅一个成功，另一报价须重新计算；不超客组上限 |
| 已消费后尝试撤销绑定 | 拒绝通过撤销恢复额度 |
| 三个并发佣金核对 | 返回一致的净实收基数和佣金，不重复入账 |

退款用例均采用 100 元商品、减免 10%、客组累计上限 25 元，首单实收 90 元：

- 退 45 元：后续优惠依次为 5 元、10 元；最终净实收 `90−45+95+90=230` 元，佣金 23 元。
- 退 90 元：已用 10 元额度仍占用，不能立即重复取得首笔优惠；先新增一笔普通消费 100 元，再获优惠 10 元、5 元。最终净实收 `90−90+100+90+95=285` 元，佣金 28.50 元。
- 两种情形最终累计优惠均为 25 元。额度耗尽后，小程序清除失效报价并要求重新核对，网页不显示旧优惠应付金额。

以上为现有累计计价规则的验证，未改变后台优惠或退款规则。本轮修改员工网页交互并补充测试。退款后不能立即重复取得首笔优惠，是防止循环退款恢复额度的既有行为，不应向员工宣传为“退款即可重新用券”。
