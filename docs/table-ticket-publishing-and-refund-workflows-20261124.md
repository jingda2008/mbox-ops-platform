# 整桌门票上架与退票简化开发方案

状态为本地开发及隔离验收。下文列出产品目标和开发前基线。门店正式环境及微信真机仍待验收。

## 一、上架从商品管理开始

员工在商品管理点 **门票上架**，入口在「新增商品」旁。活动运营也可打开同一张场次草稿。菜单、活动运营和复核待办共用场次及票档编号。无需在两个模块分别建商品。已存在的场次直接加票档。

| 谁、何时 | 页面显示与操作 | 完成后 |
| --- | --- | --- |
| 门店负责人，首次配置或规则变化 | 核实门店名称、地点、客服电话、举办及售票主体、入场说明、常用退票规则。保存为本店可选的规则版本 | 新场次可引用。客服与退票条款分栏，拒绝仅以电话号码充当退票规则 |
| 员工，每场一次 | 选已有场次、复制往期或新建。新建时填写演出名称、演出日期及起止时间，确认本场实际演出资料、地点及适用公示。共用封面可换 | 跨午夜明确显示结束日期，如“周五 20:00 至周六 00:30”。复用时必须确认本场事实和仍适用的规则 |
| 员工，每个票档一行 | 选桌区，编辑票名、每桌价格、每张赠分。票名可按桌区预填；零赠分明确填 0。可点“添加桌区”继续 | 一场只填一次资料。例：中间 A 区／A 区整桌票／500 元／550 分。价格与积分独立编辑 |
| 员工，核对并送审 | 同页看到顾客端商品卡、详情主要信息、展示位置、可见及开售时间、各桌区当前可售桌数。点“提交复核” | 保存整份草稿和复核任务；返回原草稿即可看到进度。草稿不出现在顾客菜单 |
| 有发布权限的复核人 | 从现有待办打开原草稿，对照上一版的场次、桌区、价格、赠分和规则变更。可退回原稿并注明哪一项需改 | 确认后发布本次勾选的票档。返回“已在点单 → 门票展示”或实际定时、隐藏、停售状态，并可预览原票档 |

**默认与选填。** 默认菜单分类为“门票”，默认关闭“同时在超嗨推荐”。选用其他分类、封面、定时可见与售卖都放在“更多设置”。展示和购买分别判断，受分类和票档两个层级的有效时段控制；显示最终结果及限制来源。未设定时按现有场次可售条件处理，结束即退出公开售票。顾客可以先看详情，购买时识别购票会员。每桌一张票、逐票赠分、积分有效一年、门票不能用积分购买、付款后安排具体桌号均由系统统一处理。

**容量与复制。** 每桌不限购票人数与场地核准总容量是两个约束。场次容量有经核实的适用值时可带入；没有就明确提示本场待核实，禁止写虚构上限。可售桌数从当前桌区、时段与订桌占用计算，发布时不指定、不锁具体桌。复制往期只复制为未发布草稿，重新选择日期并核对时间、容量和本场公示。原订单、桌号、占用、审批、已售数以及绝对的上下架日期全部排除。已有同场同桌区票档时定位原档，修改生成新版本，避免重复开售。

**上架与退票共用的规则。** 常用退票规则应支持可计算的时段、时区和边界、费用金额或费率、计算基数、舍入方式、门店原因例外及已用积分抵菜后的处理方式。由同一版本生成顾客公示和收银核算依据，展示“如需退票，请联系门店，由门店按购票时公示的规则办理”。特殊条款可保留原文并标为人工核定。新成交保存条款版本、原文、原票档及实际金额，区分购票时公示的联系信息与当前可接通的门店电话。新版本只影响后续成交。旧票只有文字时，收银展示原文与可退上限，交有权限的人核定，不能拿今天的模板推定历史约定。

**服务端约束。** 沿用场次、票档、公示版本、操作者权限及现有独立复核要求。提交草稿保存后才派发复核待办。审批打开或发布时重新校验版本；经办人不能借菜单快捷入口扩大权限。一次发布多档时，对所选版本在同一事务中校验并生效；如有冲突则指出具体行，保留草稿。重试返回原结果。回读正式版本后才报告发布成功。下架只关新销售，保留已售票履约与售后。

## 二、退票从收银原单开始

1. **顾客联系门店。** 票档显示联系方式及规则，单张票支持拨号、复制场次、票名、购票单号、第几张／共几张及票号。点击只展示资料。新旧客户端的整桌票自助申请、撤回均由服务端关闭并返回联系方式；同样检查未出票订单及通用活动退款入口。存量案由门店接续，客户仍能看进度、确认明细，普通活动维持原流程。
2. **原单定位。** 收银历史账单点“退款”、收银查票号或购票单号、接待原票“办理退票”及独立“查票”扫码均打开同一办理单。查票只读，入场核销是另一操作。原支付关联购票会员及每张票。单张直接进入，多张仅在尚未明确目标时选票；展示会员号、手机尾号、票档、票序、桌号、售后状态。有收款无出票时以原支付受理。
3. **只读预览。** 选择顾客或门店原因后展示预计原路退款、赠分原发／净用／到期／可收回、本票净抵菜款、顾客应补及门店承担。只处理原票积分批次与其实际承担的菜品金额，纳入退菜及混抵调整。现金退款同时受本票实付、原条款和原支付剩余可退额度约束，包括其他票在途退款。分摊可只填一方，差额自动带出；需要人工决定时保存依据。不得将打开页面等同建案、冻结或收款。
4. **按案推进。** 服务端按当前状态及岗位给出主操作。受理时锁原票并重算；旧预览失效时列出变化原单。零补款直接派给退款复核人。需补款则客户逐菜查看并确认，收银待办按原餐单打开应收，全部实收后自动进入复核待办。门店承担全部时按授权核定；已收顾客补款先跟踪对应原路退回。已有案显示当前负责人、等待事项和凭证。不明确的支付、在途退菜、积分归属争议指向对应原单或主管。
5. **回执与财务。** 退款复核和执行沿用审批额度与岗位分离。渠道在途显示处理中，成功回执后才显示已退款。票款、原菜品补款、补款退回和积分流水分别留凭证，按案号汇总。弱网重试与重复回调只推进同一有效案。补款变化使旧确认失效；已收后撤回先退原补款再按原规则处理票权及仍有效积分。换员工可从各自待办直接接续。待办可按案号、阶段及原餐单去重，失败可补派。

## 三、实现基线和验收

经代码核对，活动运营已有专用“新建门票场次”，已有票名／价格／赠分编辑、分类和定时设置，也已有草稿场次的独立复核、场次与单个票档合并发布、公示及票档版本检查。当前先建场次，再编辑票档；公示独立保存；票档按桌区切换逐档操作。保存草稿的实现不能作为已送达复核待办的证据。普通退款服务会拦截整桌门票，现有接待可代客建案；原积分批次冻结、逐菜分摊、顾客确认和原餐单收款已有对应代码。新工作集中于同一原单入口、规则版本、只读预览和岗位待办衔接。

| 验收 | 预期与凭证 |
| --- | --- |
| 首场和下周复用 | 首场从商品管理完成；下周只需改日期、核实本场差异。复核人从待办直接打开。留两次独立场次号、版本、操作录像 |
| 一场三个桌区，晚八点至次日零点半 | A 区 500 元赠 550 分可编辑，不必填具体桌号。预览清楚显示跨日。三档各自开售且共享真实订桌占用，草稿或无权自审不对客。核对商品卡、详情和后台读回 |
| 定时、并发、下架与历史 | 分类隐藏、尚未开售、售罄和场次结束均按有效配置展示；两人改价、重复发布与单档冲突不造成重复或半套上架；下架、改规则后已购票仍能按原约定办理 |
| 原单退票 | 一单三张只退第二张，含同尾号、零用分、部分用分、多票混抵、退菜、过期积分。查票扫码不增加到场数。两名员工重复操作关联同一案 |
| 全额用分与门店责任 | 500 元赠 550 分已用完，按适用条款分别验证“顾客补 500、门店承担 50”及“门店承担 550”。核对顾客确认、原餐单分单收款或已收补款返还、复核待办、原路退款、赠分与日报 |
| 新旧小程序与岗位接手 | 顾客可联系、查案和确认补款，不能从旧按钮绕过；门店人员无需进入活动运营重新查票。微信体验版及门店账号实测，资金结果保留支付与退款渠道回执 |

建议先实现兼容后台，包括存量票读取、店员受理、复核待办和新旧端分流；待门店路径可用后启用顾客入口切换。随后上传微信体验版，核对顾客端公示和两笔代表性售后。

## 四、本轮实现记录

商品管理可新建或复制场次，批量录入桌区草稿，复核人可在原场次核对所选票档并一次发布。服务端校验场次、公示和票档版本，同批有一档变化即回滚。公示限制客服电话冒充退票时段，并拦截付费门票沿用系统的免费活动默认说明。客户入口按菜单卡片配置展示。购票保存当时的客服及退票约定。

收银和接待可查同一原票，单票直接定位，多票按序号选择。原票能核对积分与菜品抵扣，顾客可复制票号、致电门店和确认补款。已确认的原餐单补款和收齐后的原票出现在岗位待办。文字条款下仍由授权人员核定原路退款金额。目前岗位待办能显示可复核案件，尚需完善全额收齐后直接生成审批请求。

11 月 24 日门店公开接口的三档退票时段及费用填写为客服电话。实际时段、费用和已用赠分处理依据由门店核实。已发布场次的原承诺受数据库保护。若需更正场次的退款摘要，须按更正后的资料另建场次，协调旧票档下架及既有购票人的售后；新旧场次都使用同一桌区库存。正式门店数据库、门店收退款和微信平台回执分别验收。
