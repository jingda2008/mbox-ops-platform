# M-Box陆家嘴店整晚实际经营模拟测试案例

文档版本：`1.0`
适用门店：`mbox-lujiazui / M-Box陆家嘴店`
模拟营业时段：`18:00-次日03:30`
用途：门店影子运行、上线前业务验收、员工培训考核和故障复测。

## 1. 执行与判定规则

1. 每个案例必须使用独立的`caseId`和幂等键，记录营业日、门店、桌台、桌次、预约、订单、支付、退款、权益、点歌或存酒对象ID。重复提交只能返回同一业务结果，不得生成第二条资金、库存或权益记录。
2. 系统审计事件、原POS/支付渠道流水、KDS出品记录和现场签字是验收证据；截图只能辅助定位，不能代替结构化审计或渠道回执。
3. 当前系统没有结构化入口的动作不得用自由备注冒充通过。人数变更、已入座换桌和满台排队必须分别使用预约修改、整桌换位和候补队列，不得线下重录。
4. 涉及支付、退款、赠送、折扣、存酒转赠/作废的案例必须使用两名不同员工完成申请与审批/复核；员工不得替审批人登录。
5. 顾客端只能看到本人预约、本桌桌账、本人权益和本人点歌；任何跨桌、跨会员或全店员工数据泄露均为`P0`并立即停止整晚测试。
6. 事件时间统一使用`Asia/Shanghai`。所有金额以分存储，文档展示为人民币元；所有手机号只使用脱敏测试号。

### 1.1 故障级别

| 级别 | 判定 | 当场动作 |
|---|---|---|
| P0 | 重复扣款、跨桌数据、越权资金操作、审计被覆盖、不可恢复数据丢失 | 陈经理停止相关入口；系统管理员保存日志和请求ID；周总决定停业回退；禁止手工改库 |
| P1 | 全店无法预约/开台/点单/收款、支付结果未知仍允许再次付款、退款或库存状态失真、责任链无人接管 | 切换原POS/纸单，冻结相关自动流程；陈经理和系统管理员共同建问题单，修复后从失败步骤复测 |
| P2 | 单桌、单设备、单档口、单通知失败，且有可审计人工兜底 | Mia安排替代设备或人工传单；保留原幂等键重试；当晚闭店前复核 |
| P3 | 文案、排序、非关键配置或培训动作不标准 | Mia记录员工、时间、桌台和截图，次日修正配置或培训后复测 |

## 3. 开店准备

### OPN-01 系统、设备和外部通道开店检查

- **前置：** 当日发布版本已部署；数据库已完成迁移；门店PC、两台平板、门迎手机、取送手机、吧台/厨房KDS和物理POS已编号；前一日备份可读取。
- **参与岗位：** 系统管理员主执行，陈经理复核，小薇验证POS，小青与韩师傅验证KDS。
- **步骤：**
  1. 系统管理员记录应用版本、配置版本和数据库迁移号，检查`/api/live`与`/api/ready`均为200。
  2. 分别用系统管理员、陈经理、小薇账号登录，确认签名会话、门店归属和权限菜单；尝试访问`/api/dev/*`必须被拒绝。
  3. 陈经理从`L04`发起一条测试服务并取消；小薇创建测试支付意图但不确认成功；小青、韩师傅确认各自KDS可见对应测试单后取消。
  4. 断开一台平板网络，确认订单、支付、预约、库存写入被禁止；恢复后服务动作只能按原幂等键重放一次。
- **预期：** 健康检查、鉴权、KDS路由、弱网限制全部符合；测试数据标记为演练并在开店前关闭，不污染正式桌账和库存。
- **审计证据：** 版本号、配置版本、健康检查时间、员工会话actorId、测试任务ID、支付意图ID及`closed/未成功`状态、设备编号、断网/恢复时间和请求ID。
- **失败升级：** 健康或鉴权失败为P1；开发路由可访问、跨岗位越权或离线资金写入成功为P0，立即停止开店。

### OPN-02 排班、主责链、库存与经营权限发布

- **前置：** 12名员工名单、五个区域、桌台状态、菜单、档口、演出排班和当日授权单已由门店提供。
- **参与岗位：** 陈经理主执行；Mia、小薇、小青、韩师傅逐项确认；周总批准经营权限。
- **步骤：**
  1. 陈经理核对12人19:00至03:00班次，发布小林主责休闲/散客/卡座、小吴主责互动/社交、阿杰候补休闲/互动、Mia为全店领班。
  2. 逐桌确认容量、`available/reserved/occupied/paused`状态、主责和候补；逐档口确认SKU、售价、成本、库存和出品SLA。
  3. 小薇核对收银设备、退款联系人和前一日未对账项；小青、韩师傅确认原料低库存；Mia确认服务剧本和SLA版本。
  4. 周总批准当晚赠送/折扣权限：小林单项不超过88元且限酒水，Mia不超过300元，陈经理不超过1000元；记录生效和失效时间。
- **预期：** 每张营业桌都有唯一主责和至少一个有效候补；员工角色、班次、区域、档口技能匹配；权限过期后自动拒绝。
- **审计证据：** 班次ID、桌台主责/候补变更记录、配置发布事件、商品配置版本、库存初盘、授权ID、双审批人、理由和有效期。
- **失败升级：** 缺主责/候补、库存不明或授权无审批不得开台，按P1处理；单个设备或人员资料错误为P2，修正并复核后继续。

- **前置：** 测试顾客Amy已登录本人手机；预约配置启用微信来源、生日场景和商务卡座区；测试订金500元；支付通道返回可验证流水。
- **参与岗位：** 顾客、安安、小薇、陈经理。
- **步骤：**
  1. Amy手机提交21:00、6人、商务卡座、生日场景和脱敏联系方式，连续点击提交两次。
  2. 系统仅生成一条`requested`预约和一个预约ID，订金状态为`payment_required`。
  3. 小薇登记支付意图；仅在渠道确认500元到账后录入确认流水。
  4. 安安核对姓名、时间、人数和偏好；陈经理确认预约并预留`B02`，顾客手机查看状态。
- **预期：** 重复点击不重复预约或订金；未收到渠道确认前不能将预约改为`confirmed`；顾客只能看到本人预约；生日脚本被保留到接待台账。
- **审计证据：** reservationId、原幂等键、`reservation.requested.v1`、订金意图与确认流水、`reservation.deposit_confirmed.v1`、`reservation.confirmed.v1`、配置版本和通知Outbox结果。
- **失败升级：** 重复订金或未到账即确认预约为P0；通知失败但预约状态正确为P2，人工联系并保留失败回执。

### RSV-02 非法输入、重复支付回调和取消预约

- **前置：** 准备人数0、人数101、停用来源、错误金额回调和一条已确认含订金预约。
- **参与岗位：** 顾客、安安、小薇、陈经理。
- **步骤：**
  1. 分别提交人数0、101和停用来源，确认服务端拒绝且不生成预约。
  2. 对正常预约发送金额499元的订金确认，必须拒绝；再发送500元成功回调两次，只能确认一次。
  3. 顾客在规则允许时取消；安安记录真实原因，系统把已确认订金置为`refund_required`。
  4. 小薇不得把“已申请退款”直接标成“已退款”；按`REF-02`完成渠道退款。
- **预期：** 输入约束和金额/币种校验在服务端生效；重复回调幂等；取消原因、状态和待退款责任清晰。
- **审计证据：** 被拒请求的请求ID和错误码、唯一预约ID、支付回调原文摘要、`reservation.cancelled.v1`、`reservation.deposit_refund_required.v1`。
- **失败升级：** 错误金额可确认、重复预约或重复到账为P0；仅前端阻止而服务端接受为P1。

## 5. 不同到店情况

### ARR-01 准时到店并入座

- **前置：** `RSV-01`预约时间21:00，`B02`保持预留，6人于20:50至21:10内到齐。
- **参与岗位：** 安安、小林、Mia、陈经理。
- **步骤：** 安安核对预约ID和脱敏联系方式，标记`arrived`；现场确认6人后通知小林；小林检查`B02`清台与桌码；安安建立唯一桌次并绑定预约，完成`seated`。
- **预期：** 状态按`confirmed -> arrived -> seated`单向变化；`B02`变为占用，人数为6，预约与桌次一对一；小林成为主责，Mia可见接待完成。
- **审计证据：** `reservation.arrived.v1`、`reservation.seated.v1`、tableId/tableCode/tableSessionId、到店/入座时间、操作者ID和桌台状态变化。
- **失败升级：** 绑定已被其他预约使用的桌次或出现两条开放桌次为P0；主责未收到接待通知为P2。

### ARR-02 提前到店但预留桌未释放

- **前置：** 预约21:00，客人20:15到店；`B02`仍在清台或前一桌未结清，`L04`可作临时候客位。
- **参与岗位：** 安安、小林、Mia。
- **步骤：** 安安核验预约并记录实际到店，不提前占用`B02`；Mia确认预计等待时间；小林引导至`L04`候客并建立临时服务责任，不把消费误挂`B02`；`B02`可用后再正式入座。
- **预期：** 到店时间真实；正式桌次只在桌台可用时创建；临时消费若发生必须绑定临时桌次并在换桌时可追溯，不能跨桌丢单。
- **审计证据：** 到店时间、等待通知、临时桌次ID、正式桌次ID、所有订单归属和换桌关联记录。
- **失败升级：** 若系统不能建立可追溯的临时桌与正式桌关系，判P1产品缺口，不允许靠备注或口头转账继续验收。

### ARR-03 迟到但仍在保留时限内

- **前置：** 预约21:00，门店保留规则已由经理发布；顾客20:55手机告知21:20到店，`B02`尚未释放。

- **审计证据：** 顾客联系引用、保留决定actorId/reason/timestamp、`arrived/seated`事件、通知回执。
- **失败升级：** 迟到联系或保留决定未进入结构化字段与审计为P2；重复建立预约或误触发订金退款为P1。

### ARR-04 超过保留时限后到店

- **前置：** 预约21:00，超过已发布保留时限且桌台已按规则释放，顾客22:00才到店；现场还有候补队列。
- **参与岗位：** 安安、Mia、陈经理、顾客。
- **步骤：** 安安不得直接恢复原桌承诺；陈经理确认原预约应标记迟到释放还是`no_show`；向顾客说明订金规则；如仍需入场，按新现场候补记录入队并保留与原预约的关联。
- **预期：** 已释放桌台不会被旧预约强占；原预约、订金处置和新候补是两个可区分对象；排序不能绕过更早候补客。
- **审计证据：** 原预约状态、桌台释放时间/操作者、规则版本、新候补ID、队列序号和顾客告知时间。
- **失败升级：** 无结构化桌台释放或候补关联为P1产品缺口；插队导致已承诺桌台冲突为P1运营事故。

### ARR-05 爽约与订金处置

- **前置：** 已确认预约21:00，达到门店规定的爽约判定时间；至少两次联系无回应；订金500元已到账。
