# M-BOX 扫码点单、微信身份、会员、积分与授权完整需求 V1.0

文档状态：后续开发基线，待经营参数验证，不代表已开发、已上线或已部署  
版本：V1.0  
日期：2026-08-16  
适用范围：M-BOX 顾客微信小程序、规范化服务端、员工经营端、数据库与消息渠道  

## 1. 文档目的

本需求把以下事项合并成一条可实施、可配置、可验收的业务主链：

1. 顾客扫描桌码后进入微信小程序并安全绑定当前桌次。
2. 小程序建立最小必要的微信身份，但不强迫顾客提供头像、昵称、手机号或营销授权。
3. 以不打断点单的方式邀请顾客一键成为会员；拒绝入会仍可正常浏览、点单、支付和呼叫服务。
4. 将短信营销、微信服务通知、活动推广、头像昵称、手机号和活动报名拆成独立授权或动作。
5. 建立可配置的消费积分、成长值、银卡/金卡等级、商品与权益兑换体系。
6. 消费成功后自动积分；自动积分异常先由系统重试和对账，仍失败时由店长申请、管理员审批补发。
7. 允许授权人员随时编辑草稿、预览和排期发布经营规则，但禁止规则变化追溯损害已发生交易和已获得权益。
8. 为后续替换现有小程序页面提供稳定的业务状态、接口和验收边界，避免只换视觉后破坏点单、支付或会员逻辑。

## 2. 先纠正的前提与结论

### 2.1 “使用微信身份”不等于“获取微信个人资料”

小程序进入后可以使用 `wx.login` 获取一次性登录凭证，并由服务端向微信核验后建立最小身份。该过程不应自动取得或推断顾客的头像、昵称、手机号、营销偏好或会员同意。

必须区分：

| 能力 | 是否点单必需 | 是否需要顾客单独动作 | 说明 |
| --- | --- | --- | --- |
| 最小微信登录身份 | 正式线上身份链需要 | 通常不弹出头像/手机号授权 | 仅用于建立安全主体、订单归属和本人数据隔离 |
| 桌码与桌次绑定 | 到店正式点单必需 | 顾客扫码 | 必须校验门店、桌台、令牌版本、有效期和开台状态 |
| 加入会员 | 否 | 是 | 一键加入，但必须明确同意会员规则；拒绝不影响点单 |
| 头像、昵称 | 否 | 是 | 仅用于个性化展示；可跳过、可后补、可修改 |
| 手机号 | 否 | 是 | 用于已有会员找回、账户安全或明确选择的短信触达 |
| 微信服务通知 | 否 | 是 | 需按微信平台能力单独发起订阅授权 |
| 短信营销 | 否 | 是 | 必须已有合法手机号且明确同意营销用途 |
| 活动推广 | 否 | 是 | 只表示推广目的偏好，实际发送仍需对应渠道可用且获授权 |
| 参与某个活动 | 否 | 每次活动单独确认 | 不能因为入会或营销授权而自动报名活动 |

### 2.2 不能一次获得全部授权

可以把各项选择组织为一次自然、渐进的引导，但不得使用一个“全部同意”按钮同时取得短信营销、微信通知、活动推广、头像昵称、手机号和未来活动报名。所有非必要选项默认关闭，顾客可分别同意、拒绝和撤回。

### 2.3 积分体系不是现有页面的简单补充

当前代码已有会员账户、积分余额、不可变流水基础和人工调整入口，但尚不能据此认定以下闭环已完成：

- 真实微信身份与规范化会员的一致绑定；
- 付款成功后的自动积分；
- 退款后的自动冲回；
- 可消费积分与等级成长值的分账；
- 规则版本、有效期、兑换目录和库存履约；
- 店长申请、管理员审批的异常补积分；
- 等级升级、保级、降级和宽限期；
- 积分兑换商品或权益的完整核销、取消与恢复。

因此本文件将这些内容定义为新增开发需求，而不是把“已有积分字段”写成“积分体系已完成”。

### 2.4 积分不冲抵现金

本期规则明确：

- 不提供“100积分抵1元”等现金换算；
- 不允许同一商品使用“积分加现金”拆分支付；
- 不允许积分提现、转账、购买储值或兑换现金券、无门槛金额券；
- 允许同一订单同时包含现金购买商品和一件完全由积分兑换的独立商品，但两个商品行必须分别计价、分别授权，不能互相抵扣；
- 积分只能兑换目录中明确列出的完整商品、服务、活动资格或非现金权益。

## 4. 核心产品原则

1. **先完成到店任务，再谈会员经营。** 扫码、看菜单、加购、下单和支付是主路径，入会提示不得遮挡或延迟主路径。
2. **最小身份不等于营销画像。** 只为安全主体和本人数据隔离所需的身份信息不得被自动扩展为营销授权。
3. **拒绝可继续。** 顾客拒绝入会、手机号、头像昵称、通知或推广后，仍可正常点单。
4. **授权逐项、默认关闭。** 不预勾选、不捆绑、不把“继续使用”解释成同意营销。
5. **规则可配置但不任意回写历史。** 新规则只影响生效后的新业务事实；已获得积分、已确认权益和已发生交易按锁定版本处理。
6. **金额、资格、等级、时限和权限必须强类型化。** JSONB 只保留图片、展示文案等灵活内容，不作为金额、资格、状态、时限、排序或授权的唯一运行依据。
7. **所有积分变化可解释、可对账、不可静默修改。** 每一笔增加、扣减、过期、冲回、补发必须有来源、规则版本、余额结果和审计记录。
8. **资金和履约优先安全失败。** 未核实付款不得积分；未核实积分兑换不得出品；未知支付结果不得重复奖励或释放应保留的状态。
9. **经营灵活性由版本化配置实现。** 不是在代码中写死阈值，也不是让任何人直接改生产数据。

## 5. 角色与权限

### 5.1 顾客角色

| 角色状态 | 可用能力 |
| --- | --- |
| 到店匿名桌次顾客 | 浏览菜单、加购、提交桌次点单、查看本桌状态、呼叫服务；不能查看会员历史 |
| 已验证微信顾客 | 上述能力，加上本人订单连续性、本人预约/活动状态和安全会话恢复 |
| 已入会顾客 | 上述能力，加上积分、成长值、等级、兑换目录、权益和偏好 |
| 已找回历史会员 | 合并验证后的历史积分、等级和权益；合并前不得展示疑似他人的数据 |

### 5.2 员工与经营角色

建议新增或拆分以下权限，权限名称可按现有规范化权限目录调整，但职责必须保持：

| 权限代码 | 用途 | 建议角色 |
| --- | --- | --- |
| `loyalty.policy.view` | 查看积分和等级规则 | 店长、管理员、财务 |
| `loyalty.policy.manage` | 创建、编辑规则草稿 | 店长或会员运营 |
| `loyalty.policy.approve` | 审批重大规则 | 管理员或财务复核人 |

### 5.3 权限硬约束

- 服务端必须二次校验权限，前端隐藏按钮不构成授权。
- 申请人不得审批自己的补积分申请。
- 规则创建人不得独立批准并发布自己创建的重大经营规则。
- 任何积分直接调整必须填写原因、来源和关联单据；普通“漏积分”不得绕过审批走自由调整。
- 顾客信息按本人、责任桌、门店和岗位范围隔离；不能因为拥有会员运营入口就导出全量手机号。

## 6. 桌码、微信身份与点单端到端流程

### 6.1 目标流程

```text
扫描桌面小程序码
  -> 微信打开固定小程序路由并携带短 scene
  -> 小程序立即发起最小微信登录
  -> 服务端用一次性 code 向微信核验并建立短期顾客会话
  -> 服务端校验门店、桌台、桌码版本、令牌、开台状态
  -> 已开台：显示正式菜单
  -> 未开台：显示等待开台页并安全轮询
  -> 无效/过期/跨店桌码：阻止正式点单并提示重新扫码或呼叫员工
  -> 菜单内以轻量卡片邀请加入会员
  -> 顾客加入或跳过后继续原点单位置
```

### 6.2 桌码要求

- 正式桌码必须是微信可识别的小程序码或经确认可可靠唤起小程序的合法入口，不以普通网页二维码替代验收。
- `scene` 只携带短引用或短令牌，不放客户资料、长期秘密、支付密钥、AppSecret 或可长期复用的全店凭证。
- 服务端保存桌码版本、签发时间、失效时间、轮换原因和状态。
- 换码后旧码必须失效；已建立的有效桌次会话是否保留，由明确策略决定，不能靠客户端缓存猜测。
- 同一桌码在未开台状态只进入等待页，不允许提前建立可下单的活动桌次。
- 顾客从微信“最近使用”进入且没有有效桌码时，只能浏览来店前内容；正式菜单可预览，但下单按钮必须要求扫码并校验已开台。

### 6.3 最小微信身份要求

- 小程序端调用 `wx.login`，把一次性 `code` 发送至 M-BOX 服务端。
- 服务端使用配置在服务端的 AppID/AppSecret 或合规平台适配器完成 code 交换。
- 客户端不得提交或指定可信 `openid`、`unionid`、会员 ID 或身份等级。
- 服务端只返回短期访问会话和公开顾客标识；不向小程序返回 AppSecret、会话密钥或身份加密密钥。
- 同一微信主体重进时应恢复同一规范化顾客关系；匿名桌次行为只有在安全匹配后才可合并。
- 身份冲突时不得自动覆盖既有会员，必须进入“找回/合并待确认”。

### 6.4 身份失败时的降级

| 失败 | 顾客体验 | 系统要求 |
| --- | --- | --- |
| 微信 code 临时获取失败 | 提示重试；菜单可浏览 | 不伪造登录成功 |
| M-BOX 身份服务短时不可用 | 若签名桌次仍有效，可保留桌次浏览、加购和现场服务；正式下单是否允许按安全策略配置 | 不把随机客户端值当作微信身份 |
| 在线支付需要微信主体但身份未建立 | 明确提示线上支付暂不可用，提供已配置的员工协助收款或其他合法渠道 | 不模拟支付成功，不重复建单 |
| 桌码无效或跨店 | 阻止正式点单 | 清除错误桌次缓存并要求重新扫码 |

## 7. 会员加入体验

### 7.1 展示时机

会员邀请必须满足：

- 已识别有效桌码且菜单已可用；
- 最小微信身份已建立，或系统明确支持先匿名入会意向、后安全绑定；
- 当前顾客不是已识别会员；
- 本桌本次访问尚未点击“暂不加入”；
- 不覆盖购物车、不遮挡首屏主操作、不弹全屏强制框。

建议位置：菜单标题与分类导航之间或首个商品列表之后的轻量卡片。若首屏信息已经拥挤，应放在第一屏下沿，不占据超过一个普通商品卡的高度。

### 7.2 推荐文案

标题：`加入 M-BOX 会员`  
说明：`消费自动积分，查看门店赠送与活动权益。手机号、头像和通知都可稍后选择。`  
主按钮：`一键加入会员`  
次按钮：`暂不加入`  
文字入口：`已有会员，找回权益`  
规则提示：`点击加入即表示同意《会员规则》和《隐私说明》；不会自动开启短信或活动通知。`

### 7.3 一键入会

`MEM-001` 顾客点击“一键加入会员”后，服务端基于已验证微信主体创建或返回唯一会员账户。  
`MEM-002` 新会员不得以手机号、头像、昵称作为入会前置条件。  
`MEM-003` 入会命令必须幂等，重复点击或网络重试不能创建多个会员。  
`MEM-004` 入会成功后原购物车、菜单分类、滚动位置和桌次状态保持不变。  
`MEM-005` 成功反馈使用轻提示，并在“我的”页显示会员号、积分、成长值、等级和权益。  
`MEM-006` 入会不自动勾选任何营销、通知或活动报名。  
`MEM-007` 顾客点击“暂不加入”后，本次桌次不再重复提醒；跨桌次提醒冷却期可配置，建议默认 30 天。  
`MEM-008` 顾客拒绝或关闭会员邀请，不得降低菜单、价格、库存、点单、支付或服务能力。  

### 7.4 已有会员找回

- 已经与当前微信主体绑定的会员直接恢复，不再索要手机号。
- 当前微信未绑定、但顾客声称已有会员时，可通过手机号验证、原会员码或人工受控流程找回。
- 获取手机号必须由顾客点击专用按钮，不能因点击“找回权益”直接视为授权。
- 发现一个手机号对应多个候选会员时，不自动合并；显示安全提示并转人工核验。
- 合并必须保留来源账户、积分流水、权益使用历史和审批记录，不能只把余额相加后删除旧事实。
- 合并完成前，不展示任何候选账户的完整积分、订单或隐私信息。

## 8. 授权与通知需求

### 8.1 授权模型

每项授权至少保存：

- `customer_id`；
- `purpose_code`：用途；
- `channel_code`：渠道；
- `status`：未询问、已同意、已拒绝、已撤回、平台失效；
- `policy_version_id`；
- `notice_version_id`；
- `granted_at`、`withdrawn_at`、`expires_at`；
- `source`：小程序、员工协助、客服更正；
- 微信平台返回的模板/授权结果引用；
- 审计操作者和请求幂等键。

影响营销、通知和隐私的字段不得只存在自由 JSON 键中。平台原始回执可作为只读 JSONB 快照保留，但运行决策必须读取强类型状态。

### 8.2 分项要求

| ID | 项目 | 默认 | 触发方式 | 拒绝后的影响 | 撤回方式 |
| --- | --- | --- | --- | --- | --- |
| `CNS-001` | 最小微信登录 | 按必要身份链执行 | 小程序启动后由系统建立 | 身份链失败按 6.4 降级 | 退出登录/撤销授权后清理可撤销会话 |
| `CNS-002` | 加入会员 | 未加入 | 顾客点击“一键加入会员” | 不影响点单 | 申请关闭会员；依法保留必要交易记录 |
| `CNS-003` | 获取手机号 | 未授权 | 找回账户、安全验证或顾客主动补充 | 不影响点单与新会员加入 | 删除/更换手机号及撤销非必要用途 |
| `CNS-004` | 获取头像昵称 | 未授权 | “完善资料”页面主动操作 | 使用默认头像和称呼 | 删除或替换 |
| `CNS-005` | 微信服务通知 | 未订阅 | 在具体通知价值出现时调用平台授权 | 页面内状态仍可查询 | 在“消息与授权”页关闭并遵循微信平台状态 |
| `CNS-006` | 短信服务通知 | 未启用 | 有手机号后针对必要服务另行说明 | 改用页面内查询或其他已授权渠道 | 随时关闭 |
| `CNS-007` | 短信营销 | 未同意 | “接收优惠和活动短信”独立开关 | 不影响任何交易服务 | 页面关闭、短信退订、客服撤回 |
| `CNS-008` | 活动推广目的 | 未同意 | 活动偏好页独立选择 | 仍可主动浏览和报名活动 | 随时关闭 |
| `CNS-009` | 单个活动报名 | 未报名 | 活动详情页确认人数、规则、费用和联系人 | 不影响其他活动或点单 | 按活动取消/退款规则处理 |

### 8.3 发送门禁

发送活动推广必须同时满足：

1. 顾客同意“活动推广”用途；
2. 对应发送渠道当前可用且已获授权；
3. 活动符合顾客可见范围和门店范围；
4. 未命中退订、免打扰、频控或黑名单；
5. 文案和目标链接属于已发布版本；
6. 留存发送请求、平台回执、失败原因和退订结果。

仅获得手机号不等于同意短信营销；仅加入会员不等于同意微信通知；仅同意活动推广也不等于自动报名。

### 8.4 频率建议

以下仅作为试点默认值，后台可配置且需受上限保护：

- 营销短信：建议每位顾客每 7 天最多 1 条、每 30 天最多 4 条；
- 活动推广：建议每位顾客每 7 天最多 2 次跨渠道触达；
- 服务通知不计入营销频控，但必须与真实订单、预约、活动或权益状态直接相关；
- 夜间安静时段建议 21:30 至次日 09:00 不发送营销信息；具体时间按合规和经营确认。

## 9. 积分与成长值双账户

### 9.1 定义

| 账户 | 用途 | 可否消费 | 是否影响等级 | 退款处理 |
| --- | --- | --- | --- | --- |
| 可用积分 | 兑换指定商品、服务、活动资格或权益 | 可以 | 不直接决定等级 | 按原交易冲回对应积分 |
| 成长值 | 计算普通、银卡、金卡等级 | 不可以 | 是 | 按原交易扣回对应成长值 |

不得继续使用单一 `lifetime_points` 同时承担“可兑换余额”和“等级计算”两种含义。

### 9.2 计分基础

默认计分基数为已核实付款中的“符合规则的净实付金额”，以分为计算单位。建议公式：

```text
符合规则的净实付金额
= 已核实的商品/服务实付金额
- 已核实退款金额
- 不计积分的费用与商品金额
```

默认不计入：

- 赠送商品、零价商品和用积分完全兑换的商品；
- 储值充值、礼品卡购买、可退押金和保证金；
- 小费、运费、包装费或明确配置为不计积分的附加费；
- 未付款、付款未知、已关闭、已撤销或模拟成功的交易；
- 被经营规则明确排除且已在顾客规则中说明的商品或渠道。

是否将活动报名费、订金和员工协助付款计入，可按商品/活动/渠道配置，但必须有明确规则版本，不得从自由文本或快照临时推断。

### 9.3 推荐试点默认值

下表为开发和影子测算的建议初值，不是未经验证即可上线的最终经营政策：

| 参数 | 建议默认值 | 可配置范围/约束 |
| --- | --- | --- |
| 基础可用积分比例 | 每实付 1 元获得 1 积分 | 正数有理比例；以分计算后统一取整 |
| 基础成长值比例 | 每实付 1 元获得 1 成长值 | 与可用积分分开配置 |
| 普通会员积分倍率 | 1.0 倍 | 仅作用于可用积分 |
| 银卡积分倍率 | 1.1 倍 | 不放大成长值，避免等级循环加速 |
| 金卡积分倍率 | 1.2 倍 | 不放大成长值 |
| 可用积分有效期 | 18 个月 | 建议允许 12–24 个月；变更不追溯缩短已获得批次 |
| 兑换扣减顺序 | 先到期先使用 | 强制，不建议配置为后到期先用 |
| 小数处理 | 每笔按分计算，最终向下取整 | 必须固定并在规则中说明 |
| 退款冲回 | 按原订单行和原规则版本 | 强制，不能按退款时的新规则重算 |

### 9.4 促销积分

- 活动可设置额外积分，但必须是独立促销规则版本，不覆盖基础积分规则。
- 促销规则需定义适用门店、商品、会员等级、时间、倍率或固定值、单人上限、总预算和是否可叠加。
- 同一订单命中多个促销时，叠加顺序必须确定；默认仅取最高一项，除非规则显式允许叠加。
- 活动奖励不得在顾客仅报名时自动发放；应在付款、签到或活动完成等明确业务状态后发放。

## 10. 等级体系

### 10.1 等级定义

本期公开等级为：

1. 普通会员；
2. 银卡会员；
3. 金卡会员。

现有代码中的黑卡不作为本期公开等级，默认禁用、不可自动升级、不可由普通运营人员手工分配。未来如启用，必须另立版本和审批。

### 10.2 推荐试点门槛

| 等级 | 建议升级条件 | 建议保级条件 | 有效期 |
| --- | --- | --- | --- |
| 普通会员 | 成功入会 | 无 | 持续有效，除非账户关闭 |
| 银卡 | 滚动 12 个月成长值达到 3,000 | 上一等级周期成长值达到 2,000 | 12 个月 |
| 金卡 | 滚动 12 个月成长值达到 10,000 | 上一等级周期成长值达到 8,000 | 12 个月 |

建议设置 60 天降级宽限期。宽限期内显示“还差多少成长值可保级”，但不得夸大或制造虚假紧迫。

以上门槛必须先用真实历史消费分布测算。当前只有商品目录价格和成本基础，不能据此证明等级分布合理。上线前至少验证：

- 过去 12 个月可识别顾客的人均、P50、P75、P90、P95 实付；
- 顾客到店频次和跨桌/拼桌归属；
- 高额套餐是否由一人付款但多人消费；
- 退款、赠送、活动收费和员工代付占比；
- 预计银卡、金卡人数及权益成本。

### 10.3 升降级规则

- 每笔成长值写入后异步或事务内重算等级，结果必须幂等。
- 升级立即生效，并生成等级事件和权益发放事件。
- 退款导致成长值低于升级门槛时，不立即静默降级；按已发布规则判断是否撤销错误升级或进入周期复审。
- 周期复审使用当时已锁定的保级规则版本。
- 等级人工修改只用于经批准的纠错或经营例外，必须设置到期时间和原因，不能覆盖系统计算事实。
- 银卡和金卡的积分倍率只影响可用积分，不反向增加成长值。

## 11. 会员权益与积分兑换

### 11.1 权益类型

建议把以下权益强类型化：

- `gift_product`：完整商品赠送；
- `service_experience`：服务或体验；
- `activity_access`：活动报名资格或优先权；
- `reservation_priority`：预约优先资格；
- `customization`：明确的免费客制项；
- `birthday_benefit`：生日权益；
- `tier_benefit`：等级自动权益；
- `points_redemption`：使用积分兑换获得的权益。

“金额权益”“现金抵扣券”和积分现金换算默认不在本期范围内。现有 `credit` 或金额型权益如果历史上存在，只能作为受控历史兼容，不得由积分兑换目录新建。

### 11.2 兑换目录

每个可兑换项必须配置：

- 稳定兑换项 ID 和版本；
- 展示名称、图片、说明；
- 所需积分；
- 对应商品、服务、活动或权益定义；
- 适用门店、会员等级和时段；
- 总库存、每日库存、单会员日/月/生命周期上限；
- 是否需要到店、是否需要有效桌次；
- 是否需要员工确认交付；
- 有效期、取消规则和积分返还规则；
- 适用商品停用、缺货或产能不足时的替代与失败提示；
- 成本金额、预算归属和经营审批记录。

### 11.3 推荐兑换档位

以下以当前目录价格和账面成本作初步试点建议，实际采购成本、损耗、赠送占比和履约人工尚未核验：

| 所需积分 | 建议兑换范围 | 建议单份实际成本上限 |
| --- | --- | --- |
| 600 | 基础小食、无酒精饮品或指定低成本单品 | 18 元 |
| 900 | 指定小食或较高成本基础产品 | 30 元 |
| 1,500 | 指定精品单品或轻体验权益 | 45 元 |
| 2,500 | 指定活动资格或体验型权益 | 75 元 |

建议初始限制每位会员每天最多 1 次实物兑换、每 30 天最多 4 次，单个兑换项还可设置更严格上限。目标权益实际成本建议控制在会员净实付收入的 2%–3%，超过阈值触发预警而不是自动停掉已确认权益。

### 11.4 兑换流程

```text
顾客查看兑换详情
  -> 系统检查会员、积分、等级、门店、时段、库存、产能和个人限额
  -> 顾客明确确认“使用 N 积分兑换完整商品/权益”
  -> 事务内锁定兑换项和积分批次
  -> 扣减或暂留积分并生成兑换记录
  -> 到店商品进入待交付；活动资格进入待确认/报名状态
  -> 员工按权限确认实际交付或系统确认履约
  -> 完成核销；失败/超时按规则释放并返还积分
```

### 11.5 订单与 KDS 边界

- 积分兑换商品应以独立订单行展示，标记 `pricing_kind=points_redemption`、现金金额为 0、积分数量明确。
- 同一现金商品不得拆成“积分 + 现金”。
- 兑换事务未确认前不得创建 KDS 出品任务。
- 积分已可靠扣减或暂留并生成履约授权后，才允许对应零价兑换商品进入 KDS。
- 若同一订单含现金商品和积分兑换商品，两类行分别满足付款门禁和兑换门禁后才能出品，避免现金未付商品因兑换行而提前制作。
- 顾客桌账和“我的权益”必须能看到兑换商品名称、使用积分、状态、有效期和交付结果。

### 11.6 取消与返还

- 未交付且允许取消：返还原积分批次；已过期批次是否给予短期恢复期由规则明确，建议恢复 7 天。
- 已交付：默认不可在线撤销；纠错走员工受控流程。
- 缺货或门店原因无法履约：全额返还积分，并可按独立服务补偿规则处理，不能自动换成现金。
- 活动取消：返还积分资格，并按活动退款规则处理现金部分；两种事实分别记账。

## 12. 自动积分主链

### 12.1 触发条件

只有同时满足以下条件才能自动积分：

1. 订单属于唯一规范化顾客或已确认会员；
2. 支付提供方回调或主动查询已确认付款成功；
3. 支付金额、币种、订单和门店一致；
4. 订单未被标记为模拟、测试、关闭或风险阻断；
5. 订单已锁定有效积分政策版本；
6. 同一支付/订单来源尚未发放过相同积分。

### 12.2 处理顺序

`PTS-001` 下单时记录积分政策版本，不立即发积分。  
`PTS-002` 付款结果为 `unknown` 时不发积分，也不判定失败。  
`PTS-003` 付款成功被权威确认后，根据锁定政策、订单行和净实付计算积分与成长值。  
`PTS-004` 在同一积分命令中写入可用积分流水、成长值流水、余额快照、等级评估事件和审计。  
`PTS-005` 使用支付 ID、订单 ID、奖励类型和规则版本建立唯一来源约束，重复回调只重放同一结果。  
`PTS-006` 积分发放成功后通过页面内消息展示；微信服务通知仅在顾客已授权且模板可用时发送。  
`PTS-007` 不能因为通知发送失败而回滚已经正确入账的积分。

### 12.3 退款冲回

- 退款必须在支付提供方权威确认成功后冲回，不能在店长仅提交退款申请时先扣积分。
- 全额退款冲回该订单已获得的全部基础积分、促销积分和成长值。
- 部分退款优先按退款订单行和原规则重算；没有行级数据时才按可解释的比例算法处理。
- 冲回不得把可用积分余额直接改为负数。若会员已经使用了待冲回积分，生成“待回收积分”或受控负债状态，并限制新的积分兑换；具体客户沟通和处理策略需经营审批。
- 退款被拒绝或失败时不冲回；退款状态未知时保持待确认。
- 退款成功和积分冲回必须可通过同一退款单追溯。

## 13. 自动积分失败与人工补发

### 13.1 原则

普通漏积分不是“店长自由填写积分”的场景。系统应先从原订单、原支付和锁定规则计算应发值，店长只能申请补发系统确认的差额；管理员复核后执行。

### 13.2 自动恢复

积分任务失败后按以下顺序处理：

1. 使用 outbox/可靠任务记录失败，不丢事件；
2. 按退避策略自动重试；
3. 定时对账扫描“已付款但无积分”或“积分与规则不一致”的订单；
4. 自动恢复成功则关闭异常，不需要人工补发；
5. 超过重试次数或发现数据冲突时进入人工异常队列。

### 13.3 店长申请、管理员审批

```text
异常生成
  -> 系统计算应发积分、已发积分和差额
  -> 店长查看原订单与支付证据
  -> 店长填写说明并提交补发申请
  -> 管理员复核付款、退款、规则版本和既有流水
  -> 审批通过后系统再次重验
  -> 事务内补发差额并关闭异常
  -> 若期间自动积分已恢复，则申请自动关闭为“无需补发”
```

### 13.4 申请字段

- 异常编号；
- 会员、顾客、门店；
- 原订单、支付和业务日期；
- 锁定积分政策版本；
- 应发可用积分、已发可用积分、申请差额；
- 应发成长值、已发成长值、申请差额；
- 系统失败代码、重试次数和最后失败时间；
- 店长说明和证据引用；
- 申请人、申请时间；
- 审批人、审批时间、审批意见；
- 执行结果、流水 ID 和幂等键。

### 13.5 状态机

| 状态 | 允许动作 |
| --- | --- |
| `detected` | 系统重试、对账人员查看 |
| `retrying` | 系统重试；未到人工门槛不可重复申请 |
| `requestable` | 店长提交申请 |
| `requested` | 管理员审批或驳回；申请人不可自批 |
| `approved` | 系统执行前再次重验 |
| `executed` | 已补发，禁止再次执行 |
| `rejected` | 记录原因，可在证据变化后重新申请新版本 |
| `auto_resolved` | 自动恢复成功，无需补发 |
| `cancelled` | 申请人撤回或订单不再符合条件 |

### 13.6 防重复与退款联动

- 数据库以原支付/订单、奖励类型和政策版本建立唯一约束。
- 执行审批前重新检查是否已有自动积分或其他补发流水。
- 自动重试与人工审批并发时，只能有一个成功写入；另一方获得幂等重放或“已解决”结果。
- 后续退款必须同时识别并冲回原始自动积分和人工补发差额。
- 关怀补偿、投诉补偿等“非订单积分”走独立 `loyalty.adjust.manual` 流程，不得伪装成漏积分补发。

## 14. 经营配置中心

### 14.1 可以随时配置的含义

“随时配置”应解释为：授权人员可随时创建和编辑草稿、预览影响、提交审批、设置立即或未来生效时间；不是任何人随时直接修改正在执行的生产规则。

### 14.2 配置对象

- 入会邀请展示位置、频率和冷却期；
- 基础积分、成长值比例和取整方式；
- 商品、渠道、费用和活动是否计分；
- 会员等级门槛、周期、保级和宽限期；
- 等级积分倍率；
- 积分有效期和到期提醒；
- 兑换目录、积分价格、库存、个人限额、履约方式；
- 促销积分预算、叠加和上限；
- 短信、微信通知和活动推广频控；
- 异常重试次数、人工申请门槛和处理时限；
- 功能开关：影子、试点、正式、暂停。

### 14.3 版本与发布

每个经营政策使用“规则头 + 不可变版本”：

- 草稿可以编辑；
- 提交审批后锁定内容；
- 已发布版本不可原位修改，只能创建新版本；
- 版本需记录创建人、审批人、发布人、原因、生效时间、失效时间和影响预览；
- 同门店同一规则的生效时间不得重叠；
- 订单、积分、兑换和等级事件保存实际使用的版本 ID；
- 进行中的交易继续使用已锁定版本；新版本只影响生效后的新业务事实。

### 14.4 重大变更双人复核

以下变更至少需要创建人与审批人分离：

- 降低或提高积分获得比例；
- 缩短积分有效期；
- 调整银卡/金卡升级或保级门槛；
- 修改兑换所需积分、成本上限或总预算；
- 开放高倍率促销；
- 开放金额型历史权益或其他接近现金的能力；
- 批量补发、扣减或清理积分；
- 关闭整个积分体系。

### 14.5 紧急暂停

- 最高管理权限可因重复积分、攻击、配置错误或对账异常紧急暂停新积分、新兑换或新营销发送。
- 暂停必须填写原因并审计，可设置自动复核时间。
- 暂停不删除历史积分，不撤销已确认权益，不改变已付款订单。
- 恢复前必须完成异常范围评估、重复流水检查和影响说明。

## 17. 页面与信息架构

### 17.1 首页

首页优先展示：

1. 当前到店/桌次状态；
2. 当日已发布演出或核心活动信息；
3. 点单主入口；
4. 服务与桌账状态；
5. 会员、权益和超嗨活动的次级发现入口。

无效的经营内部状态、版本号、模拟渠道、配置缺失等信息不得占据顾客首屏。技术错误转成简短可行动提示，详细诊断仅进入日志和员工端。

### 17.2 点单页

- 未扫码：可浏览菜单，但正式下单按钮显示“扫码后点单”；不动态删除固定导航入口。
- 已扫码未开台：显示等待页和呼叫员工，不展示可提交的正式菜单状态。
- 已开台：菜单、分类、购物车和演出摘要可用。
- 会员邀请为非阻断卡片，关闭后不反复出现。
- 顾客加入会员后保持购物车和位置，不回首页。
- 商品卡优先展示名称、关键内容、价格、适合人数和可售状态；无效内部标签不得占版面。

### 17.3 我的页面

已入会顾客展示：

- 等级卡：当前等级、成长值、距升级/保级差额和周期；
- 可用积分：余额、即将到期积分；
- 兑换入口：可兑换商品与权益；
- 我的权益与赠送：名称、来源、条件、有效期、状态；
- 最近积分和成长值明细；
- 预约、活动报名和付款/退款状态；
- 消息与授权；
- 个人资料和会员找回/账户管理。

非会员展示轻量入会说明，不展示手机号、头像、短信、活动推广等一整套授权开关来增加认知负担。

### 17.4 消息与授权页

按“服务消息”和“优惠活动”分组，逐项展示当前状态、用途、上次变更时间和关闭入口。不能只显示“已授权/未授权”而不说明渠道和目的。

### 17.5 积分详情页

- 可用积分与成长值分开展示；
- 明确“积分不可抵现金，只能兑换指定商品或权益”；
- 展示每笔来源、时间、增减、到期和余额；
- 退款冲回、过期和人工补发使用不同名称；
- 有异常时提供“查看处理进度”，不提供顾客自行填写任意补分数值。

## 18. 新页面替换交接要求

用户已经开发的新本机小程序页面可以替换现有视觉层，但必须提供以下任一可核验载体：

- 本地项目绝对路径；
- 独立 Git 分支和提交 SHA；
- 不含密钥的完整项目压缩包；
- Figma/设计稿只能作为视觉依据，不能代替可运行代码。

交接时必须附：

1. 页面路由清单；
2. 需要替换的 WXML、WXSS、JS、JSON 和组件；
3. 依赖包和构建方式；
4. API 契约和模拟数据说明；
5. 页面状态截图：加载、空态、错误、未扫码、等待开台、已开台、非会员、会员、积分不足、支付未知；
6. 是否改动 AppID、合法域名、支付配置或小程序入口网址。

替换原则：

- 保持已经对接小程序码的正式路径和入口稳定，除非完成兼容跳转和重新审核；
- 视觉层不得绕过现有服务端权限、桌码、库存、付款、KDS、退款和积分门禁；
- 不把新页面内的假数据、模拟支付或本地会员状态带入正式构建；
- 先在独立分支/工作树合并页面，再做接口映射和回归；
- 页面更漂亮不等于功能完成，必须按本文件状态矩阵验收。

## 19. 失败恢复要求

| 场景 | 系统行为 |
| --- | --- |
| 入会请求超时 | 使用同一幂等键查询或重试，不创建第二会员 |
| 入会成功但页面未收到响应 | 下次 bootstrap 返回真实会员，恢复原购物车 |
| 手机号授权拒绝 | 保持新会员或匿名点单能力；找回旧会员可稍后再做 |
| 微信订阅授权拒绝 | 页面内仍可查看订单、活动和积分状态 |
| 自动积分任务失败 | 进入重试和对账，不提示虚假“积分已到账” |
| 重复支付回调 | 幂等重放，不重复积分、不重复出品 |
| 支付结果未知 | 不发积分，不重复收款，显示待核对 |
| 全额/部分退款 | 权威退款成功后按原版本冲回积分和成长值 |
| 兑换时库存被抢完 | 同一事务失败，不扣积分；提示选择其他兑换项 |
| 扣积分后履约任务创建失败 | 整体回滚或可靠任务补偿；不能扣分后无记录 |
| 店长补发审批期间自动恢复 | 自动关闭申请为 `auto_resolved`，不再补发 |
| 规则发布失败 | 全批回滚，旧版本继续生效 |
| 身份疑似冲突 | 冻结合并动作，不泄露候选会员信息，转人工核验 |

## 20. 安全、隐私与审计

- 遵循最小必要、目的明确、知情同意和便捷撤回；顾客拒绝非必要信息不得被拒绝点单服务。
- 手机号、微信主体标识和联系信息加密或令牌化保存，日志只显示掩码。
- 不在小程序、本地配置、二维码、截图或前端日志中保存 AppSecret、支付密钥和解密密钥。
- 会员、积分、授权、订单和退款查询按本人身份隔离。
- 所有权限、规则、补发、冲回、兑换和授权变更记录操作者、原因、前后值、政策版本、时间和请求 ID。
- 审计记录不可被普通业务角色修改或删除。
- 到期删除或停止处理不再必要的个人信息；法定留存与顾客可撤回信息分开管理。
- 营销自动化不得实行不合理差别定价；会员等级可影响公开权益，但相同商品的交易价格差异必须来自已公开、可解释的规则。
- 未成年人、敏感个人信息和跨境处理如未来涉及，需单独合规评估，不在本期默认开启。

## 21. 验收用例

### 21.1 桌码与身份

- `ACC-ID-001` 正式微信扫码打开指定小程序路由，scene 可被正确解析。
- `ACC-ID-002` 有效已开台桌码进入菜单；未开台进入等待；无效、过期、跨店桌码不能下单。
- `ACC-ID-003` 服务端实际核验微信 code；伪造 openid、会员 ID 或客户端 assertion 被拒绝。
- `ACC-ID-004` 身份建立不请求头像、昵称和手机号。
- `ACC-ID-005` 身份服务失败时不伪造登录成功，并按降级策略保留安全能力。

### 21.2 入会与拒绝

- `ACC-MEM-001` 非会员在菜单中看到非阻断邀请，首屏主点单按钮可用。
- `ACC-MEM-002` 点击暂不加入后，本桌不再重复弹出，仍可完整下单和支付。
- `ACC-MEM-003` 不授权手机号、头像和通知仍能一键成为新会员。
- `ACC-MEM-004` 重复点击、断网重试和返回页面只创建一个会员。
- `ACC-MEM-005` 入会成功不清空购物车、不改变分类和滚动位置。
- `ACC-MEM-006` 已有会员找回遇到多账户时不自动合并、不泄露信息。

### 21.3 授权

- `ACC-CNS-001` 所有可选授权默认关闭，无预勾选。
- `ACC-CNS-002` 获取手机号不自动开启短信营销。
- `ACC-CNS-003` 入会不自动开启微信服务通知或活动推广。
- `ACC-CNS-004` 同意活动推广不会自动报名任何活动。
- `ACC-CNS-005` 撤回后新的营销发送被阻止，历史合法业务事实保留。
- `ACC-CNS-006` 只有用途同意和渠道授权同时有效时才发送。

### 21.4 自动积分

- `ACC-PTS-001` 已核实付款只发一次积分和成长值；重复回调不重复发。
- `ACC-PTS-002` 未付款、支付未知、模拟成功和已关闭订单不发积分。
- `ACC-PTS-003` 排除商品、费用、赠送和积分兑换商品不计积分。
- `ACC-PTS-004` 规则在下单后变化，仍按订单锁定版本发放。
- `ACC-PTS-005` 全额退款全额冲回；部分退款按原订单行冲回。
- `ACC-PTS-006` 通知失败不回滚正确积分，积分失败不返回虚假到账。
- `ACC-PTS-007` 积分余额、成长值和各自流水可独立对账。

### 21.5 人工补发

- `ACC-SUP-001` 系统可识别“已付款但未积分”，并先自动重试。
- `ACC-SUP-002` 店长只能申请系统计算差额，不能为原订单任意填写积分。
- `ACC-SUP-003` 店长提交后不能自批；无审批权限者直调接口返回 403。
- `ACC-SUP-004` 审批执行前再次校验付款、退款和既有积分。
- `ACC-SUP-005` 自动恢复与人工审批并发只产生一笔积分。
- `ACC-SUP-006` 补发后的退款能冲回自动和补发两部分。

### 21.6 等级与兑换

- `ACC-TIER-001` 普通、银卡、金卡按已发布版本升级、保级和降级；黑卡默认不可达。
- `ACC-TIER-002` 银卡/金卡倍率只增加可用积分，不增加成长值。
- `ACC-RED-001` 积分不足、兑换项停用、缺货、超限或不适用时不扣积分。
- `ACC-RED-002` 同一商品不能积分加现金拆分支付。
- `ACC-RED-003` 兑换成功后顾客可见商品、积分、状态和有效期。
- `ACC-RED-004` 未确认兑换不得进入 KDS；确认后只为对应兑换行创建一次任务。
- `ACC-RED-005` 门店原因履约失败返还积分，不自动改成现金补偿。

### 21.7 配置与权限

- `ACC-CFG-001` 授权人员可随时保存草稿和预览，但已发布版本不可原位修改。
- `ACC-CFG-002` 重大规则创建人不能自批；发布人必须有独立权限。
- `ACC-CFG-003` 排期版本无时间重叠，进行中交易继续使用锁定版本。
- `ACC-CFG-004` 紧急暂停阻止新积分/兑换，但不删除历史余额和已确认权益。
- `ACC-CFG-005` 跨店、越权、过期员工会话和仅前端隐藏的按钮均不能绕过服务端权限。

### 21.8 设备与体验

- 微信开发者工具、iOS 真机、Android 真机分别覆盖小屏、标准屏和大屏。
- 验证大字体、横竖屏、安全区域、弱网、重复点击、返回前台和扫码重进。
- 验证会员卡片不遮挡菜单，按钮可单手点击，空态和错误提示不过度占据版面。
- 验证页面无内部枚举、数据库状态、模拟渠道或开发版提示泄露到正式环境。

## 22. 测试层次

1. **单元测试**：金额换算、取整、有效期、倍率、等级、退款冲回、频控。
2. **数据库测试**：唯一约束、追加式流水、余额一致性、跨店隔离、并发兑换、申请人不可自批。
3. **接口测试**：身份伪造、幂等、权限、规则版本、失败恢复和错误码。
4. **支付联动测试**：成功、失败、关闭、超时、未知、重复回调、主动查询和退款。
5. **KDS/库存测试**：未付款不出品、未兑换确认不出品、并发库存不为负。
6. **小程序自动化**：扫码、等待开台、菜单、入会/拒绝、授权、积分、兑换和补发进度。
7. **真机测试**：iOS/Android 微信、不同系统版本、弱网、前后台切换和平台授权弹窗。
8. **经营影子测试**：不真实发积分和权益，只计算预期结果并与历史交易对比。
9. **真实岗位验收**：顾客、店长、管理员、服务员、财务分别执行完整流程。

自动化测试通过不等于真实微信授权、真实支付、消息送达或门店岗位验收通过。

## 23. 上线策略与指标

### 23.1 推荐阶段

1. **14 天影子测算**：只计算、不发放，验证比例、等级分布、退款和成本。
2. **30 天有限试点**：限定门店、部分会员或指定时间；兑换目录只开放低成本、低风险项。
3. **扩展试点**：确认积分对账、异常补发和权益履约稳定后扩大。
4. **正式启用**：完成真实微信、支付、消息、数据库、岗位和财务对账验收后发布。

### 23.2 必看指标

- 扫码成功率、有效桌码识别率、等待开台转化；
- 入会邀请曝光、加入率、拒绝率和对点单转化的影响；
- 手机号、头像、微信通知、短信营销和活动推广的独立同意率；
- 付款订单自动积分成功率、入账延迟、重复积分率；
- 自动恢复率、人工补发率、审批时长；
- 30 日复购率、会员与非会员客单差异；
- 银卡/金卡人数分布和权益使用率；
- 积分兑换率、过期率、兑换成本/会员净实付收入；
- 退款积分冲回完整率、积分负债和投诉量；
- 短信/微信发送成功率、退订率和投诉率。

建议经营成本红线：兑换与等级权益的实际成本合计先以会员净实付收入的 2%–3% 为试点目标。该目标必须按实际采购成本、损耗和履约人工复核，不能只用菜单账面成本证明合理。
