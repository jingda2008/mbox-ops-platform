## 2. 已确认缺陷与整改标准

### PA-01 / SYS-092：点单页同桌恢复后，服务和购物车也会卡住（P1，既有问题扩展）

证据：`miniprogram/pages/order/index.js:733`、`:737`、`:1251`、`:1267`、`:1526`、`:1551`。

实际执行当前页面脚本：

1. 发起“呼叫服务员”或购物车加一份，API响应故意延后。
2. 调用页面`onHide`，随后原请求完成。
3. 返回同一桌，执行实际`preparePage`。桌台范围未变化，所以仅在`scopeChanged`分支中的busy重置没有执行。
4. 第二次操作被busy门禁直接拦下；服务总请求仍为1，`quickServiceBusy=call`；购物车总请求仍为1，`cartSyncing=true`。

复现保留了真实生命周期、generation、写操作处理函数；菜单/轮询等无关读取用桩代替。它证明前端无法恢复，未模拟真实服务器共享车事务，也不证明服务器锁住桌台。

整改：读取排序、身份/桌次范围、每次写操作分别管理。返回时重建操作状态并核对服务端结果，不能把未知写操作直接当失败再加一份。修复要覆盖服务、状态、点单三页及支付宝同型脚本。

关闭标准：同桌切后台、进入详情/服务进展后返回、请求失败、响应丢失、换桌均可恢复；旧桌响应不能污染新桌，购物车不能多加、漏加。

### PA-02 / SYS-096：酒水偏好“可多选”保存后丢失（P2）

证据：`miniprogram/pages/profile-preferences/index.wxml:48`；`index.js:67`、`:113`；接口字段白名单见`server/normalized/customer-experience-api.ts:1786`。

隔离执行真实页面：选择“鸡尾酒+葡萄酒”，保存正文被转换为`preferredAlcohol: mixed`，重新读取后只剩“都可以”。这不是显示省略，而是发送时丢掉所选集合。支付宝对应页也有相同转换。

整改有两条合理路径：若业务只支持一个主要偏好，界面改为明确单选；若保留多选，则前端、接口、存储、个人偏好读取及推荐消费方共同支持集合，旧`mixed`不能反推原来的选择。不得只修改文案为“保存成功”或擅自推测历史丢失数据。

关闭标准：单选、多选、都可以、取消选择、保存重进及旧数据迁移均有明确结果；相同选择能完整往返，推荐端不把“只选两种”误当“没有偏好”。

### PA-03 / SYS-097：消息读取失败被显示为“暂未配置”（P2）

证据：`miniprogram/pages/profile-notifications/index.js:23`、`:24`、`:45`及WXML空状态分支。

两个授权读取接口都失败时，各自catch返回空数组，最后`loading=false,error='',options=[]`，页面显示“暂未配置消息模板”。用户无法区分网络故障、身份过期、尚未授权和门店未配置，也没有当前页重试按钮。支付宝对应页同样吞掉读取异常。

整改：区分配置可用性、本人授权记录和请求失败；部分成功保留已读结果，对失败部分提供重试。显示“是否收到提醒”必须以授权次数、发送资格和实际回执分别说明，不能把“已准备好”视为已送达。

关闭标准：双接口失败、仅一项失败、401、真实无模板、无授权、已拒绝和授权已消耗各显示正确状态；不因失败自动更改同意状态，也不阻止点单与预约。

### PA-04 / SYS-098：预约日期变化后的旧响应覆盖（P2）

证据：`miniprogram/pages/reservations/index.js:250`、`:270`。独立演出页`performances/index.js:147`已有日期+请求序号检查，但预约页没有使用对应保护。

隔离实际脚本：先请求9月10日，再选9月11日；11日响应先返回“不可预约+新场次”，10日响应后返回。最后日期仍为11日，场次却为`OLD-DAY`，可预约状态也被改成true。

提交前仍会重新查询可用容量，因此本轮不将其描述为已造成超卖或错日落单；已确认的是展示错日、允许基于旧状态进入下一步，以及选择旧场次后提交可能被拒绝。支付宝预约页存在相同无序读取结构。

整改：把日期、时间、人数、请求序号组成读取快照；旧响应及旧finally不得覆盖当前展示或提前清除loading。日期变化清理不匹配场次；提交使用同一份冻结表单快照并以服务端为准。

关闭标准：日期/时间/人数快速变化，旧成功晚到、旧失败晚到、不同响应顺序都只呈现当前查询条件；原选择失效时清楚提示，不静默改日期或替换场次。

审美/便利性建议（不是执行失败结论）：会员管理、客户活动、库存上架等页面重复标题/说明较多，空状态也偏高，核心操作常被推到首屏下方；窄屏底栏“收银与退款”“演出与点歌”会拆为两行。建议短底栏标签、简短状态摘要、按需展开说明，并让有真实待办时优先展示待办。
