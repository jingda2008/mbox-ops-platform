## 2. 开发原则

**经营适配（2026-09-13用户明确）：** 少人手、一人兼岗是设计前提；点单、加单、收款和顾客体验优先。正常流程尽量不增加点击、必填和等待，已有数据自动带入，日志后台记录；异常集中在原业务入口，只有确需现场接手才移交。责任岗是权限能力，不意味着门店必须增加一个人；实际退库确认可由已有授权的兼岗员工在同一售后入口完成。一次退款审核规则继续沿用，不能以简化为由假报退钱、实物或出品结果。完整操作规则和销售/效率验收见执行规范第0节。

1. 复用现有订单、桌次、库存流水、打印任务、权限和营业日报机制，不另建平行账本。
2. 金额取原订单成交快照；不使用当前菜单价格重算历史订单。套餐子项不重复计费，缺失历史数据明确标记，不补造。
3. 支付、退款、制作配送、库存和打印是不同事实。退款成功不等于取消制作、实际退库或完成交接。
4. 新桌扫码只调整本人当前桌位；整桌迁移、订单归属调整、账单合并必须使用各自明确操作。
5. 网络超时不等于操作失败；使用原请求核对结果。打印结果未知不得自动盲重发。
6. 按岗位授予动作权限；查看、导出、打印、退款、退库、停止出品、配置和补打分别校验服务端权限。
7. 所有时间采用明确的门店营业日与北京时间口径，不用自然日替代营业日。
8. 提交、合并、后端部署、小程序上传/版本选定、Windows升级、真机及实物验收分别留证。

优先级：P0 为优先防止错桌、错单、重复处理及库存账务失真；P1 为本批必须完成的准确性与操作闭环；P2 为本批后段体验和运维改进。优先级不是删减范围的依据。

## 3. 统一开发模块

### REQ-01 桌台消费金额与出品双视图（P1）

现状：桌台详情已有商品单价、数量、小计及套餐内不另收费标识，主体偏出品进度；现场入口及版本待核。

要求：
- 核账视图显示名称、规格、成交单价、数量、优惠、优惠后小计；整桌显示消费合计、应收、实收、退款、净收、待收及适用的多收提示，各字段沿用权威金额读模型。
- 出品视图显示待付款、待制作、制作中、待送达、已送达、取消、无需出品及待核对状态，保留操作人和时间的可查入口。
- 套餐母项计费，子项显示实际选款与含于套餐；赠送、取消、退款项目保留清晰标记。
- 只有商品、规格、成交价及备注相同的项目才可汇总；允许展开原订单。不同桌次不可仅按桌号合账。
- 金额缺失显示待核实，不显示伪造的0；退款不直接按“收款减退款”生成应催收余额。

验收：普通品、套餐、赠品、折扣、取消、部分退款、同桌多单和同桌号不同桌次均对账一致；历史改价不影响原账单。

### REQ-02 桌台数据刷新与弱网恢复（P1）

现状：桌台明细约10秒刷新，一次失败后停止自动刷新，需人工恢复。

要求：显示最后成功更新时间；旧数据保留但明确标记过期；网络恢复、页面重新可见时重新核对，采用有上限的退避重试。鉴权失效、权限拒绝等错误不得无限重试。切换桌次时清除旧桌展示，取消或隔离旧请求，避免晚到结果覆盖当前桌。提供手动刷新及可复制的问题编号。

验收：短暂断网恢复后新增订单及送达状态自动更新；快速切桌、慢请求、退出页面无串数据；服务器持续失败不造成请求风暴。

### REQ-03 本人扫码换桌与归属保护（P0）

现状：已有热启动扫码更新、缓存清理、请求隔离和本人位置调整能力；现场旧桌问题未复现定因。

要求：
- 收集实际扫码入口、码参数、客户端版本和时间，定位扫码解析、会话、页面生命周期、缓存或请求时序问题。
- 有效新码校验成功后自动更新当前桌号、桌次和购物车作用域；下单前服务端再次校验归属。切换未完成时不得沿旧桌提交新单。
- 成功明确提示已切到目标桌；无效码、未开桌、无权进入等给出准确原因，失败恢复遵循原有安全机制。
- 旧凭据按现有身份模型撤销或失效；会员身份保留，旧桌购物车和付款状态不污染新桌。
- 旧订单保持原归属；旧桌未送达商品显著提示并提供员工协调入口。整桌迁移、订单迁移、账单合并与本人换桌分开。

验收：冷启动、未退出、后台恢复、连续扫两桌、重复扫同桌、翻台后重扫、无效码及弱网；微信和支付宝分别验证。无需右上角刷新，不能访问或搬走他人订单。

#### REQ-03-A 扫码强制同步规则（2026-09-12用户确认补充）

明确要求：**扫码触发桌台状态强制同步，页面自动更新，无需用户手动刷新。** 不以强制重启整个小程序或单纯重新渲染页面代替服务端桌次核验。

1. 每次桌码扫描均重新校验服务端当前桌号、桌次和本人绑定，包括扫同一码及翻台后重扫；不得因本地已有桌号或二维码文本相同而跳过核验。
2. 扫码立即进入“正在同步桌台”状态，暂停该客人的新订单提交；停止旧桌轮询并隔离旧请求。不得冻结原桌其他顾客的正常操作。
3. 采用单调递增代次或等效机制，只允许最后一次扫描的有效响应更新当前状态；旧扫描、旧轮询或旧付款页面请求晚到不能覆盖新桌，也不能回写旧凭据。
4. 服务端校验成功后，将桌号、桌次、凭据和购物车作用域作为一致状态更新，再重新读取新桌数据、恢复下单并提示“已切换至目标桌”。清理旧桌显示和临时状态，但保留会员身份、真实订单、付款记录及必要的结果核对信息。
5. 同步失败、断网、无效码、未开桌或无权进入时，明确提示“桌台同步未成功”及重试入口；不得静默恢复旧桌并允许继续下单。确需恢复原桌时，应明确告知并经服务端重新核验后恢复，不能仅凭缓存放行。
6. 下单提交携带最新已核验桌次/绑定版本或等效标识，服务端校验其与当前有效归属一致；不一致时拒绝这次提交并触发重新同步，不得悄悄改投到另一桌。
7. 本人自行换桌时旧订单保持原归属并提示待送达事项；员工正式整桌转桌后再扫码，以服务端正式转桌结果为准，既有订单依转桌记录处理。两种操作不得混用。
8. 微信、支付宝各自适配扫码入口和生命周期，不能用某一端测试结果替代另一端验收。

新增验收 E2E-19：无需退出小程序或点击右上角刷新，依次验证新桌扫码、同码重扫、翻台重扫、员工转桌后扫码、连续快速扫两桌、后台恢复、断网重试和旧请求晚到。除桌号显示外，必须核对下一笔真实测试订单的服务端桌次归属，以及制作/配送/打印所读取的目标桌信息；不得出现“页面新桌、订单旧桌”。无效码或同步未完成时，不得向旧桌提交新单。测试在隔离环境与授权现场分别留证，不以生产新增订单作为默认验证方式。

### REQ-04 退款后的履约与库存处理闭环（P0）

现状：退款、停止出品和实际退库分散；已有未制作终止入口及独立退库机制。

要求：
- 退款按原因区分商品退货/取消、退差价、多收款退回等；商品类关联具体原订单与商品，不能只凭整单出现成功退款推导所有商品可退。

- 待处理事项跨页面、交班、营业日保持可查；退款执行和后续实物操作分别幂等，不能因退库重试再次退款。

验收：退款申请/处理中/失败不作为成功退款；部分退款、合付退款、退款与接单并发、重复通知、多收款退款均不误停、不重复出品或回库。

### REQ-05 实际退库、数量上限与库存可售同步（P0）

验收：一瓶水完整链路、两瓶退一瓶、重复点击、并发退库、已释放预留、已消耗配方、整瓶ml商品、套餐及兑换商品；库存与成本流水、前台可售状态一致。

### REQ-06 打印串单定位与岗位路由（P0）

现状：制作票按bar/kitchen拆分，收银票可含全部商品；具体事故缺打印任务与现场队列证据。

要求：逐级核对异常票种、商品岗位/分类、任务站点、目标设备、Windows队列及物理打印机，形成根因记录后再调整。配置页展示完整对应关系、最近心跳和版本；配置变更留前后值与原因，校验真实队列，并以明显测试票核对。

验收：一单酒水+小吃，吧台/后厨只收到各自制作票；收银汇总遵循配置；某台离线不错误转发另一台；加单只制作新增项目；补打不产生库存或履约动作。

### REQ-07 小票按用途排版（P1）

现状：Windows已有桌号大字逻辑，但实装待核；文本商品、单价、小计仍分行。

版式参考：用户于2026-09-12补充的实体票据照片。仅借鉴其信息层级与字号反差，不照搬图片中的店名、编号、金额、品名或其他业务内容。参考照片的有效特点是：桌号、票种、菜品、数量和应付/合计明显大于辅助信息，员工能在较远距离快速识别；不足是部分数字和字段过于拥挤，M-BOX实现时须保持对齐、留白和完整换行。

要求：
- 桌号独占醒目大字行，人数另列；店名、票种、营业日、生成时间、操作人可识别。
- 制作票突出岗位、桌号、名称规格、数量、备注；配送票突出取货岗位、桌号、批次与数量。
- 消费票显示成交单价、数量、金额及合计；收退款票突出本次实际金额与方式，原消费明细不得让人误解为再次收款。
- 长名称、规格及备注完整换行，金额列对齐；长技术编号降低视觉优先级但保留追溯手段。
- 明确测试、加单、补打、退款等标识；后续页可识别所属票、页码和桌号；总金额不可在分页重复累计。
- 58mm/80mm或实际门店纸宽分别实测；大字体、纸耗、长单分页统筹设计，不只改HTML预览。

#### REQ-07-A 结账单信息层级

1. 票头第一视觉层级为桌号，使用整行超大、粗体，例如“桌号 A28”；票种“结账单/预结账单/已结账凭条”紧邻显示且明显区分，不能只靠小字标题判断。
2. 第二层级为应付金额或净应收金额，使用大号粗体并独占清晰区域。原价、优惠、已付、退款、待确认、多收等为次级字段，分别列示，不能用一个模糊“合计”覆盖不同财务含义。
3. 商品区域采用稳定列结构：品名/规格、数量、成交单价、小计。品名允许换行，数量和金额不得被长品名挤掉；套餐内商品明确“不另收费”，赠品显示0元及赠送标识。
4. 单号、营业日、打印时间、操作人和支付方式保留但缩小；内部UUID、技术状态和长流水号不得占据票头主视觉，可使用短编号或二维码承载完整追溯信息。
5. 未付款账单必须标明“预结账/未收款”，已付款凭条标明“已收款”，退款后新快照标明退款与净额，避免顾客把预结账单误认成付款凭证。

#### REQ-07-B 点菜单/制作单信息层级

1. 票头第一视觉层级同时包含制作岗位和桌号，例如“吧台｜A28”“后厨｜K7”，两者均使用大号粗体；点菜单、加菜单、暂停/取消通知采用醒目标识，避免拿错票种。
2. 菜品名称和数量使用大字。数量靠右或使用独立列，统一显示“×2份/×1杯/×1套”等可执行单位；套餐名称、子项和规格必须看出父子关系。
3. 口味、做法、忌口、加急及客人备注使用粗体或边框突出，优先级高于单号、员工等辅助信息；普通制作票不以价格为视觉重点。
4. 同一订单跨吧台和后厨时分别出对应岗位内容，禁止为了版式统一而把另一岗位菜品打印进制作单。配送或收银汇总票另用明确标题。
5. 加单只打印新增商品并标记“加单”；暂停/取消单必须显示原桌次、原单短号、商品和数量，使用与正常点菜单不同的醒目标记。旧纸票无法撤回，电子确认及现场核对仍需保留。

#### REQ-07-C 字号、密度与物理验收

- 使用相对层级而非只规定一个固定字号：桌号/应付金额为最大层级，票种/品名/数量为第二层级，备注为第三层级，技术编号和时间为辅助层级。桌号及关键金额的实际字高应至少约为正文的1.8倍，最终数值按打印机驱动和纸宽实测调整。
- 保留足够上下留白和分隔线；不得因放大关键字段导致商品漏印、金额截断、分页缺桌号或纸张高度溢出。
- 80mm作为当前照片的主要参考，58mm必须独立重排，不可简单等比例缩小。字体粗细、中文字符宽度和热敏打印浓度均需实物检查。
- 提供结账单、点菜单、加菜单和暂停/取消通知各自的打印预览，但完成标准必须包含门店真实设备出纸；预览或Windows队列成功不能替代纸面可读性验收。

验收：长中文、长编号、套餐、零元赠品、多数量、重点备注、跨页长单，在两台真实打印机上无截字、错位、漏项或用途误识别。另在正常站立查看距离下，由非开发人员抽测：3秒内识别桌号和票种；点菜单5秒内识别主要菜品、数量和关键备注；结账单5秒内识别应付/已付/退款/净额。该时间为现场可读性测试目标，不替代金额逐项核对。

### REQ-08 打印任务追踪与安全补打（P0）

要求：按钮保留返回请求编号并提供本次任务直达；显示目标设备、份数、排队/提交/失败/未知等真实状态。系统已提交不宣称物理已出纸。明确未提交错误按既有策略有界重试；结果未知停止盲重发，人工核对后按权限补打。补打关联原票、原因与操作人，原快照不可变。

验收：离线、缺纸、超时、断电临界点、网络恢复、连点和多员工并发；不重复扣库、收退款或出品。失败与未知均能从业务入口找到对应任务。

### REQ-09 原票补打与最新账单版本（P1）

要求：明确区分补打原快照、按最新消费生成新账单、生成新的日报快照。每份包含生成时间、版本或可追溯编号，旧票保留；新账单重新读取权威数据，补打保持原金额。不得通过简单清除所有幂等记录解决按钮锁定。

验收：首次打印后加单、优惠调整、部分退款再生成账单得到新金额；补打原票仍为原金额；请求超时重试核对同一快照，不意外生成多票。

### REQ-10 营业日期范围查询与打印（P1）

现状：历史查询支持起止营业日，手动日报打印仅单日；多日收退款已有汇总，经营销售汇总仅单日条件下生成。

要求：
- 起止营业日校验；支持单日、多日及汇总/明细/两者，打印前预览范围、订单数、金额和预计纸量。
- 扩展后端期间销售、优惠、赠送及所需待收口径，复用权威数据；缺字段不可默认为0。
- 销售按原订单营业日，资金按入账营业日；跨日退款可追溯原单。期间待收明确为所选订单截至生成时的余额或历史时点余额，二者不得混用。
- 打印全部筛选结果，不只当前页。当前全量查询上限5000单，范围扩大时明确提示或分批生成，禁止静默截断。
- 无交易可生成明确空报告；跨页重复表头、页码、合计位置清楚。
- 临时快照、正式日结记录和历史快照补打区别呈现；打印不自动提前结束营业日。晚到款保留新快照/差异核对入口。

验收：单日、多日、跨午夜、跨月、空日、退款跨日、晚到款、权限裁剪和超限；页面、导出和打印采用同口径数据。

### REQ-11 筛选范围、资金总账与金额下钻（P1）

要求：显著区分全店期间资金与当前桌号/员工/订单筛选结果。资金合计不随订单筛选变化时，标题和打印必须明确标识；若增加筛选资金统计，需要有可靠分摊依据。金额可下钻原订单、支付、退款和相关流水；不将活动款误当桌台销售。缺权限不展示为0。

验收：搜索某桌/员工后不会把全店净收误作该桌收入；合付、活动、部分退款及跨日数据解释一致。

### REQ-12 交班异常清单（P1）

要求：整合未结清订单、支付/退款待确认、退款后商品未处理、已做好未送达、打印失败/未知。复用原事实与待办，不另建不同步的异常账。系统自动汇总和更新，员工在原入口处理；同一授权员工可兼岗，无需每单填写负责人或逐岗移交。确需他人接手时显示实际接手岗位/人员、最近进展、时间和操作入口；可交接但不强行结清、取消或删除。只对有动作价值的变化提醒，避免重复报警，不遮挡点单、加单和收款主入口。

验收：交班和切营业日后异常仍可追踪；处理完成后按权威状态消除；历史记录保留，重复事件不新增重复待办。

### REQ-13 权限不足的移交与审计（P1）

要求（按第12/13节更新早期权限表述）：本店在岗服务人员均可对可访问订单申请退款，并直接执行正常未付挂单的单品/数量停止；退款由另一位有权人员完成一次审核，线上批准后自动执行。审核、实际退库、特殊已制作/已消费免单或损耗、打印配置及补打按既定角色分权。无权处理的事项显示接手岗位和移交入口；服务端对查询、动作、历史范围、导出和打印独立复核，敏感操作留人、时、因、前后值及关联对象。

验收：不同在岗服务人员可申请及正常未付停菜；不能自审、越权审核或越权退库；已制作/已送达保留事实，特殊处置沿既定授权；旧订单、跨门店及直接接口访问不能绕过授权。

### REQ-14 版本核对与现场排障（P2）

要求：集中显示后端、小程序和Windows打印程序版本、更新时间与最近心跳；区分已部署、已上传、已选定、已安装和已验证。客户端版本不能可靠取得时明确显示未知，不伪造一致。相关错误保留可复制编号；日志禁止存付款码、完整凭据或无关个人信息。

验收：旧客户端或旧打印程序可被识别；排障能关联版本、桌次、请求及打印任务。后端发布不自动宣称打印程序升级成功。

先修REQ-16的确定加锁顺序缺陷，同时准备REQ-15历史只读预演清单；随后补支付分类与必要的历史处理。负责人开发时登记，实际版本和日期以验证结果确定。两项已纳入正式需求，但不取消“未复现前端竞态暂缓修改”的限制，不借此增加全局刷新、全局重试或营业阻断。


## 12. 服务人员退款申请与一次审核（用户最新明确要求）

本节优先于前文及旧实现中相冲突的多级退款流程，补充REQ-04、REQ-13。目标：每一位本店在岗服务人员均可在可访问的本店订单内申请退款，只需一次有权限人员审核，简单高效。申请权不等于直接退款权，不扩大跨店访问。

### REQ-04-B 全员可申请、一次审核

1. 在桌台订单详情提供“申请退款”入口，不要求服务人员先进入收银后台。选择商品/数量或退款金额、选择简短原因，提交一次即可。可退金额由服务端根据原付款和已有退款计算，套餐和合付按原分摊规则处理。
2. 本店在岗服务人员均拥有申请权限；审核由有退款审核权限的另一位人员执行。申请人不得审核自己的申请；审核岗位沿用或由门店指定，不默认授予所有人员审核权。
3. 一次审核通过后，线上原路退款由系统按原支付渠道自动执行，不再要求收银二次审核或另点执行。拒绝填写简短原因并通知申请人。金额上限沿用已确认业务政策；审核人额度不足转交具备额度的人完成这唯一一次审核，不增加审批层级。
4. 现金/外部POS等无法自动退回的方式，审核后进入实际退付及凭证登记；这是执行事实，不是第二次审核，不得假报系统已经退钱。
5. 申请人和审核人均能看到待审核、已拒绝、退款处理中、退款成功、结果待核对/失败及下一步。审核通过不等于渠道退款成功；结果未知重试核对原退款，不创建第二笔。
6. 重复点击及多名员工对同一商品申请均校验剩余可退额度并幂等处理；一名审核人决定后，其他人的旧页面不能再次执行。

### REQ-04-C 未制作商品及时暂停出品

此为衔接前述客人不要商品的现场反馈的建议实现：申请商品取消退款时，后台原子核对未开始制作的商品并标记“退款审核中，暂停制作”，通知相应岗位，不等待资金到账再采取现场止损动作。暂停不是退款成功，也不是永久取消。

- 未制作判定与接单/开始制作操作并发互斥；已开始的商品明确显示“已开始，需现场处理”，不能假报已停。
- 只暂停申请涉及的商品，不冻结整桌或其他订单；退差价、多收款退款不暂停制作。
- 审核拒绝或申请撤回后，进入明确的现场处置状态，由服务人员确认继续制作或进一步协调，不静默自动恢复出品。该现场操作不构成第二次退款审批。
- 审核通过后停止相关出品；库存按原有预留释放/实际退回规则处理，申请阶段不直接增加库存。退款执行失败时保留资金待办与商品处置事实，不自动恢复制作或再次收款。
- 打印过的制作票必须有可见的暂停/取消提示及岗位同步，不能只修改顾客页面。纸票无法撤回，须由现场核对。

暂停机制实施前做最小并发和岗位验证，复用现有状态与通知能力；不扩大成全局暂停或新增多层确认。

新增验收：
- E2E-26：不同服务人员均能从订单详情申请；无审核权者不能执行退款，自审拒绝；一次授权审核后线上退款自动执行。
- E2E-27：未制作商品申请与制作开始并发，仅一种有效结果；其他订单正常制作；审核拒绝/撤回有明确后续处理，不能永久挂起或静默恢复。
- E2E-28：部分商品、差价、多收款、现金/POS及渠道超时分别正确处理；多人重复申请/审核不多退，线下凭证登记不增加审核层级。

本轮仅将最新业务规则写入需求，未修改权限、业务代码或生产数据。REQ-04-C的具体暂停状态设计为建议实现，不将用户的“一次审核”表述扩展为无审核直接退款授权。


## 13. 按下单与支付情况进行单品停止（用户最新确认）

本节补充并优先细化REQ-01、REQ-04、REQ-05、REQ-13及第12节；按真实付款情况处理，不仅依赖订单来源或页面“挂单”标签。

### REQ-04-D 三种场景统一规则

| 场景 | 服务人员操作 | 金额处理 | 审核 |
|---|---|---|---|
| 客人自助下单，已经支付 | 选择单品及数量，停止后续出品并申请该商品退款 | 按原订单成交价、优惠和原付款分摊确定可退金额 | 沿第12节，一次有权限人员审核，线上原路自动执行 |
| 服务人员协助点单，已经支付 | 与自助已支付完全一致，支持单品及数量 | 同上，不能因协助点单而变成直接抹账 | 同上，不增加审批层级 |
| 挂单，尚未支付 | 服务人员可选择任意菜品及数量停止，不必取消整单 | 取消对应有效应收，剩余商品继续挂单；不生成退款 | 正常停止动作不引入退款审批；在岗服务人员按本店可访问订单直接操作并留痕 |

具体要求：
1. 订单详情统一提供商品级操作；可选一个或多个品项及数量，默认全部未处理数量，允许部分数量停止，例如3瓶水停1瓶，其他2瓶保留。停止某商品不影响同桌其他订单或本单其他商品。
2. 已支付的商品取消申请即时进入停止/暂停后续出品的处理链路，不等待退款到账；依第12节保留审核中状态、拒绝/撤回后的现场处置，不能静默自动重做。审核通过、退款处理中、退款成功分别展示，原收款不删除。
3. 未支付挂单无需绕到收银退款入口；停止成功立即更新商品状态、剩余数量、订单应收、桌台汇总、吧台/后厨及配送队列。全部品项停止后本单不再产生有效应收，但不因此自动关桌或关闭其他订单。
4. “任意菜品”指服务人员可选择任意订单品项，不受品类或下单来源限制；已经完成的制作/送达不能倒改成未制作。已开始、已做好或已送达品项仍提供处理入口，按实际阶段记录停止后续履约、取消应收及必要的损耗/实物处置；不假报能撤销已经发生的制作。已送达品项不得显示“已停止制作”，应准确显示取消计费/售后处置。一般动作使用简短原因并记录操作人，既有已明确的特殊经营授权规则不得静默绕过。
5. 真实支付状态由服务端提交时复核：若页面显示未付但刚刚收款、合付或存在部分实收，不得直接走“零退款取消应收”；刷新并进入已付款部分退款/剩余未付取消的对应处理。渠道结果未知保留资金核对事项，但不能阻止针对未制作商品的及时停止出品。
6. 套餐父项、含于套餐子项、赠品分别标识。停止套餐子项不等于按单点售价退款；可退金额遵循原成交分摊和既定套餐规则。部分取消引起优惠门槛变化时，只按已确认价格政策计算，不能擅自猜测补价规则。免费赠品停止不产生退款。
7. 库存按真实阶段：仅预留的释放占用；实际已消耗的不自动回原料；未开封实物退回按退库事实恢复，已恢复不得重复。停止、退款、退库分别记录并可追溯。
8. 制作开始、配送、停止及支付并发时由后端决定唯一有效结果；同一数量不得同时正常出品和成功停止。重复点击、多员工操作以原品项及剩余可处理数量校验，不能多取消、多退或重复释放库存。
9. 已打印制作票无法撤回，岗位页面及既有打印机制须提供对应停止/暂停通知，明确原桌次、原订单、商品与数量，不能让补打被当新制作。
10. 订单中心、桌台明细、顾客订单、收银和打印账单采用同一状态和金额事实。保留原商品、原金额、停止数量、原因、操作人、时间、审核/退款/库存处理记录，不删历史行。

验收：
- E2E-29：自助已支付订单含多个商品，仅停退其中一种的部分数量；一次审核，未选商品继续履约，退金额和库存正确。
- E2E-30：协助点单已支付执行同样动作，入口、权限及审核步骤与自助一致；线上和线下退款遵循各自真实执行方式。
- E2E-31：未付挂单选择任意品项及部分数量停止，不走退款审批，剩余应收与岗位队列同步；全部停止后该单无待收，桌台及其他订单不受影响。
- E2E-32：停止与制作/送达/支付并发，旧页面未付款不造成已收款无退款的抹账；已制作和已送达事实保留。
- E2E-33：套餐子项、赠品、优惠商品、合付和部分实收按原金额事实处理，不能以当前单点价或退款金额反推数量。

实施仍遵守最小必要修改、局部同步、不增加多级审批和全局阻断。本节为需求确认，未执行代码开发或生产变更。


## 14. 单品停止与售后的完整场景补充

来源：用户要求不限于已举三种情况，继续考虑实际营业组合。以下为需求场景覆盖，不是宣称这些情况全部已发生或现有系统全部缺失。继续遵守稳定性优先；优先复用既有规则，仅为已确认业务需求及有证据缺口实施必要变化。

### 14.1 判断依据与简单入口

不要只按“自助/协助/挂单”分类。后台共同判断实际付款及退款、商品数量和履约进度、套餐优惠、实物情况、原桌次及处理记录。员工仍从订单详情选择商品和数量、简短原因，系统展示停止数量、取消应收、拟退款、库存处理及需要现场确认的结果；不让员工手选数据库状态，不增加多级审批。

“停止”只代表停止选定数量的后续履约；“取消应收”“退款”“实物退回”分别落事实。无须退款的未付挂单依第13节直接停止，实际已完成商品保留完成及成本记录。已支付退款依第12节一次审核。客人提出取消可由服务人员代申请；本次不自动新增客人无审核直接退款能力。

### 14.2 场景矩阵

| 编号 | 情况 | 必须处理的规则 |
|---|---|---|
| CASE-01 | 未付且未开始制作 | 直接停止选择数量、取消相应有效应收、释放原预留；其他商品继续 |
| CASE-02 | 自助/协助已付、未开始制作 | 申请涉及数量立即暂停后续制作，一次审核后执行退款；退款终态与现场处置分开 |
| CASE-03 | 付款弹窗仍开着、扫码付款尚无终态 | 可先停未制作部分；并行核对原付款，不伪造未付。取消后晚到成功仍入账并形成退款待办，不重新启动制作 |
| CASE-04 | 部分已付、剩余未付 | 基于权威订单应收和原付款分摊，分别处理应收取消与应退款；不能简单把整件售价全额退款，也不能只取消应收忽略实收 |
| CASE-05 | 多笔付款/现金+线上/多人分付 | 记录退款来源与各付款剩余额度，按原付款执行；总退款不超确认实收减已退及在途占用。退款路线或优先顺序缺既定规则时待明确，不默认把线上款改退现金 |
| CASE-06 | 多单合付，只取消其中一件 | 精确关联原订单、原品项及付款分摊，其他原单不改；批次合计与逐单分摊一致 |
| CASE-07 | 一行多份、其中几份已做/已送 | 支持按数量分段处理，不将整行一刀切；如果现有模型只记录整行状态，必须补足可追溯数量/子任务能力后才允许承诺“部分未制作已停止” |
| CASE-08 | 吧台未做、后厨已做或反之 | 按商品及岗位分别返回处理结果；不可把部分成功提示为整单停止成功 |
| CASE-09 | 已接单但实际尚未动手 | “已接单”不当然等于已消耗，但缺实际记录时不能推测未制作；由对应岗位核实阶段。核实属于现场事实，不新增退款审批层级 |
| CASE-10 | 已制作、已做好、配送途中 | 停止后续动作并提示岗位核实实际已做数量；已消耗成本保留，不恢复原料。配送途中需实际拦截确认，不仅改屏幕 |
| CASE-11 | 已送达，未开封退回 | 可以退款申请及退货处理，实物收到后依规则回库；“退款成功”与“已收到实物”不能相互替代 |
| CASE-12 | 已送达/已开封/已消费，但投诉退款 | 可申请审核退款，保留原制作送达及成本，不自动回库；未付情况下取消计费仍依第13节和既有经营权限留原因 |
| CASE-13 | 少送、漏送、做错、送错 | 可选择退对应部分或补送/重做，明确原商品与补救任务关联，不能既自动退款又自动再收款；做错损耗与重做耗料分别记录 |
| CASE-14 | 客人换商品 | 旧商品停止/退款与新商品新单明确关联，不能直接覆盖历史品名价格；差价按原有收退款流程，不默认跨付款净额抵扣。换品是否净额结算需单独业务规则 |
| CASE-15 | 套餐子项、选配、加价项、赠品 | 停制作可定位实际子项；免费项目不生成现金退款；退款依真实计费及既定分摊，不能用当前单点价代替 |
| CASE-16 | 券门槛、满减、会员折扣、积分/权益 | 退款金额、券是否恢复、已获积分/权益是否撤回各按既定政策。未确认口径不自动补价、补券或扣积分；后续权益处理保留待办，不能阻塞先停止未制作商品 |
| CASE-17 | 已退款一部分，又取消剩余商品 | 计算已申请、已批准、在途、已成功退款及商品已处置数量；拒绝申请释放其占用，不释放仍在途额度；不得多退或重复停止同一数量 |
| CASE-18 | 退款审核中，申请修改/撤回或拒绝 | 未执行前支持按状态撤回；修改商品、数量、金额、原因等影响决定的内容使旧审核失效，由新版本接受一次有效审核。已开始资金执行不可假装撤回，先查原退款结果。停止后的商品不静默恢复制作 |
| CASE-19 | 审核通过，部分退款通道成功、另一部分失败 | 分付款显示结果和未完成金额；成功部分不再重发，仅恢复未确认/失败部分的原执行或经确认的新尝试；申请整体不能虚报全退成功 |
| CASE-20 | 退款超时/结果未知，随后回调成功 | 保留同一退款标识查结果，回调重复不多记账；未知不当失败，也不能点击再退造成重复 |
| CASE-21 | 渠道后台/线下已经退款，系统后来才收到 | 核验外部退款与原付款、金额、来源匹配后关联，不能再发一次；未证实外部退付不得直接改成功 |
| CASE-22 | 审核人不在线、交班、跨日、关桌后售后 | 待审核和商品处置有责任岗位及提醒；提醒不反复轰炸，超时不自动批准退款或恢复制作；旧订单按原桌次处理，不要求重新开桌 |
| CASE-23 | 客人换座、整桌转桌或原桌已翻台 | 本人换座不改变原订单；正式转桌沿权威转桌记录定位。通知标明原单/当前配送目标，不能把旧单退款或停止通知发给下一桌次 |
| CASE-24 | 打印机断网、岗位屏离线或仍拿着旧纸票 | 后台可停止且电子任务不再接单，但物理作业是否已停止须现场核实；显示通知未送达/未确认状态及人工联系提示，不把出纸作为退款前置 |
| CASE-25 | 两名服务员同时申请，审核与制作同时发生 | 服务端基于版本、可处理数量及付款剩余额度裁决；后提交者得到最新结果，不重复停止、退付、释放库存。已获合法决定不会被旧页面覆盖 |
| CASE-26 | 提交成功但客户端超时、刷新失败或重新登录 | 同一操作先恢复原编号查结果，不立即创建第二次；已成功事实与读回失败分别提示，确认剩余数量后才能开始新操作 |
| CASE-27 | 已有成功付款但页面仍显示未付 | 服务端拒绝过期的“无退款取消计费”方案，重新给出真实付款处理；不因页面旧状态删改已收款事实 |
| CASE-28 | 同一单全部品项停止 | 单笔订单取消应收/退款按状态完成，原记录保留；不自动关闭整桌、会员会话或其他人的订单，不把未完成退款待办清走 |

### 14.3 不变量及开发缺口检查

- 数量：原下单数量、申请涉及数量、暂停/停止数量、实际制作送达数量、实物退回数量分别可追溯。“已做后停止后续履约”允许事实同时存在，不应把制作历史和停止状态错误设成互斥；只有同一未制作数量的接单/停止竞争需裁决。
- 金额：退款只源自确认实收且受已有退款及在途占用约束；取消未付应收不产生退款流水；付款迟到可入账但不自动恢复已取消出品。
- 库存：审核中暂停期间不凭空加库；预留如何保留/释放要与恢复制作时重新校验库存配合，不能释放后又无检查恢复。已消耗物料不回原料，实际退回只记一次。
- 审核：所有服务人员可申请，只有一次有效审核；资金执行、实物核实、审核后变更申请重新形成新版本，不混为多级审批。不得以本节复杂场景增加普通订单操作步骤。
- 非阻断：某商品异常仅影响其后续处理；其他商品、订单、桌台继续工作。付款结果未知不阻止现场暂停未制作商品。
- 状态回读：显示“已暂停未制作2份、另1份已制作待处理”等真实部分结果；失败时不整单假报成功，成功时不因通知或页面刷新失败重复执行业务动作。

### 14.4 必须沿用既定政策或单独确认的金额口径

开发前查现有已确认政策；没有明确依据才提出具体选项，不猜测：
1. 部分付款/多种付款来源时，取消商品对应的已付分摊与退款路线。
2. 套餐部分退、满减失效、券恢复、积分/会员权益调整。
3. 换品是否允许差价净额结算、如何关联原收退款。
4. 已制作/已消费未付款商品取消计费与损耗的既有岗位授权范围。

这些不明确事项不应阻塞不依赖金额决策的未制作商品及时停止。不得自动把退差价、多收款退款转成商品退货。
