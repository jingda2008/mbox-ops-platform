## 2. 整改前阻断问题基线

以下第2至4节保留2026-07-15首次审计时的原始发现，用于追溯；关闭状态以第0节复核表为准。

### P0-01 云端是多实例临时 JSON，会丢数据并产生分裂账本

首次审计时 Cloud Run 配置为 `MBOX_REPOSITORY=json`、`MBOX_JSON_STATE_PATH=/tmp/mbox-state.json`，最大实例数为3；当时就绪接口也返回 `repository=json`。每个实例拥有独立临时文件，同一晚的请求可能落到不同实例，造成桌态、订单、支付、库存和任务互相不可见；实例回收或部署后数据会丢失。

经营后果：错桌、漏单、重复服务、账款不一致、审计证据丢失。

上线条件：切换到同一套 PostgreSQL，禁止 `staging/production` 使用 JSON；完成跨实例并发、重启、发布和恢复验证。

### P0-02 真实微信/聚合支付没有接入主链路

首次审计时顾客结账在非本地环境只创建 `wechat_jsapi` 支付意图，但返回的 `wechatJsapiParameters` 始终为 `null`。当时Postar适配器和查单补偿模块只有独立代码/测试，尚未注册支付下单、回调、查单和退款路由。

经营后果：客人自助支付和服务员出示支付二维码均不能完成真实收款；只能依赖物理 POS 人工报送。

上线条件：完成服务商商户参数、服务端下单、验签回调、未知结果查单、部分退款和日对账的小额真金白银闭环。

### P0-03 发布证据与当前云环境不一致

首次审计时发布文档声称验证环境为香港、PostgreSQL正常，但实际服务区域为`asia-east1`且仓储为`/tmp` JSON；测试数也已过期。

经营后果：上线决策可能基于错误证据，无法形成可信的版本签字和事故追溯。

上线条件：发布证据由 CI/CD 自动生成并绑定 commit、镜像摘要、Cloud Run revision、数据库和验收结果；禁止手写“PASS”替代实时证据。

## 3. 整改前高风险经营缺口

### P1-01 高风险“双人审批”可由操作人代填

存酒转赠/作废和整店导入由当前登录员工在页面或请求中直接提交 `approvedBy/approvalActorId`。服务端只验证该员工存在、角色有权且与操作人不同，没有要求第二人登录、输入独立 PIN 或处理待审批任务。

经营后果：一个人可以冒名完成存酒作废、转赠或整店配置导入，双人防损失效。

整改：建立独立审批单；第二人在自己的会话中批准，记录审批会话、时间、设备和前后快照；操作人不能替审批人提交。

### P1-02 卡座低消、订台消费规则和补差不存在

桌台、桌次和桌账模型没有最低消费快照、已消费金额、剩余差额、达标提醒或经理豁免。预约案例虽要求核对低消，代码只处理人数和订金。

经营后果：卡座无法按订台承诺结算，服务员无法提前提醒补单，收银只能线下计算，容易争议和漏收。

整改：配置区域/桌台/时段低消；入座时固化规则快照；桌账实时显示差额；结台强校验并支持有审计的经理豁免。

### P1-03 KDS 没有缺货、退回、取消、错品和重做状态

出品状态只有 `queued -> preparing -> completed -> picked_up -> delivered`。整晚案例中的“热厨缺货”和“错品补做”没有对应领域状态、原因、关联原明细和库存冲销；现有整晚自动测试只覆盖正常出品链路。

经营后果：厨房/吧台只能把异常单一直挂起或伪造完成；顾客补做、取消、退款和库存无法对齐。

整改：增加 `rejected/stockout/cancelled/remake_required/remade` 等事件化流程，强制原因和经理处置，补做任务关联原 `orderItemId/kdsTaskId`，禁止覆盖原记录。

### P1-04 不支持合台、拆单和部分收款

转桌明确拒绝目标已占用桌台，但没有专用合台流程。收款接口自动选择该桌所有未支付商品，不能按人、按商品、按数量或按金额生成本次收款单；商品级部分退款已具备，但付款前拆账未具备。

经营后果：朋友拼桌、加桌、多人分别付款、公司与个人分开结账只能线下处理，系统账与 POS 流水难匹配。

整改：合台保留多个原桌次或建立组合桌账；支付意图由收银选择商品/数量/金额，防止重复分配并支持剩余应收。

### P1-05 库存只有销售商品数量，没有鸡尾酒配方和原料耗用

库存余额按 `productId + unitCode` 管理，订单提交按销售商品数量扣减。没有 BOM、原料、标准杯量、单位换算、开瓶/损耗和理论耗用差异模型。

经营后果：啤酒等整件商品可管理，但鸡尾酒无法核算基酒、辅料和标准出杯，不能承担夜店防损和毛利分析。

整改：建立原料 SKU、配方版本、单位换算和标准耗用；销售、赠送、重做、报损分别生成库存事件；盘点输出理论/实盘差异。

### P1-06 日结只有 API，没有店长交班工作台

后端有营业日关闭阻断，但前端没有日结入口；没有现金抽屉、POS/微信/支付宝分类实收、交班计数、待对账差异、签字和强制复核。`reported_pending_reconciliation` 可被视作已收款并允许结台，营业日关闭也不阻断该状态。

经营后果：能把桌清掉，但不能证明“钱、单、货、班”一致。

整改：增加交班/日结页面，按渠道汇总系统应收、渠道实收和差异；未对账项必须解释并指定次日责任人，经理复核后切日。

### P1-07 销售归属没有进入桌次、订单和支付

`salesOwnerId` 只存在会员资料，订单、桌次和支付没有订台销售、现场销售、协助员工或归属变更记录。

经营后果：无法计算销售业绩、提成和客户维护归属，也无法审计转桌/换服务员后业绩归谁。

整改：在预约和开台时记录销售归属快照，允许经理有原因地变更；订单与实收按明确规则分摊并保留历史。

### P1-08 多实例通知调度存在重复发送窗口

每个应用实例每秒扫描通知队列，并在 PostgreSQL 状态事务提交前调用外部发送接口。多个实例可同时读取同一条待发通知并各自发送，随后只有一个状态提交成功；CAS 不能撤销已经发生的外部发送。

经营后果：权益、召回或服务通知可能重复触达，影响客户体验并产生重复优惠争议。

整改：使用数据库 Outbox 租约/`SKIP LOCKED` 先原子认领再发送；记录供应商消息 ID；失败后由同一幂等键重试。

### P1-09 共享平板切换员工时未清除离线数据

退出只删除登录 token 和员工名称，IndexedDB 中的桌台、任务快照及待同步动作仍保留。下一位员工在弱网/离线时可能看到上一岗位缓存，并可能以新会话重放旧动作。

经营后果：岗位隔离在共享设备和弱网场景下不完整，存在信息泄露和误操作风险。

整改：离线存储按门店+员工分区；切换员工时清理或封存旧快照/队列；未同步动作必须由原员工重新认证后处理。

## 4. 效率与后续范围

### P2-01 临客开台路径过长

运营台显示“可开台”，但空桌不能直接点击开台。临客要进入预约页、新建现场预约，再依次确认、到店、入座。功能可完成，但高峰期操作过多。

整改：门迎在桌台页使用“临客开台”，一次录入人数、来源、销售归属和低消确认，1至2次确认完成。

### P2-02 AI、耳机和摄像头仍是规划能力

当前“AI大脑”实际是确定性事件、SOP 动作卡、SLA 和责任链调度；没有 LLM 建议层、耳机推送、视频抽帧或人脸/酒水余量识别。商业 V1 文档已把视觉列为 `PLANNED`，不应在销售或门店培训中表述为已上线。

整改：先完成事件闭环和经营数据质量，再以只读建议方式接入 LLM；摄像头只做关键事件抽帧 PoC，单独完成隐私合规和误报评测。

## 5. 已通过的关键能力

- 员工签名会话、岗位权限、桌台数据范围和服务员候补责任链已有自动测试。
- 一桌一码、桌次隔离、换桌后旧会话失效、翻台不串账的核心结构正确。
- 客人服务请求支持可配置频率限制和相同需求合并；默认每60秒最多5次。
- 菜单商品、图片、时段供应、临时售罄、购物车和服务员协助点单已经形成主流程。
- 商品级赠送/折扣授权、商品数量级退款、物理 POS 待对账状态和不可变审计基础可复用。
- 正常 KDS 制作、取走、送达及自动生成取送任务的主链路可用。

1. 支付服务商提供商户号、密钥/证书、签名样例和测试环境，完成小额支付、重复回调、未知结果查单、部分退款和账单对账。
