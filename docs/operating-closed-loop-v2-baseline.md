# M-BOX 经营闭环 V2.1：实施基线与切换原则

本文件记录 2026-08-24 在 `origin/main` 的重新核验结果，用于约束本轮迁移与发布；它不是生产验收或外部审批证据。

## 已确认的基线

- 本轮分支从 `b59f27c5944520231a07fb1ae05e2c6b21e60c52` 创建；规范化迁移为 `001` 至 `105`，而非旧兼容目录中的 `001` 至 `025`。
- 已有统一商品目录、渠道可售判定、配方/库存/成本、桌次订单、支付、KDS、打印桥、活动报名/候补及规范化会员、积分、等级、权益的基础实现。
- 顾客点单购物车仍按设备本地存储；服务端没有以有效 `table_session_id` 为范围的购物车聚合、代次、版本或原子命令。
- 顾客桌次摘要仍直接读取员工内部 `display_name`；没有已审批的顾客公开展示资料。
- 小程序隐私页仍是候选内容；现有发布证据只校验运营主体、联系信息、保留策略版本、第三方清单版本和复核附件，未绑定正式政策版本、内容摘要和批准/生效事实。
- 旧会员页仍调用旧会员门户，并包含旧等级；规范化“我的”页使用新的会员接口。
- 顾客端仍存在原始错误文本透传、开发标记和英文界面标签，不能作为正式发布包。

## 实施边界

1. 规范化 PostgreSQL、规范化订单/付款/库存/会员服务继续是唯一业务事实来源；不恢复整店 JSON 运行态，也不以小程序本地状态作为权威。
2. 每项数据库变更使用新的前向规范化迁移，提供兼容读写策略、测试和回滚条件；不得修改已应用迁移。
3. 共享购物车、订单、支付、库存和审计必须在同一权威事务边界或通过可恢复的幂等命令闭环；不得用前端轮询或整份数组覆盖处理并发。
4. 正式隐私内容、微信审核/上传、真实支付、实体打印与员工姓名公开，仍依赖文档列出的外部真实材料。缺失时可完成代码与模拟验证，但发布门禁必须失败关闭。

## 实施顺序

1. 顾客发布底座：正式隐私政策模型与门禁、顾客安全错误映射、中文扫描、顾客公开员工资料。
2. 同桌协作：服务端共享购物车、版本/代次/幂等/会话撤权、共享结账与付款访问一致性、双机验证。
3. 会员与业务闭环：旧会员入口切换、跨订单精确积分/成长值、权益/活动/库存/收银的缺口补齐。
4. 发布：迁移演练、自动化与真实数据库验证、容量/真机/真实角色证据、不可变 Release、部署和读回。

## 外部阻断项

正式生产和微信发布需要真实且已批准的隐私政策材料、微信平台配置及回执、生产支付与门店访问、员工顾客展示名批准清单、打印设备参数、容量基线和真机验收。它们不由代码替代，也不会在缺失时伪造。
