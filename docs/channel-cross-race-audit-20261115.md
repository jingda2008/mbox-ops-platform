## 修复

发现小程序把 HTTP 200 的空对象、不完整绑定信息或其他券的回执视作成功，可能提前清除原请求恢复记录。先新增8个失败复现，再修复：

- 领取必须返回非空券号；绑定必须返回本次券号、绑定号和客组号。
- 校验在持久化请求完成前执行；缺失、错误类型、空白或券号不符均保留原记录。
- 失败后的恢复沿用原幂等编号，并携带仅查询原回执的恢复标记，不自动发起一次新核销。
- 员工网页绑定入口同步补齐类型、客组号及明确选择券号的一致性校验；浏览器重启后仍可恢复原请求。原操作未核对前不能换券重做。

本轮后台业务规则未改，新增实际跨层并发回归。已有数据库唯一约束、事务锁、消费上限、退款与账本规则保持。

## 前后端交叉模拟

将真实小程序券包页面、API封装、请求恢复日志，通过模拟微信网络接口接到真实 Fastify 路由与独立 PostgreSQL。身份由测试夹具提供；现金收款及退款事实为隔离数据，不访问支付机构。

两套故障场景分别是：后台成功后丢失响应、后台成功后返回不完整回执。每套执行：

1. 小程序实际领券，顾客与两个员工请求同时绑定同一张券。
2. 数据库仅有一张券、一次绑定；前端保留待核对错误及原请求记录。
3. 生成并模拟支付100元原价、90元应付订单，生成后续报价。
4. 开启未提交的90元全额退款事务；从数据库阻塞关系确认佣金核对确实等待该事务。
5. 同时提交整桌转移、两次旧报价消费和小程序原请求恢复，再提交退款。
6. 转桌与回执恢复完成；两次旧报价均被拒绝，没有生成第二张订单。
7. 券包显示已兑现历史；已用优惠仍为10元，不恢复额度；三次并发核对的净计佣基数及佣金均为0，追加差额为0。
8. 小程序恢复请求沿用原编号并带恢复标记，仅在完整回执验证后清理日志。

另外运行原有渠道并发领取、赠品、拆桌/合桌、共享封顶、撤单、退款、结算及权限回归。员工网页验证覆盖恢复模块及实际使用的回执校验函数，本轮未做浏览器界面录屏。
