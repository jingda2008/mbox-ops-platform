# 多人转桌、拆后合桌与退款加单并发审计

后续修订：本报告中“旧无快照调用保留兼容”的边界已由 [旧客户端与恢复审计](channel-movement-recovery-audit-20261115.md) 收紧为只恢复已完成原请求；无快照的新拆并桌不再允许。下文保留当时验证记录。

时间：2026-11-15。仅本地开发、隔离数据测试；暂不部署。

## 本轮修复

1. 拆并桌网页预检、提交增加即时防重复保护；提交期间不能切换拆桌/并桌或关闭操作窗。
2. 桌次、实际桌位、位置版本、人数或目标桌状态改变后，旧预检不能提交；迟到的名单、预检或提交结果不覆盖新桌。目标变化不会让预检一直停在加载中。
3. 后端预检返回 `movementGuard`，包含源桌位、位置版本、源桌人数、目标人数和容量。网页原样提交，后台复用现有拆并桌事务锁内校验；不一致时拒绝执行，要求重新预检。缺少该字段的预检结果，网页不能提交。

事实区分：已识别顾客的旧请求原本就可能被参与记录位置校验拦截，不能说所有旧请求都能绕过。新增快照检查补强了无已识别顾客的整桌并桌及位置、人数变化的预检约束。没有修改优惠、退款、佣金业务规则，也没有数据库迁移。

兼容边界：后端仍接受未携带 `movementGuard` 的历史调用，保留原有参与记录和营业状态检查；新增网页必须收到并提交快照。新增保护应由前后端配套发布，不能把本轮结果推断为所有旧客户端已获得同样保护。

## 模拟结果

| 场景 | 已验证行为 |
|---|---|
| 两名不同员工把同一桌转向两个目标 | 一个成功、另一个冲突；原成功请求重试只返回回执，不再转一次 |
| 两名不同员工把两桌转向同一空桌 | 一个成功、另一个冲突；顾客实际位置和桌次一致，原优惠绑定保留 |
| 预检后整桌被转走，再提交旧拆桌请求 | 拒绝旧请求；刷新名单取得新的参与记录及预检后可以执行 |
| 无已识别顾客的整桌并桌，源桌预检后转走 | 携带旧快照的请求被拒绝，两桌保持营业状态 |
| 原客组拆桌，再由两名员工同时合回原桌 | 只合并一次；原订单不迁移复制、原绑定不新增，客组优惠不重置 |
| 合桌后使用已关闭拆出桌的旧报价 | 拒绝；原桌重新报价只给剩余额度 |
| 退款先提交、加单等待 | 通过 `pg_blocking_pids` 确认真实锁等待；退款提交后旧报价被拒绝，重新报价 |
| 加单先提交、退款等待 | 同样验证真实锁等待；已成立订单不被事后改价，后续优惠按最新净消费重新计算 |
| 前端连点、返回迟到、换桌、目标占用变化 | 不重复发起请求，不采用过期预检、不误报新桌操作成功 |

退款交叉用例：100 元商品、减免 10%、客组累计上限 25 元；首单实收 90 元，退款 45 元。

- 退款先提交：下一单优惠 5 元，再下一单优惠 10 元。
- 加单先提交：下一单优惠 10 元，再下一单优惠 5 元。
- 两条路径均累计优惠 25 元、净实收 230 元、佣金 23 元，三次并发佣金核对一致。顺序会影响每一笔订单，不能要求两种时序的单笔金额完全相同。

## 员工操作与后续验收

- 遇到“位置、人数、容量已变化”：刷新名单、核对当前桌号，重新预检；不要继续点旧确认。
- 拆后合桌：核对原券、原渠道和累计优惠；历史订单仍在原桌次，不能因为合桌再次送券。
- 退款与加单同时发生：以服务端重新确认的报价为准，退款不恢复已使用额度。
- 正式发布后仍需现场验证双设备转桌、微信重新扫码及实际退款。此次没有部署、上传小程序或修改生产数据。
