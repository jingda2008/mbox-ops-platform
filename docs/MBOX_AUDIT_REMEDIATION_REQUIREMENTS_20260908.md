## 2. 所有整改必须遵守的业务不变量

| 约束 | 必须保持的规则 |
| --- | --- |
| 营业与财务分离 | 支付查询慢、异常或未知，只影响该支付尝试的财务核对，不能锁桌图、点单、服务、其他订单或其他员工 |
| 允许再次收款 | 按用户经营要求，所有员工岗位应具备发起收款能力；账号/门店授权仍由服务端核验。未确认结清时，员工明确选择重新收款可以创建独立尝试；不能靠授予退款、调账或系统管理权限实现 |
| 成功到账才收敛 | 已确认足额到账，禁止继续按同一原应收金额发起收款；部分到账则按经核验的剩余应收处理。现金/POS须有明确确认和独立凭证；“发起”“请求已收”“二维码已生成”不是到账 |
| 每笔尝试独立 | 同一次请求重试使用原编号；员工明确另收一笔使用新尝试、新商户单号。不能按同金额、同菜品或同桌永久去重 |
| 多收不重复营业 | 多笔迟到成功保留全部收款事实，超额进入退款待办；不重复创建出品、不重复扣库存、不重复计算同一订单销售收入。不得篡改旧支付为失败 |
| 离店结清 | 桌台显示本地未结应收，结台按本地结清及服务/出品处置规则；结果未知的历史尝试进入财务追踪，不作为整桌永久不可用条件。不允许把真实未收款隐藏成已结清 |
| 权威事实与历史 | 金额、单位、可售、成本、角色权限、条款版本和财务状态由服务端强类型事实决定；展示快照不能承载新的经营真值；更正留痕，不删除凭证或历史审计来消除提醒 |
| 授权可拒绝 | 会员、手机号、订阅消息各自有独立授权范围和状态，不默认勾选，不以消息拒绝阻断不依赖它的点单/预约。发布版本和真机授权单独验收 |
| 输入与未知结果可恢复 | 明确失败保留输入；写成功但刷新失败不能要求重新新增。离页不让页面永久忙碌，也不能把未确认写入简单清空后盲目重发 |

## 3. 按关联链路组织的实施包

实施包不是新增风险数量；已确认问题沿用SYS编号。标注“联动回归”的范围不代表已经证明存在缺陷。负责人为建议协同岗位，不代表已派单；目标版本统一为“下一统一修复候选，实施时确认编号”。

### REQ-01 异步对象归属与页面恢复（P1基础包）

主风险：SYS-092；共同依赖：SYS-088、098、102。负责：前后端、测试。

- 拆开三种身份：账号/门店/桌次等业务上下文、页面读取请求代次、一次写入尝试。轮询换代不能取消正在提交操作的收尾；旧桌结果又不能进入新桌。
- 每个结果及其错误、loading、finally均核对所属对象。A慢B快、旧失败晚到、快速切换对象不得覆盖当前页面或解除另一操作的保护。
- 保存能恢复的最小操作信息：业务对象、尝试编号、提交正文/摘要、状态。恢复必须经权限校验，按账号和桌次隔离；敏感信息不存入无期限普通日志。
- 离开/切后台再返回：已成功则显示已处理，明确失败则保留输入并可重试，未知则核对原尝试。只对同一提交保护，其他无关按钮继续可用；并发安全仍由后端保证。
- 适用：服务、服务进展反馈/催办、点单快捷服务、购物车同步；收款、预约和演员歌单使用同一原则，但不强塞成一套混合状态变量。

关闭标准：延迟201/明确失败/丢响应、6秒轮询交错、同页返回、重新进入、换桌/换账号、页面销毁均有测试；数据库只有预期的业务效果，busy不会永久残留，旧对象信息不泄露。

### REQ-02 全入口收款、释放与晚到到账闭环（P1）

主风险：SYS-088—089。依赖：REQ-01、03、05、11；负责：支付开发、收银、财务。

- 本桌收款、收银工作台、协助点单内收款、顾客支付恢复使用一致的支付状态契约。订单名、应收、二维码、支付动作必须来自同一个核验过的订单/尝试对象。
- 新创建的未决支付与重新进入读到的未决支付，均提供“保留上一笔待核对，继续收款”。不得依赖列表尚未刷新的旧字段才显示入口；顾客明确退出支付也应释放操作层。
- 释放是本地受控操作，不等待渠道查单/关单成功。保留原渠道编号与财务追踪，允许扫码、付款码、现金、POS等已支持方式另起尝试。无法访问本地服务时不得虚报释放成功，但整页必须仍可返回并说明状态。
- 创建新尝试前服务端原子核对应收和已确认收款；多员工并发、查询/回调反序仍能归到各自尝试。不能只依赖前端隐藏按钮防止已结清订单重收。
- 晚到成功造成多收：保存全部渠道流水、更新超额状态、幂等生成退款待办；退款审核/执行权限与发起收款权限分开。支付、退款、对账、出品、积分和营业报表均不得重复入账或漏冲回。
- 保留既有持久化退避、停止追踪条件和重启恢复。自动任务与页面查询共享限频边界；状态无变化不反复新增同型审计。具体渠道有效期、终态和IP字段按正式接口约定核对，不能自造过期判定。
- IP风控等明确发起失败提供原因及切网/备用支付指引；新发起使用新商户单号。不能把所有网络错误翻译成“本次未扣款”，只有渠道证据足够时才使用该文案。

| 页面状态 | 必须表达 | 允许的操作与关联结果 |
| --- | --- | --- |
| 等待渠道确认 | 结果未确认，不等于失败 | 查结果；释放该尝试并继续收款；不锁桌 |
| 未确认、已释放 | 上一笔仍在核对，营业可继续 | 另起尝试；明确多收风险；历史尝试保持可查 |
| 明确失败/关闭 | 此次尝试已终结，展示可靠原因 | 按剩余应收重新发起，不能复用终结商户单号 |
| 足额到账 | 已确认结清 | 原应收收款按钮不可用，其他新订单不受影响 |
| 晚到多收 | 已发现多收，并显示退款待办状态 | 进入授权退款处理；待办生成失败必须显式报警并可恢复 |
| 退款处理中/失败/成功 | 分别表达等待、失败可处置、已确认退款 | 不能将提交成功当退款到账；终态队列与历史分开 |

关闭标准：A/B切单反序不串码；扫码/付款码新建后立即可释放；查询长时间不回及服务重启不影响其他桌；两员工先后/并发收款、迟到双成功、重复回调、部分退款、退款失败重试均有隔离数据库读回。真实资金验收须另行授权。

### REQ-03 一次操作只生效一次，合法再次操作不受阻（P1基础包）

主风险：SYS-090—091；关联SYS-101、103。负责：前后端、测试、财务。

- 稳定“本次提交”编号；网络重试、超时、丢响应、返回恢复沿用原编号和正文。只有用户明确开始下一次业务操作才换编号。
- 服务端指纹仅纳入决定业务含义的稳定输入；随机生成的记录ID、处理时间等不得导致同一请求冲突。账号/门店归属仍校验；刷新凭证不把同一订单变成新订单。
- 同编号同正文返回原结果；同编号不同正文明确冲突；不同编号的有意相同业务允许。数据库事务、防并发约束、返回结果与业务效果一并落地，不能只禁用按钮。
- 协助点单普通单/赠送单检查订单、菜品拆分、库存、KDS和打印任务；权益检查暂留/核销；费用检查流水、修订和利润。复查更正、团购券及共享提交封装，不把疑似同型问题直接计为已复现。
- 保留已有数据。历史疑似重复费用按凭证与业务意图人工核对后更正，不能自动删除同金额记录。

关闭标准：分别执行“写入成功但响应丢失→重试”“相同编号并发”“正文改变”“成功后有意再新增”；每条链数据库效果次数正确。订单上下文/登录凭证到期时有恢复途径，不因换凭证静默创建第二单。

### REQ-04 商品、ML、套餐选择到出品成本的贯通（联动回归，涉及资金/库存不得降级验收）

关联：SYS-090、104，R05/R17、V01/V02/V08/V09。负责：商品/库存开发、厨房、吧台、门店运营、财务。

- 检查完整链路：后台商品与销售规格 → 发布/渠道/可售规则 → 顾客与员工目录 → 套餐固定项/选择组 → 每份购物车选择 → 订单不可变明细 → 厨房/吧台出品、打印、库存与成本/利润。
- 所有员工岗位按协助点单权限读取适当目录，不能要求商品管理权限才能看小食。商品被隐藏须在授权管理端可追溯到明确原因；前台查询失败不能当作“没有该类菜品”。核对搜索、分类、分页和缓存失效；下架后旧购物车提交仍由服务器重新校验。
- 后台必须能配置固定项、可选商品、每组选择数量/限制、是否允许重复、差价（如已有支持）与销售单位。保存/发布检查不存在的选项、停用单品、缺价/缺配方/缺成本等；不无声代客换品。是否新增尚不支持的业务能力须另确认，不在布局修复中暗加。
- 从“加入套餐”进入时优先到选择区，浏览详情仍可先看图文。同款两份各自维护选择，第3份不继承第1/2份；未选完不可确认，取消不加购，修改一份不影响另一份。大量选项可搜索/分组滚动，不强求所有选项一屏挤完。
- 同桌多人并发编辑共享车须有版本冲突或明确合并策略，不能最后写覆盖掉别人的选择；重新进入恢复服务端权威状态。下单冻结所选单品、份数、规格、版本与价格，不只存一段展示文字。
- 出品/打印必须含具体所选酒水与数量、制作备注、份序；去重打印重试不重复出品。取消、退品、补做、退款和库存恢复沿既有业务规则分别处理，不能“一退款就无条件回库”。
- ML仍为员工配方/损耗录入的明确单位；商品销售单位与库存基础单位不同则显示转换依据。瓶容量、每份用量、损耗、采购成本换算由统一规则处理，禁用无提示的“0.0几瓶”输入。件数、毫升、金额、比例、人数、日期等全部数字字段有单位/格式提示。
- 套餐成本按实际选中单品与用量汇总；订单收入按套餐成交价，优惠影响毛利，不按单点原价虚增收入。确认无差价条件下选择不同成本酒水仍应改变成本；缺成本不能显示成0成本/高利润。历史订单成本冻结，不随今日配方价格回写。

关闭标准：保护已验证的3款4份/两份不同选择案例，并补订单、KDS、库存、打印任务、成本和退款分摊读回；覆盖整瓶/单杯/ML、多组选项、停用/售罄/调价、并发共享车、成本缺失、舍入边界。精确利润口径与采购计价沿已批准规则，未知规则由财务确认，不由开发猜测。

### REQ-05 桌台、待办、服务与出品的同步闭环（P1关联）

主关联：SYS-092、089；负责：运营前后端、收银、服务、厨房/吧台。

- 服务按钮创建任务后，顾客服务进展、员工任务、桌图角标、完成/催办状态更新同一任务事实；提交响应丢失可恢复原任务，不复制创建。
- 桌边服务常用选择改为紧凑可读网格，提交忙碌仅影响同一操作；“正在通知”必须区分发送中、已收到、已接单和处理失败。样式整改不能掩盖卡busy。
- 桌图颜色按本地未结应收、营业与实际待办决定；红/黄角标之外同时有文字、金额/数量。支付查询错误不得把整桌涂成长期不可用。
- 汇总、过滤条件和列表使用一致范围：门店、营业日、区域、责任桌与权限。全店提醒与“我的范围”统计必须明确区分；出现“有1张待支付、下面无桌”时能解释范围或进入对应列表，不能一个按钮无论如何点都无结果。
- 退款提交/批准/执行/终结、出品超时处置和交班遗留完成，都更新工作台列表与计数；终态离开默认待办但历史仍可搜索。仅通知已读不等于退款/制作已完成；人工关闭需角色、理由和审计，不能给所有员工无限关闭财务事实的权限。
- 建议验收目标：操作成功后当前页立即更新并核验读回，其他在线页在正常网络下15秒内完成本地状态同步；此为待测目标，不是目前性能事实。不以高频渠道查询实现页面同步。

关闭标准：完成/失败/取消/晚到回调、跨日/跨区、不同角色同时操作、上一营业日处理、列表为空但全店有异常、事件丢失后刷新恢复；各处计数与明细可对上，正常操作无全屏锁死。

### REQ-06 费用、员工工资、权限和利润入口（P1/P2）

主风险：SYS-091、093—095；依赖REQ-03、10、11。负责：财务开发、老板、财务、权限管理员。

- 保留每门店每周期一个工资批次，改为多人草稿明细，支持追加、修改、移除和整体核对/确认/入账。已入账更正留痕，不直接编辑历史；不能只删除周期防重约束。
- 同周期至少三人、已有草稿追加第二人、同员工重复、并发编辑、确认时并发补录均有明确结果。草稿、已确认、已入账、作废/更正状态与按钮契约须在实现前对齐当前模型。
- 房租、乐队、厨房、员工工资、其他自定义费用支持既有每日/周期录入；工资和手工人工费用不得无提示双计，周期费用重复生成需幂等。厨房原材料成本与经营费用须分清，避免同一采购/耗用重复影响利润。
- 月薪/时薪/按场等按已批准规则计算；缺勤、部分月份、扣补、税费等未定义政策不能猜。核算、经营入账、实际发工资是不同状态，不将工资批次入账标为银行已转账。
- 费用保存按REQ-03只落一笔，成功但列表刷新失败显示已保存及记录入口；支持月份/日期、搜索、稳定分页、历史详情和更正。不能只显示前50条而总数包括全部。
- 导航、模块内容、读取接口、具体按钮与写入接口按最小权限一致：纯费用查看、纯工资查看、费用管理、工资确认/入账分别能完成授权动作；服务员无权读工资不得通过接口绕过。
- 报表按同一范围和口径展示收入、商品成本、经营费用、人工及利润，能够追到原始单据/更正；更正和作废只影响应影响的期间并明确会计口径。

关闭标准：0/1/50/51/500条、跨月搜索与更正；100元丢响应重试仍100元；三人工资、并发、重复员工、周期费用重跑、最小角色矩阵、利润到明细核对。已有历史金额不做未经核对的批量清理。

### REQ-07 会员、偏好、条款、权益和消息的统一契约（P2）

主风险：SYS-096—097、103、105、108；依赖REQ-01、03、09、11。负责：会员开发、运营、权限/隐私负责人。

- 酒水偏好保留多选语义，前端、接口、数据库、初始化读取和推荐消费方往返一致。定义未选择、“都可以”、单选、多选的区别；“都可以”不得与具体选项矛盾。旧mixed值不能推断恢复成用户没留下的原组合。
- 配置缺失不使个人资料保存依赖一个无关推荐策略；推荐不可用与偏好读取失败要分别诊断。重试、重新进入、旧客户端和微信/支付宝对照验证；推荐降级不能阻止基本点单。
- 先验证活动入口及已发布有效条款，再展示入会与手机号入口；条款缺失/失败/更新时明确暂未开放/重试/重新确认。无效活动ID不先弹邀请；首页、我的、活动/分享入口规则一致，找回会员单独保留。
- 订阅模板配置、顾客授权记录、可用次数/适用上下文、实际发送结果分别展示。两接口部分失败保留已成功部分并单独重试；拒绝/未配置/用完/读取失败不混为“暂无”。不自动改变同意状态。
- 优惠券及权益页的加载、错误、成功空态、成功有数据互斥。失败提供页内重试；上次数据若保留要标未刷新，不允许据缓存完成核销；切换账号不残留旧权益。
- 使用权益按当前权益/桌次/操作意图防连点和重试重复暂留。允许明确申请两份，但不能通过“正在提交时再点一次”偷偷占两份；取消、超时、换桌、员工核销、额度恢复形成闭环。
- 积分/成长值账户、兑换扣减、权益暂留/交付、订单支付/退款联动保持幂等；用户看到的数量须解释可用/暂留/已用，不能把暂留算成已核销。年度规则/有效期/必读限制保留全文入口。

关闭标准：偏好多选保存读取和实际推荐消费；有效/缺失/过期条款的全部入口；双接口单败/双败/401/正常空态；同权益双击、返回重试、明确两份、取消过期、换桌、员工履约与额度读回；真实手机号、订阅、核销与积分交易另列验收。

### REQ-08 预约、演出与表单恢复（P2）

主风险：SYS-098、101—102；依赖REQ-01、03、11。负责：预约/演出开发、门迎、舞台。

- 预约可用场次/容量按日期、时间、人数和请求代次归属；旧成功、错误或finally不能覆盖新条件。切换后清理不再有效的演出选择；提交时按完整快照再次服务端校验，不能仅凭前端可用标识受理。
- 演员及歌单按演员ID/搜索/请求代次隔离；切换时关闭不匹配编辑。保存、停用都核对当前目标归属及服务端权限，不能用下拉显示的演员名代替歌曲真实归属。
- 演员新增、批量歌单、单曲编辑、场次新增，仅确认写成功才能清空或关闭。明确失败留输入；成功但刷新失败保留成功凭证；结果未知先查原操作，不重新生成第二份。
- 联动回归：场次取消/改期/停用 → 首页、演出日历、顾客预约选择 → 员工预约待办、顾客通知资格 → 点歌/舞台列表。不能删除仍被预约/订单引用的演出事实，不能无提示清除顾客已选偏好。

关闭标准：日期A慢B快/旧失败、人数变更、提交前容量变更；演员A慢B快、编辑中切演员、停用取消；四类表单覆盖拒绝/断网/丢响应/成功后刷新失败；后台读回正确对象且输入不无故丢失。

### REQ-09 小程序公共布局体系与逐处整改（P2）

主风险：SYS-104、106—107；覆盖R01—R18与V01—V09。负责：页面设计、小程序开发、测试、门店审阅。

- 先在原生运行时验证默认样式与页面规则的覆盖关系，再形成明确组件约束。不要全局写固定宽度、无限提高优先级、到处加隐藏溢出或缩小全部文字来压住截图问题。
- 六类按钮分别定义：主要提交、次要操作、网格/短选项、文字链接、关闭/分享图标、头像。规则包含宽高、最小/最大尺寸、外边距、内边距、收缩、对齐、行高、disabled/loading/selected状态及可点击范围。
- 网格单元扣除实际内边距和gap后分配宽度；子项允许在单元内收缩，长标签按内容换行；父容器没有横向滚动不代表子按钮没有相互覆盖。
- 桌边服务候选：常规屏优先3列2行，小屏/大字按2列3行或自然换行；判断依据为实测标签和点击范围，不按机型名字硬编码。常用动作和服务进展优先，自定义需求紧随，长说明折叠。
- 套餐选择字号采用紧凑正文层级，不抢过套餐名和确认操作；价格、已选数量、必选条件、选中态清楚。缩紧无效留白，不缩到必须眯眼或精确点按；实际字体与行高以原生样稿和用户审阅确认。
- 关闭/分享保留小巧可见图形和足够点击范围；浅/深图片及滚动后都可辨识。头像方形布局、圆形裁切且不得拉伸；图文缺图/坏图分支能利用可用宽度。
- 横滑轨道可以保持不换行，但卡内恢复正常换行；摘要截断必须可查看完整标题/规则。图片按内容选择裁切或完整展示，不因撑高/撑宽破坏卡片和商品价格区。
- 购物车条、tab栏、底部确认、弹层底栏共存时，滚动内容有实际底部避让；最后一项价格/按钮和输入错误可滚动到达。避让基于真实安全区与栏高度，不重复加安全区，也不把固定高度当所有设备通用值。
- 少量数据弹层按内容收紧，多数据限高滚动；确认区独立但不覆盖正文。处理键盘后输入、错误与操作可见，关闭/返回恢复滚动与焦点，不残留透明遮罩拦截页面。

关闭标准：18处逐项留修复前后原生图与边界读数；21页和公共弹层回归，包含按钮所有状态、长数据、小屏、大字及键盘。不得只改网页预览或只证明整页scrollWidth合格。

### REQ-10 员工网页的信息层级与操作便利（P2）

主风险：SYS-099；联动所有19路由。负责：网页开发、页面设计、各岗位。

- 费用刷新、财务页签、设备动作、账号操作等交互的实际命中区域达到项目采用的44×44 CSS像素基准并防收缩；这是项目验收基准，不冒充所有平台唯一标准。图标外观可以更小，命中区不能互相遮挡。
- 页面共同层级：当前对象/关键状态 → 本次主要操作 → 列表/输入 → 按需查看的规则说明与历史。重复标题、长解释、无数据高指标卡应压缩，不删除风险提醒和审计入口。
- 手机端筛选项清楚分组、可折叠但展示已选条件；底栏标签使用可理解短名称，不挤成破碎多行。主动作不和危险的取消、退款、作废、停用紧贴且同色。
- 费用、库存上架、会员规则等长表单提供段落、进度/保存反馈及错误定位；默认值、必填项、单位和权限限制明确。更多项目后仍能定位刚保存记录，不能保存后跳至空白顶部。
- 桌图保留区域、责任桌、待收款/异常的一步入口；颜色加文字，不只靠红点。页面内弹层、浏览器返回、底部导航不覆盖输入或相互抢滚动。

关闭标准：19路由在手机窄屏、桌面和适用横屏复验；关键按钮实际点按、表单失败保留、真实待办优先显示。美观方案由门店审阅，布局几何合格不自动等于审美通过。

### REQ-11 通用状态、权限、缓存与数据一致性（跨系统保护包）

主关联：SYS-094、097、108；服务所有实施包。负责：前后端、权限管理员、测试。

- 通用读取状态定义为：加载中、成功有数据、成功为空、失败、部分失败、旧数据待刷新。错误不吞成空数组；重试不清除已验证的其他模块结果；错误码/关联请求号可诊断但不暴露客户隐私或密钥。
- 通用写入状态定义为：编辑中、提交中、明确成功、明确拒绝、结果未知。每个按钮明确重试的是原尝试还是新意图；同一业务不能在不同页面给出相反结论。
- 对导航可见、按钮可点、API授权、服务端对象归属分别反测。岗位继承、临时权限撤回、停用账号、会话过期时，既不能有权无入口，也不能无权接口仍能执行。
- 所有缓存包含适当的门店、账号/会员、桌次、营业日或查询条件边界；退出/换号/换桌不显示他人账单和权益。写成功后更新或失效相关列表/汇总；刷新消息丢失时可通过安全读回恢复。
- 配置、价格、条款、配方/成本与规则版本变更有明确生效范围；订单/财务历史冻结事实不可被新展示配置覆盖。后端新旧接口共存期与小程序旧版本明确兼容，不假定所有顾客立刻升级。
- 监控沿用/补齐：支付长时间未知、已释放仍高频查单、单笔异常查询次数、双成功收款、成功无对账、退款终态未关闭待办、渠道/IP错误异常升高；另监测同意图多业务记录、恢复后busy残留和投影计数不一致。告警需去重、归属和处理入口，不反过来阻断营业。
- 告警阈值与采样按既有配置和现场量校准，5分钟未确认可作为重点观察条件；这不是强制判失败或停止财务追踪的时限。日志避免全量银行卡、手机号、会员身份和授权凭证。

关闭标准：跨角色/跨门店/换桌/会话失效、缓存过期、部分接口失败、旧版本读写、事件重复/丢失均有契约测试；账单/待办/库存/权益/利润分别与权威记录核对。

### REQ-12 逐页逐键证据与交付门禁（P2）

主风险：SYS-100。负责：测试、开发、发布负责人、门店验收。

- 实施前更新源码/构建/数据版本清单；先保留每个已确认反例，修复后运行同一反例及关联链路。复现问题的测试“通过”不能标为修复通过。
- 微信和支付宝适用页面/样式/数据契约保持对应，支付、登录、手机号等平台适配保留差异；静态同构不替代各平台原生验收。
- 网页预览、微信原生、真实iPhone/Android微信、真实支付/核销、物理打印分别留证。禁止改受测高度/overflow后声称没有遮挡；缩放截图、修改设备信息不是真实小屏/大字体。
- 每个问题必须关联：改动文件与版本、前后对照、自动测试、实际操作、后端读回、未完成边界、风险清单状态。缺少证据就保留待验，不批量打勾。
- Git本地提交、推送/合并、后端部署、微信开发版本上传、设置体验版、真机验收分别核实回执。当前无任何一项发布授权；后续以用户明确命令为准。

## 7. 每个按钮及失败分支的验收合同

逐键登记单位是“页面＋实际动作＋角色/对象状态”，不是WXML绑定数量。输入、滚动、授权事件与动态重复行分清；重复行至少覆盖首/中/末、长内容、禁用和权限边界实例。

每条验收记录必须具备：

| 字段 | 必须回答的问题 |
| --- | --- |
| 入口与前置 | 哪页/哪个弹层？什么角色、账号、门店、桌次？缺条件时能否解释并正确返回？ |
| 点击与命中 | 实际可点范围是否正确？与邻项/遮罩重叠吗？disabled/loading/selected真实吗？ |
| 请求与归属 | 发的是哪个对象、哪个版本、哪个意图编号？旧响应能否串入新对象？ |
| 权威效果 | 产生/修改哪些订单、流水、库存、任务、额度或配置？权限与并发约束在哪里？ |
| 成功反馈 | 当前页、上一页、列表、汇总、角标、另一员工页如何同步？能否独立读回？ |
| 失败与未知 | 必填、403/401、服务失败、超时、丢响应、刷新失败分别显示什么？输入与编号是否保留？ |

### 7.1 视觉与设备矩阵

- 以320/360/390/430逻辑像素作为布局边界样本，记录实际可提供的原生环境；缺某一原生宽度不能用缩放冒充。员工网页另测桌面与适用横屏。
- 微信原生正常字号及真实放大设置；真实iPhone/Android微信。各自记录型号、系统、微信/基础库、可用视口、安全区和候选版本。
- 每页至少加载/成功空态/有数据/错误；含长标题、多记录、大金额、缺图/坏图和已登录/未登录。按页面业务补待处理/处理中/完成/拒绝/退款等状态，不给不存在的状态凑数。
- 每个有固定栏或弹层的页面留首屏、滚动到底、弹层和键盘状态；金额、价格、提交、关闭、错误定位和末条操作都可到达，不要求所有内容首屏可见。
- 同时测整页边界、组件内边界、相邻控件重叠、文字换行/行高、图片比例和实际命中范围；不能只测页面是否有横向滚动条。
- 验证各入口返回路径与遮罩清理，底栏不会重复、安全区不会叠加、输入法关闭后布局恢复。平台分享/电话/手机号/扫码等须真机与明确授权，不用桩返回冒充。

## 8. 数据兼容、改造顺序与成本控制

### 8.1 数据和接口要求

- 优先复用现有强类型模型、支付退避与业务服务；需求不等于要求整体重写或新增数据库表。只有当前模型无法表达经确认的契约时才增加迁移。
- 先做兼容读取和新增字段支持，再切前端写入；跨版本阶段旧客户端不得把新的多选/逐份套餐数据覆盖回单值。必要时采用明确的版本能力检查，而非静默降级丢数据。
- 工资沿整店周期批次扩展明细；偏好历史mixed保留来源不臆测；账务、支付、退款、成本快照与审计不可破坏性覆盖。迁移做备份/恢复、重复执行、防锁表与大样本耗时评估。
- 同步检查事件消费者、定时任务、投影、缓存键、导出/报表、打印和测试契约。增加字段不等于下游已经使用；每条要求有实际读取/写入消费者证据。
- 历史数据修正单独列候选记录、原因、金额影响、回滚/更正方法并获授权；不得把“改程序”的命令解释成可批量清除营业历史。
