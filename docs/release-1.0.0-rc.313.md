# 1.0.0-rc.313 营业日特殊订单查询修复

rc.312 的 PR 全库 4,807 项通过，但在混合历史库中，5,002 单的财务用例仅汇总部分即耗时 52,467 ms。进一步使用 PostgreSQL 的嵌套执行计划，在受限账号下发现候选订单集重复扫描 5,001 次，检查约 2,500 万行。单门店空历史库的执行计划未复现这一问题。[PR 数据库验证](https://github.com/jingda2008/mbox-ops-platform/actions/runs/45167876763/job/137669553727)

schema 365 将本次营业日期范围内需要按原账复核的特殊订单号一次去重，再按订单号关联。升级脚本只调整现有函数的查询结构并更新版本元数据。由门店现有 schema 363 直接升级时会依次应用 364 和 365。渠道索引及已确认补菜款的收银余额修复均随本补丁交付。账款、积分、门店营业配置及票档由原流程维护。[上一个候选的修复与核对](release-1.0.0-rc.312.md)

在同一套混合历史数据生成流程中，受限账号连续读取单日、日期范围、空日期和跨店结果，耗时由 1,045 ms 降至 25 ms。新增执行计划回归会统计日期范围订单集的实际访问行数，并保留原财务和渠道用例限时。

从全库测试保留一份隔离快照并刷新统计信息后，通用执行计划还会重复关联收款汇总。单营业日诊断触发 10 秒查询上限。函数现按实际门店和起止日期生成计划，该设置仅在函数内部生效。相同快照、相同账号下，两次 5,002 单查询分别用时 17 ms 和 10 ms。回归同时检查候选订单访问次数和连接过滤掉的行数。

## 门店后台发布核对

2026-11-23 21:55 CST。门店后台已由 rc.310/schema 363 升至 rc.313/schema 365，提交 `ca70380c`。就绪接口、镜像摘要、写入状态及门店目标均已核对。最终切换窗口内新增 4 个订单、4 条支付记录、1 个会员、1 个积分账户和 1 个订单积分批次。按创建时间复算，5 张发生增量的表中存量记录指纹均吻合，另外 5 张表的快照一致。新增支付记录中 3 条成功，1 条失败，对应原单已取消、未收款。

同一营业日 2026-10-29 的 21 笔订单，切换前后按原单核对的订单数、应收、欠款和待处理退款等全部汇总字段相等。单次只读查询为 154 ms、19 ms。两次快照之间的缓存及营业负载可能不同。

主线 4,807 项数据库测试全部通过。5,002 单的财务汇总检查耗时 55 ms，范围订单集共访问 10,009 行。渠道回归沿用 5 秒上限。

第一次切换后，发布机访问员工页面超时并触发自动应用回退，rc.310 在兼容的 schema 365 上恢复服务。随后通过物理网卡访问相同公网 HTTPS 域名，保留证书验证、原时限和四个页面的浏览器检查，复验通过后完成切换。首次操作与最终切换之间另有两次员工开桌，原有桌次名单和状态校验值一致。最终售票档为 0。

隔离历史快照以 153 单、279 笔收款、220 笔退款演练升级、重跑及恢复，核对了 8 份原日结和 155 项商品奖励计算基础。本地全库 4,806 项通过，容器恢复用例由远端执行。独立营业 HTTP 验证 2,400 个请求全部成功。
