## 1. 问题与目标

李艳提交商品售后退款后，三沐在收银页点击普通退款“复核通过”，出现“支付服务暂时不可用，请稍后重试”。这类申请已有原商品售后单，审批需要同时维护售后决定和关联退款。当前普通退款入口未区分来源，直接更新退款状态被一致性保护拦截；统一错误提示又把内部审批冲突表达为支付服务故障。

目标：员工从收银页看到该申请后，能直接打开对应的原商品售后单，由有权限的另一人完成一次审批。原售后决定、退款执行及界面状态一致；旧页面和直接接口调用也必须受到保护，不能靠隐藏按钮解决全部问题。

## 3. 需求清单

### R1. 识别退款来源，给出准确入口

- 收银工作台返回退款来源及服务端核实的原售后单关联、可执行动作。以实际关联表为准，不依赖 QR 前缀、申请原因或客户端传入的 caseId 判断。
- 普通资金退款继续使用现有普通复核流程；商品售后关联退款展示“商品售后退款”，主操作为“处理原售后单”，打开准确原单，无须员工重新搜索。
- 详情保留桌号、原订单、商品与数量、退款金额、申请人、申请时间、原因、售后状态、资金状态。展示退款进度时不得仅用售后“已批准”代替资金“已退款”。
- 对商品售后关联退款，不再显示能够独立改变退款决定的普通“复核通过”“复核驳回”按钮。驳回、撤回同样沿原售后状态机处理，保持既有权限。
- 已完成记录显示结果及凭证和查看入口；仍有实物处置、岗位通知的，保留对应待办，不再次出现资金审批按钮。
- 返回列表保留查询条件和位置；原单不可读、关联异常或权限不足时，明确原因和可执行下一步，不能静默跳转普通审批。

### R2. 后端保护与一次审批

- 普通退款 approve/reject 接口在权限与作用域核实后识别原售后关联。对关联退款，返回受控业务冲突，引导原售后入口；不得独立修改退款决定，也不得偷偷代批原售后单。
- 建议错误码 REFUND_REQUIRES_CASE_DECISION、HTTP 409；已授权响应可带 caseId、orderItemId 等内部导航必要字段。字段和命名开发时与既有契约统一。
- 原售后审批复用既有命令服务，在同一事务中更新原售后决定及全部关联退款的审批状态；任一失败不得留下部分审批或启动部分新退款。
- 继续执行门店作用域、有效员工权限、审批额度、禁止申请人自审、退款累计不超可退实付及原付款归属检查，不增加第二轮业务审批。
- 保留 quantity_refund_single_decision 等数据库保护，不能删除触发器、放宽约束或绕过授权消除报错。
- 兼容已打开的旧网页、直接接口请求及跨端请求；不能只依赖前端判断。execute、retry、manual-result 等资金入口检查已有原售后决定和原执行前提，允许合法接续，不笼统禁止全部售后关联退款执行。

### R3. 区分错误原因与资金结果

| 情形 | 员工提示与操作 |
|---|---|
| 普通入口处理商品售后退款 | “这笔退款属于商品售后，请进入原售后单审批。”提供准确原单入口 |
| 无审批权限或额度不足 | 显示无权/额度不足的真实原因，沿现有有权岗位指引，不显示支付服务故障 |
| 他人已处理或页面过期 | “该申请已处理，请查看最新结果。”读取最新状态，避免再次提交 |
| 原售后关联不可用 | “原售后单暂无法读取，请刷新；仍无法读取时联系管理员。”保留可追踪错误编号，不提供绕过路径 |
| 审批成功、渠道处理中 | “已批准，退款处理中。”后续按原记录更新结果 |
| 渠道结果未知 | “退款结果待核对，请查看原记录，勿重新申请。”沿既有核对机制处理 |
| 渠道明确失败 | 展示安全且具体的失败原因，只有符合既有条件时提供原记录重试入口 |
| 未分类内部异常 | “退款处理异常，请刷新查看原记录；仍有异常请提供错误编号。”不能声称一定未提交或已退成功 |

不得把所有 23514 都映射成同一售后错误：金额、状态及其他约束失败需分别诊断。接口只返回安全业务提示，不向员工展示 SQL、堆栈或数据库约束正文。

### R4. 幂等、并发与执行状态

- 重复点击、弱网重试、审批响应丢失、两名审批人并发、旧普通入口与原售后入口同时操作，最终只有一个有效审批决定；没有重复创建退款、重复渠道提交或重复入账。
- 明确采用原关联退款继续执行；不能为绕过审批失败生成新的退款号。原幂等键、商户退款号与渠道去重机制继续有效。
- 线上退款在审批事务成功后接续既有原渠道执行与核对；已审批后进程重启能够恢复原待执行记录。渠道调用不得发生在未提交的审批事务内。
- 现金及其他线下退款沿现有实际退付/独立凭证流程；审批成功不能自动标记现金已经交给客人。
- 按原规则处理已审批失败、处理中、未知结果和额度占用；不得因界面报错或刷新释放未确认款项的可退额度。
- 列表局部刷新展示服务端最新资金与售后状态；读取失败保留上次状态并标注刷新失败，不显示虚假的成功或无待办。

### R5. 日志和排查证据

- 记录 requestId、命令类型、门店作用域、退款 ID、原售后单 ID、处理阶段、业务错误码；受控关联拒绝与真正内部异常区分日志级别。
- 数据库异常日志允许记录经过白名单或安全清洗的 constraint/trigger 标识及代码位置，便于区分审批冲突；禁止记录支付密钥、PIN、令牌、完整支付载荷、顾客隐私或未经处理的数据库 detail。
- 业务拒绝也应可按请求关联查到；成功审批、渠道执行、核对结果、退款入账各有对应记录。日志不得虚构“渠道已受理”或“未扣款”。

### R6 / REQ-04-CLOSE：弹窗随时有可用的退出入口（SYS-225）

- 将标题与“关闭商品处理”放在始终可见的关闭栏，长内容在独立区域滚动。弹窗高度随实际可见视口和安全区域调整；内容滚动、长错误、字体放大、横竖屏切换和软键盘弹出不能遮住全部关闭入口。
- 关闭按钮触控区域至少 44×44 CSS px。可以采用固定或吸顶实现，验收以可见、可点为准；不以“按钮仍在 DOM 中”作为通过标准。
- 修正全局错误自动定位与弹窗内滚动的配合：错误须可见，标题和关闭栏同时保持可达，不滚动背后的页面，不因轮询反复抢走用户滚动位置。
- 关闭仅结束查看，不等待退款、退库或岗位通知完成，也不触发退款撤销、恢复商品、取消请求、损耗登记或通知确认。业务请求在途时仍可退出；返回列表和再次打开按原幂等记录恢复或查询，提示结果待确认，不当作操作未发生。
- 保留桌面 Escape 关闭、退出后焦点回到原“处理商品”入口。不要把遮罩点击作为唯一退出方式；是否增加遮罩关闭可依现有弹窗交互统一决定，不以缺少遮罩关闭本身判定资金故障。
- 检查该商品弹窗内打开换品等子弹窗的情况：当前层关闭只退出当前层，最上层的关闭入口可达，不能将父级和子级一起误提交或一起清除业务状态。

负责人：员工前端、测试负责人。目标：下一次包含本项的员工网页发布，版本待定；iPhone 微信现场验收由门店操作岗位执行。

### R7 / REQ-04-RETURN：退库容量证据一致并能解释失败（SYS-226）

- 开发先追溯原商品/配方用量、单位换算、实际批次包装、原库存扣减和配置变更记录，列明 500 ml 与 330 ml 的来源。保留“已证记录冲突”和“尚未确认哪项错误”的区别，不能仅因500不是330的整数倍就判断为配方成品。
- 有完整证据的单一整包装商品，按对应销售/批次的有效包装证据核对回库资格；不能因后来修改当前档案就无条件否定旧交易，也不能用当前档案覆盖历史扣减事实。原证据缺失或冲突时进入可追踪的库存核对待办。
- 新增或修改整包装商品的单位、包装容量与单品扣减规则时，校验它们的一致性并提示影响；仅对确认为整包装销售的商品应用该规则，不把按杯售卖或配方原料的合法分装当作异常。
- 员工打开实物处理前，服务端返回可否“确认收回入库”及具体原因。没有资格或证据冲突时，展示“库存记录待核对”，不提供必然失败的入库按钮；提交时仍重新校验，防止读取后配置变化。
- 本例提示可写为：“这件商品原记录扣减500毫升，与包装档案330毫升/瓶不一致，暂不能确认退库，请交库存负责人核对。退款已完成，不用再次退款。”金额、容量及退款状态均来自实际记录；其他订单不得套用本例数据。
- 配方成品、已开封商品、容量冲突和原始库存证据缺失分别说明原因。拒绝误回库不意味着只能选“已消耗，不回库”；不得诱导员工为清待办虚报损耗。
- 保留未开封实物收回确认、原扣减上限、逐份/分批处理、权限、幂等和实际库存流水。回库只沿核实过的原单位和批次，不用退款金额推算库存数量，不重复恢复库存。
- 历史冲突的处理方案须明确证据、影响数量、处理责任人及前后对账。对真实记录的修正沿既有授权和审计流程实施，不能直接改写原销售流水、批量将330改500或删除整包装校验。没有足够证据时保留待核对状态，但弹窗仍可关闭。

负责人：商品库存配置负责人、库存后端、测试负责人；门店核实瓶身及实物。目标：下一次包含本项的库存售后修复发布，版本待定。界面关闭与明确错误提示可先完成，不以现场瓶身信息未到位阻塞独立开发；历史库存处置必须等待必要事实。

### R8：明确剩余事项与处理人，不用“处理中”混淆（联动SYS-225/226）

- 工作台和详情分开显示资金、实物、岗位通知：例如“退款已完成 ¥78；实物待核对1份；吧台通知待知悉1条”。真实状态读取失败时标识刷新失败，不伪装为无待办或资金失败。
- 对库存冲突显示具体阻塞原因、应联系的有权岗位和查看原记录入口；对尚未收回、未确认消耗、通知未确认分别给出下一步，不强迫不具备条件的员工完成操作。
- 关闭弹窗与完成售后是两个独立动作。仅关闭不消除待办；资金与实物满足现有条件后完成售后，仍有岗位通知时可继续保留通知待办。不能为了页面清空而提前完成售后。
- 展示待确认通知的生成时间、阶段和岗位；申请阶段已知悉不自动算作审批后新通知已知悉。打印完成也不代表岗位已知悉。是否应合并后续同文通知，须另有业务规则，本项不自动删除或代确认。
- 资金已经成功而实物未完成时，不再引导重新退款；原实际实物、通知处理完成后，列表和详情刷新至相应最新状态。

负责人：员工前端、售后后端及门店执行岗位，与SYS-225/226一起验收。
