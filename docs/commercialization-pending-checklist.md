## 1. 当前结论

`rc.46` 已经部署到阿里云验证环境，但不能按正式商业生产系统验收。

当前已经完成：

- 客户和员工共用菜单、搜索、图片、购物车和订单链路。
- 81项V2/V3商品、17个组合商品及成本基线。
- 套餐对客显示一个商品，对内拆成出品、库存和绩效组件。
- “今夜特别推荐”、三档比较、快速选择和摇一摇。
- 推荐曝光、接受、摇一摇、购物车和放弃行为事件。
- PostgreSQL、规范化运营读模型、CI、不可变镜像、备份和回滚证据。

当前明确未完成：

- 真实微信/星驿支付、退款、物理POS和日结联调。
- 一次特惠升级的服务端资格、价格、库存和唯一核销控制。
- 完整的推荐会话、产品计划版本、升级关系和体验编排领域。
- 打印机、KDS设备和真实门店网络验收。
- 订单重点备注已在本地完成全链路开发和自动测试，但尚未部署、打印实机验收或真实岗位交接验收。
- 66条P0/P1经营验收项。

云端当前仍是：

- 支付：模拟模式。
- 打印和其他硬件：未配置真实设备。
- 语音转写：未启用生产服务。
- 213条经营TC：147条通过、50条未执行、16条阻塞。

## 4. P0-01 一次特惠升级

**当前状态：禁止启用。**

价格测算和页面表达可以继续保留为草稿，但当前商品配置只有普通推荐字段，行为系统只能记录`upgrade_accepted`。它不能证明升级资格，也不能代替正式升级交易。当前还没有一套服务端能力保证“一桌一次、来自哪一笔商品、是否过期、库存是否足够”。

### 4.1 必须新增的服务端对象

建议建立`SpecialUpgradeOffer`和`SpecialUpgradeRedemption`，至少保存：

```text
offerId
policyId / policyVersion
tableSessionId
businessDate
sourceOrderId
sourceOrderItemId
sourceProductId / sourceProductVersion
targetProductId / targetProductVersion
sourcePaidNetAmount
normalUpgradeAmount
specialUpgradeAmount
discountBudgetAmount
validFrom / validUntil
inventorySnapshotVersion
status: eligible | reserved | redeemed | expired | cancelled
idempotencyKey
createdAt / redeemedAt
```

### 4.2 服务端必须同时校验

- [ ] 桌台已经开台，且`tableSessionId`仍为当前桌次。
- [ ] 同一桌台会话只能成功使用一次特惠升级。
- [ ] 来源必须是明确的`sourceOrderId + sourceOrderItemId`，不能只传商品名称。
- [ ] 来源订单已经真实支付成功，支付未知或待对账时不能升级。
- [ ] 来源订单行属于当前桌次、当前营业日和当前账单。
- [ ] 来源SKU在已发布白名单内，不能按价格或商品名称模糊判断。
- [ ] 赠饮、权益、团购券、员工酒、已退款、已冲销商品不得作为来源。
- [ ] 来源订单行没有被其他套餐或升级使用。
- [ ] 当前时间没有超过可配置有效期；首期建议沿用下单后45分钟。
- [ ] 目标商品仍为已发布、启用、未售罄且当前时段可售。
- [ ] 目标套餐人数、核心酒种、座区和演出剩余时间仍适配。
- [ ] 重新计算目标套餐增量组件库存，不能只看套餐头商品状态。
- [ ] 吧台、冷食和服务产能允许履约。
- [ ] 特惠补差来自已发布规则，员工不能手工输入任意成交价。
- [ ] 特惠升级后的增量变动成本不超过补差35%，且增量贡献毛利大于0。
- [ ] 价格、成本、商品、来源实付、优惠预算和规则版本形成不可变快照。
- [ ] 两台设备同时提交时，数据库事务只能允许一笔成功。
- [ ] 重复点击或网络重试复用原幂等结果，不重复下单、扣库存或出品。

### 4.3 正确的价格计算

```text
普通应补差额 = 目标商品当前成交价
             - 来源商品实际已付净额
             + 已选固定补差项

特惠应补差额 = 普通应补差额
             - 已发布的一次性特惠预算
```

限制：

- 不能按来源商品标价抵扣，只能按实际已付净额。
- 特惠预算必须有活动版本、适用时间、总预算和单桌上限。
- 页面展示前和提交时各计算一次；结果变化时要求客人重新确认。
- 价格尚未正式批准前，后台只能保存为草稿，不能返回给客户页面。

### 4.4 原子执行顺序

```text
锁定桌台会话
→ 锁定来源订单行
→ 锁定特惠资格
→ 重新校验价格/时间/库存/产能
→ 创建升级订单和价格快照
→ 标记来源订单行已计入
→ 扣减增量组件库存
→ 生成KDS和服务任务
→ 核销一次性资格
→ 写入审计事件
→ 返回同一个成功结果
```

其中任一步失败，全部回滚。

### 4.5 退款和异常

- [ ] 退款按套餐头、来源实付和已履约组件分摊。
- [ ] 已喝完的来源商品不能再次全额退款。
- [ ] 目标套餐取消时恢复未履约库存，但不得恢复已使用的一次性资格，除非经理走独立补救审批。
- [ ] 价格变化、售罄、超时和库存不足分别返回可理解的客户文案。
- [ ] 店长可以做服务补救，不能篡改原下单时间或伪装正常升级。
- [ ] 每笔例外必须记录发起人、批准人、原因码和金额，发起人与批准人分离。

### 4.6 必须通过的测试

- [ ] 同一桌连续点击两次。
- [ ] 客人手机和服务员平板同时点击。
- [ ] 同一来源订单行拆成两个升级请求。
- [ ] 转桌、并桌、拆账和翻台后继续使用旧资格。
- [ ] 来源商品已赠送、已退款、部分退款或支付未知。
- [ ] 页面显示后目标商品售罄或价格改变。
- [ ] 页面显示后跨过有效期。
- [ ] 增量组件中任一原料不足。
- [ ] 数据库并发冲突、请求超时和客户端重试。
- [ ] 升级后部分退款、全单退款和KDS取消。
- [ ] 收银、服务员、店长和老板四种权限。
- [ ] 日结能够核对来源实付、补差、特惠预算、成本和增量毛利。

**启用证据：**服务端自动化测试、PostgreSQL唯一约束、并发测试、真实员工演练、5笔真实小额支付和退款、日结审计表。
