## 修复后的规则

1. **新拆并桌必须有快照。** 网页端新请求缺少 `movementGuard` 时返回 409 和明确的未提交状态，不移动顾客。不能通过正文伪造 `requireGuard:false`、`receiptOnly:false` 或改放 `nativeGuard` 绕过。原生入口继续要求自身快照及员工身份。
2. **已完成的历史请求仍能核对。** 先按原员工、原请求编号和原参数检查已完成回执，再判断是否允许新操作。即使旧请求没有快照、普通幂等缓存已删除，仍可从永久移动记录返回原结果；不创建新移动、审计或待发送事件。修改原参数或换员工会拒绝。
3. **恢复只查原结果。** 网页发送 `x-table-movement-recovery: 1`。未找到原回执时明确返回“本次未执行”，不补做原请求；员工需刷新名单、重新预检并主动确认新操作。权限变化、网络异常等不能被当成“原请求未提交”。
4. **网页保留原请求。** 发出前保存原员工、编号、桌次、名单和快照。结果未知时阻止改参数或跨桌新建操作，显示“核对原拆并桌结果”。同一标签页刷新或重新进入操作窗后可以恢复；其他员工只能看到提示，不能代为重放。
5. **回执和刷新都成功才清理。** 校验事件号、目标桌次、人数、容量和时间；回执损坏时保留原请求。已确认回执后若名单刷新失败，只重读名单，不再次提交。空值、对象或缺少身份标识的名单不能冒充刷新成功。

本轮收紧了上一轮的旧客户端兼容边界：旧页面不能继续发起无快照的新拆并桌，需刷新至支持版本；历史已完成回执仍保留恢复能力。整体转桌入口原本已强制要求原桌位和位置版本，没有把它误判为同一缺口。无数据库迁移。

## 模拟场景

| 场景 | 结果 |
|---|---|
| 旧客户端拆桌、匿名整桌并桌不传快照 | 新请求拒绝，移动记录为零；补齐快照后可执行 |
| 伪造正文开关或使用错误的快照字段 | 不能绕过服务端要求 |
| 请求发出前断网 | 恢复查询不执行；明确无回执后清理待核对状态，重新预检确认才能新建 |
| 服务端成功后响应丢失 | 重进页面后使用完全相同的编号和参数，只查询原回执 |
| 服务端成功但返回损坏的回执 | 保留请求，恢复后只有一条实际拆桌记录 |
| 成功回执后名单读取断网或损坏 | 保存已确认回执；恢复只读，不再次 POST |
| 连续点击提交/恢复 | 同一操作窗口只有一次发出；恢复共用进行中的请求 |
| 切换员工、权限撤销、存储不可读 | 不以新员工重放，不清除未知结果，不发出替代请求 |
| 旧拆桌→转桌→合桌→转桌→再次拆桌 | 旧请求恢复只返回旧事件；桌位、人数、位置版本及原渠道绑定不改变 |
| 普通幂等缓存删除后并发恢复旧请求 | 永久回执仍有效，移动、审计和待发送事件数量不增加 |
| 原请求被改桌号或换员工 | 冲突拒绝，不读取或执行他人的请求 |

“断网恢复”使用真实网页 API 模块对接 Fastify 和隔离 PostgreSQL，传输层分别注入发送前失败、提交后丢响应和回执损坏；没有以纯假成功响应替代服务端执行验证。

## 员工操作及边界

- 页面提示缺少快照：刷新页面、核对当前名单、重新预检，不能继续使用旧页面直接确认。
- 页面提示原拆并桌待核对：点“核对原拆并桌结果”；不要改桌号、换员工重试或手动清除恢复记录。原桌已结束时，可从其他营业桌的拆并桌入口核对原操作。
- 明确提示原请求未执行：重新核对位置及人数，再做新的预检确认。
- 恢复记录使用当前标签页的持久会话存储；关闭标签页、清除浏览器数据或换设备不在本轮自动恢复保证内，应核对服务端移动记录，不能据此认定从未提交。
- 后端上线后旧网页的新拆并桌会被拒绝，因此需配套刷新网页版本；本轮不部署、不上传小程序、不修改生产数据。正式发布、双设备现场及真实资金仍需独立验收。
