# M-BOX客户端指令责任流转验证 1.0.0-rc.22

## 验证目标

验证客户通过桌码网页、后续小程序/服务号共用接口或预约入口发出的需求，能够进入正确责任岗位，由有权限人员处理，并把状态同步回客户侧。员工Web、Android壳和iOS壳共用同一套服务端权限与状态机，因此本轮以API端到端测试为主，不把浏览器本地成功当作后端完成。

## 自动化流转矩阵

| 客户动作 | 后端责任链 | 验证结果 |
|---|---|---|
| 选择心情 | 个性化关怀任务 -> 桌台责任服务人员 -> 到桌处理 | 任务与匿名情绪事件同时留存；完成后客户提示消失 |
| 加水、冰块柠檬、协助点单、买单 | 主服务员 -> 候补 -> 主管/店长升级 | 七类服务配置全部可创建、可见、接单、到桌和完成 |
| 投诉 | 主管/店长优先接管 | 责任人可见并闭环，普通无关岗位不能越权处理 |
| 生日关怀、个性化需求 | 服务专员或配置岗位 -> 桌台责任人协同 | 关怀内容完整到达责任人，完成后客户端清除待办 |
| 自助点单与支付 | 支付成功 -> 酒水/冷厨/热厨分流 -> 打印队列 | 三个工作站按商品路由；错误岗位制作返回403 |
| 出品完成与送桌 | 制作岗位 -> 取送责任人 -> 客户订单 | 取货、送达、订单fulfilled和客户端delivered一致 |
| 点歌 | 服务确认 -> 收银收费 -> 舞台运营执行 | pending_payment、paid、accepted、performing、completed完整回传 |
| 线上预约 | 服务人员与经理台账 -> 确认 -> 到店 -> 入座 | 全体具备预约权限的岗位可见；入座后生成生日关怀和待点单流程 |

## 本轮发现并修复

1. 自动改派可能把任务分给不负责该区域的同岗位员工。现在角色候选人必须同时满足门店数据范围和当班区域。
2. 系统或SOP明确指定的责任人可能因为普通区域校验无法处理自己的任务。现在已分配责任人可继续操作，其他人员仍受岗位与桌台范围限制。
3. 送桌任务沿用完整KDS编号，长订单编号会超过Fastify路径参数限制并返回414。现在使用固定长度哈希编号，并自动迁移旧任务、事件、审计和KDS关联。
4. 已完成服务不会继续出现在客户会话中；服务端任务与事件仍保留，支持后续响应率和未响应分析。

## 自动化证据

- 新增`server/client-responsibility-flow.test.ts`，覆盖六组跨客户端、跨岗位完整流转。
- 七类顾客服务逐项执行，不只检查创建成功，还验证责任人投影、岗位匹配、接单、到桌、完成和客户侧清除。
- 支付出品链覆盖酒水、冷厨、热厨、两台打印分流、制作权限、取送和客户订单状态。
- 点歌与预约分别跨越服务、收银、舞台、经理和专员岗位。
- 旧送桌任务编号迁移在`server/fulfillment-service.test.ts`单独回归。

## 发布边界

本轮证明软件内部责任流转可以闭环，但不等于真实硬件或外部渠道已经送达。微信支付、服务号/企业微信通知、物理打印机、耳机和摄像头仍必须以服务商或设备回执作为商业发布证据；当前验证环境仅允许员工模拟和门店影子运行。
