# 历史退款对账补录

仅适用于本地已成功、原收款已确认且有正确收款流水，但缺少退款对账流水的历史记录。当前退款命令会在同一事务写入对账；终态回执重放无副作用，不能用重新退款或反复回放解决旧缺口。历史缺口形成原因未证实。

`scripts/repair-historical-refund-ledger.mjs` 是按单受控的数据维护工具，不在 HTTP、后台定时任务或正常收退款链路中调用。复用当前已部署的渠道观察授权、追加对账和审计模块，后台服务无需重启。

## 证据与执行

1. 在原生产运行环境通过既有星驿适配器调用只读 `refundQuery`，绑定商户、原平台付款号、商户退款号、平台退款号、金额、币种；保存完整受限证据及 SHA256。同步响应可能不带签名，必须如实标记；成功判断来自 HTTPS 直连、适配器绑定校验，不能将普通 JSON 文件当作签名证据。
2. 工具接受 `mbox-bound-historical-refund-query-v1` 的受控采集文件。证据包含本地原付款/退款整行 SHA256、原渠道身份、标准化观察、HTTP/code、原响应 SHA256 和渠道成功时间。文件与摘要只能由受信操作员提供，不开放给客户端。不要把订单/渠道明细或凭据提交仓库。
3. 在运行目录含 `dist-normalized`、`package.json` 的已部署应用环境，使用受限 runtime LOGIN；从本机加载既有运行配置，不输出凭据。明确绑定生产 SHA：

```sh
node /tmp/repair-historical-refund-ledger.mjs \
  --proof /tmp/protected-refund-query.json \
  --proof-sha256 VERIFIED_64_HEX_SHA256 \
  --expected-commit VERIFIED_40_HEX_COMMIT
```

默认完整执行后 **ROLLBACK**，不留对账、观察或审计。预演与独立只读复核通过后，使用完全相同的脚本、证据和参数增加 `--apply`。执行文件和证据以0700目录、0600文件短暂放置；执行后删除容器临时副本，主机保留受限审计档案。

## 边界

- 原记录指纹、成功状态、金额、币种、原收款对账、渠道身份及总退款上限都必须匹配。原记录变化、已有冲突流水、未成功或跨门店即停止。
- 中国星驿成功时间使用 `sucOrderTime`（UTC+08），按门店实际营业日截止点计算，不使用补录日期；与原成功记录跨营业日时停止复核。
- 单事务按订单、付款、退款顺序锁定；语句5秒、锁等待750毫秒、闲置事务5秒。只追加一条渠道观察并消费、退款对账、审计；不更改付款、退款、订单、库存、积分，不触发外部收退款。
- 重复执行必须同时匹配已有流水、消费观察和审计，返回 `already_repaired`；并发操作仅一次落账。审计追加失败则全部回滚。
- 局部修复后独立复核全历史付款/退款与对账、原订单欠款及生产健康。程序成功退出本身不能代替数据复验。

## 验证

`server/normalized/historical-refund-ledger-repair.integration.test.ts` 纳入标准隔离 PostgreSQL 测试；使用真正的受限 LOGIN。覆盖默认回滚语义、历史营业日、原金融事实不变、8路并发幂等、审计失败整笔回滚、金额/身份/状态/日期/门店/指纹/证据摘要错误及已有冲突流水。
