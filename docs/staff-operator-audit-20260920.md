# M-BOX 员工实际操作审计：缺陷、证据与整改验收

审计日期：2026-09-20。对象：店内服务人员，覆盖门迎、吧台、后厨、收银及兼用的管理者。

后续：[第二轮新增 5 个问题点](staff-operator-audit-round2-20260920.md)已完成，涉及多人转桌、跨页切人、团购和活动草稿。本文保留第一轮范围和证据，不重复计数。

## 结论

确认 **8 类缺陷**。优先处理：部分现金重复记账、同一瓶酒重复登记、桌台记录与推荐规则草稿无法提交。界面改版应同时修复这些状态和恢复逻辑，否则做成 App 后仍会遇到相同问题。

7 类在实际网页与本地后端环境中复现，其中部分使用明确的网络故障注入；另外 1 类为实际前端在模拟成功回执下复现的异步状态错误，已单独标注。不是“线上已经发生 8 类事故”的结论，也不是所有漏洞已穷尽的保证。

- 基线：独立工作树 `mbox-ux-audit-20260920`，SHA `887461043e521463f73b9bd17efa381e4eeea6ad`，版本 `1.0.0-rc.214`；本轮开始时远端 main 同 SHA。未核验本次基线的生产部署身份。
- 环境：真实网页构建、真实应用后端、PostgreSQL 16 临时数据库；本机 18891 / 18892。收付款通道模拟，后台通知与打印等 worker 关闭，没有操作生产资金、订单、库存或员工授权。
- 岗位：按仓库门店配置装载 13 位员工及其权限；存酒专题使用既有 V9/会员测试夹具，额外测试授权不能当成线上现有授权。
- 验证：现有浏览器 **102 通过，0 失败、0 跳过、0 flaky**（约 8 分钟，包含顾客触发与移动适配）；另有 **97 项后台定向测试通过**（6 文件，包含数据库集成及单元校验）。这些通过项之外的探索性操作揭示了下列缺陷。
- 业务源码未修改。本轮交付为审计、复现证据与待处理清单，不是修复、部署或门店验收。

## OP-01：部分现金收款关闭重开后重复登记

1. 有权限员工进入 W01 本桌收款，选择未结订单，输入本次现金 10 元。
2. 点击“现金已收”并确认。让本地后端实际提交成功，再丢弃成功响应。
3. 页面提示“网络连接失败，请检查网络后重试”。关闭收款窗口后重新进入。
4. 再输入同一笔 10 元并确认，后端接受为另一笔现金收款。

最终一次复现：待收 `244 → 234 → 224` 元。两次请求均返回 201，生成不同现金凭证与幂等键。数据库两条 payment 的金额均为 1000 分、provider 均为 cash、status 均为 succeeded。可复现的是**部分金额、回执未知、关闭重开再登记**；不能扩写为任何支付都会重复扣款，也不是突破整单应收上限。

余额重新读取后确实减少，但没有明确显示“刚才那笔已登记”或提供原操作核对入口，重新提交被当成新收款。这种异常恢复要求员工自行推断余额变化，风险过高。

源码：`src/normalized-ui/staff-actions/TablePaymentSheet.tsx:46,190-224`。原现金尝试只存在组件 `useRef`；卸载后丢失。`staff-actions-api.ts:851` 直接提交人工收款。服务端同凭证/同编号防重仍有效，错误发生在前端丢失原操作身份后换了编号。

整改与关闭条件：跨窗口/刷新保留未知现金操作；先核对或恢复原登记，再显式发起新的收款。覆盖成功回执丢失、关闭、刷新、切人、同金额不同真实收款、部分与全额，逐笔核对 payment/分摊/账务；不把多次真实收款一概合并。

证据：`exploration.json` 的 AUDIT-03；`cash-db-evidence.txt`；`finding-03-cash-ambiguous.png`、`finding-03-duplicate-cash.png`。

## OP-02：存酒成功后的读回失败被当成登记失败

1. 在隔离会员夹具录入新存酒，会员号为测试号，数量 1 瓶，拍照后登记。
2. POST 登记接口真实返回成功，只让随后 GET 列表请求失败。
3. 页面只提示网络失败，照片与表单内容仍保留，“登记存酒”再次可用。
4. 不修改任何内容、不再拍照，再点一次登记。

生成 `20260920-155919-MBX-CARD320-1` 和 `20260920-155922-MBX-CARD320-2` 两张单；每张 `original_quantity=1`、`remaining_quantity=1`、`status=stored`。这是重复的顾客寄存记录，不是证明门店商品库存也增加了 2 瓶。

源码：`src/normalized-ui/BottleCustodyPanel.tsx:50`，写入成功后 `await list()`，其后才清照片并显示成功；列表报错跳过清理。`recoverable-command.ts:36` 在写请求成功时已经释放原尝试，第二次点击生成新编号。

整改与关闭条件：写成功即保留成功凭证并消费这一次表单；读回失败显示“已登记，列表待更新”，只允许刷新原结果。原照片/表单不能再次无意生成同单；真实追加寄存必须有明确的新登记步骤。验收同时比对单据、寄存量、照片及事件数量。

证据：`custody-exploration.json` 的 AUDIT-07；`custody-db-evidence.txt`；`finding-07-custody-refresh-failed.png`、`finding-07-duplicate-custody.png`。

## OP-03：桌台情况及推荐规则草稿提交失败

无需断网。在真实网页填写“客人需要加一杯冰水”，勾选需要马上处理，点击“识别并核对”；正常请求返回 `500 CUSTOMER_EXPERIENCE_FAILED`，页面显示“客户体验服务暂时没有接上”。管理者打开推荐规则、创建并保存默认参数草稿，同样返回 500。

后台堆栈明确指向 `appendOutboxMessage`：`observation-…` / `recommendation-policy-…` 展示编号被传入要求 UUID 的字段。数据库查证新观察记录为 0，指定测试规则草稿为 0，说明事务回滚。

源码：`server/normalized/customer-experience-service.ts:3378-3401` 和 `3527-3550` 把 publicId 传给 `commandOutcome`；该辅助函数 `3745-3770` 原样用于 aggregateId；`server/normalized/command-executor.ts:329-337` 使用 `$5::uuid`。

整改与关闭条件：业务消息关联真实数据库 UUID，展示号保留为展示标识，不能删掉审计或消息写入来规避。验证记录→确认→任务→修订完整链路，以及推荐规则草稿→复制→独立审批→发布；增加经过真实 service、command executor、事务和 outbox 的接口测试。

同辅助函数中，顾客推荐、推荐行为、跟进任务及演出阶段等还有类似传 publicId 的调用，属于**代码关联风险**；本轮没有逐一操作成功前置状态，不将这些一并写成已复现故障。

为什么原测试没发现：现有观察浏览器验收只检查输入框、无语音入口、触控大小；观察数据库测试重点在 repository，未走上述完整服务与 outbox 路径。

证据：`backend-flow-exploration.json` 的 AUDIT-06/06b；`runtime-error-evidence.txt`；`observation-policy-db-evidence.txt`；`finding-06-observation-500.png`、`finding-06-policy-500.png`。

## OP-04 / OP-05：连接与加载状态缺少真实依据

OP-04：登录后直接打开 `/staff/live`，将 `/api/staff/workspace` 返回 503；请求失败已经返回，仍只显示“正在连接门店工作台”，没有业务页重试按钮。顶部“工作台”仍可返回，因此不称为永久无法恢复。`NormalizedStaffApp.tsx:40-50,104-116,169` 吞掉非登录错误并保留空导航。

OP-05：已有首页数据时使刷新请求断网，错误提示与绿色“连接正常”并存。`NormalizedStaffWorkspace.tsx:250-254` 固定在线文案，与真实 phase 无关。保留旧数据应同时明确“更新失败，当前显示上次数据”和更新时间。

关闭条件：首次进入失败、刷新失败、离线、恢复、权限到期分别可辨识；失败有明确原因与重试，旧缓存不被称为最新；弱网期间涉及金额和数量的提交继续由后端校验。

证据：`exploration.json` 的 AUDIT-01/02；`finding-01-stale-online.png`、`finding-02-route-loading.png`。

## OP-06：存酒单切换时携带另一单的修改草稿

在第一张存酒单展开改期，输入 `2026-12-01 20:00` 与“仅准备调整第一张存酒单”；不保存，选择另一张存酒单。等待新单详情和加载完成，标题已经变化，日期、原因仍相同，“保存到期时间”可点击。本轮仅证明错误内容跨单带入，没有提交错误改期。

源码：`BottleCustodyPanel.tsx:19,29,48`。切换详情重置了取酒数量、验证码和照片，没有重置改期日期与原因。

关闭条件：草稿绑定到具体存酒单，切单时明确保留于原单或清空；返回原单按规则恢复；不会把原单修改内容提交到新单。再存数量、原因及其他按单状态一并检查，但未复现项不得直接计数。

证据：`custody-switch-exploration.json`；`finding-08-custody-draft-leak.png`。

## OP-07：桌台记录慢响应覆盖新内容

由于 OP-03 阻断真实解析，本项使用实际页面并注入符合现有接口结构的成功回执来验证前端状态；没有声称真实数据库已经保存错误记录。

- 输入 A“客人说这杯太甜，稍后再处理”，点击识别并延迟回执；期间改为 B“客人需要马上加一杯冰水”，勾选需要马上处理。A 的结果回来后，文本框为 B、紧急勾选为真，核对区却显示“只记录，不派现场任务”；点击保存，发送的 rawExcerpt 仍为 A。
- 保存响应延迟时，继续输入下一条记录；旧保存回执到达后，新输入被清空。

源码：`TableObservationSheet.tsx:54-66,70-85,130-133`。编辑仅清空当时的 draft；没有校验返回结果对应的输入版本，保存完成也无条件清空当前输入。

关闭条件：识别与保存均绑定输入版本；旧结果不得恢复成可确认状态；保存期间可选择锁定编辑或将下一条草稿独立保存。OP-03 修好后，还必须用真实接口验证“原话、紧急标记、服务任务”一致。

证据：`observation-ui-fault-injection.json`；`finding-04-observation-ui-stale.png`、`finding-04-observation-ui-input-lost.png`。

## OP-08：桌台推荐网络错误无就地恢复

桌台→查看/调整推荐，首次读取断网后显示“网络连接失败，请检查网络后重试”，弹层只剩“关闭推荐调整”。关闭再打开可恢复，因此归为恢复入口缺失，不称为数据损坏。

源码：`TableRecommendationSheet.tsx:31-40,63-83`。请求只由挂载 effect 发起，失败状态没有重试动作。

关闭条件：提供重新读取及明确加载/无推荐/失败状态；重试留在当前桌次，并防止切桌后旧响应串入。

证据：`observation-exploration.json` 中已完成的 AUDIT-05；`finding-05-recommendation-retry.png`。同文件早期观察场景的失败记录由 OP-03 解释，不计作另一缺陷。

## 操作覆盖与边界

| 员工任务 | 当前证据 | 结论 / 边界 |
|---|---|---|
| 设备验证、岗位登录、高频导航 | 13 员工配置 + 浏览器回归 | 配置岗位入口通过；不代表生产授权覆盖一致 |
| 找桌、预约到店、散客开台、关台 | 现场与预约完整浏览器场景 | 正常流通过；直接业务页初始化故障见 OP-04 |
| 协助点单、多人共享购物车 | 正常下单、顾客端触发与店长同步场景 | 已通过；现金异常恢复另有 OP-01 |
| 吧台与后厨制作、按份出品、取送 | 真实订单串联、多岗位 + 10 项刷新恢复专题 | 通过覆盖内场景；不是营业高峰压测 |
| 商品售后、部分退款、补送、重做 | 多个实际浏览器场景含丢回执恢复 | 通过；保留申请、审核、执行、实物处理的区别 |
| 现金与线上收款 | 浏览器 + 资金极限数据库测试 | 原凭证防重、退款约束通过；未知现金操作跨窗口身份丢失不通过 |
| 入库、盘点、库存并发 | 库存 API、盘点批量 UI | 自审、过期盘点、并发扣库约束通过，不能为简化界面删除 |
| 会员办理、礼遇、存酒、导出 | 会员/V9 夹具、真实数据库与假摄像头 | 主要正常流通过；存酒 OP-02/06 不通过；真实手机拍照和服务号验证码未实测 |
| 桌台情况与现场服务记录 | 本轮正常网页提交、后端日志 | OP-03 阻断；OP-07 前端缺陷另用模拟回执验证 |
| 推荐规则及推荐协助 | 实际创建草稿、故障读取 | OP-03/08 不通过；同源调用尚需补测 |
| 管理配置、退款权限、日结 | 配置读回、角色及自动日结专项 | 覆盖内通过；真实跨夜班次、交接及经营复核未现场演练 |
| 团购平台核销 | 本轮审阅代码，原 SYS-268 继续开放 | 未用真实四平台券验证；不以页面可见证明核销成功 |
| 打印与外设 | 浏览器打印恢复、导出预览 | 未验证 Windows PrintBridge、扫码枪和实物小票 |
| 未来 App、移动布局 | 既有 320/360/390/横屏浏览器测试及窄屏操作 | 不等于 iOS/Android 真机后台恢复、相机、软键盘、弱网实测 |

“收银与退款”入口对普通服务员可见，不必然等于越权：其可能拥有退款发起权限。已确认服务员不能直接进入设置页；判断越权应再看具体按钮和后台权限，而不是仅凭菜单名称。

## 先改什么，之后如何做 App

1. 先修复 OP-01/02/03，补齐跨窗口恢复与完整事务验收。优先保护金额、寄存量及服务记录。
2. 统一“处理中 / 已成功 / 结果待核对 / 仅刷新失败”的状态与动作。提交成功后，读回失败只能重查，不能重新办理原业务。
3. 草稿绑定桌次、单据与员工；切换对象时不串内容。把连接可信度、最后更新时间和异常恢复入口纳入统一组件。
4. 在这些规则之上实施前一轮的岗位导航、业务术语及页面分层方案。存酒等长页面应变为“查询→单据详情→办理”的连续任务入口。
5. 真机与门店再验收：真实弱网、员工交接、相机/扫码、真实支付、实物交付/打印，以及高峰多员工并发。不能把本次单机通过数换算成营业承载能力或误操作率。
