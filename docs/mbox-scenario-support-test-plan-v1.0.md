# M-BOX 场景化系统测试与异常支撑方案 V1.0

文档状态：新测试规范，待执行
编制日期：`2026-08-23`
适用范围：M-BOX 陆家嘴中心员工端、顾客小程序、服务端、PostgreSQL、支付/退款、库存、KDS、打印、营业日与发布恢复
时区：`Asia/Shanghai`

## 1. 目的与结论边界

本方案把既有 213 条经营 TC、质量模型、岗位手册和自动化工具整理成可以按步骤执行的场景包。它不替代原 TC，也不把历史通过、代码存在、页面可见或本地模拟自动认定为当前版本通过。

每个场景必须同时回答五个问题：

1. 员工或顾客具体做什么。
2. 页面和设备应立即显示什么。
3. 服务端、数据库、审计和外部渠道必须留下什么强事实。
4. 失败时系统如何阻断、重试、降级或恢复。
5. 自动支撑失效后由哪个岗位接管，什么条件下才可继续经营。

任何场景只有“页面显示成功”，但缺少订单、库存、支付、KDS、打印、审计或渠道事实，均判定为失败。自动化通过只能证明其覆盖层；真机、实物打印、真实支付、真实退款、现场网络和岗位协作必须单独执行。

## 2. 测试结果和停止规则

### 2.1 统一结果

| 结果 | 定义 |
|---|---|
| `pass` | 所有前置成立，操作、界面、强事实、支撑和证据全部符合预期 |
| `fail` | 产品、数据、权限、状态、性能或恢复行为不符合预期 |
| `blocked` | 外部渠道、真机、硬件、人员或环境缺失，测试无法真实执行 |
| `not_run` | 尚未执行，不能写成通过 |
| `invalid` | 测错版本、前置数据错误、误连旧服务、源码漂移、观察数据不守恒或测试工具自身故障；修正后原样重跑 |

### 2.2 立即停止条件

出现以下任一情况，停止对应入口，保留现场，不用删数据、改库或刷新页面掩盖：

- 重复扣款、超额退款、支付成功但系统无账、系统成功但渠道无账。
- 跨桌、跨客户、跨门店读取或写入；旧桌令牌可继续操作新桌。
- 库存为负、同一出品重复扣减、最后一份被两单同时卖出。
- KDS 状态回退、同一品项重复制作或送错桌且无可追溯处置。
- 无权限员工能够收款、审批本人退款、改库存、改打印路由或发布经营配置。
- 日结、关台或发布过程覆盖未结资金、未完成履约或历史证据。
- 敏感信息、PIN、完整手机号、支付密钥、付款码或令牌进入日志和截图。

## 3. 测试环境和证据等级

| 等级 | 环境 | 可证明 | 不能替代 |
|---|---|---|---|
| E1 | 静态、类型、单元测试 | 规则、金额、状态机、权限分支、格式 | 数据库事务、真实浏览器、硬件和渠道 |
| E2 | 隔离 PostgreSQL 集成环境 | 事务、约束、RLS、幂等、并发、迁移、审计 | 真机交互、真实支付和实物库存 |
| E3 | 本地/候选浏览器与小程序预览 | 真实路由、布局、点击、跨页面状态 | 微信真机能力、现场弱网和生产第三方 |
| E4 | 门店真机/实物/沙箱或测试商户 | 摄像头、扫码、热敏打印、支付退款、网络切换 | 正式营业连续稳定性 |
| E5 | 受控现场营业演练 | 岗位协作、峰值、交班、日结和恢复 | 不得用一次演练推断长期容量 |

每份证据至少包含：完整提交 SHA、迁移版本、环境 ID、营业日、北京时间、设备/浏览器/小程序版本、执行账号与岗位、业务对象公共编号、请求/审计编号、脱敏截图或录像、数据库只读核对、外部流水（如有）、结果和缺陷编号。

## 4. 测试工具与使用边界

| 层级 | 工具/命令 | 主要用途 | 合格结果 | 不足边界 |
|---|---|---|---|---|
| TC 基线 | `npm run quality:tc-register:test`、`npm run quality:tc-register:verify` | 防止必需 TC 被删除、降级或改写 | 必需编号、优先级和定义摘要一致 | 不代表 TC 已执行 |
| 质量模型 | `npm run quality:model:verify` | 核对 KDS 状态机和经营不变量 | 状态、转移、TC 映射完整 | 不证明运行实现正确 |
| 静态与领域 | `npm run check`、`npm run test:normalized` | 类型、规则、接口契约和无数据库回归 | 0 error；所有应执行项通过 | PostgreSQL 条件跳过项不算通过 |
| PostgreSQL | `npm run test:normalized:postgres` | 迁移、事务、RLS、并发、幂等和强事实 | 从空库连续迁移；全部应执行文件通过 | 仍不是现场数据或真实渠道 |
| 浏览器 E2E | `npm run test:e2e:normalized` | 员工端和顾客 Web 关键旅程 | 真实点击、路由和可见状态符合预期 | 不替代微信真机 |
| HTTP 验收 | `npm run acceptance:normalized:http` | 接口可达性和端到端业务核对 | 请求、状态和数据库事实一致 | 不证明视觉和触控体验 |
| 负载 | `npm run acceptance:normalized:load` | 代表性经营混合负载与不变量 | 到达率、错误率、事件循环和最终账守恒 | 一轮本机结果不等于生产容量 |
| 浏览器启动 | `npm run test:browser-startup` | 首开、登录至可操作界面 | 按冷/暖启动口径独立记录 | API 延迟不能冒充页面可操作时间 |
| 运行证据 | `npm run runtime:quality:test`、`npm run quality:evidence:verify` | 日志、指标、敏感信息和证据完整性 | 原始制品可校验且与提交绑定 | 证据完整不等于业务通过 |
| 架构 | `npm run architecture:normalized:test`、`verify`、`new`、`zero` | 防止旧路径和新旁路回流 | 所有门禁为 0 或通过 | 不替代业务验收 |
| 小程序 | `npm run release:miniprogram:test`、`build`、`verify` | 构建、凭证域、包结构和静态契约 | 构建产物与提交一致 | 上传、微信审核、摄像头和手机号授权需真机 |
| 发布恢复 | `npm run release:config:test`、`npm run release:system:test` | 配置、锁、备份、迁移、恢复和回滚策略 | 故障注入和恢复证据通过 | Linux `flock`、生产密钥和维护窗需正式环境复验 |
| 商业总门禁 | `npm run test:commercial`、`npm run release:quality-gate` | 汇总代码、数据库、E2E、负载和必需 TC | 全部 P0/P1 有合格证据才可放行 | 不允许用本地脏工作区签发生产结论 |

## 5. 固定测试数据

所有数据使用独立测试营业日和明确的 `TEST-*` 名称，禁止使用真实顾客手机号、真实员工 PIN 或生产付款码。

| 对象 | 固定数据 |
|---|---|
| 营业日 | `B0` 为当前测试营业日，`B1` 为跨零点后的同一营业日延续，`B2` 为下一营业日 |
| 桌台 | `TEST-L01`（4人）、`TEST-B01`（6人）、`TEST-S01`（2人） |
| 酒水商品 | `TEST-BEER`（整瓶条码入库）、`TEST-COCKTAIL`（配方原料扣减）、`TEST-WINE`（批次成本） |
| 后厨商品 | `TEST-HOT`（需制作）、`TEST-SNACK`（默认充足、不管理库存） |
| 顾客 | `TEST-GUEST-A/B`；同桌不同身份；证据只用掩码和公共编号 |
| 预约 | `TEST-RES-NORMAL`、`TEST-RES-NOSHOW`、`TEST-RES-DEPOSIT` |
| 支付 | 1 分/1 元测试商户交易与模拟渠道严格分开标记；模拟结果不得写成真实支付 |
| 打印机 | `TEST-CASHIER-80MM`、`TEST-BAR-80MM`、`TEST-KITCHEN-80MM` |

每轮开始前保存数量基线：顾客、预约、开放桌次、订单、订单项、KDS、支付、退款、库存移动、任务、打印任务、审计和 Outbox。结束时逐项核对增量，不能只查页面。

## 6. 正常场景包（N）

### N-01 门店口令、员工登录与岗位切换（P0）

- 前置：有效门店口令；老板、运营、店长、收银、服务员、调酒师、后厨、舞台各一个测试账号。
- 操作：首次输入门店口令；依次登录各岗位；退出后切换下一岗位；最后返回原岗位。
- 应得结果：门店口令只在规定生命周期验证；每次员工切换都要求本人凭证；快捷入口切换页面后不消失；各岗位只看到本职入口。
- 强事实：每次登录/退出/拒绝都有员工、门店、设备、时间和原因；历史业务动作不因姓名或岗位变化被改写。
- 系统支撑：连续错误锁定、会话过期、权限被撤后下一次操作立即拒绝。
- 人工接管：锁定由身份管理员按流程解锁；不得共享 PIN。
- 证据：各岗位首屏截图、直接调用一个无权限 API 的 403、登录审计只读查询。

### N-02 开始营业、岗位到岗与责任区（P1）

- 操作：创建 `B0` 营业日，员工签到，分配门迎、服务、收银、吧台、后厨和候补责任。
- 应得结果：同一门店只有一个有效营业日；责任区、主责、候补和缺岗清楚可见；没有到岗的人不接新任务。
- 强事实：营业日、班次、岗位快照、责任版本和发布人不可覆盖。
- 系统支撑：缺岗时提示指定替补，不自动扩大资金/审批权限。
- 证据：营业状态、员工工作台、责任版本及审计。

### N-03 商品、条码、配方与成本建档（P1）

- 操作：创建整瓶酒、鸡尾酒、后厨商品和默认充足小吃；为整瓶酒绑定条码，为鸡尾酒配置配方和每份标准消耗；录入售价和生效版本。
- 应得结果：整瓶酒可扫码识别；鸡尾酒显示配方但不向顾客泄露成本；小吃可售且不要求库存批次。
- 强事实：商品、品类、销售路由、条码、BOM、单位、成本和生效时间均为强字段；旧订单保留当时快照。
- 系统支撑：重复条码、单位不兼容、配方总量异常或缺少档口时拒绝发布。
- 证据：管理员页面、条码反查、配方版本、权限审计。

### N-04 扫码收货与批次成本（P1）

- 操作：手机允许摄像头；扫描 `TEST-BEER` 条码；录入数量、批次、供应商、单价和凭证；再次扫描同商品新增一批不同成本。
- 应得结果：扫描后定位商品而不是直接加库存；员工确认批次信息后才入库；两批数量和成本分开；手工输入条码可作为明确备用入口。
- 强事实：每批数量、单位成本、供应商、入库人、时间和凭证不可覆盖；库存等于移动流水求和。
- 系统支撑：摄像头拒绝时给出开启权限和手工录入；重复提交幂等，不重复入库。
- 证据：iPhone、安卓、华为真机各一段录像；批次和库存移动查询。

### N-05 预约、确认、到店与开台（P1）

- 操作：顾客预约人数/时间/偏好；门迎确认；顾客到店；门迎选择实际桌台并开台。
- 应得结果：预约阶段不预绑具体桌；到店才建立唯一桌次；小程序和员工端显示同一人数、状态和桌号。
- 强事实：预约、客户、到店、桌次和责任门迎形成时间线；重复提交不新增第二预约。
- 系统支撑：容量超限要求说明；桌台占用冲突返回明确 409。
- 证据：顾客与门迎双端截图、预约/桌次公共编号、审计。

### N-06 未扫码浏览菜单、扫码后进入点单（P1）

- 操作：未扫码打开小程序菜单；查看商品、演出和会员引导并拒绝；再扫描当前桌固定码。
- 应得结果：未扫码可浏览公开菜单但不能下单；拒绝会员仍可继续；扫码后绑定当前桌次并显示购物车/下单入口。
- 强事实：匿名浏览不生成虚假会员或订单；桌台权限来自有效 guest session。
- 系统支撑：未开台时提示联系员工并刷新；旧码/旧令牌不能写入新桌次。
- 证据：真机录屏、会话公共编号、拒绝同意后的行为记录。

### N-07 同桌多人点单与重复商品提示（P0）

- 操作：A、B 分别扫码同桌；A 下酒水，B 下后厨商品；10 分钟内再次选择同一商品并确认。
- 应得结果：两人共享已点商品和履约状态，但未付款订单和个人权益不串人；重复商品先提示，确认后可继续。
- 强事实：每个订单只属于发起客户；幂等键只对应一个订单；KDS 和库存副作用各一次。
- 系统支撑：连续点击重放同一结果；相同幂等键不同载荷稳定拒绝。
- 证据：A/B 双端截图、订单/KDS/库存数量守恒。

### N-08 吧台、后厨、取餐与送达（P0）

- 操作：酒水和后厨分别接单，依次执行 `queued -> preparing -> completed -> picked_up -> delivered`。
- 应得结果：调酒师只见吧台商品，后厨只见厨房商品；桌号和品名字体清楚；服务员只见待配送；顾客看到真实进度。
- 强事实：每次状态迁移有唯一操作者和时间；完成制作只创建一次配送任务；`delivered` 不回退。
- 系统支撑：并发点击只有一人成功；错品/重做创建关联异常，不覆盖旧事件。
- 证据：三岗位页面、KDS 事件链、配送任务、顾客状态。

### N-09 配方扣减、整瓶扣减与默认充足商品（P0）

- 操作：完成一杯鸡尾酒、一瓶啤酒和一份小吃的出品。
- 应得结果：鸡尾酒按 BOM 各原料扣一次；啤酒按销售单位扣一次；小吃不产生受管库存扣减但保留销售成本快照。
- 强事实：库存不得为负；订单项、KDS 和库存移动关联一致；退款不自动回库。
- 系统支撑：缺配方/库存时下单或制作前明确阻断，不能负库存硬完成。
- 证据：出品前后批次余额、库存移动、成本快照。

### N-10 服务呼叫、接单、到桌与完成（P1）

- 操作：顾客请求加水；主责接单、到桌、完成；顾客再次反馈未解决。
- 应得结果：顾客先看到“已收到/正在安排”，不能提前显示完成；重新请求关联原任务；经理可查看处理时间。
- 强事实：创建、领取、到桌、完成、重开和执行人完整留痕。
- 系统支撑：主责超时转候补，再升级店长；通知失败不丢任务。
- 证据：顾客/服务员双端录像、任务事件和升级记录。

### N-11 微信支付、查单与消费明细凭条（P0，真实通道）

- 操作：顾客对未付金额发起微信支付；完成微信授权；系统接收渠道结果并主动查单；生成 80mm 消费明细凭条。
- 应得结果：支付受理与最终成功分开；只有权威渠道确认后显示已付；凭条含陆家嘴中心 L+MALL、桌号、人数、商品明细、实付、支付方式、时间和脱敏交易号。
- 强事实：系统金额、币种、商户订单号和渠道交易号唯一一致；重复回调只入账一次。
- 系统支撑：超时保持 `pending/unknown` 并查单，禁止引导重复支付。
- 人工接管：三沐查渠道，李艳复核；未知结果不口头改成功。
- 证据：测试商户小额流水、系统支付记录、回调/查单审计和实物打印。

### N-12 退款申请、分人审批、渠道完成（P0，真实通道）

- 操作：三沐选择原支付中的一件商品申请部分退款；李艳审核；调用渠道；主动查询到账。
- 应得结果：申请人不能审批本人退款；可退额按原实付分摊；处理中占用额度；成功后原销售日不变，退款记实际营业日。
- 强事实：订单项、原支付、退款、申请人、审批人、渠道流水和金额闭环；KDS/报损/回库另做处置。
- 系统支撑：重复申请、超额、金额/币种/原交易不符均拒绝或保持待核对。
- 证据：两岗位操作录像、测试商户退款到账和系统/渠道对账。

### N-13 自动打印和打印路由（P1）

- 操作：一个订单同时包含吧台和后厨品项；观察订单受理时的制作单；完成支付后再观察消费明细凭条。
- 应得结果：订单受理后，吧台只打印酒水制作单、厨房只打印厨房品项；支付权威成功后，收银才打印完整消费明细。桌号醒目、备注可读；支付回调或页面重试不能让制作单、消费凭条重复打印。
- 强事实：打印任务含目标打印机、模板、业务对象、尝试次数和结果；配置修改有权限和版本。
- 系统支撑：打印机离线进入待重打/人工清单，不回滚支付，不路由到错误档口。
- 证据：三张实物小票照片、打印任务和配置审计。

### N-14 会员自愿同意与微信手机号选择（P0）

- 操作：顾客打开会员邀请；先拒绝；再次进入后主动勾选协议并点击加入；微信弹出手机号选择；顾客选择号码。

- 证据：微信真机录屏、同意和联系方式动作审计；截图不含完整手机号。

### N-15 结台、交班和结束营业（P0）

- 操作：确认余额为 0、履约完成、投诉关闭；结台；逐岗交班；结束 `B0` 营业。
- 应得结果：结台后桌台可重新开台，前桌实时数据不泄露；结束营业自动关闭满足条件的遗留桌，不能清掉有未结对象的桌。

- 证据：闭店前后清单、桌次状态、业务日、审计和下一桌扫码反证。

## 12. 最终判定

### 12.1 可合并代码

- 相关正常、拒绝、重复、并发、超时和恢复场景均有 E1/E2/E3 证据。
- 质量模型、TC 基线、类型、数据库、浏览器、架构和差异检查通过。
- 现场项可以明确记为 `blocked/not_run`，但不能伪报通过。

### 12.2 可进入现场试运行

- 所有会影响点单、出品、收款、库存、权限、打印和关店的 P0/P1 在候选环境通过。
- 真机扫码、摄像头、80mm 打印、网络切换和测试商户小额支付完成。
- 每个异常都能定位责任岗位，不依赖开发人员直接改数据库救场。

### 12.3 可商业发布

- 原 213 条经营 TC、增量专项、规范化候选和发布入口的必需 P0/P1 均绑定当前不可变提交证据。
- 真实支付、退款、POS/现金（若启用）、渠道对账、三台打印机和岗位协作通过。
- 代表性峰值、备份恢复、维护窗、回退边界和发布后观察计划通过。
- 所有未完成项都在商业清单中；任何 P0 未完成均为 `DENY`，P1 风险接受必须有负责人、有效期、补偿和复验期限。
