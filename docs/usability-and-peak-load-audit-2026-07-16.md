# M-Box 三视角易用性与 300 人压力审查

审查日期：2026-07-16  
营业模型：20:30-02:00，共 330 分钟，累计到店 300 人，按 75 组、平均 4 人建模。

## 结论

系统已经具备门店验证条件。顾客扫码点单和呼叫服务的主流程简单；服务员与店长首页能直接看到责任桌台、待办和风险。此次发现并修复了两个界面问题和一个高并发数据问题。

上线前仍必须完成至少 3 个真实营业晚班的员工演练，重点观察员工是否在 30 秒内接单、出品是否按工作站完成、替补是否及时接管。压力测试证明系统能承载请求，不代表员工执行质量已经达标。

## 客户视角

- 扫桌码后直接识别桌台和服务专员，不要求先注册或关注。
- 点单、服务、订单三个入口含义明确；菜单有图片、价格、规格、状态和固定结算入口。
- 常用服务从首页进入后一次点击即可提交；个性化需求填写后单独提交。
- 手机 390x844 视口无横向溢出；服务页主要按钮可在一个屏幕内看到。
- 下单到模拟支付成功形成闭环；正式支付仍需以星驿/微信商户正式参数做支付验收。

## 服务员视角

- 登录后首先看到责任桌台、个人任务、待送出品和待点单桌台。
- 高风险事项可以从数字指标直接进入任务列表，任务卡包含桌台、等待时长、负责人和下一步动作。
- 平板横屏原有“侧栏 + 工作入口”重复，本次已在宽屏隐藏重复入口；手机端继续保留入口。
- 正式云端原有无签名示例“顾客端”链接，本次改为仅本地开发模式显示，防止员工进入无效桌码。
- 多岗位员工仍按后台配置合并权限，不因界面精简而丢失可执行职责。

## 店长视角

- 首页直接显示营业桌台、待处理任务、SLA 风险和 KDS 待办。
- 点击 SLA 风险一次即可进入任务队列，并可直接接管或指派。
- 现场、任务、预约、订单/KDS、库存、收银、权益、点歌、布局和配置按权限隔离。
- 宽屏首页移除与侧栏重复的入口后，风险和待办成为第一视觉重点，720p 屏幕不再被无效入口占用。

## 压力测试

测试环境：本机隔离 PostgreSQL 16，40 并发连接，不使用云端真实营业数据。

真实 HTTP 业务压测共 613 个请求，失败 0：

| 流程 | 请求数 | P50 | P95 | 最大值 |
| --- | ---: | ---: | ---: | ---: |
| 顾客获取桌台会话 | 300 | 18.5 ms | 36.6 ms | 121.4 ms |
| 顾客创建订单 | 75 | 348.8 ms | 392.8 ms | 397.8 ms |
| 顾客模拟支付 | 75 | 391.6 ms | 1010.7 ms | 1037.1 ms |
| 顾客呼叫服务 | 35 | 426.0 ms | 799.0 ms | 822.2 ms |
| 员工工作台刷新 | 120 | 130.3 ms | 276.1 ms | 291.9 ms |

另外用 3 个独立服务实例同时进行 300 次 PostgreSQL 写入。修复前因聚合状态乐观并发冲突仅成功 12 次；改为事务内行锁排队后成功 300 次、失败 0，P95 为 1487 ms，吞吐约 189 次写入/秒。

## 经营验收标准

- 顾客呼叫提交成功率 100%，页面立即显示已收到。
- 正常网络下顾客读操作 P95 小于 500 ms，关键写操作 P95 小于 2 秒。
- 任何已付款订单不得丢失、重复出品或串桌。
- 服务呼叫 30 秒内被接单；超时自动升级候补、主管或店长。
- 出品开始、完成、取餐、送达必须形成闭环，异常可追溯到岗位和时间。
- 店长在首页两次点击内能到达风险任务并接管。

## 仍需现场验证

- 夜店弱网、员工平板休眠、耳机断连和微信内置浏览器回前台后的恢复能力。
- 正式星驿支付的付款码、二维码、异步通知、退款和对账。
- 300 人到店时的实际桌台周转分布、员工步行距离和主责/候补负载阈值。
- 现场音乐噪声下的耳机播报可懂度，以及员工对提醒的确认习惯。
