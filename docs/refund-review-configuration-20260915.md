## 原因与证据边界

本会话生产只读查询时，仅一笔 `requested` 退款：BAR2、3000分、三沐于2026-09-15 00:17发起，退款ID `ff833158-ab82-4408-bd98-c9153e580431`，无商品售后单关联。

系统原本支持角色权限和角色审批额度配置，但分散在“岗位权限”“审批与范围”；权限可单独授予、额度可为空，保存成功不代表能执行退款复核。`refund.approve` 同时控制通过和驳回，两者均校验额度。本次保留此业务规则和禁止自审，不增加真实退款或放宽限额。

## 实现

1. 在“系统配置 → 管理员控制中心 → 退款复核”中选择岗位，勾选允许复核，填写人民币单次上限。权限与额度一次发布；停用同时关闭该岗位的两项配置。额度支持分，空值、零值、负数或超过两位小数不能启用。
2. 已发布人员配置按有效岗位、个人允许/禁止、有效人民币额度展示完整配置或缺项；不足两名完整配置员工时提示可能无人处理。该列表不等同每笔退款的实时资格，实际执行继续检查金额、申请人和状态。
3. 后端验证启用额度必须为有效正整数分；新授予退款复核岗位权限必须已有或同批配置有效额度。员工例外增加退款复核权限也必须有有效所属岗位额度。失败整批回滚。
4. 沿用现有管理员授权、幂等发布、审计、重新读取和运行时配置保护。个人明确禁止优先。未额外授予退款执行权限、系统管理权或指定真实人员额度。
5. 通过/驳回错误分别提示本人申请、缺复核权限、缺有效额度或超额。收银页面不再笼统要求收银本人“交给收银”。
