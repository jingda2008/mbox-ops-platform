# 历史空结果、迟到请求与双设备拆并桌审计

范围：员工网页与后端。本轮仅本地开发和隔离数据测试；未部署、未上传小程序、未修改生产数据。

## 发现及修复

1. **查不到回执不等于未执行。** 原代码把 `TABLE_MOVEMENT_RECEIPT_UNAVAILABLE` 标为 `not_committed`，网页随即清除原请求。尚在网络途中、尚未进入数据库的请求仍可能迟到。这是实际协议缺口，已改成结果未知；保持原编号、原员工和原参数，禁止用新参数覆盖。即使旧后端仍错误返回 `not_committed`，新版网页也保留记录。
2. **明确撤回原请求。** 待核对卡新增“撤回未确认的原请求”。沿用原编号和正文，通过 `x-table-movement-seal: 1` 明确提交；普通核对仅使用 recovery 头，不撤回。已有真实回执时只读取回执并刷新名单，不撤销移动；尚未执行时持锁写入永久封存记录。事务提交后才返回 `TABLE_MOVEMENT_REQUEST_SEALED` 和明确未执行状态。迟到原请求只能得到封存结果，不能移动顾客。
3. **撤回断网后仍可核对。** 撤回响应丢失保留原记录，再次核对或撤回仍使用原编号。撤回记录存入现有追加式审计账本，普通幂等缓存删除后仍生效，不生成移动事件或出品消息，不需新增数据库迁移。
4. **迟到响应不覆盖新操作。** 原操作的迟到成功或封存响应不得清除或覆盖另一个较新的本地请求记录；账户不匹配时不核对、不撤回。
5. **同一编号不能变更拆并桌类型。** 永久封存按拆并桌命令编号绑定，不按拆/并分别放行；真实移动记录也交叉检查另一类型。普通缓存清理后，换员工、改参数或把拆桌改为并桌均拒绝。
6. **历史提示不暗示“可以重做”。** 有历史记录和空列表都说明：只证明所列操作已经完成，找不到匹配记录不能证明原请求未执行，也不能阻止迟到请求。查询不会创建移动或封存。

## 实际操作规则

| 当前情况 | 员工操作 | 系统行为 |
|---|---|---|
| 提交后断网、无法确认 | 点击“核对原拆并桌结果” | 查询原编号，查不到则继续待核对 |
| 明确不再等待原请求 | 点击“撤回未确认的原请求” | 若未执行则永久封存；若已执行只返回真实回执 |
| 撤回也断网 | 再次核对或撤回原请求 | 不换编号、不自动新建移动 |
| 已确认封存，仍需拆并桌 | 核对现场，重新预检后明确提交新操作 | 新编号与新快照；迟到旧编号仍被拦截 |
| 换设备且原本地记录已丢失 | 查服务端历史，核对现场及当前名单 | 不能凭空推断原编号，不能用空历史直接宣称未执行 |
| 两台设备都核对后提交 | 使用各自预检快照 | 服务端锁内核对移动版本，同一旧状态只允许一个移动生效 |

独立设备无法识别一个从未到达服务端、且编号已丢失的原请求。不能把“历史已读”视为取消或业务意图的全局去重。本轮用锁内版本校验防止迟到原请求与基于同一状态的新请求重复生效；状态已变后必须重新核对现场并明确新意图。未自动执行反向拆并桌。
