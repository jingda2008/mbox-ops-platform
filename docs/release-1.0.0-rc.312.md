# 1.0.0-rc.312 财务历史和渠道赠品到期查询修复

rc.311 主线全库复跑有两项超时。财务历史用例限时 60 秒，渠道赠品到期用例限时 5 秒。隔离库中，在有 5,000 笔已付历史单的门店，逐单调用应收与欠款函数的原日结耗时 7,885 ms。渠道到期任务处理 100 个客组，发起了 100 次渠道订单明细查询，返回 16 行，寻找可关闭无桌客组另耗时 725 ms。远端超时日志只提供用例总时长。

schema 364 增加按营业日区间汇总的调用者权限函数，单日日结共用该函数。先选定门店和日期内的订单，再关联全部日期的原单回款。普通已付单批量核对收款，含退菜、成功退款、旧挂桌用分、退票补菜款和结转欠款的订单保留原逐单计算。跨日追收继续按原单核对。迁移增加渠道原归属及改归属的客组索引，涉及两张渠道表的短时建索引写锁，部署前核对表规模及在途营业操作。迁移无需重写营业订单、付款、积分或票档。

渠道到期任务沿用每批 100 和原事务锁。先核对原客组及更正记录，有订单的客组才展开财务明细。无桌客组按有效归属汇总未关桌次。取消折扣先检查有无已取消的相关订单，符合条件时继续审核支付、制作、备货与释放事实。

员工按实际演出建场次、上架票档。微信正式版、真机交易和现场凭证延续原验收记录。

隔离 PostgreSQL 同口径复验，顾客用完 550 分后确认补款 500 元，原有批量查询错误返回应收及欠款均为 0。修复后收款前分别为 500、500 元，原单收款后分别为 500、0 元。使用门票和挂桌积分的订单按原单权威函数算应收。收银、工作台、营业历史和经营看板共用余额口径。

受限数据库账号的执行计划显示，有 5,002 单的营业日一次读取 5,002 单，汇总 SQL 耗时 8.739 ms。空营业日命中营业日索引，付款底表的实际扫描次数均为 0，耗时 0.083 ms。数字为隔离库一次执行。渠道复验中每批仍检查 100 个客组，4 条到期，0 项失败，单批从 1,909 ms 降到约 411 ms；客组使用随机标识，两轮明细返回行数会随排序变化。生产只读查询显示两张待建索引的表在核对时均为 0 行。
