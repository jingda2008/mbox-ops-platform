# 渠道优惠转桌、拆桌、并桌：前后端联动测试

核验时间：2026-11-12 17:56 CST。当前未部署候选。使用真实本地临时PostgreSQL与实际HTTP转桌接口，以及真实React组件/小程序请求代码的隔离模拟；未操作生产或真实资金。

## 结论

转桌会改变顾客位置和可用桌次凭证，前端必须刷新或重新核验；推荐来源、既有消费和同一客组优惠额度应连续保留。新增7项数据库联动测试、2项小程序跨桌响应恢复测试及4项浏览器检查，最终通过。未发现需要修改业务代码的新增转桌缺陷，本轮仅增加测试和记录；这不是全系统无漏洞或现场验收结论。

## 已实际执行的场景

| 场景 | 后端验证 | 前端/营业影响 |
| --- | --- | --- |
| 整桌A转B，转前已有优惠订单，转后继续加单 | 真实HTTP转桌保留原table_session_id和visit；旧新订单仍属同一推荐批次；相同转桌请求重放不再移动 | 位置和凭证变化须刷新核验，不能继续信任旧桌连接 |
| 转前优惠10%，每客组最多15元；转前消费100元、转后再消费100元 | 第一单优惠10元，第二单只优惠5元，总额15元，没有重新发券或重置上限 | 加单按服务端新报价；不按新桌重新发满额优惠 |
| 上述两单收款后退款 | 隔离现金成功事实分别90/95元；计佣基础185元、按10%为18.50元；原第一单退20元后基础165元、佣金16.50元 | 退款仍引用原订单/支付；未移动历史支付或把退款挂到新订单。金额是测试样例 |
| 一批客人部分拆到新桌 | 相关业务未结时HTTP409，整笔未移动；原订单、出品及支付事实完成后可拆；两桌同visit，累计减免不超15元，L仍是原客组上限 | 拆桌前处理未结事项；不能通过拆桌增加限用次数 |
| 全员并入无既有消费目标桌 | 原桌关闭、目标桌保留同一渠道visit，visit不提前结束，原券可在目标桌计价 | 正常并桌后在目标桌核验，不必重复领取 |
| 两个不同渠道客组并桌 | HTTP409；两桌状态、人数、已有券及移动事件保持原状态 | 不自动合并归属；分别核对或按主管流程处理，不能承诺直接并桌 |
| 无渠道客组并入渠道客组；渠道客组并入已有消费桌 | 均被拦截，不给其他客组历史/后续消费自动套来源 | 即使有剩余座位，也须先核对客组来源 |
| 已预留但未出品的赠品随部分客人拆桌 | 原券及库存预留保留，目标桌下赠品单；重复点击仍返回同一订单，仅1个KDS任务 | 到目标桌从原券办理，不另送一份；实际打印/配送方向仍待现场验收 |
| 员工看A桌预览时切换到B桌，A响应后到 | React组件清空输入，旧预览不出现，不能据此绑定B | 需要在B重新选择顾客和优惠 |
| 员工在A提交绑定，中途切换到B | 实际发出载荷仍为A；晚到结果不覆盖B，B不展示A的成功/恢复操作 | 到原操作桌核对，不把A回执当作B已绑定 |
| 顾客在原桌提交后切换桌次，原响应成功或断网晚到 | 不在新桌报告成功、不清除原桌待核请求；返回原桌恢复使用同一编号 | 结果未知时不得清缓存、换编号重复核销 |
| 既有转桌原生流程 | 同时复跑原位置管理27项测试：身份人数、全员/部分移动、凭证撤销、幂等重放、位置版本、容量、权限与业务冲突 | 不是只测渠道表或只看界面桌号 |
