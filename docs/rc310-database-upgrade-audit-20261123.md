# rc.310 数据库升级后审计

2026 年 11 月 23 日，北京时间。审计对象为陆家嘴门店正式后台 `7f82408e`，从 rc.308 的 schema 322 升至 363。主要数据快照截至16:56，随后补核历史日报和库存字段。正式检查均为只读；写入、重复迁移及恢复演练仅在独立本地数据库进行。建议维持当前后台版本，整桌票继续暂缓开售。

## 仍会改变经营行为的地方

1. **普通餐单也经过新逻辑。** 订单应收、原挂账收款、退菜核价和积分退款已扩展。新餐饮积分抵扣会按菜品份次和积分批次保存来源；旧抵扣如无份次来源，代码走原恢复算法。正式库已有54条历史积分占用记录，本次未将其追补为新份次流水。审计时新增的两笔普通支付已对平，首笔真实用分、混抵和后续退款仍需现场及渠道回单。
2. **第一次发布票档会影响全店普通桌。** 当前实现检查门店是否曾存在已发布的票档版本，独立于开售时间、演出时段与区域。首次发布会令新开桌的餐饮门槛归零并采用点单结算模式，也会改变部分在桌预收及转桌的门槛计算。撤下票档是追加版本，历史发布记录保留，因此撤下最后一张也不会自动恢复原门槛。开发方案已有全店取消餐饮低消的要求。现场需明确“发布”这个生效时点，并核对历史预收款如何分配。当前票档数0，108张桌的基础门槛字段均没有正值，2个在用桌次也没有正值。[迁移334](../database/normalized-migrations/334_optional_dining.sql)
3. **商品可见性函数有4项差异。** 以同一正式数据在02:00、17:00、22:00分别按新旧匿名可见规则复算，每个时点346个商品中均有4个由可见变为隐藏。三款白州已经停用；在用的「冬恋蜜柚（有酒精）」归在对顾客隐藏的「特调鸡尾酒」分类。四款均未设商品可见时间。旧普通顾客菜单本已过滤隐藏分类，未见这4款因本次升级从原普通菜单消失；持卡专属入口和旧客户端应另行验收。[可见性迁移](../database/normalized-migrations/347_product_menu_visibility.sql)
4. **普通开桌、换桌和预订增加同店容量锁。** 物理桌次或预约锁的有关写入会获取同一门店事务锁，再校验票务承诺。隔离库用两个数据库连接对同店两张不同桌分别插入开桌记录，均无票档。保持第一笔事务未提交，在322上第二笔可立即写入，在363上第二笔触发测试设定的400毫秒锁超时；释放第一笔后重试成功。原预约入口已有部分路径会主动取同一把锁。正式只读采样未见锁等待，繁忙时段员工端的延迟和超时率仍待验证。[容量迁移](../database/normalized-migrations/330_table_ticket_shared_capacity.sql)
5. **应用回退与数据库恢复要分别处理。** 此版发布清单记录的回退方式为应用镜像，数据库回退需要单独恢复。仅切回 rc.308 会保留363的函数、约束和触发器；直接整库覆盖为15:27备份会遗漏随后成功的两笔收款及对应营业流水。发生故障时先核实新增业务、停写点和渠道结果，保留现账并验证补回方法，再决定前向修复或恢复路径。本次未在生产实施回退。

## 开桌、排票与普通预订并发复验

本节使用本机临时 PostgreSQL 数据库、合成员工和订单。所有请求均经过真实事务提交或回滚。修复只调整后台取锁顺序和接口提示，沿用 schema 363。门店现用的 rc.310 尚未包含此修复。

| 操作 | 修复前 | 修复后 |
| --- | --- | --- |
| 接待与收银开不同桌，门店没有票档 | 6 批，每批 8 个并发开台命令。48 笔均成功，P95 为 43 ms，最慢 51 ms。 | 相同模型下 48 笔成功，P95 为 44 ms，最慢 52 ms。用原请求编号重放全部 48 笔，每次返回原桌次，数据库恰有 48 个营业桌次。统计包含命令处理和事务提交。 |
| 普通开桌或整桌换桌，与后台排票争同一张桌 | 在现场操作已锁定物理桌、准备写入时，让持票排桌进入。查询数据库确认双方发生等待后继续，实际收到死锁错误 `40P01`。 | 桌台管理、普通开桌和整桌换桌三个入口均完成在先的营业操作，排票收到桌况冲突。再次排同桌仍被拒绝，票上没有错误的桌位锁。 |
| 3 张桌已有 2 张已付款票，排票到 A，同时由接待和收银分别申请开 B、C | 容量保护有效。允许一次开桌，另一次返回 HTTP 500，员工无法判断能否改选。 | A 排票成功，B、C 中一个返回 201，另一个返回 409 并提示需保留已购桌票的桌位。两次开桌请求均按原编号重试，成功的返回原桌次，被拒绝的仍返回同一原因。区域可售余量为零。相同时段电话预约 A 被拒，A 只有一个有效预约锁。 |
| 同区两个重叠场次只有一张桌 | 原验收同时发起自助购票、代选购票及电话预约或现场开台。复核发现旧开台测试省略了主服务员，即使因为缺少主服务员失败，旧断言也可能通过。 | 补齐主服务员，并校验失败原因。电话预约和现场开台两组各只有一个成功，两场余量均为零。 |

开桌先取得排票使用的门店容量锁，再锁具体桌台。换桌、拆并桌沿用已有的桌次移动锁，然后取得容量锁，再写入物理桌次。数据库在提交时仍会核对同店已售票占用，因此持锁慢事务仍能让其他桌等待。48 桌数据来自本机两次测量，仅作量级参考。

相关 PostgreSQL 和接口回归覆盖 10 个测试文件，共 202 项通过。票务、普通预订、桌台管理、整桌换桌、拆并桌、原餐单及退票路径均在本地执行。[并发用例](../server/normalized/table-ticket.integration.test.ts)

浏览器 18 个用例通过，包含桌台权限、主服务员开台及交接、代客开台重试和接待界面恢复。其中桌台服务 4 项使用独立历史夹具补跑。常规检查及构建通过，常规 Vitest 为 3,102 项通过、2,775 项条件跳过；上述 202 项是单独启用 PostgreSQL 的专项回归。生产依赖审计报告 0 个已知漏洞。

营业 HTTP 负载以每秒 5 次操作、每场景 60 秒依次运行开台、下单、制作、服务。第一轮 2,400 个请求全部成功，其他验证同时运行期间，后厨制作 P99 为 1,546.51 ms，超过 1,000 ms 门槛。停止并行验证后用同样参数重跑，2,400 个请求均成功，开台 P95/P99 为 41.13/46.08 ms，后厨制作 P99 为 71.54 ms，重复领单与状态异常均为零。第二轮运行指标全部达标。工作区有未提交修复，两轮结果均不具备正式版本证据资格；完整商业发布门禁另缺微信正式版发布凭证。运行记录保存在本机发布证据目录 `rc310-table-tickets/db-audit/capacity-concurrency/`。

门店验收应保留两台设备的操作时刻、桌号、票号、原请求重试结果及最终桌况。已排桌客人到店，现有接待流程是在桌台页开实际桌次，再按原票核验关联；现场需核对接待交接时实际入座人与原票的对应关系。服务端压测使用合成请求，微信真机、真实营业网络和桌边操作仍待验证。
