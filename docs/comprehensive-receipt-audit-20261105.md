## 3. 修复原则和兼容处理

配置服务在命令事务和回执锁之后复核当前权限；不能仅依赖入口返回的权限快照。现金交接、会员运营开关、原生公共执行器复用已有 `reauthorizingCommands`，保留各自首次执行的版本、双人审批、营业状态等条件。顾客回执按当前桌次/预约所属关系检查，保留规范顾客身份的业务规则。

没有原操作者证据的旧配置指纹不能自动采用为另一员工的成功结果；新命令绑定员工。旧指纹不匹配时保留原键并核对记录，不能自动换键重做。原生包装器继续使用其原有身份指纹与永久回执合同。

售后新回执保留，旧过期回执明确拒绝重新执行；长期回执会增加保留量，不能再按24小时缓存清理。前端恢复通过原请求键做只读查回执，缺失时要求核对。已存在待确认请求时，各类错误都保留原键和正文，刷新商品状态不清除待确认操作。历史旧客户端与已被清理的历史回执缺少完整原操作证据，不能凭空恢复成功，也不能宣称能自动重建这类历史事实。

配送确认响应只保留履约信息；保存原动作时间和员工，旧回执缺少时间证据时返回未知。AI相对调度按原输入延迟构造指纹，重试不重算为不同意图；新执行的时间合法性仍验证，原已提交请求的恢复不受后来时间流逝误伤。

## 4. 已有保护与排除的误报

- PR421已有 `staffAuthorizedCommands` 对应员工命令会在锁后和回执返回前重验，不能仅凭两参数 `execute` 形式判为漏洞。CustomerExperience和ActivityOperations的已包装路径属于这种情况。
- 原生员工管理和手动积分在验权前取得员工配置锁，正式权限写入也取得同一把锁。直接绕过该锁删除测试权限得出的并发结果不能作为真实接口漏洞证据。
- 顾客服务“创建”已有当前桌次绑定、规范身份和请求指纹保护，不能由本轮反馈/心情缺陷推断创建同样有问题。
- 会员报表的范围检查在只读事务内，历史订单和硬件来源权限有专项回归。先前报表/媒体/等级权益测试只支持其实际覆盖分支。
- 通知及营销worker存在发送前当前接收资格/授权复核，未知外部结果不会直接自动重发。AI定时worker另有当前工具权限检查；本轮缺陷是HTTP旧回执，不是全部调度执行。
- 支付/社交回调检查签名、主体和已验证观察；本地回归不能代替真实渠道、真机通知、资金及出纸验收。
- 已批准发布的业务规则是否继续执行，取决于政策状态、资源和顾客同意，不能机械规定“原起草人撤权就必须停止全部后续业务”。
