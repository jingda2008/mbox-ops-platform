本次仅补齐现有系统缺口，**不重做已实现的支付记录、幂等、后台退避查询和晚到款核对机制**。

实施目标：从“释放后才能收款”改为“未知支付不占收款资格”，同时让营业界面只突出真正需要员工处理的事项。

## PAY-01 未知支付不再占用收款资格

- 取消“存在未释放支付就拒绝新收款”的限制。
- 有收款权限的员工可直接再次收款、切换支付方式。
- 不要求先释放、查单、关单、填写理由或等待超时。
- 风控拒绝、取消、断网、无响应、支付中等状态，只影响对应尝试。
- 只有确认足额到账才拦截新收款；部分到账按剩余应收收款。
- 保留原有岗位权限，不扩大员工收款权限。

**验收：**原支付持续未知时，员工仍能正常发起线上收款或登记实际收到的现金、POS款项。

## PAY-02 收款界面恢复直接操作

- 存在未知支付时，仍展示正常收款按钮。
- 取消“先释放再收款”的前置操作。
- 不持续转圈，不反复显示“查询到账中”。
- 本次失败给出简短、具体提示，不阻塞下一次操作。
- 原支付状态保留在订单详情，不强迫员工处理。

**验收：**无需先进入查单或释放流程，即可完成下一次收款。

## PAY-03 统一营业状态与提醒口径

| 业务事实 | 营业界面显示 |
|---|---|
| 实际消费未收清 | 待收金额及收款入口 |
| 已足额收清 | 已结清 |
| 已取消且无需收款 | 退出日常待办 |
| 原支付结果未知 | 不独立占据营业待办、桌台角标或反复提醒 |
| 已确认多收 | 明确的多收退款待办 |

- 桌台、收银、订单中心、员工汇总及小程序采用一致口径。
- 旧支付未知不能覆盖账单已结清状态。
- 收款成功后及时刷新关联页面，避免旧缓存误导员工。
- 不在桌台新增查询、打印入口。

**验收：**同一订单在不同岗位和客户端显示一致；真实欠款不消失，旧未知支付不冒充营业待办。

## PAY-04 解除历史记录对“释放标记”的依赖

- 日常待办不能仅因旧支付缺少释放标记，就长期保留。
- 综合账单是否仍需收款、桌次状态及财务核对状态判断。
- 当前五笔旧未知支付纳入限定修复清单。
- 保留原支付事实、历史流水和审计，不伪造成功、失败或关闭。
- 修复可重复执行，不重复入账、不改库存、不影响新营业数据。

**验收：**符合退出条件的历史记录不再回到营业待办；财务历史仍可查询。

实施前需将上述五笔记录的准确ID、原订单/桌次、当前应收及核对状态固化为白名单，并在执行前回读。五笔为用户指定的历史范围，不以本次文档登记冒充最新数据核验；状态已变化的记录按前置条件跳过并留痕，不扩大修复对象。先预演、后独立回读；不重新打开已处理的¥20退款。

## PAY-05 财务核对与营业操作彻底分离

复用现有后台查询机制，补齐以下关联：

- 新收款发起不依赖旧支付查询或关闭结果。
- 原支付继续按现有退避机制核对，不恢复高频查询。
- 停止自动查询后转为明确的财务核对状态，不继续显示为营业“处理中”。
- 核实现有财务核对入口、权限、负责人及处理闭环；缺失部分补齐。
- 原支付晚到造成多收，复用并验证现有多收处理链路。

**验收：**渠道持续故障不影响营业；多收不会遗漏，也不重复出品或计算销售额。

财务核对负责岗位、具体入口与状态流转需在实施中明确记录；已有入口先复用。不得因退出营业待办而删除或隐去应由财务处理的事实。

## PAY-06 必须同步完成的回归测试

| 验证场景 | 必须满足的结果 |
|---|---|
| 多员工同时收款、同一按钮连点、断网重试 | 同一次操作仍幂等，显式新操作才建立新尝试；权限不扩大 |
| 新收款与原支付成功回调同时发生 | 并发核算已确认到账及剩余应收；已确认足额不再发起新收款，已在途款晚到则进入多收处理 |
| 部分付款、线上与现金/POS混合收款 | 现金/POS仅登记实际收到的款项，剩余应收与各笔事实一致 |
| 两笔先后成功、重复或乱序回调 | 不重复入账、出品或计算销售额；实际多收明确形成退款待办 |
| 取消订单晚到到账、服务重启后恢复核对 | 原事实及退避/终止状态可恢复，晚到资金进入既有核对与多收链路 |
| 历史修复后各页面刷新及再次执行修复 | 待办与金额一致，真实欠款保留，符合退出条件的未知记录不反复出现；重复执行不产生新入账或库存变化 |

**关键区别：同一次操作重试仍须防重复；员工主动再次收款才产生新尝试。不能简单删除拦截条件而不补并发测试。**
