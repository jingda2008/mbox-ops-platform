# 活动服务契约发布与恢复门禁（rc267 / schema 274 → 282）

本次采用既有 contract 维护发布链，不支持在升级后的数据库上单独换回 schema 274 应用。此文档是执行条件与恢复约束，不代表已经部署、恢复演练生产库或完成实体打印验收。

## 为什么需要停旧程序

生产前置只读核对的基线为 `4880b733dfd9d49ddfb7c6b7080d9a2c68660ec0`、schema 274。最终目标 SHA、镜像 digest、迁移摘要仍须由正式发布 manifest 冻结并核对，不能用分支名代替。

- 275 移除每会员每活动唯一报名假设，加入每份套餐、加购、入场批次、独立餐号与制作来源。旧报名代码按旧单条语义查询和更新，不能作为新数据的兼容实现。
- 275 将 `activity_production` 加入打印源队列。原 274 `PrintSourceWorker` 会领取该类型，却没有对应分派方法。精确旧源码在全新 schema 282 的受限 LOGIN 数据库探针中将该任务重试 8 次后标为 `dead`，没有生成打印单。探针只在本地隔离库执行，无设备 I/O。
- 新卡、售卖时段、旧券承诺和补偿保留履约必须由新应用继续处理。不能以旧应用 `/ready` 返回正常、打印队列暂时为空或尚未开始活动作为兼容证明。
- **282 本身不是新增不兼容边界。** 经营报表即时生成既有 `daily_settlement` 冻结快照和原 `print_jobs`；新增活动成本表通过数据库触发器记录。不能仅因有新功能就强制每次迁移停写。

发布脚本明确保留原 96 边界，新增 275 边界。274 → 282 跨越 275；281 → 282 不因 282 单独触发 contract。这个判定不是所有未正式发布过的任意中间镜像的兼容认证。

## 本次执行顺序

1. 正式发布沿原权限、不可变镜像、配置、运行身份和迁移摘要检查。应用、备份、维护数据库登录保持分离；备份恢复服务引用及 root-only 凭据配置沿用 `database-maintenance.env`、`pg_service.conf` 和 `pgpass`。不向应用注入维护凭据。
2. 由上一镜像 manifest 的 schema 与目标 schema 判断跨契约。若旧镜像 manifest 是 274、实际库已跨到 275 以上，禁止把这个旧镜像当作正常可恢复基线，应进入原 planned-maintenance 前进修复流程。
3. 先记录生产 `mbox-health-watchdog.timer` / service 的运行状态，临时停止两者且确认当前巡检已退出；不改 enabled 状态或配置。现有 watchdog 会先设置容器重启策略再检查发布锁，且发布失败释放锁后能重启 `mbox-app`，所以不能只靠 `release.lock` 保证持续停写。原入口切为维护 503，停止旧应用及 worker、禁用自动重启，并确认同旧 SHA 容器与数据库客户端已排空。**排空完成后**才取得冻结备份、恢复身份与备份完整性证据；不复用停写之前的近期备份作为自动恢复点。
4. 应用 275～282 及配置。候选以 `contract_candidate`、worker 关闭、数据库只读方式完成健康与深链检查。旧程序保持停止，不能与新候选共同消费队列。
5. 写入持久 `.contract-write-resumed` 标记后启动新版本写入和 worker，再切流、核对公开身份并归档证据。部署 manifest 记录 `contractBoundary: 275` 及 `rollbackMode: forward_only_after_contract_cutover`。
6. 上线核对真实迁移版本、当前 SHA / digest、旧容器停止且不自动重启、待打印来源与失败原因、支付和退款回调、经营报表范围/缺项。仅在新版本就绪核验通过，或旧库与旧程序同时恢复且核验通过后，按原 active 状态恢复 watchdog timer；仍在维护/前进修复时保持停止。实体打印和真实支付退款分别留证，不能以脚本单元测试替代。

## 出错如何处理

| 时点 | 允许的恢复 | 禁止的操作 |
|---|---|---|
| 数据库未改、尚未恢复新写入 | 原流程恢复原入口；核验旧程序与数据库身份 | 未核验便宣布恢复成功 |
| 已迁移，但 `.contract-write-resumed` 尚不存在 | 停止候选；从排空后的冻结备份恢复数据库；核验 schema 与原 manifest、身份、私有与公开健康后才启动旧程序 | 在新 schema 上直接启动 274 |
| `.contract-write-resumed` 已存在，即使尚未切流 | 保持/重新进入维护、停新写入，保留原数据库与事实；用兼容新契约的修复版本走既有前进恢复流程 | 恢复旧备份抹去新写入；启动旧 274 worker；通过修改标记伪装尚未写入 |
| 已切流或已验证后发生错误 | 同上；原恢复函数同时检查候选名和已改名的当前容器，避免改名后漏停新 worker | 因状态已不是 `cutover_started` 就跳过停写 |

常规手工 rollback 脚本会拒绝 `forward_only_after_contract_cutover`。即使清单被误标为 `application_image`，第二道契约门禁仍会阻止 282 → 274，写入 `application-contract-rollback-guard.json` 并保持旧 worker 停止。Docker 查询/停机失败时不能声称已经排空。

不要直接执行旧发布包内的旧回退脚本或手工 `docker start` 旧容器绕过当前门禁。若新版本已恢复写入，应保留财务、核销、任务、打印回执等新事实；原库的恢复/重放须另有核对方案，不能以普通镜像回退代替。
