## 需要修复的两处

### BTN-20260926-01：清空购物车确认未绑定原桌次与版本（P2）

- 位置：`miniprogram/pages/order/index.js:1844-1860`；支付宝端同名 `clearCart`。
- 条件：在 A 桌发起清空确认，异步等待确认期间页面的有效桌次/购物车状态变成 B 桌，然后原确认回调返回确认。
- 实际：`currentTableRequest()`、`cartGeneration`、`cartVersion` 都在确认后读取，因此调用清空接口时带上 B 桌的新版本；响应后的写入保护也认为 B 是有效目标。服务端版本校验不会识别这次确认原本属于 A。
- 影响：条件满足时可能清除新桌次购物车。不会由此删除已提交订单或已发生收款。尚未证明现场发生过误清；微信原生弹窗与跨桌重入的真机触发方式仍需验收。
- 证据：`scripts/button-audit-cart-scope.test.mjs` 执行真实页面处理函数，通过受控的桌次变化验证实际 API 参数；微信与支付宝两端均复现。日志：`artifacts/button-audit/cart-scope-reproduction.log`。
- 建议：弹窗前捕获原桌次请求、generation/version；确认后重新验证原作用域和写入资格；版本变化应刷新并重新确认，不能自动使用新版本。
- 完成条件：跨桌确认不发出写请求；同桌新增/删改导致版本变化不误清；正常清空、取消弹窗、失联重试回归；两端真机确认。

### BTN-20260926-02：取餐异常“查看原出品”入口循环（P2）

- 位置：`src/normalized-ui/staff-actions/PickupBoard.tsx:125`；`three-screen-route.ts:3-5`；服务端链接生成于 `server/normalized/pickup-workflow-query.ts:118-123`。
- 条件：已绑定取餐设备，以只有 `kds.deliver` 权限的取餐账号登录，收到旧出品待核对提示。
- 实际：链接指向 `/staff/fulfillment?factId=...`，`pickupOnlyEntry()` 仅排除含 `screen` 的查询参数，仍将该链接路由到取餐屏；原任务卡没有呈现。再次点击会重复同一路径。
- 影响：普通取餐不受此项影响；有旧退库、异常或拆份待核对时，页面提供的处理入口不能到达目标。
- 证据：`tests/normalized-e2e/normalized-button-audit.spec.ts` 使用真实隔离登录、真实设备设置及实际权限，注入与服务端一致的 attention 读模型验证点击路由；数据库异常数据的生成本次没有通过业务操作制造。测试断言 URL 带原 factId、仍显示取餐工作台、原任务卡数量为 0。
- 建议：为取餐岗位提供有权查看的最小任务核对/交接入口，或显示“需值班经理处理”并提供明确切换路径。不能直接赋予桌台管理、退款或全店历史权限，也不能只去掉重定向后让员工撞上 403。
- 完成条件：取餐最小权限下可到达明确的异常核对/交接界面，返回不循环；已有登录、设备、原回执恢复和权限拒绝测试继续通过。
