# 转台、预收额度与跨日补收开发记录

更新：2026-11-08 20:43 CST。状态：本地开发与验证通过，schema301—304候选；未部署、未上传小程序，未执行真实收退款。服务费转换按用户取消决定排除。

## 已确认的业务规则

| 场景 | 最终行为 |
| --- | --- |
| 员工 VIP1 转 VIP2 | 保持原桌次及购物车归属，小程序重新进入或当前页面刷新后使用 VIP2；首页轮询15秒、点单页轮询5秒。转台不会另开桌次或重置余额。 |
| 低消500转低消1000 | 以目标桌低消和当前已确认净收款计算缺口；已收500则提示补500，补款继续抵商品。再次转台重新按目标计算，不累加重复差价。 |
| 转到更低低消的桌 | 使用目标桌低消，保留现有收款；不自动退款。保留原开桌低消、每次转台和减免依据。 |
| 顾客小程序自行下单 | 余额足够且本桌低消资金要求已满足才能确认；不足提示补款并保留购物车，待付款成功后重新确认商品。补款金额覆盖低消缺口及本次消费资金缺口，不把两者简单相加。 |
| 员工协助点单及自填收款 | 可以低于本桌低消收款，仍显示商品剩余应付；也可收多于已点商品的金额，多出部分留作本桌预收额度。仅已实际确认的款可用。 |
| 商品1100，员工先收800 | 该单仍欠300，可继续发起收款。分次收款不免除剩余应付，也不自动生成服务费。当前预付模式下订单全额结清后才放行制作。 |
| 商品1100，员工收1500 | 原收款分配1100到商品，剩400供顾客小程序加购。后续点500则补100；抵扣分配不会再次生成实收分录。 |
| 跨日挂账 | 已确认履约欠款沿原单补收；未确认履约的员工挂桌账保留待核对，由授权员工逐单确认金额（可为0），再继续收款。不能因未付款直接认定顾客欠款。 |
| 跨日尚有原预付款未知或晚到 | 原款保留在原桌次，阻止直接按新欠款再收；先核对原款，不能把晚到回调重新开桌或释放已关桌的制作任务。 |
| 客人不要的余额 | 本批不实现服务费转换。余额、退款仍沿原款处理。 |

“低消要求”和“商品应付”分别展示：员工先收低于低消的金额不会免除顾客后续自行点单时的补足规则。已关联但未结清的商品继续参加后续预收款分配，按下单顺序优先结清；界面将这些订单标为“已关联，继续结清”，核对金额包含它们。员工收款需原有收款权限，以及当前桌负责人/协助人或全店收款权限；现金、POS、外部收款继续要求各自登记权限与真实收款凭据。

## 实现位置

- `301_carryover_tab_review.sql`、`carryover-tab-review.ts`：跨日未履约挂账待核对，确认决定不可变，原营业日和当前收款营业日分开。
- `302_transfer_prepayment_minimum.sql`：目标桌有效低消、转台快照及减免基线；保留原开桌事实。
- `303_staff_table_credit.sql`、`staff-table-credit.ts`、`staff-table-credit-api.ts`：员工收款金额、原订单关联、作用域与桌台权限、持久幂等收据。
- `304_guest_credit_holds.sql`、`table-prepayment-repository.ts`：补款期间按购物车版本预留已有余额；变更/支付终态后释放；晚到原款与跨日核对保护。
- `table-credit-settlement.ts`：成功收款后按原款分配到关联商品，全部结清才放行；回调、查单重放不重复入账或制作。
- `StaffTableCreditPanel.tsx`：收银页、员工桌台及协助点单后的统一自填收款入口；原待付二维码恢复、查单及受权限控制的关闭。
- 微信与支付宝 `pages/home`、`pages/order`：当前桌号同步、转台低消弹窗、补款确认及原购物车保留。
- `checkout-print-summary.ts`、`print-ticket-source.ts`：票据分别列累计预收、已抵商品及可用余额；合计扣除已分配金额，避免把原款和分配各计一次。

新增员工接口：`GET /api/payments/table-prepayment/:sessionId`、`POST /api/payments/table-prepayment`、`POST /api/payments/table-prepayment/:paymentId/resume`。沿用原支付渠道查单、关闭和回调能力，未修改渠道协议。

员工自填收款的幂等回执长期保留；同键改变金额拒绝，旧回执过期也拒绝重新执行。桌号/低消版本变化必须刷新，待确认原款必须先核对。购物车补款时的余额预留和退款预留共同参与可用余额计算，金额以数据库事务校验为准。
