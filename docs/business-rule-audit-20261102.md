## 结论与证据等级

### RULE-AUDIT-20261102-01：普通库存接口的旧回执绕过当前权限检查（P2，已复现，未修复）

在 `inventory-api.ts` 的 `execute` 中，普通 Web 非报损操作的权限检查位于业务 handler 内；`command-executor.ts` 在命中幂等记录后先返回结果，不再调用 handler。原生接口与报损有单独再授权保护，不能把一个入口通过的测试推广到全部入口。

两项本机测试使用真实 PostgreSQL 和独立受限 LOGIN（无 superuser、无 BYPASSRLS、继承 mbox_runtime），通过 Fastify inject 执行实际路由、命令执行器及权限仓库。测试的身份解析采用现有测试夹具，未跑生产 Cookie 登录；静态核查 `normalized-request-context.ts` 和 `staff-auth-command-service.ts` 确认生产解析会读取当前权限，但库存 execute 不会据该权限拒绝普通缓存重放。未验证有人在生产利用此行为。

| 场景 | 首次结果 | 撤权后同键重试 | 撤权后新键 | 写入事实 |
|---|---|---|---|---|
| 创建物料后撤销 inventory.manage | 201 | 200，replayed=true | 403 | 物料仍只有1条 |
| 成本校正后撤销 inventory.cost.view | 200 | 200，旧 weightedUnitCostMinor=26.125000 仍返回 | 403 | 校正仍只有1条 |

这是当前授权与旧响应读取不一致，**不是已证实的重复入库、重复扣款或匿名越权**。复现者是原操作者，持相同请求及幂等键。下一步应统一普通和原生入口的重放授权；保留操作权限但失去成本权限时，还要检查各类响应中的成本字段。关闭需要先红后绿的回归、同账号/换账号/撤权/跨门店、历史回执及审计次数验证；不能简单清空缓存来绕过问题。

### RULE-AUDIT-20261102-02：部分拆并桌仍将账号数当作人数下限（P2，规则风险，未认定为新现场事故）

`ParticipantMovementSheet.tsx` 和数据库命令仍拒绝“部分移动1人、选择2个账号”。既有集成测试 `still rejects partial split and merge when selected identities exceed the explicitly moved headcount` 明确保证这一拒绝；本轮回归亦通过。

这属于上轮有意保留的保守规则，而不是 rc277 全员并桌修复失效。如果业务确有“一人对应多个有效账号，需要一起部分移动”，该规则仍会阻断；但登记人数偏低、已离开账号仍在、多人使用不同账号也可能解释数量差异。仅凭账号数大于人数，不能判定哪个解释成立，也不能自动增加人数或把全部账号强行移动。

下一步先以业务实例确定“哪些账号随哪些实际人员移动”的确认方式，再分别定义部分移动人数、账号集合、源桌剩余人数、未扫码客人、旧凭证撤销和订单归属。若修改规则，应同时覆盖 UI、普通/原生 API、锁内校验及 SQL CHECK。关闭标准：业务场景与反例明确、受限角色集成验证、人数守恒及账号不丢失；现场验收另记。

## 后续采用的检查方法

每个功能先写独立业务规则，再核对实现。规则卡应列：真实对象、计量单位、有效状态、权限、允许变化、必须保留的事实、失败后恢复方式；不能直接把现有 if 条件抄成“正确规则”。

| 检查层次 | 要问的问题 | 具体方法与例子 |
|---|---|---|
| 概念和基数 | 两个数量为何应相等？是否只是平时碰巧相等？ | 账号≠人；订单≠付款次数；退款成功≠实物已退；商品可售份数≠材料库存；没有数据≠0。构造0、1、多以及不相等的合法状态。 |
| 业务不变量 | 操作前后，什么必须保持正确？ | 移动不凭空增减登记人数；重试不重复业务效果；财务按已确认流水核对且容纳晚到、多收、退款在途；历史订单归属不被转桌改写。不要把“任何时刻付款都不超过应收”写成不变量，它会误拒晚到付款事实。 |
| 状态与时序 | 单步都合法，换个顺序是否冲突？ | 预览→他人修改→提交；成功→回执丢失→重试；成功→撤权→重试；退款与晚到支付互换顺序；关桌→新开桌→旧扫码重试。 |
| 并发和故障 | 两人同时做，或在中间断线会怎样？ | 最后一份库存两人抢、两人同时关桌、提交后响应前断线、重复/乱序渠道通知、事务失败回滚；检查最终账/库存/事件，而非只检查HTTP成功。 |
| 多层一致性 | 页面、预检、执行、数据库是否采用同一规则？ | 普通Web、原生端、顾客端直接调用分别核查；真实受限角色与RLS；SQL NULL/整数溢出/边界；迁移前合法历史数据升级后仍可读、可处理。 |
| 自动组合和反证 | 测试是否只能证明自己写的假设？ | 状态机生成操作序列、固定随机种子保留最小失败序列；属性测试验证不变量；交换独立操作应得到等价结果；移除关键保护的变异测试应被用例抓住。生成规则本身也须业务复核。 |

不需要盲目穷举所有组合：先覆盖资金、库存、权限、桌次的高影响交叉，再对普通组合采用成对覆盖；关键三因素（如晚到支付＋关桌＋重试）明确专项。保留回归时间和不稳定测试成本，失败不能靠放宽断言“变绿”。

优先顺序：①普通接口重放授权及成本字段；②部分移动的人员/账号语义；③退款与库存、付款与关闭的跨模块序列扩展；④其他预约、会员、优惠及任务流程。已存在测试应复用，但需增加业务反例和模型生成，不能仅以用例总数衡量质量。

本轮没有改业务代码，也没有推送、创建PR或部署。审计结论和风险已登记商业化清单；后续修复、发布及现场验收应分别留下证据。
