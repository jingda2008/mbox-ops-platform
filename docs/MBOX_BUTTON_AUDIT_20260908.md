## 2. 新问题、上下依赖与修复标准

### BA-01 / SYS-101：失败后仍清空表单（P2）

浏览器实点：新增合成演员→维护歌单→成功导入一首歌曲→填写另一首→将导入请求明确返回503。错误提示出现，但textarea变为空字符串，员工必须重输。

原因：`src/normalized-ui/StaffModulePanel.tsx:591`的`run`捕获异常后正常返回，调用方不知道成功与否。`:650`导入后无条件清空；`:606`演员新增后清空；`:667`歌曲更新后关闭编辑；`:684`场次新增后清空日期。后面三处是同型源代码证据，本轮没有把它们全部计作浏览器故障实点。

整改：返回明确成功结果或重抛可分类错误，只有确认成功才能清空/关闭；查询刷新失败必须与写入失败区分。响应丢失时保留原请求编号和正文，先核对结果，不要每次重试生成新业务意图。不能只把错误提示改成成功或静默忽略。

关闭标准：演员、批量歌单、单曲、演出场次逐项验证明确拒绝、断网、响应丢失、写入成功但刷新失败；输入与编辑对象保持，恢复后能继续且不重复创建。

证据：`artifacts/button-audit-20260908/song-import-error.json`与同名PNG，`textareaAfterFailure=""`；浏览器日志`/tmp/mbox-button-audit-20260908-browser-rerun.log`。

### BA-02 / SYS-102：演员/歌单读取乱序（P2）

浏览器故障注入：延迟演员A歌单读取→选择B→B返回空列表→A迟到返回。最终演员选择仍为“隔离演员B”，列表和编辑框是“前一演员A的歌曲”。只注入查询结果，没有保存编辑或对生产发请求。

原因：`StaffModulePanel.tsx:574`的`loadCatalog`没有请求序号或演员/搜索快照保护；迟到结果直接`setCatalogSongs`，旧finally也能提前清除loading。`:658`编辑直接采用列表中song，`:667`以该song.id更新，因此不能靠当前下拉选中B来保护编辑归属。

整改：按演员ID、搜索条件和请求序号隔离结果；切换演员立即关闭不匹配编辑、清理旧列表。加载与失败状态也须归属同一请求。执行保存/停用前核对目标歌曲属于当前演员；保留服务端权限检查。

关闭标准：A慢B快、A旧失败晚到、搜索快速变化、编辑中切换演员，都不能显示/操作错误对象；取消编辑不写入；A请求不能解锁B的提交状态。

证据：`song-previous-performer-race.json`明确记录B选择与A编辑值，同名截图；`/tmp/mbox-button-audit-20260908-deep-panels.log`。

### BA-03 / SYS-103：权益使用重复暂留（P2）

页面证据：`miniprogram/pages/profile/index.wxml:147`仅设置loading，未禁用按钮；`index.js:882`检查会员与桌码，但没有检查正在提交的权益ID。执行当前真实事件函数，首个请求未返回时第二次仍调用API。

依赖：`miniprogram/utils/api.js:901`每次生成新的请求编号；`server/normalized/customer-benefit-api.ts:190`将编号传入暂留服务；`benefit-repository.ts:376`只对同编号重放，不把不同编号视为同一次操作。

隔离PostgreSQL实际迁移到162后的验证：同一顾客、同一桌、同一权益，共2份额度，以两个不同编号并发各申请1份→**2笔暂留、quantityReserved=2、quantityRedeemed=0**；第三笔超额申请被拒绝。独立SELECT读回一致。故不能称为无限领取、重复核销或实际资金损失。

整改：提交中按权益/桌次锁住同一操作；一次意图使用稳定编号，未知结果先恢复已存在的暂留。若允许有意使用多份，应有明确数量/再次申请操作，不应靠提交中的重复点击。不要添加永久唯一约束而误禁止同桌合法使用第二份。会员页、会员中心、员工权益待办、取消/过期释放均需核对数量与状态。

关闭标准：双击、弱网重试、切后台返回、重新进入页面、两份有意申请、取消与过期、员工核销、额度不足、换桌等均有明确结果；普通权益不得冒用每日点心的特殊幂等规则。

证据：`native-handler-evidence.json`、`benefit-db-readback.json`；`/tmp/mbox-button-audit-20260908-benefit-db.log`为1项定向测试通过、7项因名称过滤跳过，不是8项全部通过。
