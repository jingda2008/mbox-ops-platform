# 会员码查询活动与权益

## 范围与入口

员工端「任务」沿用「扫描会员码」，也可输入完整会员号后点击「查询活动与权益」。展示已报名活动、可了解的活动、当前可用券。点心核销码仍筛选原桌台权益待办。

已报名记录分别提示确认待签到、待付款、候补、已签到、取消/退款、活动结束等状态；从结果进入「客户体验与活动 → 活动报名」，自动打开对应活动，默认只显示对应报名，可取消筛选查看完整名单。办理签到与套餐交付继续使用原操作原因、权限、幂等及库存逻辑。

## 权限与业务边界

- 会员码是身份索引，不是持有者身份认证或核销授权；现场仍须核对本人和人数。
- 查询必须登录员工并具备现有会员账户查询权限 `loyalty.account.view`。活动信息还须具备原活动查看、管理或发布权限；取餐专用账号不扩权。
- 会员号须完整精确匹配当前租户/门店有效会员，合并后读取规范客户，停用客户不可查询。不能用客户 ID 或模糊搜索替代会员码。
- 查询完整运行于只读事务，返回私有禁止缓存响应；不报名、不签到、不占券、不扣券、不出库，不返回手机号、支付 ID、内部授权或完整权益快照。
- 活动列表复用原人群可见性和支付可用性，最多 50 场；符合展示范围并不保证人数、年龄、安全确认、套餐库存等报名条件，最终由报名命令校验。最近报名最多 100 条。
- 只有活动仍开放且未结束、报名 confirmed、付款 paid/not_required 才提示可以现场核对签到；不把候补当名额。已签到不等于套餐已交付。
- 可用券复用有效期、剩余份数和券日历判断，既有暂留领取仍在原权益待办处理；固定价券提示结算付款后核销，其他权益遵循券面入口和原规则。
- 连续查询和刷新会清空旧结果；过期异步响应不能覆盖下一位客人，查询失败保留错误与重试入口。

## 2026-09-26 员工选择签到方式扩展

用户明确由员工在扫码后选择。新增「仅到店签到」和「活动签到」两个按钮。前者无需活动报名，员工核对本人后确认；后者保留原活动报名选择与签到流程。未报名不能借到店签到取得活动名额或绕过付款/须知，页面会说明如何完成报名。

- schema249新增 `member_visit_checkins`，每个会员每营业日只有一条有效到店记录，营业日沿用服务端门店时钟，陆家嘴店06:00切换。保留时间和经办员工；历史误签到可撤回，撤回严格绑定原记录 ID 与原会员、营业日，后来重新签到不受旧撤回重试影响。
- 查询沿用 `loyalty.account.view`，签到及撤回同时要求 `customer.relationship.manage`；写入前和命令事务内复核，原命令重放也先复核当前员工权限。取餐账号不加权限。
- 独立事实表不产生报名、活动积分触发事实、券、库存和套餐交付，不更新消费收入或既有会员消费到访统计。没有外部通知。
- 原始身份/日期/经办不可由运行角色改写；取消只能一次，取消原因与原记录保留。RLS限制当前租户/门店，合并会员沿规范客户族查询当日记录，避免合并后再算一次。
- 签到与撤回采用既有持久化幂等命令与审计；网页保留原请求重试键。成功或恢复回执后重新读取当前事实，防止原回执已经被他人撤回却显示仍签到。切换会员或页面后迟到响应不覆盖下一位会员。
- 新请求携带查询时的营业日，仅作过期检测；不能指定历史日期或其他员工/客户 ID。跨06:00的新操作须刷新，不自动改到新营业日；已完成旧请求可回读原回执。
