# KDS规范化权威事务升级 1.0.0-rc.68

日期：2026-08-11

## 结论

本候选已把KDS开始制作、完成制作、取货、送达、经理取消和异常处置接入规范化任务行事务。每次命令先锁定`operational_kds_tasks`中的目标任务，核对状态列、任务载荷与兼容镜像完全一致，再执行领域规则。状态、订单明细、配送任务、兼容镜像、幂等记录和不可变KDS事件在一个PostgreSQL事务中提交，任一环节失败全部回滚。

这不是整店聚合的最终移除。`runtime_states`仍作为其他领域的兼容权威及KDS同事务镜像，KDS命令仍会推进全店revision。下一阶段才适合在稳定运行证据充分后，逐步移除KDS对整店JSON写入和全店行锁的依赖。

## 已实现

- KDS任务行使用`FOR UPDATE`锁定，命令不再只相信进程内聚合副本。
- 规范化状态列、规范化载荷和兼容镜像不一致时失败关闭，不静默覆盖。
- 开始、完成、取货、送达、异常和经理取消均使用服务端操作范围幂等。
- 幂等指纹绑定当前登录员工，禁止复用他人的幂等键执行不同请求。
- 新增不可更新、不可删除的KDS命令事件账本，保留操作人、前后状态、请求摘要、营业日和revision。
- 完成制作与配送任务生成在同一事务；取货、送达与配送任务状态同事务同步。
- 服务重启只补齐缺失KDS行，不删除或覆盖已有权威任务；发现漂移则拒绝启动。
- 健康端点增加`kdsAuthorityConsistent`，候选切流和公开发布验证必须为真。
- 库存仍按现有订单提交节点扣减，本升级没有把扣减时点改到制作完成，避免重复扣库存。

## 本地真实数据库证据

在全新PostgreSQL 16中从零执行25个迁移后，`db:verify:kds`已验证：

1. `queued -> preparing -> completed -> picked_up -> delivered`完整链路。
2. 两个独立仓储实例使用同一幂等键并发操作，只执行一次并返回同一结果。
3. 通用幂等记录被清理后，同一请求复用永久KDS事件且不重复执行；更换操作人或请求内容仍拒绝。
4. 在规范化投影完成后故意抛错，运行状态、revision、KDS行、配送任务、事件和幂等记录全部回滚。
5. 直接篡改规范化KDS载荷后，后续命令失败关闭。
6. KDS历史事件的更新和删除被数据库触发器拒绝。
7. 事件写入时强制目标任务存在，但不会用永久外键阻断rc.67旧投影重建或未来历史归档；事务性删除回滚演练通过。
8. 最终KDS状态和配送服务任务状态一致。
9. 原有数据库校验通过：25个迁移、86张强制RLS表。
10. 原有规范化读取、校验和升级、跨实例调度租约接管和投影回滚验证通过。

## 尚未完成

- 当前改动尚未绑定新的提交SHA和GitHub CI运行，不能标记为正式发布通过。
- 尚未执行固定候选环境的300次KDS容量测试和三轮重复性验证。
- 尚未完成调酒师、后厨、服务员和店长的真机岗位验收。
- 真实打印机、断网恢复和阿里云蓝绿切流仍需发布阶段验证。
- KDS仍保留整店兼容镜像和全店revision锁，性能收益主要来自一致性与故障安全，不能宣称已消除聚合写瓶颈。

## 发布门禁

只有以下条件全部满足才允许部署：

- 提交级CI数据库作业执行`db:verify:kds`并通过。
- `/api/ready`返回`kdsAuthorityConsistent: true`。
- 候选镜像摘要、提交SHA和迁移校验和一致。
- KDS核心路由性能、错误率和队列等待满足rc.68门槛。
- 门店岗位验收确认制作与配送职责、异常和取消流程没有回退。
