# 全员并桌：关联账号与登记人数分开计数

日期：2026-11-02。用户授权修复、测试并更新[PR413](https://github.com/jingda2008/mbox-ops-platform/pull/413)，明确不部署、不改现场桌台和订单。本轮没有访问生产环境，所有业务写入仅发生在本机临时测试库。

## 根因及业务规则

扫码建立的是账号位置，不是对实际人数的核验。源桌登记2人、关联3账号这一状态允许产生，但全员并桌在组件、预检／执行API、数据库命令和事件约束中均沿用了“账号数不得超过移动人数”的部分移动限制。schema297只修了保留同一桌次的整桌转台，并未修复关闭源桌次的全员并桌。

独立的schema297数据库用真实受限LOGIN执行全员并桌，确定性得到SQLSTATE `40001`，业务快照不变；升级298后同一请求成功。此处是本地复现，不声称取得了新的现场故障日志。早期测试日志中两项失败来自测试夹具将关系`primary`误写成`organizer`，已纠正；这两项不作为业务缺陷证据。

当前规则：

| 操作 | 人数与账号规则 | 源桌与历史业务 |
|---|---|---|
| 整桌转台 | 保持登记人数，迁移全部账号，账号可多于人数 | 保留同一桌次、订单及付款 |
| 全员并桌 | 移动人数等于数据库锁定源桌登记人数，必须选全有效账号；目标人数=两桌登记人数之和 | 原规则关闭源桌；已结订单及付款留在原桌次，不转移、不改写 |
| 部分并桌／拆桌 | 保留明确人数覆盖所选账号的规则；拆桌后源桌至少留一人 | 原未结业务和人员归属检查不变 |

例如源桌登记2人／3账号，目标桌登记1人／1账号、容量3：全员并桌后目标登记3人、有4个关联账号，不因账号数而要求加座。若实际到场人数超过登记数，应通过独立的现场人数核实流程纠正；本修复不自动推断人数。

## 实现与保护

- 组件与预检分清人数、账号；“选择全部”保留登记人数，确认页显示“关联账号3个”。执行API将并桌是否全员交给数据库在锁内判定，不能信任客户端标志或预检旧值；普通及原生入口均覆盖。
- schema298给新移动事实增加可空的`source_guest_count_before`，由命令写入锁定源桌人数。只有整桌转台或快照证明全员并桌，事件约束才允许账号数超过人数。显式`IS NOT NULL`避免SQL CHECK的NULL语义误放行；旧事实不回填推测值。
- 对现有数据库函数作精确、计数校验的替换；前置定义漂移则迁移失败回滚，保留权限、租户隔离、未结订单／付款退款／服务、目标容量及加座、身份、版本、幂等与审计检查。
- 预检后源人数变化或新账号扫码，执行重新检查并拒绝旧请求，不能遗漏账号后关闭源桌。
- 成功并桌撤销源桌旧扫码会话；保留目标旧会话、目标主服务员及全部历史订单和付款。
