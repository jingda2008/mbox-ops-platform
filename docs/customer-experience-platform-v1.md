## 2. 活动订金配置

每个活动独立配置，不使用一个全店开关覆盖所有活动。

| 模式 | 客户报名结果 | 名额处理 | 适用场景 |
|---|---|---|---|
| 无需预付 `none` | 提交后直接确认 | 立即占用名额 | 免费活动、低违约风险会员活动、到店结算 |
| 订金可选 `deposit_optional` | 客户可付订金，也可选择不预付 | 不预付也确认；付订金的报名等待支付后确认 | 仅在业务确实给予订金客户额外保障时使用，默认不推荐 |
| 必须订金 `deposit_required` | 必须选择订金 | 暂留名额，超时未付自动释放 | 容量有限、外部采购或高爽约风险活动 |
| 全额预付 `full_required` | 必须全额预付 | 暂留名额，超时未付自动释放 | 有明确票务属性、外部成本已发生的活动 |

推荐默认：普通会员活动选“无需预付”；限量且会产生外部成本的活动选“必须订金”。“订金可选”只有在付订金与不付订金确有不同权益时才启用，否则客户没有支付理由，反而增加解释和对账成本。

### 配置字段

1. 计价方式：每人或每次报名/每组。
2. 活动总费用：按计价方式计算。
3. 订金：仅订金模式填写，必须大于0且不高于活动总费用。
4. 付款时限：5至1440分钟。
5. 客户可见付款说明：提交前展示。
6. 退款与取消说明：报名时形成快照，后续修改不追溯覆盖已报名客户。

本地候选后台可配置封面、完整详情、包含内容、可见范围、参与要求、联系说明，以及可独立升级版本号的安全和退款规则。服务端拒绝创建者自批，也拒绝详情/规则不完整的草稿。迁移088后的独立运营工作台已覆盖草稿编辑、发布后承诺保护、报名/候补名单、签到、未到、取消和退款状态查询；旧的第二套活动表单已退出默认界面，新建活动禁止未批准的`black`客群。收费活动只有在门店线上支付已开放、本地权威Provider已配置、`community.activity.payment`处于`pilot/enabled`三项同时成立时才允许发布，当前仍默认`disabled`。

客户端按“活动列表—活动详情—报名确认—支付/确认”组织。列表只保留封面、标题、日期、短摘要、价格、余位和详情入口；退款全文、人数选择、安全说明和支付确认放在详情或报名确认页。公开活动不得因报名而自动入会。

### 目标状态规则

```text
无需预付 -> confirmed
必须预付 -> payment_pending -> paid -> confirmed
必须预付 -> payment_pending -> 超时且无有效支付 -> cancelled
支付结果未知/金额不足/部分退款 -> 保留人工复核，不自动确认也不擅自释放
活动满员 -> waitlisted，候补阶段不收预付款
```

当前候选已覆盖上述免费与收费状态的本地服务端/顾客端主链：报名记录与`activity_registration`权威支付对象同事务创建；详情和“我的”可以读取状态、首次发起渠道动作或查单。支付结果为`unknown`时只能继续查单，不允许重复创建新动作；到期任务只有在渠道动作尚未创建或支付明确失败时释放名额，未知或金额不符会延长保留并写审计。满员进入候补且不收预付款；只有取消、未到或退款成功等明确释放名额后，迁移088的worker才按报名顺序并发幂等递补，收费候补在递补前不预扣款。已付款报名不能由顾客直接取消，只允许店长以`refund.request`发起，收银通过既有`refund.approve`、`refund.execute`复核执行。

## 3. 真实支付边界

当前候选已把活动报名、名额暂留和`activity_registration`权威支付对象放入同一事务；顾客端详情与“我的”使用独立的支付发起/查单接口，渠道回调复用既有权威支付处理。客户端不得把唤起支付或页面返回当成成功，`unknown`只能查单。到期任务只对未创建渠道动作或权威明确失败的付款释放名额；渠道结果未知或金额不符时延长保留并写审计/Outbox，避免误放名额。

收费能力必须同时通过三道门禁：门店线上支付开关、本地Provider配置、活动支付功能开关。活动支付开关由迁移054默认创建为`disabled`；任一门禁未通过时，必须订金和全额预付都会阻断。`deposit_optional`在支付能力临时不可用时只能选择`none`继续报名，不得展示或创建不可执行的订金动作。

退款继续沿用资金双人流程：已付款活动报名不允许顾客直接取消；店长通过`refund.request`发起，收银使用`refund.approve`和`refund.execute`复核、执行，不能自审。以上是未提交本地候选契约，不代表正式商户、渠道回调或退款已经用真实资金验收。生产开放前仍必须完成微信/星驿真实小额支付、验签回调、查单、退款、重复回调/未知状态恢复、活动账/支付账/渠道账/门店日结对账、微信真机和营业现场验收。

### 资金与经营数据的规范化边界

- 支付和退款终态只允许消费强类型`verified_provider_observations`：记录对象、渠道、验真方式、事件号、金额、币种、交易号、结算渠道、证据摘要和一次性消费状态。外部回执JSON仅作审计证据，`signatureVerified`等自由键不能入账。
- 订单提交时把单位成本、总成本、来源和商品版本冻结为强类型字段；经营贡献利润不再读取`cost_snapshot`。历史成本只做一次严格迁移，缺失、非法或相互矛盾时标记不可用，不编造金额。
- 商品可见、搜索、推荐、限购、时段、渠道、KDS、履约SLA和成本使用第一方强类型输入；默认管理接口拒绝把这些经营字段重新塞入`productSnapshot`。
- 权限范围和赠送/折扣审批额度由强类型列决定；兼容请求中的`rules/scopeValue`只作为待收紧的传输包装，服务端立即校验并写入强字段，运行时不读取其自由JSON内容。
- 预约保留时间、到店宽限、活动条款版本、权益适用商品和客户通知同意均由强字段、关联表或追加式版本记录决定。积分到账、退款冲回、积分到期和预约演出变更已使用“本人身份+具体通知类型+用途+上下文+模板+一次授权”的强门禁；正式微信模板、真机授权和真实送达未验收时继续停发。会员页不放无关的消息授权大卡片。
- 允许保留JSONB的范围仅限图片、长文案、展示编排、历史快照和外部原始回执；它们不得决定权限、隐私、资格、金额、状态、时限、筛选或排序。

## 4. 付款前单杯升级

- 只在创建支付前出现一次。
- 只匹配后台已启用的指定单杯和目标套餐。
- 服务端按当前标准价、人数、毛利下限和有效时间重新校验。
- 接受升级后，将购物车中的一杯指定单品替换为目标套餐，按目标套餐总价付款。
- 不使用“首杯免费”“付款后返88元”等表述，不允许重复抵扣、拆单共用或人工口头承诺。
- 功能默认关闭，正式菜单、BOM、成本和228/398等目标套餐确认后再配置规则。

当前候选已把锁定报价、重验当前价格与毛利、桌次/人数/时段、商品状态、套餐结构、BOM、配方、库存及强类型产能窗口，服务端替换购物车、创建权威订单、保存价格快照、库存/产能暂留和报价转换收进同一数据库事务。事务提交后才调用支付；支付待定不生成制作KDS，可信支付成功后激活产能并创建KDS，明确失败或超时释放暂留，KDS完成、取消或失败释放已激活产能。

迁移089已把升级规则和产能政策改为不可变版本，并提供起草、独立审批、第三人发布、按历史版本复制回滚草稿、吧台/厨房/收银多时间窗产能配置以及浏览/拒绝/接受/成交结果统计；顾客端报价展示或拒绝埋点失败不阻断原结账。小程序prepare遇到非身份/桌次类错误时会提交原购物车并提示降级；身份或桌次错误仍失败关闭。

功能仍由数据迁移和管理接口强制保持`disabled`。原因已经从“缺代码结构”转为“缺正式经营证据”：菜单/BOM/成本、各工位高峰产能、规则三岗分离、真实资金、故障恢复和至少三个营业晚班尚未签字。影响资格、金额或毛利底线的值继续要求强类型字段或明确策略版本，不得退回自由JSON键。

## 5. 会员权益、推荐和商品观察

### 会员权益和赠送

- “我的”展示真实可用权益、来源、数量、有效期、使用条件、活动报名和积分。
- 营销内容卡不等于到账权益；真实资格继续复用既有`benefits`和`benefit_reservations`。
- 员工赠送商品在桌账订单行明确标记；形成长期权益时还要有正式权益发放记录。
- 新的“我的”已接回真实权益、活动报名和本人预约接口；接口暂时不可用时明确提示或使用旧预约编号回退，不把营销内容卡冒充到账权益。桌账接口与页面已传递并展示权威`pricingKind/pricingLabel`，可区分门店赠送和折扣；真实赠送、长期权益发放及核销仍需岗位验收。

### 推荐证据

目标是最多展示三个方案，并先执行可售、库存、人数、本人明确商品限制、产能、时段和演出阶段硬筛选。迁移085已把“不喜欢/过敏或不能饮用”与普通“这次不需要”分开：只有顾客明确选择前两类才建立本人长期限制，本人可查看和撤回；推荐按规范客户身份族硬排除。商品如配置了适用演出阶段，只有存在可靠的当前强类型阶段事件且匹配时才可推荐。推荐卡加载后发送`exposed`，加入购物车发送`selected`，“不合适”发送`rejected`并移除卡片。结账请求的推荐归因仍在订单事务中校验本人、桌次、营业日和最终订单行。

迁移059新增强类型`payment_id`、`refund_id`、`order_item_id`、归因金额和币种，并用同租户、同门店、同订单、同支付、同退款分摊的复合外键及事件约束失败关闭。`paid`只在权威支付成功事务使订单达到全额已付时写入一次；`refunded`只在权威退款成功事务且推荐订单行的实际退款分摊金额大于零时按退款写入。事件类型、订单行、支付、退款、金额和币种都取自规范化强类型字段，生产者不得从`evidence_snapshot`或其他JSON推断；`evidence_snapshot`只保留非权威展示来源标签。重复回调/查单、失败或unknown支付、非推荐商品退款、部分/全额/多次退款和跨单/跨店伪造均由事务查询、外键和部分唯一约束共同保护。

若客户在选择推荐后接受付款前升级，小程序会刻意省略原推荐归因：保留此前`selected`意向，但不把已被套餐替换的来源商品虚写为`ordered`，套餐支付/退款也不会反推来源推荐的`paid/refunded`，升级结果继续使用独立报价证据。迁移086已补偏好聚合、衰减、相反证据、本人声明/纠正/撤回，以及有效桌账订单或权威付款后的体验计划激活；失败、unknown和全额退款不会生成或会取消待执行节点。迁移093进一步记录顾客明确移除与员工受权调整，并提供同桌后续加单和跨日同品复购的非因果分析投影。管理端已接推荐漏斗、商品体验、数据质量、原始证据和带样本量/相反证据的周度建议。真实资金与营业样本仍未校准，且加单/复购投影不得解释为推荐因果，因此不能称线上经营效果已闭环。

### 商品观察

员工在具体桌台页使用“记录桌台情况”的目标流程：

```text
原始文字/语音
→ 自动绑定桌次、订单、员工和演出
→ 只从本桌真实订单匹配商品
→ 区分客观事实、客户原话、员工判断和系统推断
→ 员工确认或修正
→ 保存原文、结构化结果、置信度和修订历史
→ 可选生成现场服务任务
```

桌台或商品级观察不得自动进入个人偏好。只有明确客户身份和可追溯证据，才进入偏好候选；偏好聚合支持证据次数、最近时间、置信度、有效期、衰减和相反证据。

当前数据层已经保留原文、解析批次、候选、事件和修订，并限制候选来自本桌订单；员工页面已可选择或反选候选、调整表达分类/事件类型/程度、查看本桌最近5条已确认记录，并以追加新版本方式修订，不覆盖历史。“需要马上处理”只在员工确认事务内创建一项任务：任务detail为空，只保存观察引用、事件数量/类型和作用范围，不复制观察原文。核心提前派单、错误候选强绑和原文扩散问题已经修复，仍需真实岗位十秒计时、数据保留和权限矩阵签字。

文字录入为必备能力且不依赖语音服务。员工观察页已有主动点击后才申请麦克风的受控转写入口，单次最长20秒，转写完成或失败后不保存原始录音；语音服务关闭、设备不支持或转写失败时仍可直接输入文字。该能力仍需语音供应商、隐私政策和iOS/Android微信真机权限验收。顾客小程序没有语音入口，本轮也不得把员工语音能力扩展给顾客。

### 预约演出与规则契约

预约页按日期展示已发布演出，选择结果通过迁移052保存为强类型`preferred_schedule_id`，并进入预约事件和公开视图；服务端只接受同一门店、当地同一日期且状态为scheduled/performing的场次。迁移090把演出取消、改期、换场改为不可修改的强类型修订并生成受影响预约；顾客可保留预约并接受结果、改选同店同日演出或清空演出偏好，系统不会自动取消预约。它始终是演出偏好，不构成座位或场次保证。

预约提交前会重新检查容量，客户端同时提交确认页展示的规则版本；迁移052/068新增并运行强类型策略确认、保留和宽限字段，版本变化时返回冲突并零写入。本人预约修改也必须提交当前策略版本；改日期时必须重新选择或清空演出。迁移090的提醒只消费单预约、预约上下文、已发布策略和准确模板的一次授权，旧通用会员同意不能放行；正式策略/模板、真机送达和岗位现场仍待验收。

### 活动联系信息与服务进度

活动报名接口只接收允许的联系输入，服务端保护适配器生成联系类型、哈希、密文、密钥编号、掩码和来源，仓储再次严格校验完整白名单后才写入；公开活动与本人报名投影不返回原值。正式使用前仍需完成密钥轮换、授权解密路径、岗位范围、保留期和到期清理验收。

顾客服务进度页面已按服务端`requestType`映射服务类型，并优先读取`assignedStaffName`，同时兼容旧字段；已分配时显示负责人，未分配才显示等待接单。字段契约回退已修，仍需真机、轮询恢复和真实服务任务状态验收。

## 6. 微信身份、会员与积分

## 7. 体验任务自动化（目标态）

目标是在有效成交并满足付款/出品门禁后，由系统按计划时间生成岗位任务，而不是要求服务员背完整SOP。迁移086已接通激活边界：桌账类计划只在有效订单后激活，需即时付款的计划只在权威付款成功后激活；失败或unknown不产生服务节点，全额退款会取消尚未执行的节点。下表仍是经营参数示例，不代表时间值已经由门店批准：

| 节点 | 默认时间 | 责任岗位 |
|---|---:|---|
| 需求与边界确认 | 0分钟 | 迎宾 |
| 第一轮核心酒水 | 5分钟 | 吧台 |
| 第一轮低气味冷食 | 8分钟 | 冷厨 |
| 第一轮口味回访 | 18分钟 | 服务员 |
| 演出衔接提醒 | 30分钟 | 舞台运营 |
| 第二轮准备 | 42分钟 | 吧台 |
| 场景互动 | 50至58分钟 | 服务员/经理 |
| 延续体验选择 | 72分钟 | 服务员 |
| 离店收尾 | 105分钟 | 经理 |

目标状态下，桌次或体验计划关闭时，未执行节点自动跳过；节点到时生成对应岗位任务并保留Outbox事件。

体验节点不得在客户仅把推荐加入购物车时激活。订单未创建、付款状态不满足门禁或桌次已关闭时不得生成岗位任务；具体节点、分钟数和责任岗位仍须版本化配置并经真实岗位演练，不能把本表建议值写死为生产事实。
