# 120 位顾客场景：出品、取送与投诉闭环审计

基线：`77744bc4e9ed308546b630590bdfa5dfe5ce5b7d`，rc.216 业务代码，2026-09-21。工作树 `/Users/jingda/mbox/mbox-120-guests-audit-20260921`。本子审计未修改业务源码、未访问生产写接口；使用本机独立 PostgreSQL 库 `mbox120_fulfillment`，schema 224，业务事务明确 `SET LOCAL ROLE mbox_runtime`。权限与角色为隔离夹具，不冒充生产实际人员授权。

## 结论

120 份食品经两批 3+2 份的跨桌制作、并发分盘、4 名取送员工和丢回执重放，最终份数、预留库存和配送批次数一致。另确认两个投诉处置缺口：日常服务页会把店长负责的普通请求排在其他区域紧急投诉之前并只露出 8 条；普通翻台员工即使没有投诉管理权，也会通过“客离翻台”把未解决投诉取消，未保留后续管理待办。

这不代表全部营业场景已证明无错。此次 120 份食品数据守恒测试与根审计的 120 顾客混合 HTTP 下单相互补充，不能把两个隔离场景拼成一场真实门店演练。单人后厨、单人调酒和服务员的实际产能仍需菜单制作时间、可同时使用设备、真实走动与异常处理耗时。

## SIM120-08 / F-01：服务页的紧急投诉被本人普通事项遮挡（建议 P2；统一 SYS 编号由根审计登记）

复现：店长兼服务员，已有 8 条本人普通送水/服务待办；其他区域客人提交紧急投诉。`OperationsQueryService` 正确返回 120 条任务且 urgent 在首位；`actionableServiceTasks` 先按“我的责任”排序，再比较紧急程度，投诉下降到第 9 位。服务页 `prioritizeActionFact` 默认只取 8 条，页面仅显示“还有 112 项，完成当前事项后自动补入”，没有服务任务的展开或搜索控件。

定位：`src/normalized-ui/staff-actions/staff-actions-model.ts:80-93`；`StaffActionsPanel.tsx:449-459`、`:1286-1287`、`:1581-1590`。这会使兼岗店长在日常服务页先看到普通请求而看不到其他区投诉，峰值时延长接管时间。该后果是风险推断，本次没有真实顾客等待时长证据。

反证与范围：主页 `StaffTodoPanel` 有显示更多，`staff-todo-model.ts` 按 urgent 优先并可携带 factId 深链定位；原投诉没有丢失，首页路径可以到达。故不能宣称“整个系统全部隐藏/永远无法处理”。建议日常服务页同样保证紧急投诉可见，并提供完整列表/查询；本人责任排序不能覆盖管理投诉优先级。验收应覆盖至少 8 条本人普通请求加跨区 urgent、120 条服务积压、直接进页面和主页深链两种入口。

## SIM120-09 / F-02：普通翻台可取消未解决投诉并丢失后续待办（建议 P1；统一 SYS 编号由根审计登记）

复现：客人离店前说明投诉未解决、要求后续答复；普通员工有 `table.close` 与 `table.turnover_unsettled`，负责该桌，但 `service.manage=false`。执行真实 `PostgresTableCustomerLeftTurnoverRepository.close` 后，投诉成为 cancelled，事件仅 `task.created` 与 `customer_left_cancelled`；后一个原因只是“顾客已经离店立即翻台”。随后真实管理查询不再出现该投诉。

权限和状态不一致：正常投诉的完成/取消路由要求 `service.manage` 和至少 4 字结果（`server/normalized/normalized-operations-api.ts:650-653`）；翻台 SQL 对该桌所有 pending/acknowledged/in_progress 服务任务无区别取消（`database/normalized-migrations/140_customer_left_table_turnover.sql:435-460`），并不判断投诉或转交管理人员。`142_customer_left_turnover_default_role_grants.sql` 还明确给 SERVER 默认翻台权限，所以“有翻台权、无投诉管理权”不是只能人为拼造的权限组合。

事实边界：取消会留下审计历史，本次不是物理删除，也没有把取消谎写为完成。缺口是“桌位可以周转”和“投诉已解决/由管理者终结”被同一通用动作混在一起；如果运营明确要求所有离店投诉不再跟进，则属于需要明确的经营政策，但当前正常投诉路由已有独立管理权限和结果要求，通用翻台绕过了该边界。

建议保留物理翻台能力，将未解决投诉转成可跨桌次/离店后继续办理的管理待办，留原桌次、诉求、负责人和结果；不能为了保投诉而把桌台锁住，也不能把原已取消记录批量改为已完成。验收覆盖普通员工/店长权限、客人在场/离店、自动翻台、并发管理处置与翻台、跨日和原键重放。

## 仍需门店证据的环节

1. 120 人不自动等于 120 并发请求或固定 120 杯/120 份食品；每人点单量、峰值到达分布和加单轮次决定负载。单调酒师若每杯有效占用 90 秒，120 杯理论净制作就需 180 分钟；这只是情景算术，非现场实测，可并行/批量会改变结果。
2. 厨房能合批不等于设备产能足够。实际设备、每批量、预计时长、出锅分盘和相容备注必须由门店校准；当前测试没有模拟真实加热与走动。
3. 服务员同时要取送、退换处理、催单解释和核对单据。店长参加服务会减少其处理投诉和独立审核的可用时间；需关注同一人不能自审的任务是否有合法第二人承接。
4. `outbox` 入队或纸票记录不证明实体打印/耳机提醒/锁屏通知到达。本子审计不验打印机实物、现场弱网和资金到账。
5. 按份停止、换品、重做、跨桌转移和旧批补送已经有大量专项覆盖；本轮只重跑当前 120 份关键守恒组合，不能将历史全部用例数加进本次执行数。


## 03:54 追加：SIM120-11 / F-03 现金收款与出品完成锁序反转（建议 P1）

根审计混合 HTTP 第 5 次运行发现 2 次 complete 500 和随后 2 次 deliver 500；240 行中最终送达 238 行。独立复核确定不是错误夹具或“未备齐不能送达”的普通 409：隔离 PostgreSQL 在 03:49:25.458、26.460、27.462、28.464 的 **4 次 40P01 死锁**分别阻断这些操作。

- KDS 线程 PID 69578 / 69585 已有 `table_sessions FOR SHARE`，等待 `orders FOR UPDATE`（日志 73—200 行；`quantity-task-lock.ts:15-16`，由 `commerce-kds-api.ts:1216` 调用）。
- 现金线程 PID 69586 已有 `orders FOR SHARE`，正在等 `table_sessions FOR UPDATE`（`payment-security-policy.ts:166-188` → `employee-table-access.ts:55-58`）。
- 因而一个方向是桌次→订单，另一个是订单→桌次，构成闭环等待；PostgreSQL 终止一个事务后返回通用 500。`NormalizedCommandExecutor` 没有传重试设置，`transaction-runner.ts:193` 默认冲突重试为 0。

第 7 次 HTTP 日志进一步把请求错误号与 `errorCode=40P01` 绑定，且这次现金也成为受害者：两次 complete、一次 deliver、一次现金和立即同键现金重放均发生死锁。现金错误位置明确为 `employee-table-access.ts:84 ← :55`。**竞争持续时立即重试仍可再次失败**；不能只让员工重复点击。

新增确定性探针用两条真实业务锁函数，仅在已取得首把锁后设置测试调度屏障，没有伪造 SQL 结果。两事务稳定得到一成功、一 `40P01`；竞争结束后两路径分别重试可成功。最终专项 **4/4 通过，无跳过**，其中最后 1 项证明死锁现象而非证明已修复。输出 `final-with-deadlock-output.txt`，汇总证据 `cash-kds-deadlock-evidence.json`。它证明数据库回滚后锁路径可恢复；完整 HTTP 原幂等键恢复由根审计另验，不把函数重试冒充完整支付成功。

历史区别：`docs/req-15-a-order-performance-20260914.md:47-55` 的 4 次旧死锁是购物车/顾客参与记录路径；此次等待环是现金订单授权与 KDS，不重复报那 4 次旧事件。可关联 SYS-202 / REQ-16 的混合峰值验收，但应单独记录这条新根因。

此外，03:49:33 的大量 `40001` 来自后续 120 设备扫码阶段，和前述 40P01 不是同一错误。扫码代码已有 `serializable, retryOnConflict:2`（`guest-session-repository.ts:748`），所以不能把它描述为完全没有重试；仍需根审计按最终 HTTP 失败率和回读恢复单独评价。

修复方向是统一桌次、订单等父对象锁序并保留当前桌次/权限重新校验，覆盖付款与制作/取走/转桌/关桌的两方及三方并发；有限重试只能作为已回滚冲突的辅助恢复，不能遮盖反序根因。此追加仍未修改业务源码。
